近似数据结构

近似数据结构用可控误差换内存和吞吐，适合海量判重、基数估计和频率估计。

BloomHLLCount-Min
核心术语
Bloom Filter集合存在性判断，允许假阳性，不允许假阴性。
HyperLogLog估计不同元素数量（基数），仅需 12KB 状态即可估计 10^9 基数。
Count-Min Sketch估计元素频率，可能高估但不会低估（单方向误差）。

背景

当数据规模大到精确存储所有元素不可行时（10 亿 URL 的去重、百亿级 UV 统计），工程系统选择概率数据结构：

  • 精确方案：HashSet 存 10 亿 URL 约需 60GB 内存
  • Bloom Filter：同等规模仅需 ~1.2GB，代价是 1% 假阳性
  • HyperLogLog：统计 UV 仅需 12KB，标准误差 0.81%

核心权衡：用可量化的误差换取数量级的内存节省。误差不是随机的，而是有数学保证的上界。

运行机制：Bloom Filter

一个 m 位的 bit array + k 个独立哈希函数：

  • 插入：计算 k 个哈希值，将对应 bit 置 1
  • 查询：检查 k 个位置是否全为 1。全为 1 表示"可能存在"，有任一 0 表示"一定不存在"
  • 误判率：(1 - e^(-kn/m))^k，其中 n 是已插入元素数
  • 最优 k：k = (m/n) * ln2
  • 空间公式：给定 n 和 FPR，m = -n * ln(FPR) / (ln2)^2

工程用途：缓存穿透防护、爬虫 URL 去重、数据库 SSTable 快速排除（LevelDB/RocksDB）。

运行机制：HyperLogLog

  • 对元素哈希后观察二进制前导零的个数。直觉：看到 k 个前导零的概率是 1/2^k，所以见到的最长前导零暗示了总基数。
  • 将哈希空间分成 2^p 个桶（p 位做桶索引），每个桶记录各自见到的最长前导零。
  • 最终用调和平均数合并所有桶的估计。Redis 的 HLL 实现用 p=14（16384 桶），占 12KB。

运行机制：Count-Min Sketch

  • d 行 w 列的二维计数数组，配 d 个独立哈希函数。
  • 增加：对元素用每个哈希函数映射到一列，该位置计数 +1。
  • 查询：取 d 个位置的最小值作为频率估计（取 min 是因为碰撞只会高估不会低估）。
  • 误差保证：以概率 1-delta，估计值不超过真实值 + epsilon*N（N 为总插入次数）。w = e/epsilon，d = ln(1/delta)。
  • 可合并性：两个 CMS 逐位相加即可合并统计（分布式友好）。

对比总结：

  • Bloom Filter → 回答"是否存在"（membership）
  • HyperLogLog → 回答"有多少种"（cardinality）
  • Count-Min Sketch → 回答"出现了多少次"（frequency）

代码示例：Bloom Filter

package bloom

import (
    "hash"
    "hash/fnv"
    "math"
)

type BloomFilter struct {
    bits []bool
    k    int // hash 函数数量
    m    int // bit 数组长度
}

// New 创建 Bloom Filter，n=预期元素数，fp=期望假阳性率
func New(n int, fp float64) *BloomFilter {
    m := optimalM(n, fp)
    k := optimalK(m, n)
    return &BloomFilter{bits: make([]bool, m), k: k, m: m}
}

func optimalM(n int, fp float64) int {
    return int(math.Ceil(-float64(n) * math.Log(fp) / (math.Log(2) * math.Log(2))))
}

func optimalK(m, n int) int {
    return int(math.Round(float64(m) / float64(n) * math.Log(2)))
}

func (bf *BloomFilter) Add(data []byte) {
    for i := 0; i < bf.k; i++ {
        idx := bf.hash(data, i) % uint64(bf.m)
        bf.bits[idx] = true
    }
}

func (bf *BloomFilter) Contains(data []byte) bool {
    for i := 0; i < bf.k; i++ {
        idx := bf.hash(data, i) % uint64(bf.m)
        if !bf.bits[idx] {
            return false // 一定不存在
        }
    }
    return true // 可能存在
}

// 用 FNV + seed 模拟多个哈希函数
func (bf *BloomFilter) hash(data []byte, seed int) uint64 {
    var h hash.Hash64 = fnv.New64a()
    h.Write(data)
    h.Write([]byte{byte(seed)})
    return h.Sum64()
}

常见误区

误区 1：混淆假阳性和假阴性
// 错误理解：
// "Bloom Filter 说不存在，也可能存在"
// 这是假阴性，标准 BF 不会出现！

// Bloom Filter 的保证：
// 说不存在 → 一定不存在 (no false negative)
// 说存在 → 可能不存在 (has false positive)

方向搞反会导致系统设计出错——该拦截的没拦截。

// 正确使用模式：
if !bloom.Contains(key) {
    return nil // 安全短路，一定不存在
}
// 到这里需要去真实存储确认
// 因为可能是假阳性
result := db.Get(key)
return result

Bloom Filter 做的是"快速否定"，不是"确认存在"。

误区 2：不做容量规划导致误判率飙升
// 错误：固定大小，元素越来越多
bf := bloom.New(1000, 0.01) // 预期 1000 个
// 实际插入了 100000 个
// 误判率已远超 1%，接近 100%

超出设计容量后 bit array 几乎全为 1，失去过滤能力。

// 正确：监控 + 分层/定期重建
// 1. 监控填充率 (set bits / total bits)
// 2. 填充率 > 50% 时告警
// 3. 方案：Scalable Bloom Filter（多层）
//    或定期用新数据重建

必须根据数据增长规划容量或使用可扩展变体。

误区 3：把 HyperLogLog 当精确计数器
// 错误期望：
// "HLL 说 UV 是 1000523，那精确就是这么多"
// 实际标准误差 ±0.81%
// 即真实值在 ~992423 到 ~1008623 之间

HLL 给的是估计值，不能用于需要精确计数的场景（如计费）。

// 正确场景选择：
// 需要精确计数 → HashSet / 数据库 COUNT DISTINCT
// 允许 ~1% 误差 → HyperLogLog
// 允许 ~5% 误差但要更省内存 → Linear Counting

// Redis PFCOUNT 适合：
// - 日活/月活统计
// - 页面 UV 统计
// - 不适合：账单金额、库存数

选型前明确业务对误差的容忍度。

面试问答

Bloom Filter 能删除元素吗？▶
标准 Bloom Filter 不支持删除。因为一个 bit 可能被多个元素共享，清零会引入假阴性。

支持删除的变体：
1. Counting Bloom Filter：每个位置用计数器代替 bit，删除时减 1。空间 3-4 倍于标准 BF。
2. Cuckoo Filter：存指纹（fingerprint），支持删除且空间效率更高，但有载入上限。
3. 定期重建：如果删除不频繁，可以定期从真实数据重建整个 BF。
Count-Min Sketch 和 HashMap 计数有什么区别？▶
HashMap：精确计数，空间 O(n)（n 为不同元素数量），适合元素种类有限的场景。

Count-Min Sketch：近似计数，空间固定为 O(w*d)，与不同元素数无关。适合元素种类极多（如所有 URL）但只关心频率最高的那些的场景。

CMS 的缺点是只能高估不能精确，优点是内存固定且支持合并（两个 CMS 逐位相加即可合并统计）。
HyperLogLog 的 12KB 是怎么来的？▶
Redis HLL 使用 p=14，即 2^14 = 16384 个桶。每个桶记录最长前导零长度，64 位哈希最多 64 个前导零，需要 6 bit 存储。

总空间 = 16384 * 6 bit = 12288 字节 = 12KB。

标准误差 = 1.04 / sqrt(16384) = 0.81%。如果需要更高精度可以增大 p，但空间翻倍精度只提升 sqrt(2) 倍。
这三种结构分别适合什么业务场景？▶
Bloom Filter：集合存在性（缓存穿透防护、黑名单快速判断、爬虫 URL 去重）

HyperLogLog：基数统计（网站 UV、独立 IP 数、数据库 APPROX_COUNT_DISTINCT）

Count-Min Sketch：频率估计 + Top-K（热搜词排行、热 key 发现、流量异常检测）

选择标准：明确你要回答的问题是"是否存在"、"有多少种"还是"某个出现了多少次"。

工程应用与选型

  • Redis 内置支持：PFADD/PFCOUNT（HyperLogLog）、BF.ADD/BF.EXISTS（RedisBloom 模块）、CMS.INCRBY/CMS.QUERY（Count-Min Sketch）。
  • 数据库：BigQuery 的 APPROX_COUNT_DISTINCT 用 HLL；RocksDB 每个 SSTable 带 Bloom Filter。
  • CDN / WAF：用 Bloom Filter 做恶意 IP 快速判断，误判只是多查一次数据库，不影响正确性。
  • 推荐系统：用 Bloom Filter 做已曝光内容去重（避免重复推荐）；用 CMS 做实时热度排行。
  • 容量规划参考：1% FPR 的 Bloom Filter 约需 10 bit/元素；Redis HLL 固定 12KB 支持 10^18 基数；CMS 以 4 行 * 2048 列（32KB）可达 epsilon=0.001。

面试答题思路

面试中近似数据结构的考察方式：

  • 系统设计题："设计一个日活统计系统" → HyperLogLog；"设计缓存穿透防护" → Bloom Filter；"设计热搜排行榜" → CMS + Heap
  • 算法原理题：要求推导 FPR 公式或解释 HLL 前导零原理
  • 权衡分析题："为什么不直接用 HashMap" → 空间对比、可合并性、流式处理能力

回答时强调：具体数字（空间大小、误差率）、业务场景匹配（误差是否可接受）、和精确方案的对比。
