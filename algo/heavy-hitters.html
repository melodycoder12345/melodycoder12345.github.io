Top-K / Heavy Hitters

Heavy Hitters 关注流中最热的少数元素，用有限内存在无界数据流中追踪频率最高的 K 个元素。

Top-KSpace-SavingSketch
核心术语
Top-K频率最高的 K 个元素。
候选集当前可能进入 Top-K 的元素集合，大小有限。
近似计数用 sketch 保存频率估计，牺牲精度换空间。

背景

在日志分析、推荐系统、缓存热点发现等场景，数据是无界流——不能全部存下来再排序。核心约束：

  • 数据量无界，但可用内存有限（只能存 O(K) 或 O(K * polylog) 个候选）
  • 只关心频率最高的少数元素，不需要精确统计所有元素
  • 可以接受近似结果（可能遗漏边界候选或频率略有偏差）

三种主流算法：Space-Saving（有严格误差保证）、Count-Min Sketch + Heap（结合频率估计和排序）、Lossy Counting（批次衰减）。

运行机制：Space-Saving 算法

Space-Saving 维护一个固定大小为 m 的候选表（m >= K）：

  • 元素已在表中：直接将其计数 +1
  • 元素不在表中且表未满：加入表，计数设为 1
  • 元素不在表中且表已满：找到计数最小的候选，替换为新元素，计数设为原最小值 +1

关键性质：任何真实频率超过 N/m 的元素一定在候选表中（不会被遗漏），计数误差最多为 N/m（N 为总元素数）。

运行机制：Count-Min Sketch + Heap

  • 用 CMS 估计每个元素的频率（空间固定，与元素种类无关）
  • 维护一个大小为 K 的最小堆，堆顶是当前第 K 大的频率
  • 新元素到来时查询 CMS 获取估计频率，如果大于堆顶就替换入堆
  • 优点：CMS 可合并（分布式友好），缺点：CMS 只能高估可能引入假热点

运行机制：Lossy Counting

  • 将数据流分成大小为 w = 1/epsilon 的桶（batch），逐批处理
  • 每个元素记录 (count, max_error)，max_error = 当前桶编号 - 元素首次出现时的桶编号
  • 每批结束后删除 count + max_error <= 当前桶编号 的元素（确定不会进入 Top-K）
  • 保证：频率 > epsilon*N 的元素不会被删除；空间约 O(1/epsilon * log(epsilon*N))
  • 适合批处理风格的流式数据，不如 Space-Saving 实时

代码示例：Space-Saving

package topk

import "container/heap"

type Item struct {
    Key   string
    Count int
    index int // heap index
}

type SpaceSaving struct {
    capacity int
    items    map[string]*Item
    minHeap  MinHeap
}

func NewSpaceSaving(capacity int) *SpaceSaving {
    return &SpaceSaving{
        capacity: capacity,
        items:    make(map[string]*Item),
        minHeap:  make(MinHeap, 0, capacity),
    }
}

func (ss *SpaceSaving) Add(key string) {
    if item, ok := ss.items[key]; ok {
        // 已在候选表中，计数 +1
        item.Count++
        heap.Fix(&ss.minHeap, item.index)
        return
    }
    if len(ss.items) < ss.capacity {
        // 表未满，直接加入
        item := &Item{Key: key, Count: 1}
        ss.items[key] = item
        heap.Push(&ss.minHeap, item)
        return
    }
    // 表已满：替换最小计数的候选
    min := ss.minHeap[0]
    delete(ss.items, min.Key)
    min.Key = key
    min.Count++ // 原最小值 + 1
    ss.items[key] = min
    heap.Fix(&ss.minHeap, 0)
}

func (ss *SpaceSaving) TopK(k int) []Item {
    result := make([]Item, 0, k)
    // 复制并排序
    sorted := make(MinHeap, len(ss.minHeap))
    copy(sorted, ss.minHeap)
    for i := len(sorted) - 1; i >= 0 && len(result) < k; i-- {
        result = append(result, *sorted[i])
    }
    return result
}

// MinHeap 实现
type MinHeap []*Item

func (h MinHeap) Len() int            { return len(h) }
func (h MinHeap) Less(i, j int) bool   { return h[i].Count < h[j].Count }
func (h MinHeap) Swap(i, j int)        { h[i], h[j] = h[j], h[i]; h[i].index = i; h[j].index = j }
func (h *MinHeap) Push(x interface{})  { item := x.(*Item); item.index = len(*h); *h = append(*h, item) }
func (h *MinHeap) Pop() interface{}    { old := *h; item := old[len(old)-1]; *h = old[:len(old)-1]; return item }

常见误区

误区 1：认为近似 Top-K 能给出精确排名
// 错误期望：
// Space-Saving 返回 Top-10，期望排名完全正确
// 实际：频率接近的元素排名可能互换
// 边界候选可能被遗漏或误入

// 例：真实频率 [100, 99, 98, 50, 49]
// 近似结果可能是 [100, 98, 99, 51, 49]

排名可能有偏差，只有频率远超阈值的才是确定的 heavy hitter。

// 正确理解：
// Space-Saving 保证：
// 1. 真实频率 > N/m 的一定在候选表中
// 2. 计数误差 <= N/m
// 3. 频率远超阈值的排名可信

// 工程实践：取 2K 个候选，
// 只展示前 K 个作为最终结果
// 边界候选标记为"可能"

增大候选集 m 可以减小误差，代价是更多内存。

误区 2：忽略内存和精度的权衡
// 错误：设置太小的候选容量
ss := NewSpaceSaving(10)
// 在 10 亿元素的流中找 Top-10
// 误差 = N/m = 10^9/10 = 10^8
// 只有频率超过 1 亿的才能保证被追踪
// 大量真正热门的元素被遗漏

候选集太小时，误差边界太大导致结果无意义。

// 正确：候选集大小要远大于 K
ss := NewSpaceSaving(1000)
// 找 Top-10，但保留 1000 个候选
// 误差 = N/m = 10^9/1000 = 10^6
// 频率超过 100 万就能保证被追踪
// 1000 个 Item 只占几十 KB 内存

// 经验法则：m = 10*K 到 100*K

内存开销低廉，不要在候选集大小上节省。

误区 3：流式算法和批处理算法混用
// 错误：把全量数据 sort 后取前 K 个
// 当成"流式 Top-K"方案
sort.Slice(allData, func(i,j int) bool {
    return freq[allData[i]] > freq[allData[j]]
})
return allData[:K]
// 这需要 O(n) 内存存所有数据

批处理需要完整数据在内存中，流式场景不适用。

// 正确区分：
// 批处理（数据有限）：
//   HashMap 统计 + 快速选择 O(n)
//   或 HashMap + 最小堆 O(n log K)

// 流式处理（数据无界）：
//   Space-Saving / Lossy Counting
//   Count-Min Sketch + Heap

// 选型依据：数据是否能全部放入内存

先判断场景再选算法，流式和批处理是不同问题。

面试问答

Space-Saving 算法的误差保证是什么？▶
设候选表大小为 m，总元素数为 N：

1. 不漏保证：任何真实频率 > N/m 的元素一定在候选表中
2. 误差上界：候选表中任何元素的计数误差不超过 N/m
3. 高估性：计数只可能高估，不会低估

例如 m=100, N=10^6：频率 >10000 的元素一定被追踪，计数误差最多 10000。这意味着一个计数为 50000 的候选，其真实频率在 [40000, 50000] 之间。
如何在分布式系统中做全局 Top-K？▶
两种主流方案：

方案一：CMS + Heap
- 每个节点维护本地 Count-Min Sketch
- 定期合并所有节点的 CMS（逐位相加）
- 在合并后的 CMS 上查询 Top-K

方案二：两阶段聚合
- 每个节点用 Space-Saving 维护本地 Top-2K
- 汇总所有节点的候选集（并集）
- 对候选集中的元素做精确二次统计（向所有节点查询）
- 从精确结果中取全局 Top-K

方案一更省网络带宽（只传 sketch），方案二结果更精确。
滑动窗口 Top-K 和全局 Top-K 有什么区别？▶
全局 Top-K：统计所有历史数据中频率最高的 K 个，旧数据和新数据权重相同。

滑动窗口 Top-K：只统计最近 W 个元素中的 Top-K，过期元素需要被移除。

难点：Space-Saving 不支持高效删除旧元素。解决方案：
1. 时间衰减：用指数衰减权重 (count *= decay) 让旧数据自然淡出
2. 分桶：按时间分多个桶，每桶独立维护，查询时合并最近 N 个桶
3. Hokusai：多粒度 CMS 支持时间范围查询
面试中如何快速写出批量 Top-K 的最优解？▶
批量（离线）场景标准解法：

O(n log K) 最小堆法：
1. 用 HashMap 统计频率 O(n)
2. 维护大小为 K 的最小堆
3. 遍历 map，元素频率 > 堆顶就替换
4. 最终堆中就是 Top-K

O(n) 快速选择法：
1. HashMap 统计频率
2. 对频率数组做 quickselect 找第 K 大
3. 期望 O(n)，最差 O(n²)

面试推荐最小堆法：代码简洁、复杂度稳定、容易写对。

工程应用

  • Redis 热 key 发现：代理层用 Space-Saving 追踪请求频率最高的 key，达到阈值后触发本地缓存或热点打散。
  • 日志分析：ELK 栈中对错误码、慢查询 SQL、高频 API 做实时 Top-K 排行。
  • 推荐系统：实时计算热门内容候选集，作为召回阶段的补充。
  • DDoS 防护：在流量入口用 CMS + Heap 快速发现请求量异常的源 IP。
  • 搜索热词：百度/Google 搜索框的自动补全和"热搜榜"底层都是 Heavy Hitters 问题。

算法选型指南：

  • 单机 + 精确 + 数据量有限 → HashMap + MinHeap
  • 单机 + 流式 + 内存有限 → Space-Saving
  • 分布式 + 可合并 + 允许近似 → Count-Min Sketch + Heap
  • 批次处理 + 需要时间衰减 → Lossy Counting
