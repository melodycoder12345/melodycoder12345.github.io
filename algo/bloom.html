Bloom Filter

Bloom Filter 用位图和多个哈希函数判断元素是否可能存在，以可控假阳性率换取极低内存开销。

BitsetHashFalse Positive
核心术语
位图 (Bit Array)保存 0/1 的紧凑数组，m 位占 m/8 字节。
假阳性 (False Positive)实际不存在但判断为"可能存在"，是 Bloom Filter 的固有代价。
假阴性 (False Negative)实际存在但判断为不存在；标准 Bloom Filter 保证不会出现。

背景

集合成员判断是最常见的操作之一。当集合规模达到亿级时：

  • HashSet：精确，但 1 亿个 64 字节 key 需要 ~8GB 内存
  • Bloom Filter：1 亿元素、1% 假阳性率仅需 ~114MB（约 70 倍节省）
  • 代价：只能回答"一定不存在"或"可能存在"，不能获取原始数据

典型使用模式：Bloom Filter 作为前置过滤器，快速排除不存在的查询，减少对后端存储的访问。

运行机制

核心组件：m 位的 bit array（初始全 0）+ k 个独立哈希函数

  • Add(x)：计算 h1(x), h2(x), ..., hk(x)，将 bit array 对应 k 个位置置 1
  • Contains(x)：检查 k 个位置是否全为 1。有任一个 0 则一定不存在；全为 1 则可能存在（可能是其他元素碰撞导致）

假阳性率公式：

插入 n 个元素后，某一位仍为 0 的概率 = (1 - 1/m)^(kn) ≈ e^(-kn/m)

假阳性率 FPR = (1 - e^(-kn/m))^k

最优哈希函数数量：k = (m/n) * ln2 ≈ 0.693 * (m/n)

给定 n 和期望 FPR 求 m：m = -n * ln(FPR) / (ln2)^2

快速估算表：

  • 1% FPR → 约 10 bit/元素，k=7
  • 0.1% FPR → 约 14 bit/元素，k=10
  • 0.01% FPR → 约 19 bit/元素，k=13

双哈希优化：实际实现中不需要 k 个独立哈希函数。Kirsch-Mitzenmacher 证明 h_i(x) = h1(x) + i*h2(x) 即可达到同等效果，只需计算两个基础哈希。

代码示例

package bloom

import (
    "encoding/binary"
    "hash/fnv"
    "math"
)

type Filter struct {
    bits []uint64 // 用 uint64 数组模拟 bit array
    m    uint64   // 总 bit 数
    k    uint     // 哈希函数数量
}

// New 创建 Bloom Filter
// n: 预期元素数量, fp: 期望假阳性率 (如 0.01)
func New(n int, fp float64) *Filter {
    m := optimalBits(n, fp)
    k := optimalHashCount(m, n)
    words := (m + 63) / 64
    return &Filter{
        bits: make([]uint64, words),
        m:    uint64(m),
        k:    uint(k),
    }
}

func optimalBits(n int, fp float64) int {
    return int(math.Ceil(-float64(n) * math.Log(fp) / (math.Ln2 * math.Ln2)))
}

func optimalHashCount(m, n int) int {
    return int(math.Round(float64(m) / float64(n) * math.Ln2))
}

// Add 添加元素
func (f *Filter) Add(data []byte) {
    h1, h2 := f.baseHashes(data)
    for i := uint(0); i < f.k; i++ {
        pos := (h1 + uint64(i)*h2) % f.m
        f.bits[pos/64] |= 1 << (pos % 64)
    }
}

// Contains 查询元素是否可能存在
func (f *Filter) Contains(data []byte) bool {
    h1, h2 := f.baseHashes(data)
    for i := uint(0); i < f.k; i++ {
        pos := (h1 + uint64(i)*h2) % f.m
        if f.bits[pos/64]&(1<<(pos%64)) == 0 {
            return false // 一定不存在
        }
    }
    return true // 可能存在
}

// 双哈希技巧：用两个基础哈希模拟 k 个哈希
// Kirsch-Mitzenmacher: h_i(x) = h1(x) + i*h2(x)
func (f *Filter) baseHashes(data []byte) (uint64, uint64) {
    hasher := fnv.New128a()
    hasher.Write(data)
    sum := hasher.Sum(nil)
    h1 := binary.BigEndian.Uint64(sum[:8])
    h2 := binary.BigEndian.Uint64(sum[8:])
    return h1, h2
}

// FillRatio 返回当前填充率（用于监控）
func (f *Filter) FillRatio() float64 {
    set := 0
    for _, word := range f.bits {
        set += popcount(word)
    }
    return float64(set) / float64(f.m)
}

func popcount(x uint64) int {
    count := 0
    for x != 0 {
        count++
        x &= x - 1
    }
    return count
}

常见误区

误区 1：尝试从 Bloom Filter 中删除元素
// 错误：直接清零对应 bit
func (f *Filter) Delete(data []byte) {
    h1, h2 := f.baseHashes(data)
    for i := uint(0); i < f.k; i++ {
        pos := (h1 + uint64(i)*h2) % f.m
        f.bits[pos/64] &^= 1 << (pos % 64)
        // 危险！这个 bit 可能被其他元素共享
    }
}
// 删除 A 可能导致 B 被误判为不存在

一个 bit 可能被多个元素的哈希共享，清零会引入假阴性。

// 正确方案：
// 1. Counting Bloom Filter（计数器代替 bit）
type CountingBF struct {
    counts []uint8 // 4-bit 计数器
}
// 删除时减 1，不会影响其他元素

// 2. Cuckoo Filter（存指纹，支持删除）
// 3. 定期从数据源重建 BF
// 4. 业务层标记删除（维护额外黑名单）

需要删除时选择 Counting BF 或 Cuckoo Filter。

误区 2：忽视填充率导致误判率飙升
// 错误：创建后不关注容量
bf := bloom.New(10000, 0.01)
// 预期 1 万个元素，1% FPR

// 实际插入 10 万个后：
// 填充率接近 100%
// 实际 FPR 已接近 50%+
// 几乎失去过滤能力

超容量使用是 Bloom Filter 最常见的线上事故原因。

// 正确：监控 + 扩容策略
ratio := bf.FillRatio()
if ratio > 0.5 {
    alert("BF fill ratio too high")
}

// 扩容方案：Scalable Bloom Filter
// - 多层 BF，每层容量递增
// - 新元素插入最新层
// - 查询时检查所有层
// - 总 FPR = 各层 FPR 之和（控制收敛）

部署时必须监控填充率，提前规划扩容。

误区 3：在不能容忍误判的场景使用 BF
// 错误场景：
// 用 BF 做权限判断
if bloom.Contains(userID) {
    grantAccess() // 假阳性 = 越权！
}

// 用 BF 做账务去重
if bloom.Contains(txID) {
    skip() // 假阳性 = 丢交易！
}

假阳性意味着"本不该通过的通过了"，安全和金融场景不可接受。

// 正确使用模式：
// BF 只做否定判断（快速排除）
if !bloom.Contains(key) {
    return "not found" // 安全！无假阴性
}
// 肯定结果必须二次确认
return db.Lookup(key) // 去真实存储确认

// 适合 BF 的场景：
// - 缓存穿透防护（排除不存在的 key）
// - 爬虫 URL 去重（漏爬几个可接受）
// - 日志去重（偶尔多一条可接受）

BF 的价值在"快速排除"，不是"确认存在"。

面试问答

Bloom Filter 和 Cuckoo Filter 有什么区别？▶
Bloom Filter：
- 不支持删除
- 空间效率：每个元素约 10 bit（1% FPR）
- 查询需要 k 次内存访问
- 实现简单，无载入限制

Cuckoo Filter：
- 支持删除（存指纹而非 bit）
- 空间效率更高：每个元素约 7-8 bit（同 FPR）
- 查询只需 2 次内存访问（更 cache 友好）
- 有最大载入因子限制（~95%），超出后插入失败

选择建议：需要删除或查询性能敏感选 Cuckoo；容量不确定或需要极高载入率选 Bloom + Scalable 变体。
为什么 k = (m/n)*ln2 是最优的哈希函数数量？▶
直觉：k 太少时每个元素只标记少数 bit，碰撞概率低但鉴别力差；k 太多时 bit array 填满太快，碰撞概率反而增大。

数学推导：FPR = (1 - e^(-kn/m))^k，对 k 求导令导数为零，解得 k = (m/n)*ln2。

此时每个 bit 被设置的概率恰好为 50%，是信息论意义上区分能力最强的状态。

实用规则：如果 m/n = 10（每个元素 10 bit），最优 k = 10 * 0.693 ≈ 7 个哈希函数。
Bloom Filter 在 LSM-Tree 存储引擎中起什么作用？▶
LSM-Tree（如 LevelDB、RocksDB）有多个 SSTable 层级，点查时可能需要逐层搜索。

每个 SSTable 附带一个 Bloom Filter：
- 查询 key 时先检查 BF：如果返回"不存在"，直接跳过该 SSTable（避免磁盘 I/O）
- 如果返回"可能存在"，才真正读取 SSTable 的索引块和数据块

效果：对于不存在的 key，可以避免 99%+ 的无效磁盘读取。RocksDB 默认为每个 SSTable 配置 10 bits/key 的 BF（~1% FPR）。

这是 Bloom Filter 最经典的工程应用之一。
Bloom Filter vs HashSet vs Bitmap，如何选型？▶
HashSet：精确、支持删除和遍历，但空间 O(n * key_size)。适合：元素数少或需要精确操作。

Bitmap：精确、O(1) 查询，但需要元素是连续整数范围内。空间 = max_value / 8 字节。适合：ID 范围有限的去重（如用户 ID < 10 亿）。

Bloom Filter：近似、空间固定与 key 大小无关，但有假阳性且不支持删除。适合：key 是任意字符串且数量巨大。

决策流程：key 是有界整数？→ Bitmap。需要精确？→ HashSet。海量任意 key 且容忍 FP？→ Bloom Filter。
