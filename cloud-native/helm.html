背景与痛点

没有 Helm 时的痛苦

高频考点

部署一个生产级微服务到 Kubernetes，你需要手工维护至少 5 个 YAML 文件：

# 没有 Helm 时，一个微服务的典型文件清单
myservice/
  deployment.yaml     # 副本数、镜像、资源限制、探针
  service.yaml        # ClusterIP / LoadBalancer 暴露端口
  configmap.yaml      # 应用配置（数据库地址、日志级别等）
  hpa.yaml            # HorizontalPodAutoscaler，CPU/内存弹性
  ingress.yaml        # Ingress 路由规则（域名、TLS 证书）

这带来三类典型痛点：

  • 手工 apply 易出错：kubectl apply -f . 要确保目录完整、顺序正确，一旦出错无法自动回滚
  • 多环境重复维护：dev / staging / prod 各自一套几乎相同的文件，只有 image tag、副本数、资源限制不同——修改一处要同步三份
  • 版本管理缺失：谁在什么时候 apply 了什么版本？没有 release 历史，无法快速回退到上一个已知正常状态

Helm 的解法：将这 5 个文件打包成一个 Chart，用 values.yaml 参数化环境差异，一条 helm install 完成所有资源的有序创建，并记录 Release 历史支持随时回滚。

核心概念

五大核心对象

核心
概念定义类比
ChartHelm 包，包含 K8s Manifest 模板 + 默认 values + 元信息软件安装包（.deb）
ReleaseChart 在集群中的一次安装实例，同一 Chart 可有多个 Release（不同名）已安装的软件实例
RepositoryChart 仓库，存储打包好的 Chart（ArtifactHub、Harbor、OCI Registry）apt 软件源 / npm registry
Values参数文件，覆盖 Chart 默认配置，template 中用 {{ .Values.xxx }} 引用软件安装时的配置选项
Revision每次 install/upgrade/rollback 都生成一个新的修订版本号，从 1 递增git commit 历史

Release 独立性：在同一个集群同一个 Namespace 中，可以运行 helm install myapp-v1 ./mychart 和 helm install myapp-v2 ./mychart 两个完全独立的 Release，互不干扰。这是 Helm 与直接 kubectl apply 的关键区别之一。

Release 状态机

进阶
状态含义如何恢复
deployed当前活跃的已部署版本—
failedinstall 或 upgrade 失败（超时、K8s 拒绝等）helm rollback 或 helm upgrade --atomic
superseded已被新 revision 替代的历史版本可 rollback 到该版本
uninstalling正在删除中等待完成
pending-installinstall 正在进行（Hooks 执行中）等待或检查 Hooks
pending-upgradeupgrade 正在进行等待或强制回滚

Release 历史存储在 Kubernetes Secret 中（Helm v3 默认），格式为 sh.helm.release.v1.<release-name>.v<N>。可用 helm history <release> 查看完整历史。

Chart 目录结构

完整 Chart 目录解析

核心
mychart/
├── Chart.yaml          # 必填：Chart 元信息
├── values.yaml         # 默认参数（可被 --set 或 -f 覆盖）
├── values.schema.json  # 可选：对 values 做 JSON Schema 校验
├── templates/          # Go template 渲染的 K8s Manifest 模板
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── hpa.yaml
│   ├── _helpers.tpl    # 下划线开头：命名 helper，不直接渲染
│   └── NOTES.txt       # install 成功后显示给用户的说明文本
├── charts/             # 子 Chart（依赖），由 helm dependency update 填充
│   └── redis-18.0.0.tgz
├── Chart.lock          # 锁定依赖版本（类似 package-lock.json）
└── .helmignore         # 打包时忽略的文件（类似 .gitignore）

description: My web app
type: application    # application | library

Deployment 模板示例（templates/deployment.yaml）

核心
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}    # 调用 _helpers.tpl 中的命名函数
  labels:
    {{- include "mychart.labels" . | nindent 4 }}  # 缩进 4 空格插入
spec:
  replicas: {{ .Values.replicaCount }}              # 引用 values
  selector:
    matchLabels:
      {{- include "mychart.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "mychart.selectorLabels" . | nindent 8 }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: {{ .Values.service.port }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}  # 将 values 转为 YAML 并缩进
          livenessProbe:
            httpGet:
              path: /healthz
              port: {{ .Values.service.port }}
          {{- if .Values.ingress.enabled }}  # 条件渲染
          env:
            - name: APP_HOST
              value: {{ .Values.ingress.host }}
          {{- end }}

_helpers.tpl — 命名助手模板

进阶

_helpers.tpl 是 Helm 约定的辅助文件，文件名以 _ 开头不会被直接渲染，专门用于定义可复用的命名 template，避免每个文件重复写相同的 label 和 name 逻辑。

{{/*
返回 Chart 全名（Release.Name + Chart.Name，最长 63 字符）
*/}}
{{- define "mychart.fullname" -}}
{{- if .Values.fullnameOverride }}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" }}
{{- end }}
{{- end }}

{{/* 公共标签（所有资源都应携带） */}}
{{- define "mychart.labels" -}}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" }}
{{ include "mychart.selectorLabels" . }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}

{{/* Selector 标签（Deployment / Service 匹配用） */}}
{{- define "mychart.selectorLabels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}

Values 优先级

六层 Values 覆盖优先级（高 → 低）

高频考点

同一个 key 在多个地方设置时，优先级高的覆盖优先级低的（merge，非替换整个文件）：

1
--set
命令行直接设置，最高优先级。helm install ... --set image.tag=v2.0
2
--set-string
同 --set，但强制值类型为字符串（避免 10 被解析为数字）
3
-f file.yaml
指定 values 文件，可多次使用，后面的覆盖前面的。-f values-prod.yaml
4
values.yaml
Chart 内置默认 values，优先级较低
5
父 Chart
父 Chart 的 values.yaml 中 子chartname.key 可覆盖子 Chart 默认值
6
子 Chart 默认
子 Chart（依赖）自带的 values.yaml，优先级最低
# 多环境部署：只维护差异文件，不重复整份配置
# values.yaml（公共基准）
image:
  repository: myrepo/myapp
  tag: "latest"
replicaCount: 1

# values-dev.yaml（只写差异）
replicaCount: 1
resources:
  limits: {cpu: 200m, memory: 256Mi}

# values-prod.yaml（只写差异）
replicaCount: 3
resources:
  limits: {cpu: 2000m, memory: 2Gi}
ingress:
  enabled: true
  host: myapp.prod.example.com

# 部署命令
helm upgrade --install myapp ./mychart -f values.yaml -f values-prod.yaml \
  --set image.tag="$(GIT_SHA)"

  --dry-run                # 只渲染，不实际提交
  --debug                  # 打印渲染后的完整 Manifest

helm upgrade — 三路合并

高频考点

upgrade 不是简单替换，而是 三路合并（3-way strategic merge patch），类似 git 的三方合并：

路径含义
previous上次 helm install/upgrade 时记录的 Manifest（存在 Release Secret 中）
current集群中实际存在的资源状态（可能被 kubectl 手动修改过）
desired本次 helm upgrade 渲染出的新 Manifest

合并规则：如果 current 相对 previous 有变化（手动改过），且 desired 没有覆盖这个字段，则保留 current 的修改；如果 desired 明确指定了这个字段，desired 优先。这解决了"手动 kubectl 修改 vs Helm 管理"的冲突问题。

# upgrade 基本用法
helm upgrade <release-name> <chart> [flags]

helm upgrade myapp ./mychart -f values-prod.yaml --set image.tag=v1.3.0

# --install：Release 不存在时自动 install（CI/CD 幂等部署）
helm upgrade --install myapp ./mychart -f values-prod.yaml

# --atomic：任何步骤失败则自动 rollback 并返回非零退出码
helm upgrade --install myapp ./mychart --atomic --timeout 5m

# --cleanup-on-fail：upgrade 失败时删除本次新创建的资源（不是回滚，是清理）
helm upgrade myapp ./mychart --cleanup-on-fail

helm rollback / uninstall

核心
# 查看历史（每次 install/upgrade/rollback 都是一个 revision）
helm history myapp
# REVISION  UPDATED           STATUS     CHART          APP VERSION   DESCRIPTION
# 1         2024-01-01 ...    superseded mychart-1.0.0  2.3.0         Install complete
# 2         2024-01-02 ...    superseded mychart-1.1.0  2.4.0         Upgrade complete
# 3         2024-01-03 ...    failed     mychart-1.2.0  2.5.0         Upgrade "myapp" failed: ...
# 4         2024-01-03 ...    deployed   mychart-1.1.0  2.4.0         Rollback to 2

# 回滚到上一个 revision（不带版本号 = 上一个）
helm rollback myapp

# 回滚到指定 revision
helm rollback myapp 2

# rollback 的本质：把 revision 2 的 Manifest 重新 apply 给 K8s
# K8s 执行 Deployment 滚动更新回退，同时生成新的 revision（此处为 4）

# 卸载 Release（删除所有关联 K8s 资源）
helm uninstall myapp

# 保留 Release 历史（默认删除）—— 便于后续查看或重装
helm uninstall myapp --keep-history

helm template — 纯渲染调试

调试必备

helm template 在本地渲染 Chart（不连接集群，不创建 Release），是 CI 校验和调试模板的利器：

# 渲染全部 Manifest 到 stdout
helm template myapp ./mychart -f values-prod.yaml

# 只渲染指定 template 文件
helm template myapp ./mychart --show-only templates/deployment.yaml

# 输出到文件后用 kubectl apply（GitOps 纯 Manifest 模式）
helm template myapp ./mychart -f values-prod.yaml > manifests.yaml
kubectl apply -f manifests.yaml

# 配合 kubeval / conftest 做 CI 校验
helm template myapp ./mychart | kubeval --strict
helm template myapp ./mychart | conftest test -

工程场景

CI/CD 幂等部署模式

工程核心

helm upgrade --install 是 CI/CD 的标准做法：Release 存在则 upgrade，不存在则 install，天然幂等，重跑不报错。

## GitHub Actions / GitLab CI 示例
deploy:
  script:
    # 1. 配置 kubeconfig（或通过 OIDC 获取临时凭证）
    - aws eks update-kubeconfig --name prod-cluster

    # 2. 幂等部署：同一命令在首次和后续部署都有效
    - helm upgrade --install myapp ./charts/myapp
        --namespace prod
        --create-namespace
        -f charts/myapp/values.yaml
        -f charts/myapp/values-prod.yaml
        --set image.tag=${CI_COMMIT_SHA:0:8}  # 用 Git SHA 固定镜像版本
        --atomic          # 失败自动回滚，保障集群稳定
        --timeout 8m      # 超时时间 > K8s readinessProbe 等待时间
        --wait             # 等到 Pod Ready 才算成功

    # 3. 验证（可选）
    - helm test myapp --namespace prod

最佳实践：始终用 Git SHA（而非 latest）作为镜像 tag，确保每次部署可追溯、可回滚到精确版本。结合 --atomic 保证集群状态一致性。

Chart 测试：helm test

进阶

Helm Test 在安装后执行一次性测试 Pod，验证服务是否真正可用（不只是 Pod Running，而是业务层面的健康）。

apiVersion: v1
kind: Pod
metadata:
  name: "{{ include "mychart.fullname" . }}-test-connection"
  annotations:
    "helm.sh/hook": test          # 关键注解：标记为 test hook

Helm Hooks

Hook 生命周期与类型

进阶

Hook 是在 Release 生命周期的特定阶段执行的 K8s 资源（通常是 Job 或 Pod），用于数据库迁移、配置初始化、健康验证等需要在部署前/后执行的一次性操作。

Hook 类型触发时机典型用途
pre-install模板渲染后，任何资源创建前创建数据库 schema、申请证书
post-install所有资源创建并 Ready 后发送 Slack 通知、暖机 API
pre-upgradeupgrade 时，更新任何资源前数据库迁移（migrate）
post-upgradeupgrade 完成所有资源更新后缓存预热、冒烟测试
pre-rollbackrollback 执行前备份当前状态
post-rollbackrollback 完成后告警、清理临时资源
pre-deleteuninstall 删除资源前备份数据、优雅排水
post-delete所有资源删除后清理外部资源（S3、DNS 记录）
testhelm test 命令触发端到端功能验证
# 数据库迁移 Hook 示例
# templates/hooks/pre-upgrade-migrate.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: "{{ .Release.Name }}-pre-upgrade-migrate"
  annotations:
    "helm.sh/hook": pre-upgrade
    "helm.sh/hook-weight": "-5"   # 多个同类型 Hook 的执行顺序（数字小先执行）
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          command: ["./migrate", "--direction=up"]
          env:
            - name: DB_URL
              valueFrom:
                secretKeyRef:
                  name: {{ .Release.Name }}-db-secret
                  key: url

hook-delete-policy 说明：before-hook-creation（再次触发时先删旧的）+ hook-succeeded（成功后自动删除）是最常见组合，可避免 Job 残留导致下次 upgrade 时的命名冲突。

面试题

Helm v2 和 v3 的核心区别是什么？▶
最核心区别是 去掉了 Tiller（v2 的服务端组件）。

Helm v2：客户端 helm CLI + 服务端 Tiller（运行在 K8s 中，拥有 cluster-admin 权限），所有操作通过 gRPC 调用 Tiller。Release 历史存在 ConfigMap 中。

Helm v3：纯客户端，直接调用 K8s API Server，权限与 kubectl 用户权限相同（RBAC 约束）。Release 历史改存在 Secret 中（数据加密更安全）。三路合并策略也是 v3 引入的改进。

工程意义：v3 不再有 RBAC 漏洞（Tiller 过于强大的权限问题），多租户集群更安全。
Chart.version 和 Chart.appVersion 有什么区别？▶
version（Chart 版本）：Chart 包本身的 SemVer 版本，每次修改 templates、values、依赖等 Chart 内容时递增。Helm 用它做版本管理和依赖解析。

appVersion（应用版本）：仅供标注用的字符串，表示该 Chart 默认安装的应用软件版本，不影响 Helm 任何行为，只在 helm list 中显示。

实际场景：image.tag 通常与 appVersion 对应，但更好的做法是通过 CI 的 --set image.tag=... 覆盖，而非频繁修改 appVersion。Chart.version 应在 Chart 本身逻辑发生变化时才递增。
helm upgrade 失败后集群处于什么状态？如何恢复？▶
失败后 Release 状态变为 failed，K8s 资源可能处于部分更新状态（一部分 Pod 已是新版本，另一部分仍是旧版本，取决于 RollingUpdate 进度）。

恢复方式：
1. helm rollback myapp：推荐。Helm 将上一个 superseded 版本的 Manifest 重新 apply，触发 K8s 滚动回退，生成新 revision。
2. 如果用了 --atomic：Helm 在检测到失败（超时或 Hooks 失败）时自动执行 rollback，无需手动干预。
3. 如果 Hook 失败导致 stuck：先手动删除失败的 Hook Job，再 helm rollback。

注意：--cleanup-on-fail 只删除本次 upgrade 新创建的资源，不执行完整 rollback。
如何在 Helm 中管理 Secret？安全最佳实践是什么？▶
直接把密码写进 values.yaml 或 values-prod.yaml 并提交 Git 是危险的。常见解决方案：

1. helm-secrets 插件：集成 SOPS，values.yaml 中密文存储，运行时用 KMS/GPG 解密后注入。
2. 外部 Secret 管理：K8s Secret 不通过 Helm 管理，而是由 External Secrets Operator 从 AWS Secrets Manager / HashiCorp Vault 同步。Chart 的 template 中直接 valueFrom.secretKeyRef 引用已存在的 Secret。
3. CI 环境变量 + --set：密码通过 CI 的 masked 变量传入 --set db.password=$SECRET，不落盘。

生产推荐：External Secrets + Vault，最小化 K8s etcd 中的明文数据。
Helm 和 Kustomize 怎么选？▶
两者解决不同问题，也可以组合使用（Kustomize 管理 Helm 渲染输出）：

选 Helm 当： 需要打包分发 Chart（给外部用户用）；应用结构复杂，需要条件渲染（if/range）；需要 Release 生命周期管理（install/upgrade/rollback/history）；依赖其他 Chart。

选 Kustomize 当： 只管自己团队的应用；以 overlay 方式管理多环境差异，不需要复杂模板逻辑；Manifest 已经存在且不想引入模板复杂度；已被 kubectl 原生支持（kubectl apply -k）。

组合： ArgoCD / Flux 支持 "Helm + Kustomize"，先用 helm template 渲染，再用 Kustomize patch 做环境差异化调整。
Release 历史存在 Secret 中有大小限制吗？▶
有。K8s Secret 单条数据的大小限制是 1 MiB（etcd 的 value 限制）。每个 Release 的每个 revision 都对应一个 Secret（base64 + gzip 压缩存储）。

触发问题的场景：Chart templates 非常多、渲染出的 Manifest 很大（如包含大量 CRD 或大型 ConfigMap inline 数据）。

解决方案：
1. 不在 values 中 inline 大文件（用 ConfigMap 的 .Files.Get 代替）
2. 控制 release history 数量：--history-max 10（默认 10，可在 helm upgrade 时指定）
3. 大型静态配置数据用 K8s ConfigMap 存储，不走 Helm template 渲染
4. 考虑把大 Chart 拆分为多个子 Chart

常见误区

❌ 修改了 values.yaml 但没 upgrade，以为会自动生效
# 错误认知：
# 改了 values.yaml 里的 replicaCount
# 以为 K8s 会自动感知并调整

# 实际情况：
# Helm 不是 operator，不持续监控
# values.yaml 只是模板参数文件
# 不运行 helm upgrade，
# 集群中什么都不会变化

# 这与 K8s ConfigMap 热更新不同！
# ConfigMap 挂载为 volume 时，
# K8s 会自动 watch 并更新文件
# 但 Helm values 是一次性渲染参数

Helm 是命令式工具，values 改动必须显式执行 upgrade 才能同步到集群。

# 正确做法：
# 修改 values 后必须执行 upgrade

helm upgrade myapp ./mychart \
  -f values.yaml \
  -f values-prod.yaml \
  --reuse-values   # 复用上次的 values，
                   # 只覆盖显式指定的部分

# 确认变更已生效
helm get values myapp    # 查看当前 Release 的 values
helm get manifest myapp  # 查看当前 Release 的 Manifest
kubectl get deploy myapp -o yaml | grep replicas

通过 helm get values 和 helm get manifest 验证变更是否已实际生效。

❌ 用 --set 传复杂数组/对象时语法错误
# 错误：--set 的数组语法容易写错

# 设置数组元素（错误写法）
helm install myapp ./mychart \
  --set env=["KEY=VAL"]   # ❌ 不支持

# 深层嵌套对象（容易拼错）
helm install myapp ./mychart \
  --set a.b.c.d=value     # 超深路径极易出错

# 含特殊字符（逗号、花括号）
helm install myapp ./mychart \
  --set hosts={a.com,b.com}  # Shell 可能展开

--set 的数组和特殊字符语法很反直觉，复杂结构应改用 -f 文件。

# 正确：复杂结构用 -f 临时文件

# 数组正确语法
helm install myapp ./mychart \
  --set "hosts[0]=a.com,hosts[1]=b.com"

# 更好：复杂覆盖写临时 values 文件
cat > /tmp/override.yaml <<EOF
hosts:
  - a.com
  - b.com
env:
  - name: KEY
    value: VAL
EOF

helm upgrade --install myapp ./mychart \
  -f values.yaml \
  -f /tmp/override.yaml   # 结构清晰，不易出错

复杂结构始终通过 -f yaml 文件传入，可审查、可版本控制。

❌ helm template 本地渲染成功，但 helm install 集群失败
# helm template 不连集群，不验证：
# - K8s API 版本兼容性
# - CRD 是否存在
# - RBAC 权限是否足够
# - 资源名称是否冲突
# - imagePullSecret 是否存在

# 常见场景：
# Chart 用 networking.k8s.io/v1 Ingress
# 老集群只有 extensions/v1beta1
# helm template 渲染正常
# 但 helm install 时 K8s 拒绝

helm template 是纯本地 Go template 渲染，不能替代真实集群验证。

# 增加 CI 校验层次

# 1. helm template + kubeval 检查 schema
helm template myapp ./mychart | \
  kubeval --strict --kubernetes-version 1.28.0

# 2. helm install --dry-run 连接集群做服务端验证
helm install myapp ./mychart --dry-run \
  --namespace prod

# 3. 使用 .Capabilities 做版本条件渲染
{{- if .Capabilities.APIVersions.Has "networking.k8s.io/v1/Ingress" }}
apiVersion: networking.k8s.io/v1
{{- else }}
apiVersion: extensions/v1beta1
{{- end }}

用 --dry-run 连接真实集群做服务端验证；用 .Capabilities 处理多集群版本差异。

❌ kubectl 手动修改资源后，helm upgrade 覆盖丢失
# 场景：线上紧急扩容
kubectl scale deploy myapp --replicas=10

# 此时 CI 触发 helm upgrade
# 三路合并中：
# previous.replicas = 2 (helm 记录的)
# current.replicas  = 10 (kubectl 改的)
# desired.replicas  = 2 (values.yaml 的)
#
# desired 明确指定了 replicas
# desired 优先 → 强制回到 2 ！
# 手动扩容被悄悄覆盖

三路合并中 desired（Helm values）会覆盖 current（kubectl 修改），紧急变更会丢失。

# 解决方案 1：弹性伸缩由 HPA 管理
# values.yaml 中不写固定 replicaCount
# 由 HPA 动态控制副本数
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 20

# 解决方案 2：紧急扩容后立即同步 values
# 修改 values-prod.yaml → commit → helm upgrade
# 走正规 GitOps 流程

# 解决方案 3：--reuse-values
# 复用上次 helm 记录的 values
# 但这不能保留 kubectl 的修改
helm upgrade myapp ./mychart --reuse-values

黄金法则：Helm 管理的资源不要用 kubectl 直接修改；弹性伸缩交给 HPA。
