Redis Stream

Redis Stream 是一种只追加的日志式数据结构，每条消息有唯一的时间戳序号 ID。 消费者组（Consumer Group）维护 last-delivered-id 游标， 追踪已投递位置；PEL（待确认列表）记录已投递但未 ACK 的消息，保证 At-Least-Once 语义。

Stream 与 Kafka 对比

  • Redis Stream 是单节点内存结构，Kafka 是分布式磁盘日志
  • Stream 的 Entry ID 即为 offset，包含时间戳，可按时间范围查询
  • PEL 对应 Kafka 消费者的未提交 offset，但粒度是单条消息
  • XCLAIM 允许将超时未 ACK 的消息转移给其他消费者，Kafka 无此机制
  • Stream 适合单机低延迟场景，Kafka 适合高吞吐分布式场景

常见工程场景

  • 替代简单队列：XADD 写入，XREADGROUP 消费，XACK 确认
  • 事件溯源：Stream 不删除历史，可从任意 ID 重放
  • 多消费者分工：不同 Consumer Group 独立消费同一 Stream
  • 延迟检测：XPENDING 查出长时间未 ACK 的消息并重试
  • XADD events * action login user_id 42 — 写入一条事件
  • XREADGROUP GROUP g1 c1 COUNT 10 STREAMS events > — 读新消息

At-Least-Once 保证机制

消息被 XREADGROUP 读取后立即进入 PEL，不论消费者是否处理完毕。进程崩溃后，下次启动可通过 XPENDING 获取 PEL 中的消息重新处理。XACK 后消息从 PEL 永久移除，确保不会重复计费或重复操作。结合消费端幂等设计，可实现 Exactly-Once 语义。

内存与消息保留

XADD 时通过 MAXLEN ~ N 参数限制 Stream 长度（~ 表示近似裁剪，性能更好）。Stream 不会因消费者消费而删除条目，不同消费者组各自维护游标，互不干扰。消息只有在显式调用 XDEL 或触发 MAXLEN 裁剪时才被移除。
