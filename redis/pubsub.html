Redis Pub/Sub

Redis Pub/Sub 是一个轻量级的发布-订阅消息系统。发布者（Publisher）向频道（Channel）发送消息，订阅者（Subscriber）实时接收。消息不持久化、不确认——这既是它的设计哲学，也是它的核心局限。

SUBSCRIBEPUBLISHPSUBSCRIBE 频道订阅广播实时通知

工作模型

Pub/Sub 是纯粹的实时广播：发布者把消息推给当前在线的订阅者，仅此而已。没有队列，没有 offset，没有重试。

Publisher（发布者）

执行 PUBLISH channel message，立即广播给该频道的所有订阅者。PUBLISH 返回接收到消息的订阅者数量。

Subscriber（订阅者）

执行 SUBSCRIBE channel 后进入订阅模式，连接被"绑定"，只能接收消息，不能执行其他命令。

Pattern 订阅

PSUBSCRIBE news.* 可通过 glob 模式匹配多个频道。news.tech、news.sports 的消息都会被接收。

消息格式

订阅者收到三元组：[type, channel, message]。type 为 message（精确订阅）或 pmessage（模式订阅）。

基本命令

-- 订阅者：订阅单个频道 SUBSCRIBE notifications -- 订阅者：订阅多个频道 SUBSCRIBE channel1 channel2 channel3 -- 订阅者：使用 glob 模式订阅 PSUBSCRIBE news.* -- 匹配 news.tech, news.sports 等 PSUBSCRIBE user.[0-9]* -- 匹配 user.42, user.100 等 -- 发布者：向频道发送消息 PUBLISH notifications "user_login:42" -- 返回: 3 (表示 3 个订阅者收到) -- 查询频道信息（不影响订阅） PUBSUB CHANNELS * -- 列出所有活跃频道 PUBSUB NUMSUB notifications -- 频道的订阅者数量 PUBSUB NUMPAT -- 模式订阅总数 -- 退订 UNSUBSCRIBE notifications PUNSUBSCRIBE news.*

核心特性与局限

消息不持久化，不确认：订阅者离线期间发布的消息永久丢失。这是 Pub/Sub 的设计选择，不是 bug——它是为实时广播设计的，不是为可靠消息传递设计的。
  • Fire-and-Forget：发布者不知道谁收到了消息，消息发出即结束
  • 无消息堆积：订阅者来不及处理时，消息会在服务端缓冲区堆积，超出 client-output-buffer-limit 后订阅者连接被强制断开
  • 无消息历史：新订阅者只能收到订阅之后发布的消息，无法回放历史
  • 无 ACK 机制：消息送达后没有确认，发布者无法感知投递失败
  • 单线程广播：Redis 主线程处理 PUBLISH，频道订阅者过多时会影响 Redis 整体性能

适合使用 Pub/Sub 的场景

黄金法则：当消息丢失可接受时，才考虑 Pub/Sub。实时性要求高、可靠性要求低的广播场景是它的主场。
  • 实时在线状态广播：用户上/下线通知，丢失一次无所谓，下次心跳会更新
  • 缓存失效通知：数据库更新后广播失效指令，订阅者删除本地缓存；即使部分节点未收到，缓存 TTL 会最终一致
  • 实时仪表盘推送：监控数据、聊天室新消息提示，离线用户刷新页面即可获取最新状态
  • 分布式进程间通知：配置变更广播、限流规则推送，丢失后下次同步也可接受
不适合场景：订单状态变更、支付通知、任务调度——这些需要可靠投递，应使用 Redis Stream、Kafka 或专业 MQ。

Go 代码示例

// 订阅者（go-redis） func subscriber(rdb *redis.Client) { pubsub := rdb.Subscribe(context.Background(), "notifications") defer pubsub.Close() for msg := range pubsub.Channel() { fmt.Printf("收到: channel=%s payload=%s\n", msg.Channel, msg.Payload) } } // 发布者 func publisher(rdb *redis.Client, msg string) { n, err := rdb.Publish(context.Background(), "notifications", msg).Result() // n = 收到消息的订阅者数量 fmt.Printf("投递给 %d 个订阅者\n", n) } // 模式订阅 func patternSubscriber(rdb *redis.Client) { pubsub := rdb.PSubscribe(context.Background(), "user.*") for msg := range pubsub.Channel() { // msg.Pattern = "user.*" // msg.Channel = "user.42" (实际频道名) fmt.Println(msg.Pattern, msg.Channel, msg.Payload) } }

常见误区

  • 误区 1：用 Pub/Sub 做任务队列 — 消息不持久化，消费者宕机消息丢失，应改用 Stream 或 List
  • 误区 2：频道数量无限制 — 每个活跃频道消耗内存，模式订阅需要全量匹配，高频道数量影响 PUBLISH 性能
  • 误区 3：订阅模式下可执行普通命令 — 进入订阅模式后连接只能用 SUBSCRIBE/UNSUBSCRIBE/PING/QUIT
  • 误区 4：PUBLISH 成功 = 消息必然送达 — 订阅者消费太慢超出缓冲区会被踢下线，消息丢失
