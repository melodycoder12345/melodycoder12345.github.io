Redis Pipeline

Pipeline 将多条命令打包一次发送，服务端顺序执行后批量返回响应。核心收益是消除逐条命令模式下每次等待 RTT 的空白时间。动画展示相同 N 条命令在两种模式下的时间线差异：逐条模式的灰色等待段大幅缩短为 Pipeline 模式的单次往返。

PipelineRTTMULTI/EXEC批量操作吞吐优化
核心术语
  • RTT（往返延迟）命令从发出到收到响应的网络时间。逐条模式每条命令独占一个 RTT 等待。
  • Pipeline 批量多条命令可连续发送而不逐条等待响应，显著摊薄往返等待；分包、服务端执行和响应传输仍有成本。
  • 原子性Pipeline 无原子性保证，执行中可插入其他客户端命令。需要原子性用 MULTI/EXEC。
  • 缓冲区服务端按序处理命令并把回复写入客户端输出缓冲区；Pipeline 本身没有 EXEC，客户端按序读取回复。

Step 1

逐条模式：第 1 条命令

每条命令独立发送，需等待上一条完成才能发下一条。

代码对比
逐条模式
conn = redis.Dial(addr)
// 每次 Set 都等 RTT
for _, kv := range pairs {
    conn.Do("SET", kv.k, kv.v)
}
Pipeline 模式
conn = redis.Dial(addr)
// 打包发送，一次 RTT
pipe := conn.Pipeline()
for _, kv := range pairs {
    pipe.Set(ctx, kv.k, kv.v, 0)
}
cmds, _ := pipe.Exec(ctx)
MULTI/EXEC 事务
// 原子性保证：执行期间
// 其他客户端命令不插入
pipe := conn.TxPipeline()
pipe.Set(ctx, k1, v1, 0)
pipe.Incr(ctx, counter)
pipe.Exec(ctx) // 原子执行

何时使用 Pipeline

  • 批量写入：初始化数据、批量更新缓存、日志采集
  • 批量读取：一次查询多个 key 的值（用 MGET 更简洁）
  • RTT 较高时收益最大（跨机房、公网场景）
  • 命令之间没有依赖关系时（不需要前一条的返回值）
  • 单次 Pipeline 命令数建议控制在 100-1000 条，避免缓冲区过大

Pipeline vs MULTI/EXEC vs Lua

  • Pipeline：纯传输优化，无原子性，其他命令可插入
  • MULTI/EXEC：事务原子性，命令提前入队，EXEC 后统一执行
  • Lua 脚本：最强原子性，脚本执行期间 Redis 不处理其他命令
  • MULTI/EXEC + Pipeline 可组合：TxPipeline() 一次发送事务
  • WATCH 可在 MULTI/EXEC 前监视 key，实现 CAS 风格的乐观锁；若 key 在 EXEC 前变化，EXEC 返回空结果，客户端应按业务策略重试。

性能数据参考

测试场景：100 条 SET 命令，RTT = 1ms，执行时间 = 0.01ms

  • 逐条：100 × (1ms + 0.01ms) ≈ 101ms
  • Pipeline：1ms + 100 × 0.01ms = 2ms
  • 提速约 50x，RTT 越大提速越显著
  • 实测局域网内 Pipeline 吞吐可提升 5-10x，RTT 越高提升越大

注意事项

  • Pipeline 不是事务：中途若有命令失败，其他命令仍正常执行
  • 服务端将响应放入输出缓冲区，需一次性读取，注意内存占用
  • 不能在 Pipeline 中使用依赖前一命令结果的命令（如 GET 后 SET）
  • client-output-buffer-limit 限制服务端缓冲区，避免发送过多命令
  • Redis Cluster 模式下：同一 slot 的命令才能 Pipeline，否则需要手动分组
