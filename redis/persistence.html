Redis 持久化机制

Redis 通过 RDB 快照和 AOF 日志两种持久化策略确保内存数据在进程重启后可恢复。RDB 适合全量备份与快速恢复，AOF 保证写操作级别的数据安全，二者可结合使用（混合持久化）实现速度与完整性的最佳平衡。

RDBAOFforkCOW混合持久化
核心术语
  • RDB Snapshot全量二进制快照，fork 子进程写盘，恢复速度快。
  • AOF Append写命令追加日志，fsync 策略控制刷盘频率。
  • Copy-on-Writefork 后共享内存页，写时才复制，减少内存开销。
  • AOF Rewrite子进程重写 AOF，将内存状态序列化为最小命令集。

背景

Redis 作为内存数据库，一旦进程退出数据即丢失。持久化机制将内存状态落盘，使数据可在重启后恢复。RDB 提供时间点快照能力，AOF 提供命令级日志回放能力，两者配合实现高可用数据保障。

常见误区

  • RDB 与 AOF 并非二选一，生产环境推荐同时开启（混合持久化）。
  • AOF everysec 并非严格"最多丢 1 秒"，极端情况下可能丢 2 秒（上一次 fsync 延迟时）。
  • fork 不会立即占用双倍内存，COW 只在写时才复制对应页面。

工程实践

  • 混合持久化配置：aof-use-rdb-preamble yes，AOF 重写时先写 RDB 头再追加增量命令。
  • RDB 触发规则：save 900 1 / save 300 10 / save 60 10000，可根据写入频率调整。
  • AOF 推荐：appendfsync everysec，兼顾性能与安全。
  • Go SDK 触发：rdb.BgSave(ctx) / rdb.BgRewriteAOF(ctx)。

边界与代价

  • fork 内存开销：大实例 fork 时 COW 可能导致短暂内存翻倍（写入密集场景）。
  • fsync 延迟：always 策略每次写命令都 fsync，吞吐量下降明显。
  • AOF 重写期间双缓冲区内存消耗和 CPU 开销。
  • 恢复时间：纯 AOF 重放大文件可能需要数分钟，混合持久化可将此降至秒级。
