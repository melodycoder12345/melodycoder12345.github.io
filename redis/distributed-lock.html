Redis / distributed-lock

Redis 分布式锁

使用 SET NX PX 原子命令实现带租约的互斥尝试，配合 Lua 脚本避免误删他人锁；Redlock 提供多节点方案，但安全性依赖时间与故障假设，关键下游仍应使用单调 fencing token 拒绝过期持有者。

  • NX (Not eXists)仅当 key 不存在时才设置成功，Redis 原子操作保证互斥。

背景与机制

单机锁（mutex）无法跨进程协调。Redis 分布式锁利用 SET key token NX PX ttl 在共享 Redis 实例中实现互斥。NX 保证只有一个客户端成功写入（加锁），PX 设置过期时间防止崩溃死锁。释放锁时必须通过 Lua 脚本原子比较 token 后才删除 key，避免误删他人锁。

常见误区

  • 只用 DEL key 释放锁而不校验 token — 可能删掉其他客户端刚获取的锁。
  • 认为加锁成功后永远持有 — TTL 到期锁自动释放，业务未完成时另一个客户端可能趁隙加锁。
  • 把单 Redis 实例锁等同于强一致锁 — 主从切换期间锁可能丢失（脑裂写入）。

工程场景

  • Go SDK 加锁: rdb.SetNX(ctx, key, token, 30*time.Second)
  • Lua 释放: if redis.call("get",KEYS[1])==ARGV[1] then redis.call("del",KEYS[1]) end
  • 续期机制: 在持有者身份仍匹配时定期延长 TTL，并设置续期失败、暂停和最大执行时间的处理；不能承诺业务完成前锁一定不过期。
  • Redlock: 向 5 个独立 Redis 发 SET NX，>= 3 个成功且总耗时 < TTL 才算加锁成功。

边界与恢复

  • 网络分区: 客户端可能以为加锁成功，但实际 Redis 已将锁让给他人 — 需 fencing token 保护下游。
  • 时钟漂移: Redlock 依赖节点时钟近似同步，NTP 跳变可能导致多客户端同时持锁。
  • 强一致场景: 若业务不能容忍极端情况下双写，应使用 ZooKeeper/etcd 等 CP 系统。
