LRU / LFU

LRU/LFU 在容量有限时决定保留哪些数据，连接 Redis 淘汰、Buffer Pool 和多级缓存。

CacheLRULFU
缓存淘汰策略是面试高频考点（LeetCode 146/460），掌握经典实现和 Redis 的近似优化即可覆盖 90% 场景。
核心术语
LRU最近最少使用，强调时间局部性。
LFU最不经常使用，强调访问频率。
近似采样Redis 为降低成本，不维护全局精确排序。

背景

缓存永远有容量上限，需要一种策略决定哪些数据淘汰。核心矛盾在于：

  • LRU 认为"最近访问的更有价值"——追求时间局部性
  • LFU 认为"频繁访问的更有价值"——追求频率稳定性
  • 两者各有弱点：LRU 被一次性扫描（全表 scan）污染；LFU 对新热点响应慢
  • Redis 同时支持两种策略，通过 maxmemory-policy 配置选择
  • 常用配置：allkeys-lru（所有 key 中 LRU 淘汰）、volatile-lfu（有过期时间的 key 中 LFU 淘汰）
  • 扩展策略：MySQL Buffer Pool 使用 young/old 分代 LRU 抵抗全表扫描；ARC（Adaptive Replacement Cache）自动在 LRU 和 LFU 之间切换
  • Redis 8 种 maxmemory-policy：noeviction、allkeys-lru、allkeys-lfu、allkeys-random、volatile-lru、volatile-lfu、volatile-random、volatile-ttl

运行机制

  • 经典 LRU：双向链表 + 哈希表，Get 时将节点移到链表头部，Put 满时淘汰尾部，O(1) 复杂度
  • 经典 LFU：频率桶（频率相同的 key 组成链表），维护最小频率指针 minFreq，访问时频率+1 并移桶
  • Redis 近似 LRU：每个 key 对象头记录 24-bit 时钟（秒精度），淘汰时随机采样 N 个 key（默认 5），选最旧的淘汰
  • Redis LFU (4.0+)：对象头分 16-bit 时钟 + 8-bit 计数器；计数器使用 Morris counter 概率递增；同时按时间衰减，防止历史热 key 永不淘汰
  • 采样数 maxmemory-samples 越大精度越高但 CPU 消耗越大；默认 5 已接近精确 LRU 效果
  • lfu-log-factor 控制概率递增速度（默认 10），lfu-decay-time 控制衰减间隔（默认 1 分钟）

代码示例

Go 实现经典 LRU Cache（container/list + map），面试中要求手写的高频题（LeetCode 146）：

核心思路：哈希表保证 O(1) 查找，双向链表保证 O(1) 插入/删除/移动。两者组合实现 O(1) 的 Get 和 Put。

type entry struct {
    key, val int
}

type LRUCache struct {
    cap   int
    list  *list.List               // 双向链表
    index map[int]*list.Element    // key -> 链表节点
}

func NewLRU(cap int) *LRUCache {
    return &LRUCache{
        cap:   cap,
        list:  list.New(),
        index: make(map[int]*list.Element),
    }
}

func (c *LRUCache) Get(key int) (int, bool) {
    if el, ok := c.index[key]; ok {
        c.list.MoveToFront(el)     // 访问后移到头部
        return el.Value.(*entry).val, true
    }
    return 0, false
}

func (c *LRUCache) Put(key, val int) {
    if el, ok := c.index[key]; ok {
        el.Value.(*entry).val = val
        c.list.MoveToFront(el)
        return
    }
    if c.list.Len() == c.cap {
        tail := c.list.Back()      // 淘汰尾部
        delete(c.index, tail.Value.(*entry).key)
        c.list.Remove(tail)
    }
    el := c.list.PushFront(&entry{key, val})
    c.index[key] = el
}

Redis 淘汰策略配置

# redis.conf 关键配置
maxmemory 4gb                    # 最大内存，超出则触发淘汰
maxmemory-policy allkeys-lfu     # 淘汰策略
maxmemory-samples 5              # 每次淘汰采样数量

# LFU 相关参数
lfu-log-factor 10                # Morris counter 增长因子
lfu-decay-time 1                 # 计数器衰减周期（分钟）

# 查看 key 的空闲时间或访问频率
OBJECT IDLETIME mykey            # LRU: 最后访问距今的秒数
OBJECT FREQ mykey                # LFU: 当前 counter 值（0-255）

# 手动查看内存淘汰统计
INFO stats | grep evicted_keys   # 总淘汰 key 数

常见误区

  • LRU 并非万能：一次全表扫描就能把整个缓存有效数据踢走（scan pollution），MySQL Buffer Pool 因此使用 young/old 分代 LRU
  • Redis 不做精确 LRU：没有维护全局链表，采样近似即可满足需求且节省内存（每个 key 省去前后指针 16 字节开销）
  • LFU 冷启动问题：新 key 初始频率为 0 容易被立即淘汰；Redis 给新 key 初始计数值 5，确保它有机会被访问
  • Morris counter 不是精确计数：概率递增使 8-bit 能表达数百万次访问量级，但牺牲了精确性
  • volatile-lru 需要设置过期时间：如果所有 key 都没 TTL，volatile-* 策略等于 noeviction，写入会报错
  • allkeys-random 不是好选择：随机淘汰无差别踢走热数据和冷数据，缓存命中率远低于 LRU/LFU
  • 采样只在触发淘汰时执行：普通 GET/SET 不会做采样或排序，不影响正常请求性能
  • Redis 7.0+ 支持 maxmemory-eviction-tenacity：控制每轮淘汰的激进程度，避免一次性大量淘汰导致延迟尖刺
  • 淘汰时机：Redis 在每次执行写命令前检查内存，超限则同步执行淘汰直到内存降到 maxmemory 以下才执行命令
  • 集群环境下：每个节点独立执行淘汰策略，不存在全局协调；slot 迁移时已淘汰的 key 不会被传输

面试问答

Redis 的 LRU 和经典 LRU 有什么区别？▶
经典 LRU 用双向链表维护全局访问顺序，精确但每个 key 需要前后指针（16 字节开销）。Redis 采用近似 LRU：每个 key 对象头记录 24-bit 上次访问时钟，淘汰时随机采样 maxmemory-samples 个 key，比较时钟选出最旧的淘汰。采样数为 10 时精度已非常接近精确 LRU，且无额外内存开销。这种设计让 Redis 在百万 key 规模下仍能保持低内存占用。
LFU 的 Morris counter 是如何工作的？▶
Morris counter 是一种概率计数器：每次访问时，生成随机数 r，若 r < 1/(counter*lfu_log_factor+1) 则 counter++。这样 8-bit（最大 255）就能表示百万级访问量。同时 Redis 每隔 lfu-decay-time 分钟将 counter 减 1，防止历史热 key 永不淘汰，使策略能跟踪实时热度变化。lfu-log-factor 默认 10，此时 counter 达到 255 需要约 100 万次访问。
什么场景下 LFU 比 LRU 更合适？▶
当访问模式存在稳定的热点集合时 LFU 更优：如电商首页 banner、热门视频元数据。LRU 在全表扫描或批量遍历（如数据迁移、备份）场景下会被污染，瞬间把真正热数据驱逐。LFU 因为看频率而非时间，对这类一次性访问有天然抵抗力。但 LFU 不适合热点快速切换的场景（如突发新闻），此时需要较低的 decay-time 配置。
如何用 O(1) 实现 LFU？▶
维护三个数据结构：1) key-Node 哈希表；2) freq-双向链表 哈希表（同频率节点一条链，淘汰链尾）；3) minFreq 变量。Get 时将节点从旧频率链移到 freq+1 链，若旧链空且等于 minFreq 则 minFreq++。Put 新 key 时 minFreq=1。所有操作均 O(1)。这个设计比优先队列（O(logN)）更高效，是 LeetCode 460 的标准解法。

常见陷阱

误解：Redis LRU 用链表维护顺序
// 错误理解
// Redis 有一条全局 LRU 链表
// 每次 GET 都 MoveToFront
// 内存中有 prev/next 指针

// 如果真这样做：
// 1 亿 key * 16B 指针 = 1.6GB 额外内存
// 并发链表操作需要全局锁
// 每次读操作都有链表写入开销

问题：1 亿 key 需要额外 1.6GB 内存，且并发链表操作需要锁，与 Redis 单线程高性能设计矛盾。

// 实际实现
// 每个 redisObject 头部有 24-bit lru 字段
// 淘汰时随机采样 5 个 key
// 选 lru 字段最小（最旧）的淘汰
// 无链表、无锁、O(1) 额外空间

// redis.conf 配置：
// maxmemory-samples 5   (采样数)
// maxmemory-policy allkeys-lru

// 采样数对比精度：
// 5: ~91% 接近精确 LRU
// 10: ~97% 接近精确 LRU

正确：Redis 用采样+时钟近似 LRU，在精度和资源消耗之间取得工程平衡。

误解：LFU 计数器会溢出或一直增长
// 错误假设
counter++ // 每次访问 +1
// 热 key 访问百万次
// counter = 1000000
// 8-bit 早就溢出了

// 即使不溢出，历史热 key
// 计数永远很高，新热点
// 永远追不上 -> 无法淘汰旧热点

问题：不理解 Morris counter 概率递增和定期衰减机制，以为是简单计数。

// Redis 实际逻辑（server.c LFULogIncr）
double r = (double)rand() / RAND_MAX;
double p = 1.0 / (old_counter * lfu_log_factor + 1);
if (r < p) counter++;

// 概率递增：counter 越大，+1 概率越低
// lfu_log_factor=10 时：
//   counter 10 -> p=9%
//   counter 100 -> p=0.1%
//   counter 255 需要约 100万次访问

// 定期衰减：每 lfu_decay_time 分钟 -1
// 确保过气 key 的 counter 逐渐降低

正确：概率递增 + 时间衰减让 8-bit 足够表达频率且跟踪热度变化。
