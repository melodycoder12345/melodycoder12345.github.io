向量时钟

向量时钟解决了 Lamport 时钟无法区分并发与因果的问题。每个节点维护一个包含所有节点时钟的数组，消息携带发送方的向量快照，接收方通过逐位取 max 合并。当两个事件的向量无法比较大小时，它们就是并发的。

因果序Happens-Before并发检测版本向量冲突解决
核心术语
  • 向量时钟 VC[A,B,C]三节点系统中每个节点的向量，VC[A] 表示节点 A 已知的 A 的事件计数。
  • 发送规则发送消息前，自身分量加 1，将当前向量附在消息中发送。
  • 接收规则逐位取 max(本地向量, 消息向量)，然后自身分量加 1。
  • 并发 = 无法比较VC(X)[i] < VC(Y)[i] 但 VC(X)[j] > VC(Y)[j] 时，X 和 Y 并发。

规则说明
本地事件规则
VC[self] += 1
发送消息规则
VC[self] += 1
msg.VC = copy(VC)
接收消息规则
for i in range(N):
  VC[i] = max(VC[i],
            msg.VC[i])
VC[self] += 1
比较关系
A → B（A 先于 B）：
∀i: VC_A[i] ≤ VC_B[i] 且 ∃i: VC_A[i] < VC_B[i]
A ∥ B（并发）：
∃i: VC_A[i] > VC_B[i] 且 ∃j: VC_A[j] < VC_B[j]

向量时钟 vs Lamport 时钟

  • Lamport 时钟：单个整数，A → B ⟹ L(A) < L(B)，但反向不成立
  • 向量时钟：A → B 当且仅当 VC(A) < VC(B)，可双向判断
  • Lamport 时钟无法区分并发与因果；向量时钟可以精确检测并发
  • 代价：向量时钟大小随节点数线性增长，节点数多时开销较大
  • 实践中常用版本向量（Version Vector）替代，语义类似但聚焦于数据版本

工程应用场景

  • Amazon Dynamo：每次写操作更新版本向量，读取时检测冲突版本，由客户端合并
  • CouchDB：文档版本用向量记录，冲突自动检测，支持多主复制
  • CRDT：无冲突数据类型内部用向量时钟追踪操作的因果依赖
  • Git：类似概念，每个 commit 有 parent 链接，DAG 隐式编码了因果序
  • 消息去重：分布式系统中用向量时钟判断消息是否已经被因果覆盖

并发冲突的处理策略

检测到并发事件后，需要选择合并策略：

  • Last-Write-Wins（LWW）：附加物理时间戳，选最新的写入，简单但可能丢数据
  • 客户端合并：将冲突版本全部返回给客户端，由应用层合并（Dynamo 方案）
  • 语义合并：根据数据类型的语义自动合并（如计数器取 max，集合取并集）
  • CRDT：设计无冲突的数据结构，任何顺序合并都得到相同结果

向量时钟的局限

  • 大小随节点数 N 线性增长，大规模集群（N=1000）开销显著
  • 需要为每个节点分配固定 ID，动态扩缩容时向量长度变化
  • 实践替代方案：点版本（Dotted Version Vectors）解决动态节点问题
  • 矩阵时钟（Matrix Clock）可以追踪"节点 A 知道节点 B 了解到了什么"，但开销更高
  • 仅追踪因果序，不提供全局线性化顺序（需要 Paxos/Raft 才能实现线性化）
