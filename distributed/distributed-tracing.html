分布式追踪

分布式追踪将一次请求在多个服务间的执行路径串联成瀑布图（Waterfall）。横轴是绝对时间，每行是一个 Span，缩进体现 parent-child 关系。点击 Span 可查看 TraceID/SpanID 等上下文信息，直观看出哪个服务是性能瓶颈。

核心术语
  • Trace（请求链路）一次请求的完整调用树，由唯一 TraceID 标识。
  • Span（工作单元）调用链中的最小单元，有父子关系，记录耗时和标签。
  • traceparent HeaderW3C 标准：version-traceId-spanId-flags，跨服务传递上下文。
  • OTLPOpenTelemetry Protocol，统一导出 Span 数据到 Jaeger/Tempo 等后端。

W3C traceparent 格式

HTTP Header 传递格式：

traceparent: 00-ab3f...c129-0123...ef45-01
            版本  traceId(32位)  spanId(16位)  flags

  • version：固定 00
  • traceId：全局唯一，128bit，贯穿整条链路
  • parentSpanId：调用者的 spanId，下游据此构建父子关系
  • flags：01 表示采样，00 表示不采样

采样策略

  • 头采样（Head-based）：请求入口决定是否采样，全链路一致，但无法事后决定
  • 尾采样（Tail-based）：全量收集，在 Collector 层按条件过滤（如只保留 P99 慢请求）；代价是 Collector 需要缓冲全部 Span
  • 固定比例：每 N 条采 1 条，简单但会漏掉偶发慢请求
  • 生产建议：错误请求 100% 采样 + 正常请求 1-5% 采样

OpenTelemetry 架构

  • SDK：代码中创建 Span、设置属性，支持 Go/Java/Python 等多语言
  • Collector：接收 OTLP，做采样/过滤/聚合，转发到后端（Jaeger/Tempo/Zipkin）
  • 自动插桩：HTTP/gRPC/数据库驱动无需修改代码，SDK 自动注入 Span
  • 推荐部署：App → OTEL SDK → OTEL Collector → Jaeger/Grafana Tempo

关键排障场景

  • P99 慢请求定位：按 duration > 阈值过滤 Trace，找出耗时最长的 Span
  • 跨服务错误传播：某 Span status=ERROR，追溯 parentSpanId 找到根因服务
  • 数据库 N+1 问题：同一 Trace 内看到大量相似 DB Span，识别 ORM 滥用
  • 依赖拓扑分析：汇聚 SpanName 构建服务调用图，识别未知依赖和热点路径
