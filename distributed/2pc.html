两阶段提交
（2PC）

两阶段提交通过协调者广播 Prepare/Commit，让多个参与者原子性地完成分布式事务，但协调者单点和阻塞问题是其核心局限。

PrepareCommit协调者阻塞
核心术语
  • Coordinator（协调者）发起并协调两个阶段的中心节点，单点故障是 2PC 的主要问题。
  • Participant（参与者）收到 Prepare 后锁定资源等待，无法单方面中止或提交。
  • Blocking（阻塞）协调者崩溃时，参与者锁定资源无限等待——2PC 不解决这个问题。

背景与机制

2PC 是解决跨节点原子提交的经典协议，确保"要么全提交，要么全回滚"。Phase 1（Prepare）协调者向所有参与者询问是否可以提交，参与者锁定资源并记录 undo log；Phase 2（Commit/Rollback）协调者根据投票结果广播最终决定。参与者只有在协调者明确指令后才能释放锁。

常见误区

  • 2PC 不是高可用协议——协调者崩溃后参与者会无限期持锁阻塞，直到协调者恢复。
  • 网络分区下 2PC 无法保证可用性（CA 而非 AP），这是其最大局限。
  • 参与者投 Yes 之后就失去了决策权，只能等待协调者的最终指令。
  • 3PC 试图解决阻塞但引入了新复杂性，工业界更多采用 Saga/TCC 替代。

工程场景

  • MySQL XA 事务（InnoDB 支持 XA/2PC），适合同一数据库内的分布式协调。
  • 分布式数据库跨分片事务（TiDB、CockroachDB）内部使用类 2PC 协议。
  • Java JTA（javax.transaction）提供 2PC 的标准接口，XAResource 对应参与者。
  • 现代微服务更多采用 Saga 模式或 TCC（Try-Confirm-Cancel）避免全局锁。

边界与恢复

动画覆盖四个场景：① 正常全票 Yes 提交路径；② 一票 No 触发全局回滚；③ 协调者在 Phase 2 前崩溃，参与者无限阻塞；④ 参与者超时后尝试互联查询（3PC 方向）。排查时关注协调者日志状态——已写 commit 则参与者应提交，未写则应回滚。
