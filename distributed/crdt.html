CRDT
无冲突复制
数据类型

CRDT 通过数学设计保证任何副本在接收到所有操作后最终状态相同，无需协调即可合并，是协同编辑、分布式计数器和购物车的基础。

最终一致性合并G-CounterLWW
核心术语
  • State-based CRDT（CvRDT）通过合并完整状态实现收敛。合并函数是幂等、交换且结合的——无论消息顺序如何，最终状态相同。
  • Op-based CRDT（CmRDT）只传播操作，接收方重放操作得到相同结果。要求消息传递可靠且操作满足交换律。
  • Monotonic Join SemilatticeCRDT 合并操作满足幂等性、交换律和结合律，保证无论哪些副本先合并，最终结果相同。

为什么需要 CRDT？

在 AP 分布式系统中（参考 CAP 定理），分区时系统选择继续服务（Available），各副本可能独立接受写入，产生冲突。传统解决方案是"最后写入者获胜"（LWW），但这会丢失并发写入。

CRDT 从数学层面解决这个问题：设计数据结构，使得合并操作天然满足幂等性、交换律和结合律。无论副本以何种顺序收到更新，合并后的状态必然相同。

核心洞察：不是"协调写入"（需要共识），而是"设计可自动合并的数据结构"（不需要协调）。

State-based vs Op-based CRDT

State-based CRDT（CvRDT）：副本定期互相发送完整状态，接收方用 merge() 函数合并。G-Counter 示例：

// G-Counter: 每个副本维护自己的计数器向量
type GCounter = Map[NodeId, Int]

def increment(nodeId: NodeId, gc: GCounter): GCounter =
  gc + (nodeId -> (gc.getOrElse(nodeId, 0) + 1))

def value(gc: GCounter): Int = gc.values.sum

def merge(a: GCounter, b: GCounter): GCounter =
  (a.keys ++ b.keys).map { k =>
    k -> math.max(a.getOrElse(k, 0), b.getOrElse(k, 0))
  }.toMap // max 操作保证幂等、交换、结合

Op-based CRDT（CmRDT）：只传播操作（如 +1），要求可靠的消息传递和操作满足交换律（add(x) 和 add(y) 顺序无关）。通常更高效但依赖基础设施保证。

常见 CRDT 类型

G-Counter
只增计数器，merge 取 max。适合页面访问量统计。
PN-Counter
两个 G-Counter：P（加法）- N（减法）= 净值。支持递减。
G-Set
只增集合，merge 取并集。适合标签系统（不支持删除）。
2P-Set
两个 G-Set：added + removed，删除不可撤销。
OR-Set
用唯一标签区分同名元素，支持删除+重新添加。Riak 使用。
LWW-Register
带时间戳的寄存器，最高时间戳的值获胜。依赖时钟同步。

LWW 的局限性与 Lamport 时钟

LWW（Last Write Wins）是最简单的冲突解决策略：每次写入携带时间戳，时间戳大的值"获胜"。但这有严重问题：

  • 时钟漂移：分布式系统的物理时钟不完全同步，可能造成旧值覆盖新值。
  • 并发写入丢失：两个合法的并发写入，只有一个"获胜"，另一个被静默丢弃。
  • Cassandra 的使用：Cassandra 默认用 LWW，在同一 row 并发写时可能丢失数据。

Lamport 时钟是一种逻辑时钟：每个事件有一个递增计数器，消息携带发送方的计数器，接收方取 max(本地, 消息) + 1。它保证因果序但不能检测并发事件（需要向量时钟）。

// Lamport 时钟：因果关系保证
class LamportClock:
  tick(): self.time += 1
  update(received_time): self.time = max(self.time, received_time) + 1

工程场景

  • Figma 协同编辑：Figma 使用基于 CRDT 的方法（结合 OT 思想）让多人同时编辑同一画布不产生冲突，每个操作有唯一 ID 和向量时钟。
  • Riak（Amazon Dynamo 的开源实现）：默认使用 OR-Set 和 LWW-Register 作为分布式数据结构，配合向量时钟检测并发写。
  • Redis CRDT（Redis Enterprise）：Redis Enterprise 的 CRDT 模式支持 Counter、Set 等数据结构的跨地域自动合并，无需中心协调。
  • Automerge / Yjs：开源 CRDT 库，用于构建协同编辑应用（如 VS Code Live Share 的底层）。
  • PlanetScale / CockroachDB：某些内部数据结构（如 schema 元数据）使用 CRDT 思想保证跨节点最终一致。

误区与边界

误区 1：CRDT 能解决所有冲突
CRDT 只解决"数据结构层面"的冲突，不解决"业务语义冲突"。例如：两个用户同时修改一篇文章的同一段落，CRDT 可以合并，但合并后的语义是否正确需要人工判断或应用层决策。

误区 2：CRDT 是免费的
State-based CRDT 需要传输完整状态（带宽成本高），tombstone（删除标记）会无限增长需要定期 GC。OR-Set 的 tombstone 会随时间膨胀。

误区 3：Op-based CRDT 更简单
Op-based CRDT 要求可靠的消息传递（at-least-once）和操作幂等，需要消息去重机制，复杂度转移到了基础设施层。

何时选择 CRDT？：有真实并发写需求 + 可以接受最终一致性 + 数据操作能抽象为可交换操作（计数器、集合、文本插入）时，CRDT 是极好的选择。
