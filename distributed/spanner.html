Google Spanner
与 TrueTime

Google Spanner 是首个在全球范围内提供外部一致性（External Consistency）的分布式数据库，其核心是 TrueTime API——通过 GPS 天线和铯原子钟构建的有界误差时间系统。Commit-wait 机制确保事务时间戳的全球唯一性，Paxos 分组保障高可用，是 NewSQL 时代的里程碑。

核心术语
  • TrueTime API 通过 GPS 天线+铯原子钟构建的分布式时钟。TT.Now() 返回 [earliest, latest] 区间而非精确时间点，误差通常在 1–7ms 以内。不确定性是有界的。
  • 外部一致性（External Consistency） 强于串行化的一致性保证：若事务 T1 在 T2 开始前已提交，则 T1 的提交时间戳严格小于 T2。等价于线性一致性（Linearizability）。
  • Commit-Wait 事务 Leader 分配时间戳 s 后，必须等待直到 TT.Now().earliest > s（至少一个误差窗口），才能释放锁并对外可见，确保真实时间已超过 s。

工程背景：为什么需要 Spanner

2000 年代中期，Google 广告系统 F1 基于 MySQL 分片运行，跨分片事务需要大量应用层逻辑，数据迁移困难，一致性难以保证。同期 Bigtable + Megastore 的组合提供了分布式存储，但 Megastore 的强一致性代价是极高延迟。

Spanner 的目标（2012 年 OSDI 论文）：

  • 在全球分布的数据中心上提供 ACID 事务（含跨行、跨表、跨数据中心）
  • 保证 外部一致性——比串行化更强的一致性模型
  • 支持 SQL 查询，与 NoSQL 的 BigTable 形成互补
  • 引入 NewSQL 概念：同时拥有 SQL 接口和 NoSQL 的水平扩展能力

Spanner 的成功推动了整个业界重新思考「强一致性与可扩展性是否必然矛盾」，直接催生了 CockroachDB、YugabyteDB 等开源 NewSQL 数据库。

TrueTime 设计：有界误差的分布式时钟

传统 NTP 时钟误差难以精确量化（可能数百毫秒偏差），无法用于分布式事务的时间戳排序。TrueTime 通过硬件+软件双层架构解决这个问题：

硬件层：每个数据中心部署多台 Time Master 服务器，各自配备 GPS 天线接收器或铯原子钟（两种来源互为冗余），误差源相互独立，避免共因失效。

软件层：每台机器运行 timeslave 守护进程，定期向多台 Time Master 轮询并应用 Marzullo 算法计算置信区间，更新本地时钟。

TrueTime API 三个方法：

  • TT.Now()：返回 TTinterval{earliest, latest}，保证真实时间 t_abs ∈ [earliest, latest]
  • TT.after(t)：若 earliest > t，返回 true（真实时间已超过 t）
  • TT.before(t)：若 latest < t，返回 true（真实时间仍在 t 之前）
// TrueTime API 伪代码（概念示意）
type TTinterval struct {
    Earliest time.Time  // 真实时间下界
    Latest   time.Time  // 真实时间上界
}

func TT_Now() TTinterval      // 返回当前时间区间 [earliest, latest]
func TT_After(t time.Time) bool // 真实时间是否已超过 t
func TT_Before(t time.Time) bool// 真实时间是否仍在 t 之前

// 平均约 4ms，最大约 7ms（GPS 更换电池等特殊情况时更高）

外部一致性与 Commit-Wait 机制

外部一致性定义：对任意两个事务 T1 和 T2，若 T1 的提交时刻（真实时间）早于 T2 的开始时刻，则 T1 的提交时间戳 s(T1) < s(T2)。

这比串行化更强：串行化只要求存在一个等价的串行执行顺序，外部一致性还要求该顺序与真实时钟顺序一致（即等价于线性一致性）。

Commit-Wait 实现步骤：

① Leader 分配时间戳
读取 TT.Now()，取 s = latest（确保 s ≥ 真实时间）
↓
② Commit-Wait 等待
阻塞，直到 TT.Now().earliest > s（即确认真实时间已超过 s）
↓
③ 释放写锁，事务对外可见
此后任何读取操作都能看到该事务（快照时间戳 ≥ s）

为什么这样就能保证外部一致性？
设 T1 提交时间戳为 s1，T2 开始时间为 t_start。
T1 提交后，由于 Commit-Wait，真实时间 t_abs > s1。
T2 开始时调用 TT.Now()，得到 latest ≥ t_abs > s1。
T2 的时间戳 s2 = TT.Now().latest ≥ t_abs > s1。
因此 s2 > s1，即 s(T1) < s(T2)，外部一致性得证。

Paxos 分组架构

Spanner 将数据水平分片（Shard），每个分片称为 Spanserver，并组织成独立的 Paxos 组：

  • 分片（Tablet）：数据按键范围分片，每片包含一个或多个目录（Directory），是数据局部性的管理单元。
  • Paxos 组：每个 Tablet 维护一个跨数据中心的 Paxos 副本组（通常 5 副本），确保高可用。Leader 处理所有写事务，Follower 可服务读操作。
  • 全球分布：副本分布在多个地理区域，通过 Paxos 保证数据一致性。Leader 可在不同副本间切换（Leader 选举）。
  • 目录迁移：Spanner 可以在不停服务的情况下迁移 Directory（数据目录），实现负载均衡和地域亲和性。

读写事务与只读事务流程

读写事务（Read-Write Transaction）：Spanner 中最复杂、代价最高的事务类型。

// 读写事务时序伪代码
func ReadWriteTransaction() {
    // 1. 客户端读取（获取读锁，发现参与的 Paxos 组）
    data := Read(keys...)

    // 2. 客户端执行业务逻辑，准备写集合
    writes := Compute(data)

    // 3. 两阶段提交（2PC，跨 Paxos 组时）
    coordinator := ChooseCoordinator(participants)
    Prepare(participants, writes) // 获取写锁

    // 4. Leader 分配时间戳 + Commit-Wait
    s := TT_Now().Latest
    CommitWait(until TT_After(s)) // 等待 ~epsilon 时间

    // 5. 发送 Commit，释放锁
    Commit(participants, s)
}

只读事务（Read-Only Transaction）：无锁，高性能，直接读取快照：

  • 选择时间戳：调用 TT.Now().latest 作为快照时间戳，或由客户端指定历史时间点
  • 直接读快照：所有副本（包括 Follower）都能服务这类读请求
  • 无 2PC 无锁：不产生任何写锁，不与写事务竞争，延迟极低
  • 外部一致性：读取时间戳 ≥ 任何已提交事务的 Commit-Wait 时间戳，因此总能看到最新一致状态

与 2PC 的关系：Spanner 的分层协议

Spanner 并没有「替代」2PC，而是在其之上叠加了 Paxos 层解决高可用问题，形成双层协议架构：

跨 Paxos 组写事务 → 使用 2PC 协调
当写事务涉及多个 Paxos 组（不同 Tablet）时，Spanner 使用 2PC 协调跨组提交，协调者为某一 Paxos 组的 Leader。
单个 Paxos 组内 → 使用 Paxos 保证可用性
每个参与 2PC 的节点本身是一个 Paxos 组（5 副本），即使某台机器宕机，Paxos 仍能继续服务，2PC 的参与者不会因单点故障崩溃。

如何解决 2PC 阻塞问题？：在 Spanner 中，2PC 的协调者是 Paxos 组 Leader，Paxos 提供了 Leader 故障后的自动重新选举。因此虽然使用 2PC，但协调者单点问题被 Paxos 高可用所缓解——协调者故障后，新 Leader 会基于 Paxos 日志继续处理。

TrueTime 的作用：不是替换 2PC，而是为提交时间戳的全球唯一排序提供基础，实现外部一致性——这是单纯 2PC 无法做到的。

局限与工程实践

Commit-Wait 延迟开销：每个读写事务必须等待约 2×epsilon（epsilon 是 TrueTime 误差的一半），通常额外增加 10–14ms。对于单数据中心场景，这个开销相对于 NTP 方案偏高。

跨洲际延迟：全球分布的 Paxos 组写事务，多数派确认需要跨洲际光速传输（中美约 120ms），使得某些写操作延迟极高，不适合所有业务场景。

硬件依赖：TrueTime 依赖专用 GPS 接收器和铯原子钟，无法在普通数据中心复现。

开源替代方案对比：

  • CockroachDB：使用 HLC（Hybrid Logical Clock，混合逻辑时钟）近似 TrueTime，误差通过 Clock Skew 检测和等待处理，无需专用硬件
  • YugabyteDB：同样基于 HLC + Raft，PostgreSQL 兼容接口
  • TiDB：使用 TSO（Timestamp Oracle）中心化时间戳分配，Raft 管理副本，牺牲单点但架构更简单
  • Cloud Spanner：Google 托管版本，2017 年公开提供，无需自建硬件时钟设施

深度示例：时间戳排序证明与 HLC 对比

场景：用户 A 在节点 N1 完成转账事务 T1（提交时间戳 s1），随后告知用户 B（通过电话/消息——Spanner 外部信道），用户 B 在节点 N2 查询账户余额（只读事务 T2）。外部一致性保证 T2 一定能看到 T1。

// Spanner 外部一致性保证流程
// T1: 转账事务（在 Leader N1 上执行）
s1 = TT_Now().Latest    // s1 ≥ 真实时间 t1_real
CommitWait()             // 等待至 TT_After(s1) = true
                          // 此时真实时间 t_real > s1
Commit(writes, s1)       // T1 以时间戳 s1 对外可见

// T2: 读取事务（在节点 N2 上执行，T1 之后）
// 因为 T2 开始于 T1 提交后（真实时间 t2_start > s1）
s2 = TT_Now().Latest    // s2 ≥ t2_start > s1
result = ReadSnapshot(s2) // 快照时间戳 s2 > s1，可以看到 T1

// 结论：s2 > s1 → T2 一定能看到 T1 的结果 ✓

HLC（混合逻辑时钟）的近似方案：HLC 使用 max(物理时钟, 逻辑时钟) 提供因果一致性，但无法精确量化误差窗口，需要额外的 Clock Skew 检测（通常设置最大允许偏差 500ms）。若检测到时钟偏差过大，事务会 Retry，保证安全性但增加尾延迟。

// HLC 示意（CockroachDB 风格）
type HLC struct {
    Physical int64  // 墙上时钟（纳秒）
    Logical  int32  // 同一物理时刻内的逻辑计数器
}

// 发送事件：时间戳 = max(本地HLC, 物理时钟) + 逻辑+1
// 接收事件：时间戳 = max(本地HLC, 消息HLC, 物理时钟) + 逻辑+1
// 保证：因果关系下 hlc(A) < hlc(B)，但不保证外部一致性
