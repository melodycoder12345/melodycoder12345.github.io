BASE 理论

BASE（Basically Available, Soft State, Eventually Consistent）是 ACID 的对立面，也是分布式 AP 系统的设计哲学。理解 BASE 是选择数据库、设计一致性策略和容忍短暂不一致的思维基础。

最终一致性可用性Soft StateAP 系统
BASE 三要素
  • Basically Available（基本可用）即使部分节点失败，系统仍能响应，但可能降级——延迟变高、返回部分数据或旧数据。
  • Soft State（软状态）系统的中间状态可能随时间变化，即使没有新的输入（副本同步正在进行）。
  • Eventually Consistent（最终一致性）如果停止写入并等待足够长的时间，所有副本最终会收敛到相同状态。

BASE vs ACID 完整对比

ACID 和 BASE 是两种截然不同的设计哲学，理解它们的区别是架构选型的基础。

Basically Available — 基本可用

不是"完全可用"：基本可用不等于系统总是正常工作，而是允许"有损的可用性"——在异常情况下，系统会以降级的方式继续响应，而不是直接不可用。

常见的有损降级模式：

  • 延迟降级：正常情况响应 50ms，降级时响应 500ms，但不返回错误。
  • 功能降级：搜索服务故障时返回缓存的默认推荐，而非 500。
  • 数据降级：读取副本可能返回几秒前的数据（stale read），但不拒绝服务。
  • 分区降级：部分节点失联时，系统仅用存活节点提供服务（降低吞吐量但保持可用）。

CAP 定理的背景：AP 系统选择了 Availability + Partition Tolerance，牺牲了 Consistency。BASE 是对这个选择的系统化描述——不是"不要一致性"，而是"接受最终一致性换取更高可用性"。

Soft State — 软状态

软状态的含义：系统状态可能在没有新用户输入的情况下自发改变。这是因为后台的副本同步、TTL 过期、缓存失效等机制在持续运行。

具体场景：

  • 你在两个数据中心的数据库写入了一条记录，同步需要 100ms——这 100ms 内系统处于"软状态"（DC1 有，DC2 没有）。
  • Redis 缓存中的数据过期被逐出——没有用户操作，状态自动变化。
  • Cassandra 的 hinted handoff：目标节点失联时，写入暂存在其他节点，目标节点恢复后自动应用——中间阶段就是软状态。

软状态 vs 脏状态：软状态不意味着数据会丢失或损坏，而是"正在向最终状态收敛"的中间过程。这与 ACID 中"事务提交后立即一致"形成对比。

Eventually Consistent — 最终一致性

如果停止所有写入，并等待足够长的时间，所有副本最终会收敛到相同的状态。"足够长的时间"是关键——这个时间窗口内存在不一致。

最终一致性的变体：

  • 单调读一致性：用户 A 读到了版本 v2，后续读取不会看到 v1。
  • 读己所写一致性：用户写入后，自己的读取能看到自己的写入。
  • 因果一致性：如果操作 A 在 B 之前（因果关系），所有节点都先看到 A 再看到 B。
// DynamoDB 最终一致性读（默认，低延迟）
const result = await client.get({
  TableName: 'users',
  Key: { userId: '123' },
  ConsistentRead: false // 最终一致性，可能读旧数据
});

// 强一致性读（更高延迟，消耗 2× 读容量）
const result = await client.get({
  TableName: 'users',
  Key: { userId: '123' },
  ConsistentRead: true  // 强一致性读
});

工程选择：何时用 ACID，何时用 BASE

🏦
选 ACID（强一致性） 金融交易、银行转账、库存扣减（不能超卖）、订单状态变更——任何"要么全成功要么全失败"的场景，且对一致性要求高于可用性。
📊
选 BASE（最终一致性） 用户行为日志、社交媒体点赞/评论数、商品浏览量、购物车（允许短暂不一致）、推荐系统——读多写多、可以容忍短暂不一致的场景。
⚖️
混合策略（常见于大型系统） 核心交易用 ACID（MySQL/PostgreSQL），日志/分析用 BASE（Kafka/ClickHouse），缓存层用 BASE（Redis），搜索用 BASE（Elasticsearch）。
🔧
可调一致性（Tunable Consistency） Cassandra 通过 Quorum 设置（W + R > N）支持在 AP 和 CP 之间灵活切换：写 ALL 读 ALL = 强一致，写 ONE 读 ONE = 最终一致。

误区与边界条件

误区 1：BASE = "随便不一致"
BASE 不是放弃一致性，而是在严格定义的边界内接受短暂不一致，并有明确的收敛机制。你需要知道：不一致窗口有多长？用哪种策略解决冲突？

误区 2：最终一致性不需要冲突解决
当两个副本同时接受不同的写入时，"最终收敛"需要定义冲突解决策略：LWW（Last Write Wins，可能丢数据）、多版本合并（Vector Clock + 应用层决策）、CRDT（自动合并）。

误区 3：BASE 系统没有事务
Cassandra 有轻量级事务（LWT / Paxos）用于部分场景，DynamoDB 支持跨 item 事务，MongoDB 支持多文档事务——但这些事务的代价是降低性能，且仍不能跨分片。

误区 4：选了 AP 就无法保证任何一致性
AP 系统可以提供更弱但仍有用的一致性模型：读己所写、单调读、因果一致性——这些比"最终一致性"强，比"强一致性"弱，是工程实践中的常见选择。
