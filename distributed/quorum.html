Quorum 读写模型

W + R > N 保证成功写集合与读取集合至少相交，因此读可能观察到已完成写的一个副本。要从“集合相交”推导新鲜读，还必须正确解析版本，并处理并发写、失败重试、sloppy quorum 与副本修复。

W+R>NN=3读修复版本号CassandraDynamoDB
核心术语
  • W+R>N（Quorum 条件）写 W 副本成功才确认，读 R 副本；W+R>N 只直接保证两集合有交集。
  • 读修复（Read Repair）读到旧版本副本时，将最新值异步写回，使落后副本追平，Cassandra 的主要一致性补充机制。
  • 版本号/时间戳每次写入时递增版本号，读取 R 个副本后比较版本号取最大，确定最新值并返回给客户端。
  • Hinted Handoff写目标副本不可用时暂存在代理节点，副本恢复后代理节点将数据补发，Cassandra 用于提高写可用性。

W+R>N 数学原理

N=3 是最常见配置。W+R>N 等价于写集合和读集合的交集非空（鸽巢原理）：

— W=3,R=1：若读取的固定副本集与成功写集合遵循同一 N 个副本，读集合必与写集合相交；但超时写、并发写和替代副本仍需额外语义处理
— W=2,R=2：平衡，写 2 个成功，读 2 个取最大版本。容忍 1 个副本落后，也容忍 1 个节点不可用
— W=1,R=3：强读，写任意 1 个成功（最快），读所有节点取最大版本（读最慢但写可用性最高）
— W=1,R=2：W+R=3=N，不满足条件，不保证强一致，可能脏读

Cassandra 用 ONE/TWO/THREE/QUORUM/ALL 作为一致性级别别名，QUORUM = ⌊N/2⌋+1。

常见误区

  • Quorum 的集合交集性质本身不保证“读到最近一次完成的写”，更不保证线性一致性；版本选择、并发写、读写协调和故障恢复共同决定实际一致性。
  • Cassandra 默认使用 Last-Write-Wins 时间戳而非版本向量，时钟不同步会导致正确的写被旧时间戳的写覆盖。
  • W+R>N 只在写操作完全完成后才有保证。网络分区期间，写只成功了部分副本（< W），不保证后续 Quorum 读能读到这次写。
  • 读修复是异步的，读期间的修复不影响本次读的返回时间，但如果在修复完成前再次读，可能还会读到旧值。

工程场景

  • Cassandra：LOCAL_QUORUM 约束本地数据中心的响应副本数；能否获得最新值还受拓扑、并发时间戳、sloppy quorum 与修复状态影响，不应概括为线性一致。
  • DynamoDB：公开 API 提供最终一致读或特定表/索引上的强一致读；其内部副本数和 quorum 实现不是该 API 合约，不应断言为 2/3。
  • ZooKeeper：写操作必须多数派 follower 确认，读可以从任意节点（默认），启用 sync() 可强制从 leader 读。
  • etcd：写强制 Raft 多数派（W=⌊N/2⌋+1），线性读走 leader（强一致），串行读允许 stale。

一致性权衡

调节 W 和 R 实现不同权衡：

高写可用（W=1）：写 1 个节点成功即可，极少写失败，但读需要联系更多副本（R=N）来保证一致性，读延迟高。适合写多读少且对写延迟敏感的场景。

高读可用（R=1）：读 1 个节点即可（极快），写需要联系所有副本（W=N），写容错差。适合读多写少且对读延迟极敏感的场景（如计数器）。

平衡（W=R=⌊N/2⌋+1）：最常见配置，均衡读写延迟和一致性保证。
