三阶段提交
（3PC）

3PC 在 2PC 的 Prepare/Commit 两阶段之前插入 CanCommit 探测阶段，并为每个阶段引入超时机制，使协调者故障后参与者能通过 Termination Protocol 自行决策，消除了无限阻塞问题——但仍无法处理网络分区。

核心术语
  • CanCommit（预备探测）轻量级询问阶段，只检查资源是否可用，不加锁不写日志。CanCommit 失败代价极低，可零成本 Abort。
  • PRE_COMMITTED 状态参与者收到 PreCommit 后的状态：已锁定资源并写入预提交日志，「打算提交」。这是 Termination Protocol 的决策依据。
  • Termination Protocol协调者故障后参与者间的协商协议：全部 PRE_COMMITTED → 提交；有 UNCERTAIN → 查询；有 ABORTED → 全部回滚。

机制解析

3PC 通过三个阶段解决 2PC 的阻塞问题：CanCommit（轻量探测，不加锁）→ PreCommit（加锁写日志，进入 PRE_COMMITTED）→ DoCommit（最终提交）。关键在于 PRE_COMMITTED 状态——协调者故障后，参与者通过 Termination Protocol 查询彼此状态：若全员 PRE_COMMITTED 则提交，若有人 UNCERTAIN（未收到 PreCommit）则中止。

超时处理策略

  • CanCommit 阶段超时：直接 Abort。参与者未加锁，代价为零，安全且高效。
  • 等待 PreCommit 超时：发起 Termination Protocol，查询其他参与者。
  • 等待 DoCommit 超时：同上，若全员 PRE_COMMITTED 则自行提交。
  • 等待 CanCommit 响应超时：协调者直接 Abort，不等待超时的参与者。

3PC 的局限

  • 网络分区时：分区两侧各自执行 Termination Protocol 可能做出不同决策（脑裂）——这是 3PC 无法解决的根本问题。
  • 消息轮次增加 50%（6 vs 4 轮），延迟更高，吞吐量更低。
  • 协议实现复杂，状态机更难维护，工业界几乎不直接使用。
  • Paxos / Raft 等共识算法在多副本场景下更优，Saga / TCC 在微服务场景下更实用。

工程实践参考

3PC 在学术上有重要意义，但工业界极少直接使用。现代分布式系统的替代方案：① Google Spanner 使用 Paxos 分组 + TrueTime 实现全球一致性；② TiDB / CockroachDB 使用 Raft + 类 2PC 的跨分片事务；③ 微服务场景下 Saga 模式（补偿事务）或 TCC（Try-Confirm-Cancel）避免全局锁；④ 事件溯源 + 最终一致性完全绕过分布式事务。了解 3PC 的价值在于理解「非阻塞共识」的设计思路。
