Linux / cgroup

cgroup / Namespace

Namespace 改变进程看到的系统视图，cgroup 限制资源用量，两者构成容器基础。

cgroup v2NamespaceContainer
理解 cgroup + namespace 就理解了容器的本质：不是虚拟机，而是受限的进程组。
核心术语
Namespace隔离 PID、mount、network、UTS、IPC、user 等系统视图。
cgroupControl Group，限制和统计 CPU、memory、I/O、PID 等资源。
rootfs容器看到的文件系统根，通常由 OverlayFS + bind mount 构建。

背景

容器不是虚拟机——它共享宿主机内核，隔离来自两个正交机制的组合：

  • Namespace（视图隔离）：让进程"看到"独立的 PID 空间、网络栈、文件系统挂载点
  • cgroup（资源限制）：限制进程组的 CPU、内存、IO 使用量并记账
  • Docker/containerd 本质：clone(CLONE_NEWPID|CLONE_NEWNS|...) + 写 cgroup + pivot_root + exec
  • cgroup v1：每个 controller 独立层级树，配置混乱；v2：统一单一层级，所有 controller 共享一棵树
  • 隔离强度排序：物理机 > 虚拟机（独立内核）> gVisor/Kata（用户态内核）> 容器（共享内核）

运行机制

  • 8 种 Namespace：mnt（挂载点）、pid（进程号）、net（网络栈/IP/端口/路由）、uts（主机名）、ipc（信号量/共享内存）、user（UID/GID 映射）、cgroup（cgroup 根视图）、time（5.6+，时钟偏移）
  • cgroup v2 控制器：cpu（权重 cpu.weight / 硬上限 cpu.max）、memory（memory.max/high/low）、io（io.max IOPS/带宽限制）、pids（最大进程数）、cpuset（CPU 亲和性绑定）
  • Memory 控制器：memory.max = 硬限制（超出 OOM kill）；memory.high = 软限制（超出加大回收压力）；memory.current 包含 RSS + Page Cache + kernel stack
  • CPU 控制器：cpu.max = "quota period"（如 "200000 100000" = 2 核上限）；cpu.weight 控制同级竞争权重（1-10000，默认 100）
  • Docker 映射：--memory=512m → memory.max=536870912；--cpus=2 → cpu.max="200000 100000"；--pids-limit=100 → pids.max=100
  • K8s 映射：resources.limits.memory → memory.max；resources.requests.cpu → cpu.weight（按比例）；limits.cpu → cpu.max
  • PSI (Pressure Stall Info)：cgroup v2 提供 cpu.pressure / memory.pressure / io.pressure，精确量化资源争用导致的等待时间

代码示例

Go 代码：创建 cgroup 设内存限制 + 用 namespace 隔离进程：

package main

import (
    "fmt"
    "os"
    "os/exec"
    "path/filepath"
    "syscall"
)

const cgroupBase = "/sys/fs/cgroup"

// 创建 cgroup v2 并设置资源限制
func setupCgroup(name string, memLimit string, cpuQuota string) error {
    path := filepath.Join(cgroupBase, name)
    if err := os.MkdirAll(path, 0755); err != nil {
        return err
    }
    // 内存硬限制 (如 "104857600" = 100MB)
    os.WriteFile(filepath.Join(path, "memory.max"), []byte(memLimit), 0644)
    // 禁用 swap
    os.WriteFile(filepath.Join(path, "memory.swap.max"), []byte("0"), 0644)
    // CPU 上限 (如 "100000 100000" = 1 核)
    os.WriteFile(filepath.Join(path, "cpu.max"), []byte(cpuQuota), 0644)
    // PID 限制
    os.WriteFile(filepath.Join(path, "pids.max"), []byte("64"), 0644)
    // 将当前进程加入 cgroup
    return os.WriteFile(
        filepath.Join(path, "cgroup.procs"),
        []byte(fmt.Sprintf("%d", os.Getpid())), 0644)
}

// 在新 namespace 中启动隔离进程
func runIsolated(rootfs string) error {
    cmd := exec.Command("/bin/sh")
    cmd.SysProcAttr = &syscall.SysProcAttr{
        Cloneflags: syscall.CLONE_NEWUTS |   // 独立主机名
                    syscall.CLONE_NEWPID |    // 独立 PID 空间
                    syscall.CLONE_NEWNS |     // 独立挂载空间
                    syscall.CLONE_NEWNET |    // 独立网络栈
                    syscall.CLONE_NEWIPC,     // 独立 IPC
        UidMappings: []syscall.SysProcIDMap{
            {ContainerID: 0, HostID: os.Getuid(), Size: 1},
        },
        GidMappings: []syscall.SysProcIDMap{
            {ContainerID: 0, HostID: os.Getgid(), Size: 1},
        },
    }
    cmd.Stdin = os.Stdin
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr
    return cmd.Run()
}

func main() {
    // 1. 设置 cgroup: 100MB 内存, 1 CPU
    setupCgroup("mycontainer", "104857600", "100000 100000")
    // 2. 在新 namespace 中运行
    runIsolated("/var/lib/containers/rootfs")
    // 3. 清理
    os.Remove(filepath.Join(cgroupBase, "mycontainer"))
}

面试问答

容器和虚拟机的本质区别是什么？▶
虚拟机通过 Hypervisor 模拟完整硬件，运行独立的 Guest 内核，隔离强度接近物理机。容器共享宿主机内核，通过 namespace 隔离视图 + cgroup 限制资源，overhead 极低但隔离较弱。性能：容器启动 ms 级 vs VM 秒级；容器几乎零 overhead vs VM 5-10% CPU 损耗。安全：内核漏洞可突破容器隔离（如 CVE-2022-0185），需要 seccomp/AppArmor/SELinux 补充。折中方案：gVisor（用户态内核拦截 syscall）、Kata Containers（轻量 VM + 容器接口）。
cgroup v1 和 v2 的主要区别？▶
v1：每个 controller 独立层级树，同一进程可在不同 controller 的不同位置。v2：统一单一层级，进程只能属于一个 cgroup 节点，所有 controller 共享同一棵树。v2 优势：1) 配置一致性（一个目录管所有资源）；2) PSI (Pressure Stall Info) 精确测量资源压力；3) io controller 的 weight-based 更精确（v1 的 blkio 对 buffered IO 无效）；4) memory 记账更准确（Page Cache 归属正确的 cgroup）。K8s 1.25+ 默认使用 cgroup v2。
容器 memory.current 超过 memory.max 会怎样？▶
内核尝试回收可回收内存（Page Cache、slab）。若回收后仍超限，触发 cgroup OOM killer，选择 cgroup 内 oom_score 最高的进程 kill。注意：1) memory.current 包含 Page Cache，不全是堆内存；2) 设 memory.high 可在到达 max 之前施加回收压力，避免突然 OOM；3) K8s 中 memory limit = cgroup memory.max，超限时 OOMKilled 状态码 137；4) memory.oom.group=1 可让整个 cgroup 一起被 kill（而非单进程）。
PID namespace 为什么不能完全隔离 /proc？▶
PID namespace 只改变进程号映射（容器内 PID 1 = 宿主机 PID xxxxx），但 /proc 是宿主机的全局伪文件系统。不重新 mount /proc，容器内仍看到宿主机的 /proc/meminfo、/proc/cpuinfo。Docker 做法：1) mount namespace 内重新 mount -t proc proc /proc；2) LXCFS 伪装 /proc/meminfo 返回 cgroup 限制值（让 JVM/Go 正确检测可用内存）。不处理此问题：JVM 误判可用内存 → 堆设太大 → OOM；Go runtime 误判 GOMAXPROCS → 创建过多线程。

常见陷阱

误解：cgroup 就是容器
# 只设了 cgroup 限制
mkdir /sys/fs/cgroup/myapp
echo "104857600" > memory.max
echo $PID > cgroup.procs

# 进程仍能看到：
# - 宿主机所有文件 (/etc/shadow)
# - 宿主机所有进程 (ps aux)
# - 宿主机网络接口 (ip addr)
# - 宿主机主机名 (hostname)
# 完全没有隔离！只有资源限制

问题：cgroup 只做资源限制（多少），不做视图隔离（看到什么）。缺少 namespace 就不是容器。

# 完整容器 = 多层机制组合
# 1. Namespace: 视图隔离
unshare --pid --mount --net --uts ...

# 2. Rootfs: 文件系统隔离
pivot_root /new_root /old_root
mount -t proc proc /proc

# 3. Cgroup: 资源限制
echo $PID > /sys/fs/cgroup/c1/cgroup.procs

# 4. Seccomp: 禁止危险 syscall
# 5. Capabilities: 最小权限
# 6. AppArmor/SELinux: MAC 策略

# Docker 自动组合以上所有

正确：容器 = namespace（隔离）+ cgroup（限制）+ rootfs + seccomp + capabilities 的组合。

误解：memory limit = 应用可用堆内存
# docker run --memory=512m java-app
# JVM 设置: -Xmx=480m (给系统留 32m)

# 运行一段时间后 OOM killed!
# 原因：
# memory.current 包含：
#   anon (堆+栈): 300MB
#   file (Page Cache): 180MB  ← 被忽略了
#   kernel stack: 20MB
#   slab: 12MB
#   总计: 512MB -> OOM!

# JVM -Xmx=480m 只管堆
# Page Cache / off-heap 不受 -Xmx 控制

问题：memory.current 包含 Page Cache + kernel 开销，JVM -Xmx 不能按 limit 全量配置。

# 正确的内存规划
# memory limit = 512MB 时：

# JVM: -XX:MaxRAMPercentage=70
#   堆最多用 limit * 70% = 358MB
#   留 30% 给: Page Cache + Metaspace +
#              off-heap + kernel overhead

# Go: GOMEMLIMIT=400MiB
#   soft limit，触发更积极 GC
#   留余量给 goroutine stack + OS cache

# 监控关键指标：
cat memory.stat    # anon vs file 分布
cat memory.events  # oom_kill 次数
cat memory.pressure # PSI some/full

# 建议：memory.high = 80% of max
# 提前施加回收压力，避免突然 OOM

正确：应用堆内存应设为 limit 的 60-75%，留余量给 Page Cache、off-heap 和内核开销。
