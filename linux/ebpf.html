Linux / ebpf / B 类型

eBPF

eBPF 在内核安全沙箱中运行小程序，用于可观测、网络和安全扩展。

VerifierMapHook
eBPF 是现代可观测性（Cilium、Falco、bpftrace）和高性能网络（XDP）的基石技术。
核心术语
Verifier加载前静态分析：模拟所有路径，确保无越界、无无限循环、栈 ≤ 512B。
Map内核/用户态共享数据结构：Hash、Array、RingBuffer、Per-CPU Array 等。
Hook挂载点：kprobe/kretprobe、tracepoint、XDP、tc、cgroup、LSM 等。

背景

传统扩展内核能力需要编写 Loadable Kernel Module (LKM)，但风险巨大：

  • 一个空指针就能 kernel panic 宕掉整台服务器，没有沙箱保护
  • 可以访问任意内核内存和数据结构，安全审计困难
  • 加载/卸载需小心引用计数，热更新复杂且危险
  • eBPF 提供安全、高效、可热加载的内核可编程方案
  • 工作流：受限 C 代码 → clang 编译为 BPF bytecode → 内核 Verifier 验证 → JIT 编译为机器码 → 挂载到 hook 运行
  • 已在 Meta/Google/Cloudflare 等公司大规模生产使用

运行机制

  • 编译：clang -target bpf 将受限 C 代码编译为 BPF ELF 格式字节码
  • Verifier：模拟执行所有分支路径，检查：内存边界（寄存器追踪）、无无限循环（有界循环需 5.3+）、栈不超 512 字节、只能调用白名单 helper 函数
  • JIT：验证通过后即时编译为原生机器码（x86/arm64），性能接近内核原生函数
  • Hook 点分类：kprobe（动态函数入口/出口）、tracepoint（静态预埋点，ABI 稳定）、XDP（网卡驱动层，最早处理 packet）、tc（ingress/egress 流量控制）、socket（socket 级过滤/重定向）、cgroup（容器级策略）、LSM（安全模块 hook）
  • Maps 类型：BPF_MAP_TYPE_HASH（通用 KV）、ARRAY（固定大小数组）、RINGBUF（高效单生产者多消费者）、PER_CPU_HASH/ARRAY（无锁并发）、LRU_HASH（自动淘汰）、STACK_TRACE（调用栈采样）
  • Helper Functions：bpf_map_lookup_elem、bpf_get_current_pid_tgid、bpf_probe_read_kernel、bpf_ktime_get_ns、bpf_ringbuf_output 等，是 eBPF 程序与内核交互的唯一接口
  • CO-RE (Compile Once Run Everywhere)：BTF 类型信息 + libbpf 重定位，解决不同内核版本结构体偏移差异

代码示例

统计系统调用次数：eBPF C 程序 + Go 用户空间 (cilium/ebpf)：

// === 内核侧 eBPF 程序 (counter.bpf.c) ===
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 1024);
    __type(key, u32);    // syscall number
    __type(value, u64);  // invocation count
} syscall_count SEC(".maps");

SEC("tracepoint/raw_syscalls/sys_enter")
int count_syscalls(struct trace_event_raw_sys_enter *ctx) {
    u32 id = ctx->id;
    u64 *count = bpf_map_lookup_elem(&syscall_count, &id);
    if (count) {
        __sync_fetch_and_add(count, 1); // atomic increment
    } else {
        u64 init = 1;
        bpf_map_update_elem(&syscall_count, &id, &init, BPF_ANY);
    }
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
// === 用户空间 Go 程序 (main.go) ===
package main

import (
    "fmt"
    "time"
    "github.com/cilium/ebpf"
    "github.com/cilium/ebpf/link"
)

//go:generate go run github.com/cilium/ebpf/cmd/bpf2go counter counter.bpf.c

func main() {
    objs := counterObjects{}
    if err := loadCounterObjects(&objs, nil); err != nil {
        panic(err)
    }
    defer objs.Close()

    // Attach to tracepoint
    tp, err := link.Tracepoint("raw_syscalls", "sys_enter",
        objs.CountSyscalls, nil)
    if err != nil {
        panic(err)
    }
    defer tp.Close()

    // Periodically read map and print top syscalls
    ticker := time.NewTicker(3 * time.Second)
    for range ticker.C {
        var key uint32
        var val uint64
        iter := objs.SyscallCount.Iterate()
        for iter.Next(&key, &val) {
            if val > 1000 {
                fmt.Printf("syscall %d: %d calls\n", key, val)
            }
        }
    }
}

面试问答

Verifier 为什么不允许无界循环？如何处理循环需求？▶
Verifier 需要静态证明程序一定终止（不能阻塞内核路径），无界循环使得验证状态空间无穷大。Linux 5.3+ 支持有界循环：Verifier 追踪循环变量边界（如 for(i=0; i<100; i++)），确认一定退出。5.17+ 提供 bpf_loop(max, callback, ctx, 0) helper，由内核保证最多回调 max 次。对于早期内核，用 #pragma unroll 让编译器展开循环。指令数上限：5.2+ 为 100 万条，复杂度上限防止验证本身 OOM。
XDP 和 tc 有什么区别？什么时候用哪个？▶
XDP 运行在网卡驱动层（甚至可 offload 到网卡硬件），在内核分配 skb 之前处理原始 packet frame，延迟极低（<1us）。但只能处理 ingress 流量，操作受限（不能访问完整 skb 元数据如 mark/priority）。tc 运行在网络协议栈 ingress/egress hook，可处理双向流量，能访问完整 skb。典型选择：DDoS 防御和 L4 负载均衡用 XDP（在最早阶段丢弃/转发）；Service Mesh 流量管理、Pod 网络策略用 tc（需要精细的 L3/L4/L7 控制）。
eBPF Map 的并发安全如何保证？▶
Map 的 lookup/update/delete 操作本身是原子的（RCU 保护），但多步操作（读-修改-写）不是。并发方案：1) Per-CPU Map 让每个 CPU 有独立副本，汇总时用户态合并；2) bpf_spin_lock（5.1+）保护 Hash Map 值级别的临界区；3) __sync_fetch_and_add 做原子递增（如计数器）；4) Ring Buffer 天然支持多生产者单消费者无锁写入。注意：spin_lock 不能在 NMI 上下文（如 perf event）中使用。
eBPF 程序出错会导致内核崩溃吗？▶
不会。Verifier 在加载阶段已排除所有可能的崩溃路径（空指针解引用、数组越界、除零、无限循环）。运行时 helper 返回错误时程序正常退出。eBPF 唯一的"风险"是逻辑错误：XDP 程序误丢正常包（XDP_DROP）、性能影响（热路径上计算过多拖慢每个 packet）、或 Map 数据不一致导致用户态看到错误信息。但不会 panic——这是 eBPF 对比内核模块的核心安全优势。

常见陷阱

误解：eBPF 可以运行任意复杂的业务逻辑
// 尝试在 eBPF 中做 JSON 解析
SEC("socket")
int parse_json(struct __sk_buff *skb) {
    char buf[512]; // 栈上限 512 字节！
    // 无法 malloc / calloc
    // 无法调用 strlen / strchr / memcmp
    // 循环次数受限
    // 无法调用 printf 调试
    // 程序总指令数受限
    parse_json_in_buf(buf); // 验证器拒绝
    return TC_ACT_OK;
}

问题：512B 栈、无动态内存、无字符串库、指令数限制，复杂逻辑无法通过 Verifier。

// 正确架构：内核采集 + 用户态处理
// eBPF 侧：只做轻量采集和过滤
SEC("socket")
int capture(struct __sk_buff *skb) {
    struct event e = {};
    e.len = skb->len;
    e.proto = skb->protocol;
    bpf_skb_load_bytes(skb, 0, e.hdr, 64);
    // 写入 ring buffer 传给用户态
    bpf_ringbuf_output(&events, &e, sizeof(e), 0);
    return TC_ACT_OK;
}

// 用户态 Go/Python：
// - JSON/protobuf 解析
// - 聚合统计
// - 告警规则匹配
// - 写入数据库

正确：eBPF 做高效采集和简单过滤（per-packet/per-event），复杂分析放用户态。

误解：所有内核版本支持相同的 eBPF 功能
// 开发环境 kernel 6.1
// 使用了这些新特性：
// - bpf_loop() helper (5.17+)

问题：eBPF 功能高度依赖内核版本，低版本缺少 helper/map/hook/feature。

// 正确做法：CO-RE + Feature Detection

if err := features.HaveProgramType(
    ebpf.Tracing); err != nil {

// 3. bpftool feature probe 检查能力
// 4. 最低版本文档化：README 标明 kernel >= X.Y
// 5. 多版本测试 CI (kernel 4.19/5.4/5.15/6.1)

正确：CO-RE 保证可移植性，feature detection 做 graceful fallback，CI 覆盖多内核版本。
