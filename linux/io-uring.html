io_uring：Linux 异步 I/O

Linux 5.1 引入的高性能异步 I/O 接口。用两个环形队列（SQ + CQ）在用户态和内核态共享，批量提交 I/O 请求只需一次系统调用（SQPOLL 模式甚至零系统调用），大幅减少用户态/内核态切换开销，吞吐量比 epoll 高 30–50%。

SQ/CQ 环形队列零系统调用SQPOLL固定缓冲区批量 I/O
核心术语
  • SQE（提交队列项）用户态填写的 I/O 请求描述符，放入 SQ。包含操作类型、fd、缓冲区、user_data 标识。
  • CQE（完成队列项）内核填写的完成通知，放入 CQ。user_data 与 SQE 对应，res=完成字节数或负 errno。
  • io_uring_enter单次系统调用提交多个 SQE，内核批量处理后填 CQE，用户态轮询取结果，syscall 次数大幅减少。
  • SQPOLL内核线程持续轮询 SQ，新 SQE 无需 io_uring_enter 系统调用，用 100% CPU 换取零延迟。

背景：为什么需要 io_uring

传统异步 I/O 方案的问题：

epoll（事件驱动）：每次 I/O 就绪后仍需调用 read/write，每次都是一次系统调用 + 数据拷贝。1000 并发连接 = 至少 1000 次系统调用/读事件。

POSIX AIO（aio_read/aio_write）：仅支持直接 I/O（O_DIRECT），不支持 socket、pipe 等，局限性大，内核实现粗糙（用线程模拟）。

io_uring 的解法：共享内存环形队列消除系统调用开销，批量提交让 N 个 I/O 只需 1 次 syscall，SQPOLL 模式甚至做到 0 次 syscall，适合超高并发 I/O 场景。

常见误区

  • io_uring 不是零拷贝——数据仍需在内核和用户缓冲区间搬运，除非使用 IORING_OP_READ/WRITE 配合 registered buffers（固定缓冲区），才能减少部分拷贝。
  • SQPOLL 模式消耗 100% CPU（内核线程轮询），与 DPDK PMD 类似。只有 I/O 非常密集时才值得，否则用普通模式。
  • io_uring 不替代 epoll——两者可以共存，io_uring 更适合文件 I/O 和批量网络 I/O，epoll 仍然适合单个连接的事件通知场景。
  • 链式 SQE（IOSQE_IO_LINK）允许将多个操作串联，前一个失败时后续操作自动取消，适合"先写再关闭"等顺序依赖场景。

工程场景

  • 高并发 HTTP 服务器（Nginx/Envoy）：io_uring 在连接数超过 10K 时，系统调用开销占比明显，使用 io_uring 可减少 50% 以上的 syscall 次数。
  • 数据库 WAL 写入（RocksDB/MySQL）：批量 WAL fsync 用 io_uring 批量提交，将多个 SQE 合并为一次 io_uring_enter，WAL 写延迟降低 20–40%。
  • 存储引擎（ScyllaDB）：ScyllaDB 的 Seastar 框架已全面迁移到 io_uring，替换原有的 Linux AIO，实现更好的 NVMe 并发利用率。
  • 网络代理（Envoy/io_uring 实验性支持）：用 io_uring 替换 epoll+read/write，在长连接代理场景实测延迟降低 15–30%。

性能对比

基准测试（NVMe SSD，随机 4K 读，队列深度 128）：

blocking read：~30K IOPS，每次 read() 独立系统调用
Linux AIO：~200K IOPS，仅支持 O_DIRECT
io_uring（普通模式）：~350K IOPS，批量提交，支持 buffered I/O
io_uring（SQPOLL）：~450K IOPS，零系统调用，内核线程轮询

网络 I/O 场景：Nginx（io_uring）vs Nginx（epoll），10K 并发短连接，io_uring 吞吐高约 40%，CPU 使用低约 20%。
