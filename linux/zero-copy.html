Linux / zero-copy

零拷贝

零拷贝减少用户态和内核态之间的数据搬运，提高文件传输和消息系统吞吐。

sendfilemmapDMA
理解传统 4 次拷贝 → sendfile → DMA gather 的演进线索，以及各路径适用场景是核心。
核心术语
sendfile系统调用，内核态直接将文件数据发送到 socket，不经过用户缓冲区。
mmap将文件映射到进程虚拟地址空间，访问时按需加载页面。
DMADirect Memory Access，磁盘/网卡硬件直接读写内存，CPU 不参与搬运。

背景

传统文件发送到网络的路径（read + write）涉及大量冗余数据搬运：

  • 4 次数据拷贝：磁盘→内核 Page Cache（DMA）→ 用户缓冲区（CPU）→ Socket 缓冲区（CPU）→ 网卡（DMA）
  • 4 次上下文切换：read 系统调用进入内核 → 返回用户态 → write 系统调用进入内核 → 返回用户态
  • 瓶颈：数据经过用户空间只是"路过"，应用不修改内容但承担了两次 CPU 拷贝开销
  • 对于静态文件服务、消息 broker（Kafka）、CDN 等场景，用户态拷贝完全可以消除
  • 优化方向：减少拷贝次数 + 减少上下文切换次数

运行机制

  • mmap + write：mmap 将文件映射到用户虚拟地址，省去 read 系统调用。write 时仍需 CPU 从 Page Cache 拷贝到 Socket Buffer。结果：3 次拷贝 + 4 次切换
  • sendfile (Linux 2.1+)：一次系统调用完成文件→Socket。内核中 CPU 从 Page Cache 拷贝到 Socket Buffer。结果：1 次 CPU 拷贝 + 2 次 DMA + 2 次切换
  • sendfile + DMA gather (Linux 2.4+)：网卡支持 scatter-gather DMA 时，sendfile 只传文件描述符和偏移量给 Socket，DMA 直接从 Page Cache 分散读取。结果：0 次 CPU 拷贝 + 2 次 DMA + 2 次切换
  • splice (Linux 2.6.17+)：用 pipe 做内核缓冲区中转，连接任意两个 fd（不限于文件→socket），如 socket→socket 代理转发
  • 限制条件：数据不能在传输中修改（加密/压缩需要 CPU 介入）；sendfile 仅支持文件→socket 方向；对端关闭时可能 SIGPIPE
  • io_uring (Linux 5.1+)：异步 IO 框架，通过提交队列(SQ)和完成队列(CQ)实现批量零拷贝 IO 提交，减少系统调用次数
  • TCP cork + sendfile：配合 TCP_CORK 选项可将 HTTP header（小数据）和文件体（sendfile）合并到同一 TCP segment，减少小包数量

代码示例

Go 中使用 syscall.Sendfile vs io.Copy 对比：

package main

import (
    "io"
    "net"
    "os"
    "syscall"
)

// 方式 1：传统 io.Copy（4 次拷贝路径）
func traditionalSend(conn net.Conn, file *os.File) error {
    // 内部: read(file) -> userBuf -> write(conn)
    // 数据完整经过用户空间
    _, err := io.Copy(conn, file)
    return err
}

// 方式 2：syscall.Sendfile（零拷贝路径）
func zeroCopySend(conn net.Conn, file *os.File) error {
    rawConn, _ := conn.(syscall.Conn).SyscallConn()
    fi, _ := file.Stat()
    remain := fi.Size()

    var sendErr error
    rawConn.Control(func(sockFd uintptr) {
        offset := int64(0)
        for remain > 0 {
            // sendfile: Page Cache -> Socket (kernel path)
            n, err := syscall.Sendfile(
                int(sockFd), int(file.Fd()), &offset, int(remain))
            if err != nil {
                sendErr = err
                return
            }
            remain -= int64(n)
        }
    })
    return sendErr
}

// 方式 3：Go net/http 自动优化
// 当 ServeContent/ServeFile 或 io.Copy(TCPConn, *os.File) 时
// Go runtime 检测到 src=File, dst=TCPConn
// 自动调用 splice/sendfile（Linux）或 TransmitFile（Windows）
// 无需手动 syscall

// 方式 4：mmap 读取（适合需要用户态访问的场景）
func mmapRead(path string) ([]byte, error) {
    f, _ := os.Open(path)
    defer f.Close()
    fi, _ := f.Stat()
    // MAP_SHARED: 多进程可共享同一 Page Cache 页
    data, err := syscall.Mmap(int(f.Fd()), 0, int(fi.Size()),
        syscall.PROT_READ, syscall.MAP_SHARED)
    // data 直接引用 Page Cache 物理页
    // 访问时触发 page fault -> 按需加载
    return data, err
    // 用完后: syscall.Munmap(data)
}

各路径数据流对比

# 传统 read + write (4 copies, 4 switches)
  App: read(file_fd, buf, len)
       [user→kernel] DMA: disk→PageCache | CPU: PageCache→userBuf [kernel→user]
  App: write(sock_fd, buf, len)
       [user→kernel] CPU: userBuf→sockBuf | DMA: sockBuf→NIC [kernel→user]

# sendfile (1 CPU copy, 2 switches)
  App: sendfile(sock_fd, file_fd, offset, len)
       [user→kernel] DMA: disk→PageCache | CPU: PageCache→sockBuf | DMA: sockBuf→NIC [kernel→user]

# sendfile + scatter-gather DMA (0 CPU copy, 2 switches)
  App: sendfile(sock_fd, file_fd, offset, len)
       [user→kernel] DMA: disk→PageCache | DMA-SG: PageCache→NIC [kernel→user]
       # 网卡直接从 PageCache 多个不连续页面 gather 读取

# splice (0 CPU copy, pipe 做内核中转)
  App: splice(file_fd→pipe) + splice(pipe→sock_fd)
       # 适合非 file→socket 场景（如 socket→socket 代理）

面试问答

Kafka 为什么能做到高吞吐？和零拷贝的关系？▶
Kafka 消费者拉取消息时，Broker 调用 Java FileChannel.transferTo()，底层对应 Linux sendfile。数据从磁盘 Page Cache 直接通过 DMA 发送到网卡，无需经过 JVM 堆内存。配合顺序写入（Page Cache 预读命中）和批量压缩，单 Broker 可达 GB/s 级消费吞吐。关键：Kafka 不对消息做序列化/反序列化，数据按原始字节流传输，这是 sendfile 能生效的前提。
mmap 和 sendfile 的适用场景区别？▶
sendfile：文件原封不动发到网络，数据不经过用户空间。适合静态文件服务、日志传输、Kafka consumer fetch。mmap：需要在用户态随机读取/处理文件内容，它省去 read 系统调用但仍可在用户态访问数据。适合数据库 Buffer Pool、配置文件解析、搜索引擎索引。关键区别：sendfile 用户态完全不碰数据；mmap 用户态能读写但避免了显式 read 的拷贝。
TLS 加密场景为什么无法使用零拷贝？▶
TLS 需要在发送前对明文做加密运算，必须由 CPU 完成。sendfile 的前提是数据不经过用户空间且不被修改。解决方案：1) 内核 TLS (kTLS, Linux 4.13+)：加密在内核完成后仍可用 sendfile 发送密文；2) TLS offload：网卡硬件直接做加密（如 Mellanox ConnectX-6）；3) QUIC/HTTP3 用 UDP，部分实现支持 GSO + sendmsg 批量发送加密包减少系统调用。
Go 的 io.Copy 内部会自动使用零拷贝吗？▶
是的。当 dst 实现 io.ReaderFrom 或 src 实现 io.WriterTo 时，io.Copy 会调用对应方法。*net.TCPConn 实现了 ReadFrom，当 src 是 *os.File 时内部调用 splice/sendfile（通过 net.splice 和 poll.SendFile）。所以 io.Copy(tcpConn, file) 在 Linux 上自动走零拷贝路径。但如果中间包了 bufio.Writer、tls.Conn 或 gzip.Writer，则接口类型不匹配，退化为普通 read+write 拷贝。

常见陷阱

误解："零拷贝"意味着完全没有数据拷贝
// 错误理解：sendfile = 完全无拷贝
// 实际仍存在两次 DMA 拷贝：
// 1. 磁盘 -> Page Cache (DMA)
// 2. Page Cache -> 网卡 (DMA)
//
// DMA 拷贝由硬件完成
// 但仍需物理内存带宽
// "零拷贝" 的 "零" 指的是
// 零 CPU 参与的内存拷贝

问题：DMA 拷贝不可避免（硬件必须搬运数据），"零拷贝"准确含义是消除 CPU 参与的内存搬运。

// 各路径的拷贝次数对比
// ================================================
// 方式              CPU拷贝  DMA拷贝  上下文切换
// ------------------------------------------------
// read + write        2        2        4
// mmap + write        1        2        4
// sendfile            1        2        2
// sendfile + SG-DMA   0        2        2 (真正零CPU)
// splice              0        2        2
// ================================================
//
// "零" = CPU 拷贝为零
// DMA 是硬件行为，不消耗 CPU 周期
// 但消耗内存带宽和 PCIe 带宽

正确：零拷贝 = 零 CPU 拷贝。DMA 搬运数据是硬件行为，不占 CPU 算力但仍占内存/总线带宽。

误解：mmap 没有性能成本
// 大量随机访问 mmap 文件
data, _ := syscall.Mmap(fd, 0, fileSize, ...)

for i := 0; i < 1000000; i++ {
    offset := rand.Intn(fileSize - 4096)
    process(data[offset : offset+4096])
}
// 如果文件远大于物理内存：
// 每次访问新页面 -> minor page fault (~2us)
// 页面不在内存 -> major page fault (~2-10ms)
// 100万次随机访问 -> 大量 page fault
// 比显式 pread 更不可控

问题：mmap 首次访问每个页面触发 page fault，大量随机访问冷数据时开销可能超过 read。

// mmap 适合的场景
// 1. 顺序访问：内核预读窗口生效
//    page fault 只在边界触发
// 2. 热数据集 < 物理内存：
//    page fault 只发生第一次访问
//    后续全部命中 (零系统调用)
// 3. 多进程共享同一文件：
//    共享 Page Cache 页，节省内存
//
// 随机访问大冷文件用 pread 更可控：
buf := make([]byte, 4096)
f.ReadAt(buf, offset)
// 可配合 fadvise 提示预读模式：
// FADV_RANDOM -> 禁止预读
// FADV_SEQUENTIAL -> 激进预读

正确：mmap 适合顺序/热数据场景；随机访问冷数据时 page fault 成本不可控，pread + fadvise 更优。
