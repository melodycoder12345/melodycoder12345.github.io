顺序 IO / Page Cache

顺序写和 Page Cache 让 WAL、Kafka 日志和 LSM 文件获得高吞吐。

Page CachefsyncWAL
顺序 IO + Page Cache 是 Kafka/RocksDB 高吞吐的底层根因，也是理解"写入返回不等于持久化"的关键。
核心术语
Page Cache内核用空闲物理内存缓存文件数据页，读命中时零磁盘 IO。
Dirty Pagewrite() 修改后尚未刷盘的页面，断电丢失。
fsync阻塞直到文件数据+元数据写入磁盘，保证持久性。

背景

存储设备的顺序和随机性能差异巨大，Page Cache 在应用和磁盘之间充当缓冲层：

  • HDD：顺序 100-200 MB/s，随机 IOPS 仅 100-200（寻道 ~8ms）。顺序/随机性能比 ~150x
  • SSD：顺序 500-7000 MB/s，随机 IOPS 10K-1M。顺序/随机性能比 ~4-10x（NVMe 更小但仍显著）
  • Page Cache 作用：write() 写入 Page Cache 后立即返回（内存速度），后台异步刷盘；read() 命中 Cache 时直接从内存拷贝（无磁盘 IO）
  • 预读加速：顺序读时内核自动倍增预读窗口（128KB→256KB→...→2MB），下一次 read 命中已预读的页面
  • Kafka 和 RocksDB 的高吞吐核心：顺序追加写 + 热数据在 Page Cache → 消费者几乎零磁盘 IO

运行机制

  • 读路径：read(fd) → 检查 Page Cache → 命中：直接 memcpy 到用户缓冲区 → 未命中：阻塞，发起磁盘 IO + readahead 预读
  • Readahead：初始窗口 128KB，顺序模式下倍增至 vm.max_readahead_kb（默认 2MB）。可用 fadvise(FADV_SEQUENTIAL) 提示或 FADV_RANDOM 禁用
  • 写路径：write(fd) → 数据写入 Page Cache（标记 dirty）→ 函数返回 → pdflush/writeback 线程异步刷盘
  • Dirty Page 回写触发：dirty_background_ratio（默认 10%，后台开始写回）、dirty_ratio（默认 20%，进程同步阻塞等待）、dirty_expire_centisecs（默认 3000 = 30s，页面最大脏龄）
  • fsync/fdatasync：fsync = 数据 + 全部元数据刷盘；fdatasync = 数据 + 必要元数据（不含 atime/mtime）。WAL 每批写入后需 fsync 保证 crash 后不丢
  • O_DIRECT：绕过 Page Cache 直接写磁盘，应用自行管理缓冲和对齐（4KB 对齐）。数据库 Buffer Pool 用此避免双层缓存
  • sync_file_range：精细控制刷特定范围的脏页，允许后台刷盘不阻塞当前写入

代码示例

Go 代码：buffered write + fsync vs O_DIRECT vs batch sync：

package main

import (
    "os"
    "syscall"
    "unsafe"
)

// 方式 1：标准 buffered write + fsync
// 数据先进 Page Cache，fsync 保证落盘
func bufferedAppend(f *os.File, data []byte) error {
    // write: 数据写入 Page Cache (内存速度, ~ns 级)
    if _, err := f.Write(data); err != nil {
        return err
    }
    // 不 fsync: 异步刷盘，断电丢最近 ~30s 数据
    // fsync: 阻塞直到数据落盘 (SSD ~0.1-1ms, HDD ~5-10ms)
    return f.Sync()
}

// 方式 2：WAL 常见模式 - Group Commit
// 多条写入共享一次 fsync，提升吞吐
func walGroupCommit(f *os.File, batch [][]byte) error {
    for _, entry := range batch {
        f.Write(entry) // N 条写入 Page Cache
    }
    return f.Sync() // 1 次 fsync 刷全部 dirty pages
    // 批量越大，fsync 均摊成本越低
    // MySQL: innodb_flush_log_at_trx_commit=2 (每秒 fsync)
    // Kafka: log.flush.interval.messages=10000
}

// 方式 3：O_DIRECT (绕过 Page Cache)
func directWrite(path string, data []byte) error {
    f, err := os.OpenFile(path,
        os.O_CREATE|os.O_WRONLY|os.O_APPEND|syscall.O_DIRECT, 0644)
    if err != nil {
        return err
    }
    defer f.Close()

    // O_DIRECT 要求：
    // 1. 内存地址按 512B/4KB 对齐
    // 2. 写入大小按扇区对齐
    // 3. 文件偏移量对齐
    aligned := alignedAlloc(len(data), 4096)
    copy(aligned, data)
    _, err = f.Write(aligned)
    return err
}

// 方式 4：顺序写 + fadvise 提示
func sequentialWrite(path string, chunks [][]byte) error {
    f, _ := os.Create(path)
    defer f.Close()

    // 提示内核：本文件是顺序访问模式
    syscall.Fadvise(int(f.Fd()), 0, 0, syscall.FADV_SEQUENTIAL)

    for _, chunk := range chunks {
        f.Write(chunk)
    }
    // 写完后提示：这些页面不再需要（释放 Page Cache）
    fi, _ := f.Stat()
    syscall.Fadvise(int(f.Fd()), 0, fi.Size(), syscall.FADV_DONTNEED)
    return f.Sync()
}

func alignedAlloc(size, align int) []byte {
    buf := make([]byte, size+align)
    offset := align - int(uintptr(unsafe.Pointer(&buf[0])))%align
    return buf[offset : offset+size]
}

面试问答

write() 返回成功就意味着数据持久化了吗？▶
不是。write() 只保证数据进入了 Page Cache（内核内存），返回后数据仍在 RAM 中。断电或 kernel panic 时这些 dirty page 丢失。持久化需要：1) 显式 fsync/fdatasync；2) 或等待内核 writeback（dirty_expire_centisecs 默认 30s）。这就是 WAL 需要 fsync 的原因。MySQL 的 innodb_flush_log_at_trx_commit: 0=每秒刷（可丢1秒）；1=每提交刷（不丢）；2=每提交写 Page Cache 每秒 fsync（可丢 1 秒但 crash-safe 于应用崩溃）。
Kafka 为什么不用 O_DIRECT 而是依赖 Page Cache？▶
Kafka 的模式完美匹配 Page Cache：1) 顺序追加写→内核可合并 dirty page 批量刷盘；2) 消费者消费最近消息→热数据全在 Page Cache，读取零磁盘 IO（tail-read 场景命中率接近 100%）；3) sendfile 零拷贝直接从 Page Cache DMA 到网卡；4) JVM 堆外共享（producer 写入 Page Cache 后 consumer 立即可见）。O_DIRECT 会失去以上所有优势且需自行实现缓冲管理、预读和多进程共享。
什么时候 O_DIRECT 比 Page Cache 更好？▶
1) 数据库 Buffer Pool（MySQL InnoDB）：自行实现 LRU 缓存管理，不需要内核再缓存一份（避免双层缓存浪费 50% 内存）；2) 大文件一次性扫描不再访问（备份/ETL）：fadvise(DONTNEED) 也行但不如 O_DIRECT 确定；3) 应用比内核更了解访问模式。代价：需要内存对齐（4KB）、失去 readahead、小 IO 性能差、实现复杂。Rule：除非自行管理缓存，否则用 Page Cache。
大量顺序写入时可能遇到什么问题？▶
Dirty page 快速积累的三个风险：1) 超过 dirty_background_ratio(10%) 时后台 writeback 启动，与前台写竞争 IO 带宽→P99 升高；2) 超过 dirty_ratio(20%) 时前台 write() 被阻塞等待刷盘→write stall；3) 容器中 cgroup memory limit 包含 dirty page，大量写入可能触发 OOM。优化：调低 dirty_background_ratio 让刷盘更早启动；对一次性大文件用 sync_file_range 分段刷+fadvise(DONTNEED) 释放已写页；XFS 的 allocsize 预分配减少碎片。

常见陷阱

误解：Page Cache 命中高说明应用内存小
# 容器 memory limit: 2GB
# 应用堆: 500MB
# Page Cache: 1.4GB
# memory.current: 1.9GB -> 接近 OOM!

# 运维看到 free 命令 "available" 很低
# 结论："内存快用完了"

# 实际上 Page Cache 属于可回收内存
# 但 cgroup 的 OOM killer
# 不区分"值得保留的 cache"
# 和"可以回收的 cache"

问题：cgroup memory.current 包含 Page Cache，误判内存状态或触发不必要的 OOM。

# 正确判断方式
cat /sys/fs/cgroup/memory.stat
# anon 500MB       <- 不可回收（堆+栈）
# file 1400MB      <- Page Cache（压力大时可回收）
# inactive_file    <- 长时间未访问的可优先回收

# 用 PSI 看真实压力：
cat /proc/pressure/memory
# some avg10=0.00  <- 无压力
# some avg10=5.00  <- 有进程因内存等待

# 正确配置策略：
# memory.high = limit * 80% (提前回收)
# 应用堆 = limit * 60-70%
# 预留 20-30% 给 Page Cache + kernel

# 告警基于 memory.events 中的 oom_kill
# 而非 memory.current / limit 比例

正确：区分 anon（不可回收）和 file cache（可回收），用 PSI 判断真实压力，留足余量。

误解：O_DIRECT 一定比 buffered IO 更快
// 小文件高频写入用 O_DIRECT
for i := 0; i < 10000; i++ {
    f.Write(record) // 每条 100 bytes
    // O_DIRECT: 每次 write = 一次磁盘 IO
    // 但必须 4KB 对齐 -> 100B 也写 4KB
    // 写放大: 4096/100 = 40x
    // 无法合并多次小写入
}
// SSD: 10000 * 0.05ms = 500ms
// 比 buffered 慢 100x+

问题：小写入用 O_DIRECT 无法合并请求，对齐要求导致严重写放大，性能远差于 buffered。

// 同场景用 buffered + batch fsync
for i := 0; i < 10000; i++ {
    f.Write(record) // 写 Page Cache (ns 级)
}
f.Sync() // 一次刷盘，内核合并为少量大 IO
// 耗时: ~1ms 写入 + ~0.5ms fsync = ~1.5ms

// O_DIRECT 正确使用场景：
// 1. 大块写入 (>= 256KB per write)
// 2. 应用自行 buffer 到对齐大小
// 3. 需要精确控制刷盘时机
// 4. 避免 Page Cache 污染（ETL/备份）
// 5. 数据库 Buffer Pool (自管理缓存)

// 经验法则：
// 如果不确定，就用 buffered IO + fsync
// 让内核处理 IO 调度和合并

正确：小写入场景 buffered IO + batch fsync 性能远超 O_DIRECT；后者只适合大块自管理缓冲的数据库场景。
