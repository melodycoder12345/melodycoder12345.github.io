什么是 Test Doubles

替身的本质

[核心]

Test Double 是 Gerard Meszaros 在《xUnit Test Patterns》中定义的术语，指代替生产代码中真实依赖的所有测试用替代品。就像电影中的"替身演员"（stunt double）。

使用 Test Doubles 的核心原因：外部依赖（数据库、HTTP 服务、时钟）让单元测试变慢、不稳定、难以控制。通过替身，我们可以：

  • 隔离被测代码，让测试只验证它自己的逻辑
  • 控制依赖的返回值，覆盖难以触发的错误路径
  • 让测试在毫秒级内完成，不依赖外部状态
  • 验证被测代码如何与依赖交互（调用次数、参数）

五种 Test Doubles 类型

Dummy

只是传递，从不使用。填充方法签名中必须的参数，但测试不会触发它。

Stub

提供预设返回值。不关心调用方式，只返回固定答案供被测代码消费。

Fake

有真实可工作的实现，但走捷径。例如内存数据库替代真实 DB，行为正确但不生产级。

Spy

记录调用信息（参数、次数）供事后验证，可以有部分真实实现。

Mock

预先设定期望（expect），如果调用不符合预期则测试立即失败。最严格的替身。

五种类型对比

类型有实现逻辑预设返回值验证调用典型用途
Dummy无无无填充必须参数（日志器、无用上下文）
Stub最小是（固定）无控制 HTTP 响应、DB 查询结果
Fake完整可用动态无内存 DB、内存消息队列
Spy可选可选事后检查验证邮件服务被调用了几次
Mock无是（预设）预先期望严格验证交互协议

代码示例：五种类型的 Go 实现

type EmailSender interface {
    Send(to, subject, body string) error
}

// Dummy：从不被调用，只是满足接口
type DummyEmailSender struct{}
func (d *DummyEmailSender) Send(to, subject, body string) error { return nil }

// Stub：永远返回固定值
type StubEmailSender struct{ err error }
func (s *StubEmailSender) Send(to, subject, body string) error { return s.err }

// Fake：内存实现，行为真实但不持久化
type FakeEmailSender struct{ Sent []string }
func (f *FakeEmailSender) Send(to, subject, body string) error {
    f.Sent = append(f.Sent, to)
    return nil
}

// Spy：记录调用，事后可检查
type SpyEmailSender struct{
    calls int
    lastTo string
}
func (s *SpyEmailSender) Send(to, subject, body string) error {
    s.calls++
    s.lastTo = to
    return nil
}

// Mock：由框架生成，预设期望，不符则立即失败
// mockEmailSender.EXPECT().Send("alice@x.com", gomock.Any(), gomock.Any()).Return(nil).Times(1)

接口驱动设计 —— 让 Mock 成为可能

依赖接口而非实现

[核心]

Go 中 Mock 的前提是：被测代码依赖接口而非具体类型。如果 Service 直接持有 *sql.DB，则无法替换；如果依赖 UserRepository 接口，则可以注入任意实现。

// 错误：直接依赖具体实现，无法 Mock
type UserService struct {
    db *sql.DB  // 具体类型，无法替换
}

// 正确：依赖接口，可注入任意实现
type UserRepository interface {
    FindByID(ctx context.Context, id int64) (*User, error)
    Save(ctx context.Context, u *User) error
}

type UserService struct {
    repo UserRepository  // 接口，测试时可替换
}

// 生产：注入真实实现
svc := &UserService{repo: NewSQLUserRepository(db)}

// 测试：注入 Mock/Fake
svc := &UserService{repo: NewMockUserRepository(ctrl)}

Go 接口设计原则

  • 接口应该小：每个接口只包含调用方需要的方法（接口隔离原则）。一个 2-3 方法的接口比包含 20 个方法的大接口更容易 Mock
  • 在消费方定义接口：Go 惯例是接口在使用它的包中定义，而不是在实现的包中定义
  • 测试包揭示设计问题：如果一个对象难以测试，通常是因为设计问题（耦合过强、职责过多）
// 接口在消费方定义（Go 惯例）
package service

// 这里定义接口，而不是在 repository 包
type userRepo interface {
    FindByID(ctx context.Context, id int64) (*User, error)
}
// 只包含 service 实际需要的方法，不是 repository 全部方法

gomock 工程实践

安装与生成

[核心]

原 github.com/golang/mock 项目已归档；当前活跃维护的 fork 是 go.uber.org/mock。它通过代码生成创建编译期可检查方法签名的 Mock。

# 安装 mockgen 工具
go install go.uber.org/mock/mockgen@latest

# 为接口生成 Mock（source 模式）
mockgen -source=internal/service/user.go -destination=internal/mocks/mock_user_repo.go -package=mocks

# 或使用 reflect 模式（无需修改源文件）
mockgen -destination=mocks/mock_repo.go -package=mocks \
    github.com/yourapp/internal/service UserRepository

gomock 使用示例

func TestUserService_GetUser(t *testing.T) {
    ctrl := gomock.NewController(t)
    // ctrl.Finish() 会验证所有期望都被满足（Go 1.14+ 自动调用）

    mockRepo := mocks.NewMockUserRepository(ctrl)

    // 设置期望：FindByID 被调用一次，参数是 42，返回 user
    mockRepo.EXPECT().
        FindByID(gomock.Any(), int64(42)).
        Return(&User{ID: 42, Name: "alice"}, nil).
        Times(1)

    svc := NewUserService(mockRepo)
    user, err := svc.GetUser(context.Background(), 42)

    assert.NoError(t, err)
    assert.Equal(t, "alice", user.Name)
    // ctrl 自动验证：FindByID 确实被调用了 1 次
}

// 测试错误路径：模拟 DB 不可用
func TestUserService_GetUser_DBError(t *testing.T) {
    ctrl := gomock.NewController(t)
    mockRepo := mocks.NewMockUserRepository(ctrl)

    dbErr := errors.New("connection refused")
    mockRepo.EXPECT().
        FindByID(gomock.Any(), gomock.Any()).
        Return(nil, dbErr)

    svc := NewUserService(mockRepo)
    _, err := svc.GetUser(context.Background(), 1)
    assert.ErrorIs(t, err, dbErr)
}

常用 Matcher

  • gomock.Any() — 匹配任意参数值
  • gomock.Eq(v) — 精确匹配（等于默认，可省略）
  • gomock.Not(m) — 不匹配 m
  • gomock.InAnyOrder(s) — 切片内容相同但顺序任意
  • gomock.AssignableToTypeOf(v) — 类型断言
  • 自定义：实现 gomock.Matcher 接口（Matches(x interface{}) bool）

testify/mock 工程实践

手写 Mock（无需代码生成）

[核心]

testify/mock 不需要代码生成，通过嵌入 mock.Mock 手写 Mock 结构体，更灵活但需要手动维护。

import "github.com/stretchr/testify/mock"

// 手写 Mock 结构体
type MockUserRepository struct {
    mock.Mock
}

func (m *MockUserRepository) FindByID(ctx context.Context, id int64) (*User, error) {
    args := m.Called(ctx, id)
    if args.Get(0) == nil {
        return nil, args.Error(1)
    }
    return args.Get(0).(*User), args.Error(1)
}

// 测试中使用
func TestGetUser(t *testing.T) {
    mockRepo := &MockUserRepository{}
    mockRepo.On("FindByID", mock.Anything, int64(42)).
        Return(&User{ID: 42, Name: "alice"}, nil)

    svc := NewUserService(mockRepo)
    user, err := svc.GetUser(context.Background(), 42)
    assert.NoError(t, err)
    assert.Equal(t, "alice", user.Name)

    mockRepo.AssertExpectations(t) // 验证所有 On 都被调用
}

过度 Mock 的反模式

⚠ 反模式：Mock 过深，测试与实现耦合
// 过度 Mock：测试每个方法调用顺序
mockRepo.EXPECT().Begin().Times(1)
mockRepo.EXPECT().FindUser(id).Times(1)
mockRepo.EXPECT().UpdateBalance(id, amount).Times(1)
mockRepo.EXPECT().LogAudit(id).Times(1)
mockRepo.EXPECT().Commit().Times(1)
// 重构内部实现顺序 → 所有测试失败

测试验证的是实现细节（调用顺序），而非行为（转账后余额正确）。

// 正确：只验证重要的行为结果
mockRepo.EXPECT().
    Transfer(fromID, toID, amount).
    Return(nil).
    Times(1)

// 用 Fake 替代细粒度 Mock
fakeRepo := NewFakeAccountRepo()
fakeRepo.SetBalance(fromID, 1000)
svc.Transfer(fromID, toID, 100)
assert.Equal(t, 900, fakeRepo.GetBalance(fromID))

用 Fake 验证最终状态，重构内部实现不影响测试。

选择合适的 Test Double

  • 外部 IO（DB、HTTP、文件）：优先用 Fake（内存实现），其次用 Stub
  • 需要验证副作用（邮件是否发送）：用 Spy 或 Mock
  • 复杂数据初始化：用 Fake，它比一堆 Stub 设置更清晰
  • 第三方库（无法接口化）：用 Wrapper 包一层接口再 Mock
  • 时间、随机数：将 time.Now、rand.Int 注入为函数类型，测试时替换

面试问答

Mock 和 Stub 有什么区别？▶
Stub 提供预设的返回值，不关心如何被调用，只是"回答问题"。Mock 预先设定期望（这个方法应该以什么参数被调用几次），如果调用不符合预期则测试立即失败。Stub 关注状态（返回什么），Mock 关注行为（如何交互）。实际开发中两者常被混用，但概念上有明确区分。
什么情况下用 Fake 而不是 Mock？▶
当被测代码和依赖之间有复杂的双向交互时，用 Fake 更合适。例如测试缓存逻辑时，Fake Cache 有真实的读写行为，可以验证"第一次查询 DB，第二次命中缓存"。如果用 Mock，需要预设每次方法调用的参数和返回值，非常脆弱。Fake 关注最终状态，Mock 关注调用协议。对于稳定的外部 API（如支付接口），用 Stub/Mock；对于内部可替换的基础设施（如缓存、Repository），用 Fake。
如何让 Go 代码可测试？▶
核心是依赖注入 + 接口化。1) 所有外部依赖（DB、Redis、HTTP Client、时间、文件）通过接口注入，不在函数内直接创建；2) 接口定义在消费方（调用者包），只包含需要的方法；3) 避免全局状态和 init() 中的副作用；4) 将时间相关逻辑（time.Now）注入为函数参数或接口，方便测试固定时间点；5) 将随机数生成注入，测试可以使用确定性的 Seed。如果一个函数很难测试，通常是信号：它的职责过多或依赖过强，需要重构。
