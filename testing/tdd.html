TDD 核心思想

测试先行：先写测试，再写实现

[核心]

测试驱动开发（TDD，Test-Driven Development）由 Kent Beck 在极限编程（XP）中推广，核心规则只有两条：

  • 只有在测试失败时，才写新的生产代码
  • 只写让测试通过的最少代码

TDD 的本质是一种设计工具，而不只是测试工具。"先写测试"迫使你在实现前思考：这个函数的接口应该是什么？调用方怎么使用它？边界情况是什么？

Red → Green → Refactor 循环

🔴 Red写一个失败的测试
→
🟢 Green写最少代码通过测试
→
🔵 Refactor重构，保持测试通过
↩

三步详解

[核心]
  • 🔴 Red（写失败的测试）：首先写一个测试，描述你希望代码实现的行为。运行测试，确认它失败（如果通过，说明测试写错了或功能已存在）。
  • 🟢 Green（最少代码通过）：写最快让测试通过的代码，哪怕是硬编码返回值也行。目标是让测试通过，不要试图在这步写出"漂亮"的代码。
  • 🔵 Refactor（重构）：在所有测试通过的前提下，改善代码结构（消除重复、提取函数、清晰命名）。测试是安全网，确保重构不破坏行为。

完整示例：用 TDD 实现 FizzBuzz

// Step 1: Red — 写失败的测试
func TestFizzBuzz(t *testing.T) {
    assert.Equal(t, "1", FizzBuzz(1))  // FizzBuzz 不存在，编译失败 ✗
}

// Step 2: Green — 最少代码通过
func FizzBuzz(n int) string {
    return "1"  // 硬编码，只为通过当前测试 ✓
}

// Step 3: Red — 加新测试，强迫真实实现
func TestFizzBuzz(t *testing.T) {
    assert.Equal(t, "1",    FizzBuzz(1))
    assert.Equal(t, "2",    FizzBuzz(2))     // 失败 ✗
    assert.Equal(t, "Fizz", FizzBuzz(3))   // 失败 ✗
    assert.Equal(t, "Buzz", FizzBuzz(5))   // 失败 ✗
    assert.Equal(t, "FizzBuzz", FizzBuzz(15)) // 失败 ✗
}

// Step 4: Green — 真实实现
func FizzBuzz(n int) string {
    switch {
    case n%15 == 0: return "FizzBuzz"
    case n%3 == 0:  return "Fizz"
    case n%5 == 0:  return "Buzz"
    default:          return strconv.Itoa(n)
    }
} // ✓ 全部通过，可以 Refactor

TDD 如何驱动设计

测试先行迫使接口思考

[核心]

当你先写测试时，你站在调用方的角度思考 API：

  • 接口大小：测试需要 Mock 的依赖越多，说明这个函数职责越多，需要拆分
  • 命名：测试代码是第一个"文档读者"，迫使你用清晰的名字
  • 错误处理：先写测试时就必须想清楚：这个函数什么情况下会失败？如何传达错误？
  • 避免过度设计：测试只写当前需要的功能，不提前实现"将来可能用到"的特性（YAGNI）

难以测试 = 设计信号

[进阶]

如果一个函数很难测试，通常不是测试的问题，而是设计的问题：

  • 需要 Mock 很多依赖 → 函数做了太多事（Single Responsibility 违反）
  • 必须在特定顺序调用才能测试 → 隐含的状态机，需要显式化
  • 测试需要控制时间/随机数 → 这些应该作为参数注入
  • 测试难以 assert → 返回值设计有问题，或副作用过多

TDD 实践者认为：难以测试的代码是坏代码，这是 TDD 最宝贵的设计反馈。

BDD：行为驱动开发

BDD 是 TDD 的演进

[核心]

BDD（Behavior-Driven Development）由 Dan North 在 TDD 基础上发展，核心创新是用自然语言描述行为，连接业务方和开发方。

BDD 测试使用 Given / When / Then 结构：

Given 系统处于某个初始状态
When 用户执行某个操作
Then 系统应该处于某个期望状态

BDD 测试示例

// 用 testify 写 BDD 风格测试
func TestTransfer_BDD(t *testing.T) {
    // Given：两个账户，A 有 1000 元
    accountA := NewAccount("A", 1000)
    accountB := NewAccount("B", 0)
    service := NewTransferService(accountA, accountB)

    // When：A 转账 300 给 B
    err := service.Transfer("A", "B", 300)

    // Then：转账成功，余额正确
    assert.NoError(t, err)
    assert.Equal(t, 700, accountA.Balance())
    assert.Equal(t, 300, accountB.Balance())
}

func TestTransfer_InsufficientFunds(t *testing.T) {
    // Given：A 只有 100 元
    accountA := NewAccount("A", 100)
    accountB := NewAccount("B", 0)
    service := NewTransferService(accountA, accountB)

    // When：尝试转账 500（超过余额）
    err := service.Transfer("A", "B", 500)

    // Then：返回余额不足错误，余额不变
    assert.ErrorIs(t, err, ErrInsufficientFunds)
    assert.Equal(t, 100, accountA.Balance()) // 未变化
    assert.Equal(t, 0, accountB.Balance())   // 未变化
}

Ginkgo / Gomega：Go BDD 框架

// Ginkgo BDD 框架示例
var _ = Describe("TransferService", func() {
    Context("当余额充足时", func() {
        It("应该成功转账并更新余额", func() {
            // Given
            accountA := NewAccount("A", 1000)
            accountB := NewAccount("B", 0)
            // When
            err := service.Transfer("A", "B", 300)
            // Then
            Expect(err).NotTo(HaveOccurred())
            Expect(accountA.Balance()).To(Equal(700))
        })
    })
    Context("当余额不足时", func() {
        It("应该返回 ErrInsufficientFunds", func() {
            Expect(service.Transfer("A", "B", 9999)).To(MatchError(ErrInsufficientFunds))
        })
    })
})

TDD 的工程权衡

何时适合 TDD

[核心]
维度适合 TDD不适合 TDD
代码性质业务逻辑、算法、核心领域UI 布局、胶水代码
需求稳定性需求明确，变化少探索性开发，需求快速变化
团队经验熟悉 TDD 节奏团队初次引入，学习曲线陡
时间压力中长期项目，维护成本重要极端 deadline，快速验证原型
测试难度可测试的业务函数底层驱动、系统调用、硬件交互

常见误解

[陷阱]
  • "TDD 让开发变慢"：短期可能慢，长期通过减少调试时间和重构代价提升效率
  • "TDD 要 100% 覆盖率"：不是。TDD 是开发方法，不是覆盖率工具
  • "TDD 适合所有代码"：不是。UI、数据库 migration、CLI 工具等场景 TDD 价值有限
  • "先写测试等于 TDD"：TDD 的核心是用测试驱动设计，写完测试就固定实现的测试先行不是 TDD

常见陷阱

⚠ 陷阱：Green 阶段过度实现
// 错误：Green 阶段就实现了所有功能
func TestAdd(t *testing.T) {
    assert.Equal(t, 3, Add(1, 2)) // 第一个测试
}

// Green 阶段一次性写出了通用实现
func Add(a, b int) int {
    return a + b
    // 不够"最少"，但也没问题
}

这不是 TDD 的硬错误，但在复杂场景下，过度实现会绕过 TDD 帮助发现设计问题的机制。

// 正确：Green 阶段只写最少代码
func Add(a, b int) int {
    return 3  // 硬编码，让测试通过
}
// 然后加第二个测试：
// assert.Equal(t, 5, Add(2, 3))
// 这才强迫写出真实实现

对于简单函数，这显得多余；对于复杂业务逻辑，逐步驱动出正确实现非常有价值。

面试问答

TDD 和先写测试后写实现有什么区别？▶
TDD（测试驱动开发）是一种增量设计方法：每次只写一个失败的测试，写最少代码通过，然后重构，不断重复。它的核心是让测试驱动设计，每个测试都是对设计决策的探索。"先写测试后写实现"（Test-First）是在实现前写完所有测试，然后一次性实现。两者都比传统的"先写实现再补测试"好，但 TDD 的小步迭代能更好地通过测试反馈发现设计问题，Test-First 在需求明确时也是很好的实践。
TDD 和 BDD 的关系是什么？▶
BDD 是在 TDD 基础上演进的。TDD 关注的是技术层面：函数/方法的输入输出是否正确。BDD 关注的是行为层面：从用户/业务角度描述系统应该做什么。BDD 引入 Given/When/Then 语言，让测试更接近业务需求描述，可以作为活文档（Living Documentation）供非技术人员理解。两者不互斥：你可以在底层单元测试用 TDD 驱动，在上层业务场景测试用 BDD 风格描述行为。
如何说服团队引入 TDD？▶
不要强制推广，而是从高价值场景开始展示效果：1) 复杂业务逻辑（如折扣计算、规则引擎）——用 TDD 写出来的代码通常接口更清晰；2) Bug 修复——先写一个复现 Bug 的测试，再修 Bug，修复后测试通过；3) 代码重构——TDD 产生的测试套件让重构更安全。关键是展示 TDD 如何帮助思考设计和减少调试时间，而不是以"要写更多测试"的角度推广。可以先在个人层面实践几周，收集具体的收益数据，再分享给团队。
