为什么需要契约测试

微服务集成测试的痛点

[背景]

在微服务架构中，服务之间通过 API 调用交互。传统做法是建立一个共享的集成测试环境，同时部署多个服务验证它们能协作。这带来了严重问题：

  • 环境稳定性：任意一个依赖服务不可用，所有测试失败
  • 数据竞争：多个测试并发修改同一环境的数据，结果不可重现
  • 部署耦合：服务 A 要测试，必须先把依赖的服务 B、C、D 部署到测试环境
  • 破坏性变更发现晚：Provider 修改了 API 字段，Consumer 只有在集成测试时才发现
  • 反馈周期长：等待集成环境部署完成需要分钟甚至小时

契约测试的目标是：让每个服务在本地独立测试，无需依赖真实的下游服务环境。

Consumer-Driven Contract 核心概念

契约的本质

[核心]

契约（Contract）是消费者（Consumer）对提供者（Provider）的 API 的期望集合，记录为文件。核心思想是：

  • Consumer 定义契约：描述它需要什么（哪些字段、哪种格式）
  • Provider 验证契约：证明自己能满足消费者的所有期望
  • 契约文件存储在中央仓库（Pact Broker），双方通过它解耦

三个关键词

  • Consumer（消费者）：调用 API 的一方（如订单服务调用用户服务）
  • Provider（提供者）：实现 API 的一方（如用户服务）
  • Pact（契约文件）：JSON 格式，记录请求/响应的期望，包含交互（Interaction）列表

Pact 框架概述

Pact 生态

[核心]

Pact 是最流行的契约测试框架，支持多语言（Go、Java、Ruby、JavaScript、Python 等）。核心组件：

  • Pact DSL：消费者测试 SDK，用于描述期望和生成契约文件
  • Mock Server：Consumer 测试期间替代真实 Provider 的本地 HTTP Server
  • Verifier：Provider 侧工具，回放契约中的请求到真实代码，验证响应匹配
  • Pact Broker：契约文件的中央存储和版本管理服务（可以用 pactflow.io SaaS 或自托管）

Consumer 侧：定义契约

Go Consumer 测试示例

[代码]

Consumer 测试不调用真实 Provider，而是通过 Pact Mock Server 拦截请求，验证 Consumer 代码能正确构造请求并解析响应。

// consumer/user_client_test.go
package consumer_test

import (
    pact "github.com/pact-foundation/pact-go/v2"
    "testing"
)

func TestGetUser_Pact(t *testing.T) {
    p, _ := pact.NewPact(pact.MockHTTPProviderConfig{
        Consumer: "order-service",
        Provider: "user-service",
    })

    // 描述期望：当收到 GET /users/42 时，返回什么
    p.AddInteraction().
        Given("user 42 exists").
        UponReceiving("a request to get user 42").
        WithRequest("GET", "/users/42").
        WillRespondWith(200, map[string]interface{}{
            "id":    pact.Integer(42),       // 类型匹配，不限具体值
            "name":  pact.String("Alice"), // 字符串类型即可
            "email": pact.Regex("[^@]+@[^@]+", "alice@example.com"),
        })

    // 在 Mock Server 中运行实际的 Consumer 代码
    p.ExecuteTest(t, func(config pact.MockServerConfig) error {
        client := NewUserClient(config.Host, config.Port)
        user, err := client.GetUser(42)
        require.NoError(t, err)
        assert.Equal(t, "Alice", user.Name)
        return nil
    })
    // 测试通过后，自动生成 pacts/order-service-user-service.json
}

生成的契约文件（Pact JSON）

{
  "consumer": { "name": "order-service" },
  "provider": { "name": "user-service" },
  "interactions": [{
    "description": "a request to get user 42",
    "providerState": "user 42 exists",
    "request": { "method": "GET", "path": "/users/42" },
    "response": {
      "status": 200,
      "matchingRules": {  // 类型匹配规则
        "$.body.id":    { "match": "type" },
        "$.body.name":  { "match": "type" },
        "$.body.email": { "match": "regex", "regex": "[^@]+@[^@]+" }
      }
    }
  }]
}

Provider 侧：验证契约

Provider 验证

[代码]

Provider 从 Pact Broker 拉取契约，启动自己的服务，Verifier 回放每个 Interaction 的请求，检查响应是否匹配。

// provider/user_pact_test.go
func TestUserService_PactProvider(t *testing.T) {
    // 启动真实的 Provider 服务（或测试版本）
    server := startTestServer(t)
    defer server.Close()

    verifier := pact.HTTPVerifier{}
    verifier.VerifyProvider(t, pact.VerifyRequest{
        ProviderBaseURL: server.URL,
        // 从 Pact Broker 获取所有 Consumer 的契约
        BrokerURL: "https://pact-broker.example.com",
        ProviderName: "user-service",
        // Provider State 处理器：设置测试数据
        StateHandlers: pact.StateHandlers{
            "user 42 exists": func(setup bool, s pact.ProviderStateV3) (map[string]interface{}, error) {
                // 在数据库中插入测试用户
                testDB.InsertUser(42, "Alice", "alice@example.com")
                return nil, nil
            },
        },
    })
    // 验证失败 → Provider 破坏了 Consumer 的期望
}

CI/CD 集成工作流

典型 CI 流程

[工程实践]
  • Consumer CI：运行契约测试 → 生成 Pact JSON → 推送到 Pact Broker → 发布消费者版本
  • Provider CI：从 Broker 拉取所有消费者契约 → 运行 Verifier 验证 → 如果通过则允许 Provider 发布
  • Can I Deploy：Pact Broker 提供 can-i-deploy 命令，查询"这个版本的 Provider 和所有 Consumer 兼容吗？"
# CI 流程示例
# 1. Consumer 发布契约
pact-broker publish ./pacts \
  --broker-base-url https://broker.example.com \
  --consumer-app-version $COMMIT_SHA

# 2. Provider 验证后，检查是否可以部署
pact-broker can-i-deploy \
  --pacticipant user-service \
  --version $COMMIT_SHA \
  --to-environment production

契约测试的局限性

[注意]
  • 不验证业务逻辑：契约只验证接口格式兼容，不验证业务规则（如余额不足时的行为）
  • 不替代 E2E 测试：契约测试保证服务间能通信，但不验证它们组合后的业务流程正确
  • Provider State 维护成本：需要为每个场景维护测试数据设置逻辑，Provider 变更时需同步更新
  • 适用 REST/HTTP：Pact 主要针对 HTTP API，gRPC 支持有限（可用 protobuf schema 做静态契约）
  • 消费者主导：消费者定义契约，可能遗漏 Provider 的合法变更通知

面试问答

契约测试和集成测试有什么区别？▶
集成测试需要多个服务同时运行在真实（或接近真实）的环境中，验证它们能协作完成业务流程。需要共享测试环境，稳定性差、反馈慢。契约测试每个服务独立验证：Consumer 通过 Mock Server 验证自己能正确发起请求；Provider 通过回放契约请求验证自己能正确响应。双方无需同时运行，各自在 CI 中独立验证，反馈快且稳定。但契约测试只保证接口格式兼容，不保证业务流程正确，所以不能完全替代 E2E 测试。
什么是 Consumer-Driven Contract，为什么是"消费者驱动"？▶
传统做法是 Provider 定义 API 文档，Consumer 按文档实现。问题是 Provider 可能删除 Consumer 不知道的废弃字段，或者新增必填字段破坏 Consumer。CDC（Consumer-Driven Contract）反转这个关系：Consumer 明确声明它需要哪些字段、哪些格式，Provider 必须持续满足所有 Consumer 的期望才能发布。这样 Provider 就不会"无意中"破坏 Consumer——任何破坏 Consumer 期望的 Provider 变更，都会在 Provider 的 CI 中立即失败。
Pact 的 Provider State 是什么，为什么需要？▶
Provider State 描述 Provider 需要处于什么状态才能响应特定请求。例如测试"获取用户 42"，Provider 必须先在数据库中有这个用户。Provider State 就是前置条件的描述（字符串），对应一段 Provider 测试代码，负责准备测试数据。没有 Provider State，Provider 验证时会因为数据不存在而失败，导致误报。正确设置 Provider State 处理器，可以让 Provider 验证在干净环境中可靠运行。
