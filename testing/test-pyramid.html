测试金字塔概念

为什么需要分层测试策略

[核心]

测试金字塔由 Mike Cohn 在《Succeeding with Agile》中提出，核心思想是：不同层级的测试有不同的成本和价值，合理分配才能最大化质量收益。

越靠近金字塔底部的测试：执行越快（毫秒级）、成本越低、维护越容易、反馈越即时。越靠近顶部：越贴近真实用户行为，但越慢（分钟级）、越脆弱、维护成本越高。

E2E 测试
集成测试
单元测试（最多）
慢 · 脆弱 · 昂贵 ↑ 快 · 稳定 · 廉价 ↓

三层详解

单元测试（Unit Test）

[底层 · 最多]

测试最小可测单元（函数/方法），隔离所有外部依赖（数据库、HTTP、文件系统）。每个测试独立执行，无共享状态。

  • 目标：验证单个函数的业务逻辑正确性
  • 速度：毫秒级，可在提交时全量运行
  • 隔离方式：用 Mock/Stub 替代真实依赖
  • 比例建议：占所有测试的 70%+
// Go 单元测试示例：隔离 DB 依赖
func TestCalculateTotal(t *testing.T) {
    tests := []struct{
        name  string
        items []Item
        want  float64
    }{
        {"空订单", []Item{}, 0},
        {"单商品", []Item{{Price: 9.9}}, 9.9},
        {"多商品", []Item{{Price: 9.9},{Price: 20.1}}, 30.0},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := CalculateTotal(tt.items)
            if got != tt.want {
                t.Errorf("got %v, want %v", got, tt.want)
            }
        })
    }
}

集成测试（Integration Test）

[中层 · 适量]

测试多个组件协作：服务层 + 真实数据库、HTTP Handler + 路由、缓存与 DB 的联动。不再 Mock 基础设施层，而是使用真实（或内存版本）的依赖。

  • 目标：验证组件边界和集成点是否正确连接
  • 速度：秒级，通常在 CI 中运行
  • 工具：testcontainers（Docker 启动真实 PostgreSQL/Redis）、httptest
  • 比例建议：占所有测试的 20%
// 使用 testcontainers 启动真实 Postgres 做集成测试
func TestUserRepository_Create(t *testing.T) {
    ctx := context.Background()
    pg, _ := postgres.RunContainer(ctx,
        testcontainers.WithImage("postgres:16-alpine"),
        postgres.WithDatabase("testdb"),
    )
    defer pg.Terminate(ctx)

    dsn, _ := pg.ConnectionString(ctx)
    repo := NewUserRepository(dsn)

    user := &User{Name: "alice", Email: "alice@example.com"}
    err := repo.Create(ctx, user)
    assert.NoError(t, err)
    assert.NotZero(t, user.ID)
}

E2E 测试（End-to-End Test）

[顶层 · 最少]

从用户视角验证完整业务流程：模拟真实用户操作（HTTP 请求、浏览器点击），覆盖从前端到数据库的全链路。

  • 目标：验证关键业务路径端到端可用
  • 速度：分钟级，通常在发布前/夜间运行
  • 工具：Playwright、Cypress（浏览器）、Newman（API）
  • 比例建议：占所有测试的 10%，只覆盖关键路径
  • 注意：E2E 测试脆弱，依赖环境稳定性，不要用它覆盖所有业务逻辑

三层对比

维度单元测试集成测试E2E 测试
执行速度毫秒级秒级分钟级
维护成本低中高
测试范围单函数组件间连接全链路业务
依赖隔离完全 Mock真实基础设施完整部署
失败定位精准较精准模糊
推荐比例70%+~20%~10%

测试覆盖率

覆盖率的意义与局限

[核心]

覆盖率（Coverage）度量被测试执行到的代码比例。Go 提供语句覆盖率：go test -cover ./...。

  • 行覆盖（Statement Coverage）：每行代码至少被执行一次
  • 分支覆盖（Branch Coverage）：每个 if/else 分支都被执行
  • 路径覆盖（Path Coverage）：所有可能的执行路径（通常不可穷举）
// 查看覆盖率 HTML 报告
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out -o coverage.html

// 覆盖率阈值检查（常用于 CI）
go test -coverprofile=coverage.out ./...
coverage=$(go tool cover -func=coverage.out | grep total | awk '{print $3}' | tr -d '%')
if [ "$coverage" -lt "80" ]; then
    echo "Coverage ${coverage}% below threshold 80%"; exit 1
fi

覆盖率的误区

[陷阱]
  • 高覆盖率 ≠ 高质量：测试可以执行代码但不做任何断言，100% 覆盖率的测试可以完全没有价值
  • 追求覆盖率导致测试膨胀：为覆盖而写的测试通常验证实现细节而非行为，重构时大量失败
  • 80% 是经验阈值而非规律：核心业务逻辑要接近 100%，工具类代码可以宽松
  • 不覆盖的代码同样重要：错误处理路径、边界条件往往更容易有 Bug，却也最难被覆盖

分布式系统测试挑战

传统金字塔在微服务下的变形

[进阶]

微服务架构下，服务边界将集成测试拆散，传统的"集成测试验连接"变成了跨服务的 API 契约问题。

  • 服务内：仍然适用金字塔，单元测试覆盖业务逻辑，集成测试验证 DB 访问
  • 服务间：契约测试（Consumer-Driven Contract）替代依赖真实下游的集成测试
  • 全链路：E2E 测试数量应更少，测试的是关键业务路径，而非排列组合
  • 混沌工程：在生产级别注入故障，验证系统在真实故障场景下的行为（超出传统金字塔）

测试环境隔离策略

  • Test Doubles（本地 Mock）：最快，适合单元测试
  • In-process 内存实现：如 SQLite 替代 PostgreSQL，速度快但行为有差异
  • Testcontainers：Docker 启动真实依赖，行为一致但启动慢（10-30s）
  • Dedicated Test Env：共享测试环境，适合集成/E2E，但有并发冲突问题
  • Production Traffic（Shadow Testing）：复制生产流量到新版本，最真实但有副作用风险

反模式

⚠ 反模式：冰淇淋甜筒（Ice Cream Cone）

问题：大量 E2E 测试，少量集成测试，极少单元测试。金字塔倒过来。

症状：CI 跑 30 分钟、测试随机失败、难以定位根因、开发者不愿等待。

根因：团队认为"只有跑完整才算真正测试"，或者缺乏 TDD 意识导致代码难以单元测试。

修复：识别哪些 E2E 测试在测试业务逻辑（应该下沉为单元测试），哪些在测试集成点（可以下沉为集成测试）。

目标：E2E 测试只覆盖 Happy Path 的几个关键业务流程，其他全部下沉。

⚠ 反模式：测试私有实现
// 错误：测试内部实现细节
func Test_sortedInsert(t *testing.T) {
    s := &service{cache: []string{}}
    s.sortedInsert("b")   // 私有方法
    s.sortedInsert("a")
    // 内部结构变化就全部失败
    assert.Equal(t, []string{"a","b"}, s.cache)
}
// 正确：测试公开行为
func TestService_Add(t *testing.T) {
    s := NewService()
    s.Add("b")
    s.Add("a")
    items := s.List()  // 公开接口
    // 重构内部结构不影响此测试
    assert.Equal(t, []string{"a","b"}, items)
}

面试问答

测试金字塔中，为什么单元测试要占最多比例？▶
单元测试执行最快（毫秒级）、反馈最即时、维护成本最低，且可以精确定位 Bug 到函数级别。高比例的单元测试意味着大多数 Bug 可以在提交时被立即发现，而不是等 E2E 流水线跑完。E2E 测试慢且脆弱，如果大量使用会严重拖慢 CI 速度。
80% 测试覆盖率是否足够？▶
80% 是一个经验参考值，但并不绝对。更重要的是：核心业务逻辑和关键路径要接近 100% 覆盖；错误处理路径（通常最容易有 Bug）必须覆盖；边界条件（空输入、最大值、并发）要专门测试。纯粹追求覆盖率数字会导致写无断言的空测试，反而有害。应该关注"有价值的覆盖"而非数字。
集成测试和 E2E 测试的边界在哪里？▶
集成测试验证的是组件之间的连接：你的代码能否正确调用数据库、Redis、外部 API？使用真实依赖（或 Testcontainers），但测试范围仍限定在服务内部。E2E 测试从最终用户视角出发，模拟真实请求穿越整个系统（包括前端→API→DB），验证业务流程是否正确。E2E 不关心内部实现，只关心"用户能否完成任务"。
微服务架构下测试金字塔如何调整？▶
微服务引入了服务边界，传统集成测试的"验连接"需要拆分：服务内部仍然适用金字塔；服务间的 API 兼容性用契约测试（Consumer-Driven Contract / Pact）替代跨服务集成测试；全链路 E2E 只覆盖最关键的业务路径，数量极少。这样可以避免需要维护一个共享的集成测试环境，各服务独立测试独立发布。
