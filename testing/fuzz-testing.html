什么是模糊测试

自动化的边界输入生成

[核心]

模糊测试（Fuzzing）是一种自动化测试技术：通过随机或变异的方式生成大量输入，喂给被测函数，观察是否触发崩溃、Panic、数据竞争或其他异常行为。

传统单元测试的局限：开发者手写的测试用例受思维定势限制，往往覆盖不到"意想不到"的边界输入（空字节、超长字符串、特殊 Unicode、递归结构等）。Fuzzer 可以机械地探索这些边界。

  • 发现 Parser 漏洞：JSON、XML、Protobuf 解析中的 Panic
  • 发现安全漏洞：缓冲区溢出、整数溢出、SQL 注入路径
  • 发现语义错误：编码/解码往返不一致（encode→decode 不等于原始值）

Coverage-Guided Fuzzing

为什么"覆盖率引导"更高效

[核心]

早期 Fuzzer（如纯随机输入）效率极低，大多数输入无法通过基础的输入验证，浪费大量时间。Coverage-guided fuzzing（覆盖率引导）通过代码覆盖率反馈选择"有价值"的变异输入：

→

运行

→

记录新增代码路径

→

修改触发新路径的输入

→

选择

保留覆盖新路径的变体

↩

变异策略

  • 位翻转（Bit Flip）：随机翻转字节中的位
  • 字节替换：用边界值替换字节（0x00, 0xFF, 0x7F）
  • 插入/删除：在随机位置插入或删除字节
  • 字典词替换：用有意义的关键字替换（如 HTTP 方法名、SQL 关键字）
  • 结构感知变异：理解输入格式（如 JSON）并在有效结构内变异

Go 原生 Fuzzing（Go 1.18+）

Fuzz 函数语法

[核心]

Go 1.18 内置了 fuzzing 支持，无需额外依赖。Fuzz 函数和普通测试在同一文件中，使用 *testing.F 类型。

// 模糊测试：发现 ParseURL 的边界 Panic
func FuzzParseURL(f *testing.F) {
    // Seed corpus：初始有意义的输入（必须！）
    f.Add("https://example.com/path?q=1")
    f.Add("http://user:pass@host:8080/path")
    f.Add("")    // 空字符串边界

    // Fuzz 目标：必须没有 panic，且解析结果可回滚
    f.Fuzz(func(t *testing.T, rawURL string) {
        u, err := url.Parse(rawURL)
        if err != nil {
            return  // 解析错误是允许的，但不能 panic
        }
        // 往返测试：解析后再序列化应得到等价结果
        roundTripped, _ := url.Parse(u.String())
        if u.String() != roundTripped.String() {
            t.Errorf("round-trip failed: %q → %q → %q",
                rawURL, u.String(), roundTripped.String())
        }
    })
}

运行命令

# 运行普通模式（只跑 seed corpus，当作普通测试）
go test ./...

# 运行 fuzzing 模式（持续变异，直到找到 Bug 或手动停止）
go test -fuzz FuzzParseURL ./pkg/parser/

# 限制运行时间（CI 中常用）
go test -fuzz FuzzParseURL -fuzztime 30s ./...

# 找到 failing input 后，验证修复
go test -run FuzzParseURL/testdata/fuzz/FuzzParseURL/abc123 ./...

# 查看 corpus 目录
ls testdata/fuzz/FuzzParseURL/

支持的 Fuzz 输入类型

Go fuzzer 支持以下基础类型作为 f.Fuzz 的参数（t *testing.T 必须是第一个参数）：

  • string, []byte — 最常用，适合字符串解析
  • int, int8, int16, int32, int64
  • uint, uint8, uint16, uint32, uint64
  • float32, float64
  • bool, rune, byte

不支持 struct、slice（除了 []byte）、map 等复合类型。复杂输入需要先序列化为 []byte，在 Fuzz 函数内反序列化。

Corpus 管理

Seed Corpus vs Generated Corpus

[核心]

Go fuzzing 有两类 corpus：

  • Seed Corpus（种子语料库）：开发者通过 f.Add() 提供的初始有意义输入，也可以放在 testdata/fuzz/FuzzXxx/ 目录下的文件。每次 go test（非 fuzz 模式）都会执行 seed corpus，相当于普通测试用例。
  • Generated Corpus（生成语料库）：fuzzer 运行期间发现的能覆盖新代码路径的输入，存储在 $GOCACHE/fuzz/ 目录。在不同机器间不共享，只在本地累积。

发现 Bug 后的 Corpus 文件

当 fuzzer 找到导致 Panic 或测试失败的输入时，会将该输入自动写入 testdata/fuzz/FuzzXxx/ 目录，并提示如何重现：

--- FAIL: FuzzParseURL (0.42s)
    fuzzing process hung or failed to return an error:
    Failing input written to testdata/fuzz/FuzzParseURL/a3b8c9d2
    To re-run: go test -run=FuzzParseURL/a3b8c9d2

# 文件内容（corpus file 格式）
go test fuzz v1
string("http://\x00\x01\x02")

这个文件会提交到 git 仓库，成为永久的回归测试用例，防止同样的 Bug 再次出现。

实战示例

示例 1：往返测试（Encode/Decode）

[代码]

最经典的 fuzz 模式：确保 encode(input) 后 decode 结果等于 input。适合 JSON、Base64、Protobuf、压缩算法等。

func FuzzJSONRoundTrip(f *testing.F) {
    f.Add([]byte(`{"name":"alice","age":30}`))
    f.Add([]byte(`null`))
    f.Add([]byte(`"hello"`))

    f.Fuzz(func(t *testing.T, data []byte) {
        var v interface{}
        if err := json.Unmarshal(data, &v); err != nil {
            return  // 非法 JSON，忽略
        }
        re, err := json.Marshal(v)
        if err != nil {
            t.Errorf("Marshal failed for valid JSON: %v", err)
            return
        }
        var v2 interface{}
        if err := json.Unmarshal(re, &v2); err != nil {
            t.Errorf("double Unmarshal failed: %v", err)
        }
    })
}

示例 2：Parser 安全验证

// 验证自定义 Parser 不会 panic 且有完整错误处理
func FuzzParseConfig(f *testing.F) {
    f.Add("[server]\nhost=localhost\nport=8080")

    f.Fuzz(func(t *testing.T, input string) {
        // 不要 panic：无论输入如何，都应返回错误而非崩溃
        cfg, err := ParseConfig(input)
        if err != nil {
            return
        }
        // 有效配置必须满足不变量
        if cfg.Port < 0 || cfg.Port > 65535 {
            t.Errorf("invalid port: %d", cfg.Port)
        }
    })
}

适用场景与局限

最适合 Fuzzing 的场景

[工程实践]
场景为什么适合示例
数据格式解析输入空间大，边界多JSON、YAML、Protobuf、图片格式
编解码往返简单不变量：decode(encode(x)) == xBase64、URL encoding、gzip
协议实现报文格式复杂，实现易错HTTP 头解析、TLS 握手
密码学代码输入微小变化导致完全不同结果Hash 函数、签名验证
用户输入处理攻击者可控，需要健壮性搜索框、文件上传解析

局限性

[注意]
  • 无法验证业务逻辑正确性：Fuzzing 只能发现 Panic、崩溃、超时，无法验证"转账后余额是否正确"
  • 需要好的 Seed Corpus：如果 seed corpus 太简单，fuzzer 难以突破输入验证层探索深层代码路径
  • 不适合有状态操作：每次 fuzz 调用应该是无副作用的（不写 DB、不修改全局状态）
  • 长尾 Bug：发现复杂的多步骤漏洞需要非常长的运行时间

面试问答

Coverage-guided fuzzing 和随机 fuzzing 的区别？▶
随机 fuzzing 直接生成完全随机的输入，大部分输入无法通过基础验证（如输入不是合法 JSON），浪费大量时间探索无效路径。Coverage-guided fuzzing（如 libFuzzer、Go fuzzing）在每次执行后收集代码覆盖率，保留那些触发了新代码路径的输入进行变异，优先探索未覆盖的代码区域。这样 fuzzer 可以"学习"输入格式，逐步穿透验证层，发现深层 Bug。效率比纯随机高 100-1000 倍。
Seed Corpus 的质量为什么重要？▶
Seed corpus 是 fuzzer 的起点，质量决定了 fuzzer 能探索多深。好的 seed corpus 应该：1) 包含能触发各种代码分支的有效输入；2) 包含边界值（空输入、最大值、特殊字符）；3) 包含以前发现过的 Bug 对应的输入（防回归）。Seed corpus 太简单会让 fuzzer 卡在输入验证层外面。例如对 HTTP parser fuzzing，seed corpus 应包含各种合法的 HTTP 请求格式。在 CI 中（go test 不带 -fuzz），只运行 seed corpus，起到普通单元测试的作用。
在 CI 中如何集成模糊测试？▶
两种常见策略：1) 在 CI 中运行 seed corpus（go test ./...，不带 -fuzz），把发现的崩溃输入文件提交到 testdata/fuzz/ 目录，作为普通回归测试持续运行；2) 在 CI 中运行有时间限制的 fuzz（go test -fuzz FuzzXxx -fuzztime 60s），适合在 PR 时快速探索新代码路径。长时间的 fuzz 通常放在专门的 fuzz farm（持续运行的服务器，如 OSS-Fuzz）上，而不是普通 CI 流水线，因为真正有价值的 Bug 可能需要运行数小时才能发现。
