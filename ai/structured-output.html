问题背景

自由文本 vs 结构化数据

[背景]

LLM 默认输出自由文本，对人类阅读友好，但业务系统需要可编程处理的结构化数据。直接用字符串解析 LLM 输出极不可靠：

  • 格式不稳定：同一个问题每次回答的格式可能不同
  • 字段缺失：模型可能漏掉某些字段
  • 类型错误：将数字返回为字符串，或将布尔值写成 "yes/no"
  • 额外文字：在 JSON 前后添加解释性文字导致解析失败
结构化输出的目标：让 LLM 输出可按约定解析和验证的数据，避免脆弱的正则提取。语法或 Schema 合规不代表字段值真实、授权有效或业务语义正确，应用仍须验证。

JSON Mode

强制输出有效 JSON

[基础]

OpenAI 的 response_format={"type":"json_object"} 参数强制模型只输出有效的 JSON 字符串，不会有多余的 Markdown 代码块或前置说明文字。

from openai import OpenAI
import json

client = OpenAI()
response = client.chat.completions.create(
    model="gpt-4o",
    response_format={"type": "json_object"},
    messages=[
        {"role": "system", "content": "返回 JSON 格式，包含 name 和 age 字段"},
        {"role": "user",   "content": "张三，28岁"}
    ]
)
data = json.loads(response.choices[0].message.content)
# {"name": "张三", "age": 28}
注意：JSON Mode 只保证输出是有效的 JSON，不保证字段名称正确、类型符合预期或没有遗漏字段。仍需要 Schema 验证。

Structured Output（更强版本）

[进阶]

OpenAI 的 Structured Output（response_format={"type":"json_schema"}）在 JSON Mode 基础上进一步约束输出必须符合指定的 JSON Schema，利用 Constrained Decoding 在解码阶段强制执行：

response = client.chat.completions.create(
    model="gpt-4o",
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "person_info",
            "strict": True,
            "schema": {
                "type": "object",
                "properties": {
                    "name": {"type": "string", "description": "姓名"},
                    "age":  {"type": "integer", "description": "年龄（岁）"}
                },
                "required": ["name", "age"],
                "additionalProperties": False
            }
        }
    },
    messages=[...]
)

Function Calling / Tool Use

执行流程

[核心机制]

Function Calling 是获取结构化输出的另一种机制：模型不是直接输出文本，而是输出「我想调用某个函数，参数是 ...」的结构化请求，由应用层执行后把结果返回给模型。

① 定义函数 Schema

传入函数名称、参数描述（JSON Schema）、函数用途描述。模型据此决定何时调用。

→
② 模型决策

模型判断用户意图，若需要调用工具，返回 tool_calls 而非文本，包含函数名和参数 JSON。

→
③ 应用层执行

宿主系统执行函数，将结果以 tool 角色消息返回给模型，模型据此生成最终回复。

# 定义 get_weather 工具
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "获取指定城市的当前天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如 '北京'"},
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
            },
            "required": ["city"]
        }
    }
}]

# 第一次调用：模型决定是否调用工具
response = client.chat.completions.create(
    model="gpt-4o", tools=tools,
    messages=[{"role": "user", "content": "北京今天天气怎么样？"}]
)

# 模型返回 tool_calls（而非文本）
tool_call = response.choices[0].message.tool_calls[0]
# tool_call.function.name = "get_weather"
# tool_call.function.arguments = '{"city": "北京", "unit": "celsius"}'

# 应用层执行函数，将结果返回给模型
weather_result = get_weather("北京", "celsius")
messages.append({
    "role": "tool",
    "tool_call_id": tool_call.id,
    "content": json.dumps(weather_result)
})

结构化输出可靠性技术

Constrained Decoding

约束解码会屏蔽不符合目标语法的 token，可提高受支持 Schema 子集的格式合规率；不同实现支持的 JSON Schema 关键字和拒绝/截断行为不同，业务仍需解析、Schema 校验及语义校验。

Outlines / Guidance

Python 库，在本地推理时实现 Constrained Decoding。outlines 可以约束输出为 Pydantic 模型、JSON Schema 或正则表达式；guidance 支持更复杂的生成逻辑（条件分支、循环）。适合本地部署场景。

Instructor 库

封装 OpenAI / Anthropic API，将 Pydantic 模型自动转为函数 Schema，解析失败时自动携带错误信息重试（最多 N 次）。对于远程 API 调用是最实用的方案，代码最简洁。

Instructor 完整示例

[推荐方式]
import instructor
from openai import OpenAI
from pydantic import BaseModel, Field
from typing import Literal

class OrderInfo(BaseModel):
    order_id: str = Field(description="订单编号，格式 ORD-XXXXXX")
    status: Literal["pending", "shipped", "delivered", "cancelled"]
    amount: float = Field(description="订单金额（元）", gt=0)
    items: list[str] = Field(description="商品名称列表")

client = instructor.from_openai(OpenAI())

order = client.chat.completions.create(
    model="gpt-4o",
    response_model=OrderInfo,  # 直接传 Pydantic 模型
    max_retries=3,              # 验证失败时自动重试
    messages=[{"role": "user",
               "content": "订单 ORD-123456，已发货，共 3 件商品：手机、充电器、耳机，总价 3299 元"}]
)
# order.order_id == "ORD-123456"
# order.status == "shipped"
# order.amount == 3299.0
# order.items == ["手机", "充电器", "耳机"]

Schema 设计原则

字段描述比字段名更重要 最重要

模型通过 description 理解字段含义，而非字段名。amount 字段如果没有 description，模型不知道单位是元还是分，是含税还是不含税。始终添加精确的 description，包括单位、取值范围、格式要求。

用 enum 替代 free text 减少幻觉

当字段是有限取值集合时，用 enum 而非开放 string 类型。这不仅约束了输出，还减少了模型「创造性发挥」产生的错误拼写和同义词问题。

避免嵌套过深 稳定性

深层嵌套通常增加生成和消费复杂度，但不存在通用的“三层”正确性阈值。应按模型、约束解码实现和目标 Schema 做测试，必要时拆分调用。

可选字段的处理 类型安全

使用 Optional[T]（Python）或 JSON Schema 的 nullable: true 明确声明可选字段。不要让模型「猜测」应该省略还是填 null，要在 description 中说明「如果信息不存在，返回 null」。

设计对比示例

[实践]
❌ 差的 Schema 设计
class Product(BaseModel):
    name: str       # 没有 description
    price: float    # 单位不明确
    category: str  # 自由文本，幻觉多
    in_stock: str  # 应该是 bool
✅ 好的 Schema 设计
class Product(BaseModel):
    name: str = Field(
        description="产品名称，2-50字")
    price_yuan: float = Field(
        description="价格（元，含税）", gt=0)
    category: Literal[
        "electronics", "clothing", "food"]
    in_stock: bool  # 明确类型

常见误区

❌ 误区 1：JSON Mode = Schema 验证
JSON Mode 只保证输出是语法合法的 JSON（json.loads 不抛异常），并不保证字段完整性、类型正确性或值的合法范围。必须在 JSON 解析后用 Pydantic 或 JSON Schema 验证器进行二次验证，并在验证失败时重试。
❌ 误区 2：Function Calling 只能用于「调用工具」
Function Calling 的本质是「让模型以结构化格式表达意图」，不一定要真正调用外部函数。可以定义一个虚构的 extract_info 函数，专门用来从文本中提取结构化字段——这是 Function Calling 在信息提取任务中的常见用法，与实际工具调用无关。
❌ 误区 3：不加 description 靠字段名传达含义
字段名和 description 都能帮助模型理解意图，但不是正确性的唯一来源。关键字段还应使用类型、enum、范围和跨字段业务规则约束，并由宿主程序验证。
