长上下文 LLM

声明的上下文窗口只表示接口或模型允许的 token 上限，不保证模型能同等可靠地利用窗口内每个位置。长上下文还要同时处理位置外推、KV Cache 容量、注意力计算和信息检索质量。

RoPEYaRNKV CacheGQALost in the MiddleRing AttentionSliding Window
核心术语
  • RoPE 位置编码旋转编码相对位置，通过调整 θ 基频可外推到更长序列。
  • KV Cache缓存 K/V 矩阵避免重算，显存随序列长度线性增长。
  • Lost in the Middle模型对中间内容注意力弱，关键信息应放首/尾。
  • Ring Attention分块分布式注意力，显存和计算横向扩展到多 GPU。

RoPE 与位置编码外推

  • 绝对位置编码（APE）的局限：训练时只见过 0~L 的位置，推理时遇到 L+1 就 OOD（分布外），性能断崖式下降
  • RoPE 的旋转机制：对 Q 和 K 向量的第 2i、2i+1 维度按位置 m 旋转 mθᵢ 角，只要两个 token 的相对位置 m-n 相同，点积结果就相同——实现了相对位置的编码
  • Position Interpolation（线性内插）：将位置 m 除以比例因子 s=L'/L，把超出训练长度的位置映射回训练范围内，需要少量微调
  • YaRN（Yet Another RoPE ext.）：组合不同频率的缩放与注意力尺度修正；论文结果依赖模型与继续训练/微调配置，不能视为无需适配的通用倍数保证
  • LongRoPE：搜索不同维度和长度区间的位置缩放；论文展示了特定模型的扩展结果，不代表任意 RoPE 模型可直接得到相同窗口
# RoPE 旋转矩阵（简化） def rotate_half(x): x1, x2 = x[..., :x.shape[-1]//2], x[..., x.shape[-1]//2:] return cat([-x2, x1], dim=-1) def apply_rope(q, k, cos, sin): q_rot = q * cos + rotate_half(q) * sin k_rot = k * cos + rotate_half(k) * sin return q_rot, k_rot # 点积结果仅依赖相对位置

KV Cache 的显存挑战

  • KV Cache 大小公式：每层 = 2 × batch_size × seq_len × num_heads × head_dim × 2字节（fp16），128K context、32层 LLaMA-7B ≈ 128K × 32层 × 32头 × 128维 × 2 × 2B ≈ 67GB
  • Multi-Query Attention（MQA）：所有注意力头共享一组 K 和 V，KV Cache 减少 num_heads 倍，但精度略降（Falcon 使用）
  • Grouped Query Attention（GQA）：将 num_heads 个 Q 分成 G 组，每组共享一对 K/V，平衡质量和 Cache 大小（LLaMA 2/3、Mistral 使用，G=8 时 KV Cache 减少 4x）
  • KV Cache 量化：将 K/V 从 fp16 量化为 int8 或 int4，显存减半至 4 倍，但极低精度时有注意力精度损失
  • KV Cache 逐出（Eviction）：Streaming LLM 等方法保留最近 K 个 token 的 Cache，丢弃中间 token，适合无限流式生成但牺牲中间上下文

注意力机制的效率优化

  • 标准注意力的问题：全注意力的分数计算量随序列长度平方增长；朴素实现若物化单个 fp16 注意力矩阵，128K×128K 约为 32 GiB，但现代融合内核通常不会完整保存它
  • FlashAttention（1/2/3）：不将完整 QKᵀ 矩阵写入 HBM，使用分块与在线 softmax 减少读写；精确 IO 界取决于序列长度、head 维度与片上存储容量，不能只写成忽略维度的 O(n²/M)
  • Sliding Window Attention（SWA）：每个 token 只关注前 W 个 token（如 W=4096），复杂度降为 O(n·W)，Mistral/Mixtral 使用，多层叠加后感受野仍可覆盖全序列
  • Ring Attention：将序列分块到 N 个 GPU，每个 GPU 处理自己的 Q 块，通过环形 all-to-all 轮换 K/V 块完成全序列注意力，线性扩展显存
  • 稀疏注意力：BigBird 结合全局 token + 局部窗口 + 随机 sparse，近似 O(n) 复杂度，适合文档级长文本
FlashAttention 通过 IO-aware tiling 避免物化完整注意力矩阵。实际速度和内存收益随序列长度、head 维度、硬件、精度与框架集成变化，应以基准测试确认。

Lost in the Middle 与工程实践

  • 现象：“Lost in the Middle”在其多文档问答和键值检索实验中观察到位置敏感、常呈 U 形的性能；差距随模型、任务和上下文变化，不是固定百分比
  • 原因边界：论文展示的是行为评测结果，不能仅凭该结果断言由 softmax 极化这一单一机制导致
  • RAG 中的应对策略：检索后 Reranking 将最相关段落放在 prompt 首/尾；使用 LostInTheMiddle-aware 的 prompt 模板
  • RAPTOR（递归摘要）：将长文档递归压缩为多层摘要树，避免让 LLM 直接处理超长原文
  • LLMLingua 压缩：用小模型估计 token 重要性并压缩 prompt；可用压缩率与任务质量必须在具体数据上验证
  • 实测上下文利用率：NIAH（Needle In A Haystack）测试将关键句藏在不同位置的长文中，用于测试模型是否真正"利用"了长上下文

长上下文的真实价值与误区

  • 适合场景：完整代码库分析（无需 RAG 分块）、长文档问答（书籍/合同）、多轮对话历史保留、大型 repo 的 bug 定位
  • 误区 1：上下文越长越好——注意力质量随长度下降，100K token 中的关键信息可能不如 4K 精选段落
  • 误区 2：长上下文可以替代微调——长上下文做的是 in-context learning，模型无法从中"学习"持久知识
  • 推理成本：从 4K 增至 128K 是长度增加 32 倍；全注意力项的理论计算增长更接近平方，而整模型耗时还包含线性层、并行效率和内核，因此不是固定 32 倍
NIAH（Needle in a Haystack）测试已成为评估长上下文质量的标准 benchmark：在 128K token 的随机文本中藏入一个"魔法数字"，要求模型找到它。GPT-4 在 ~64K 中间位置仍有明显准确率下降。
