Prompt Engineering

Prompt Engineering 通过设计高质量的输入来引导 LLM 输出期望结果。理解 CoT、Few-shot、角色设定等技巧，以及何时选择 RAG vs Fine-tuning，是提升模型应用效果的工程手段。

什么是 Prompt Engineering？

Prompt Engineering 是通过精心设计输入文本，引导 LLM 产生期望输出的工程实践。它不是"魔法咒语"——不存在通用的万能 prompt，而是关于如何为模型提供清晰的上下文、约束和示例。

  • 本质：LLM 是条件语言模型，prompt 定义了条件分布。更清晰的条件 → 更集中的输出分布 → 更可预期的结果。
  • 边界：Prompt Engineering 无法弥补模型本身缺少的知识（用 RAG）、无法稳定地改变模型行为偏好（用 Fine-tuning），只能在模型已有能力范围内更好地激活。
  • 可测试性：好的 Prompt 要有评测闭环——写 eval 数据集，量化测量效果，而不是靠直觉判断"感觉更好"。

核心技巧

从简单到复杂，四种最基础的 prompting 技术：

# Zero-shot：直接描述任务
"将以下文本的情感分类为正面/负面/中性：\n{text}"

# Few-shot：提供示例
"根据示例进行情感分类：
输入：这个产品很棒！ → 正面
输入：差劲，完全不值 → 负面
输入：{text} →"

# CoT：要求逐步推理
"解答以下数学题，先分步骤推理，再给出最终答案：\n{problem}"

# System Prompt：设定角色和约束
[system]: 你是一个专业的代码审查员。
用中文回答，只关注安全漏洞，不讨论代码风格。
回答格式：{ 风险等级, 位置, 描述, 修复建议 }
  • 格式指定：明确要求 JSON/Markdown/列表格式，减少后处理解析成本。
  • 负面约束："不要..." 比不说更有效。如"不要道歉，不要说'当然'"。
  • 角色设定：你是一个专业的X 可以改变回答风格，但对模型不具备的能力无效。

CoT 深入：思维链为什么有效？

CoT 的有效性有理论支撑：生成推理步骤等于在 token 层面分配了更多计算（更多前向传播步骤），给模型"工作空间"处理复杂问题。

# CoT 示例：直接回答 vs 逐步推理

# 直接回答（错误率高）
Q: 停车场有 3 层，每层 40 个车位，已停 1/4，还剩几个？
A: 30 个

# CoT（准确率显著提升）
Q: 停车场有 3 层...请逐步计算。
A: 第一步：总车位 = 3 × 40 = 120 个
   第二步：已停 = 120 × 1/4 = 30 个
   第三步：剩余 = 120 - 30 = 90 个
   答：还剩 90 个车位
  • Self-consistency：对同一问题用高 temperature 采样多个 CoT 路径，取多数答案投票，进一步提升准确率（代价是 inference 成本增加 N 倍）。
  • Tree-of-Thought（ToT）：让模型生成多条推理分支，用 LLM 评估每条分支的质量，选最优路径，适合需要规划的复杂任务。
  • 限制：CoT 对知识密集型任务效果有限，模型不具备的事实知识不会因为"请逐步推理"而凭空出现。

RAG vs Fine-tuning vs 纯 Prompting

三种方案适用于不同问题，决策取决于知识来源、任务类型和成本约束：

  • 纯 Prompting → 适合：通用任务、模型已有能力足够、快速原型。不适合：需要最新知识、需要稳定输出格式。
  • RAG（检索增强） → 适合：需要引用最新或私有知识、知识库会更新、需要来源可追溯。不适合：知识库极小（不如直接塞进上下文）、任务与格式强相关。
  • Fine-tuning → 适合：需要稳定的输出格式/风格、领域专用知识难以检索、prompting 成本（token）过高。不适合：知识实时变化、缺乏高质量训练数据。
决策顺序：先尝试纯 prompting + few-shot。如果需要最新/私有知识，加 RAG。如果格式/风格不稳定、prompting 成本过高，考虑 fine-tuning。

结构化输出

让模型输出可编程处理的结构是工程化 LLM 应用的关键，有三种主要方式：

# 方式一：Prompt 约束（最简单，但不保证可靠）
"以 JSON 格式回答，字段：name, age, city。不要输出任何其他内容。"

# 方式二：JSON Mode / Structured Output（API 层保证）
response = openai.chat.completions.create(
    model="gpt-4o",
    response_format={"type": "json_object"},  # 强制 JSON
    messages=[...]
)

# 方式三：Function Calling（最可靠，schema 严格）
tools = [{
    "name": "get_weather",
    "parameters": {
        "type": "object",
        "properties": {"location": {"type": "string"}},
        "required": ["location"]
    }
}]
response = openai.chat.completions.create(
    model="gpt-4o", tools=tools, messages=[...]
)

工程实践中优先选择 Function Calling 或 Structured Output API，不要在 prompt 里靠"请输出 JSON"来保证格式，这在边缘情况下会失败。

常见误区

  • Prompt 不是代码：Prompt 没有类型系统、没有单元测试、没有稳定的依赖管理。任何 prompt 变更都需要评测集验证，不能凭直觉判断效果。
  • 更长的 Prompt 不一定更好：过长的系统提示会稀释关键约束。实验表明，模型对 prompt 末尾的内容注意力更强，重要约束应放在最后。
  • 不要过度依赖角色扮演："假装你是专业医生"不能让模型获得医学知识，只会改变语气。角色设定是风格控制，不是能力提升。
  • CoT 不万能：对于依赖最新事实的问题，让模型"逐步推理"后得出的仍是错误事实的推理链。CoT 放大已有能力，不创造新能力。
  • 忽视采样参数：同一个 prompt 在 temperature=0.0 和 temperature=1.0 下表现可能差异巨大。精确任务（代码、JSON）用 0；创意任务用 0.7-1.0。
