对象存储系统

对象存储将文件以扁平命名空间存储，通过分块上传、纠删码副本和元数据分离实现高可靠、低成本存储，是云存储（S3、OSS）的核心模式。

分块上传纠删码元数据GC
核心术语
  • Chunk（块）大文件分割成固定大小的块（如 64MB），分别上传和存储，支持断点续传，任意块失败只需重传该块。
  • Erasure Coding（纠删码）RS(6,3) 将 6 个数据块编码为 9 块（3 个校验块），丢失任意 3 块可恢复，比三副本节省 50% 空间。
  • Metadata（元数据）文件的命名空间、权限、版本和块映射，通常存在高性能数据库（TiKV/MySQL），与数据存储完全分离。

背景与机制

AWS S3、阿里 OSS、Google GCS 都采用元数据与数据分离的架构：元数据（bucket、key、大小、分块映射、权限）存高性能关系数据库；实际数据块分布在 DataNode 集群，使用纠删码（Erasure Coding）代替三副本，在同等可靠性下节省约 50% 存储成本。大文件必须分块，每块独立上传，支持并发和断点续传。

常见误区

  • 纠删码降低了存储开销，但读取需要合并多个块，读延迟高于三副本，适合冷数据场景。
  • 元数据 DB 是单点热点，需要水平分片（按 bucket+key hash），不能用单机 MySQL。
  • 分块上传的 ETag 必须对每块内容做 MD5，不能只算整体文件的 MD5，否则断点续传校验出错。
  • GC 不能在删除时立即清理数据块，因为可能有并发上传引用相同块（通过 content hash 去重）。

工程场景

  • 分块上传流程：InitiateMultipartUpload → UploadPart × N → CompleteMultipartUpload
  • 纠删码：RS(6,3) 编码，DataNode 最多 3 个同时故障仍可恢复数据
  • 元数据 DB 选型：TiKV（分布式 KV）或 MySQL 分片，存文件→块列表映射
  • Content-addressable storage：块按内容 hash 地址化，相同内容只存一份（去重）

边界与恢复

  • DataNode 宕机：纠删码允许丢失 3 个节点，后台 rebalancer 自动重新编码补全校验块
  • GC 策略：标记删除（soft delete）→ 24h 后实际 GC，扫描无引用块 → 批量清理
  • 版本控制：每次 PUT 操作生成新版本，旧版本保留直到用户显式删除或 lifecycle 规则触发
  • CAP 取舍：对象存储通常选 AP（可用性 + 分区容忍），最终一致性，写后读可能看到旧版本
