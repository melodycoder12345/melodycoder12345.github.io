TSDB vs 普通 DB

  • 写入模式：TSDB 总是追加写入（append-only），普通 DB 支持随机更新
  • 查询模式：TSDB 查询主要是时间范围扫描，普通 DB 需要全索引
  • 压缩：时序数据相邻值相近，Delta 编码 + XOR 压缩效率极高
  • 内存块：最近 2h 数据在内存 WAL 中，定期 flush 为磁盘块
  • 保留策略：按时间范围自动删除旧数据，不需要手动维护
  • Chunk 格式：每个 series 的数据按 chunk 存储，同一指标数据聚合

Prometheus 采集架构

  • Pull 模式：每 15s 向 Target 的 /metrics 接口发 HTTP GET
  • 服务发现：Kubernetes SD/Consul SD 动态发现 Target，无需手动维护列表
  • Relabeling：采集前/后对 label 进行过滤、重命名、合并
  • Remote Write：可将数据写入外部长期存储（Thanos/Cortex/Mimir）
  • Federation：Prometheus 聚合多个下游 Prometheus，用于跨数据中心
  • Pushgateway：批量任务主动推送短生命周期指标的临时中转

告警设计

  • Alerting Rule：PromQL 表达式 + for 持续时间（防止毛刺告警）
  • Alertmanager 分组：同一服务多实例的告警合并为一条
  • 抑制（Inhibit）：主机挂机时，该主机上的业务告警自动静默
  • 路由树：不同告警路由到不同接收人（PagerDuty/Slack/Webhook）
  • 静默（Silence）：计划维护窗口内，匹配规则的告警自动静默
  • 告警疲劳：合理设置 for 和 severity，避免低优先级告警淹没高优

可观测性三大支柱

  • Metrics（指标）：聚合数值，适合监控和告警，存储成本低
  • Logs（日志）：结构化或非结构化事件记录，适合排查具体错误
  • Traces（追踪）：单次请求全链路耗时，适合定位瓶颈和依赖分析
  • 三者互补：告警触发（Metrics）→ 查日志定位（Logs）→ 追踪分析（Traces）
  • OpenTelemetry：统一三者的 SDK 和协议，避免厂商锁定
  • SLO / Error Budget：基于 Metrics 定义可靠性目标和消耗速率
