API Gateway

API Gateway 是微服务架构的统一入口，将跨切面关注点（认证、限流、路由、熔断）集中处理。动画展示一个请求球依次通过串联的处理层：每层有独立状态，被拒绝时显示具体原因和 HTTP 状态码，通过后继续向下一层传递。

核心术语
  • 认证（Auth）JWT 验签、API Key 查找、OAuth Token 校验，确认请求者身份。
  • 限流（Rate Limit）令牌桶/滑动窗口控制 QPS，超限返回 429 Too Many Requests。
  • 路由（Router）路径/Header 规则匹配，将请求转发到对应微服务。
  • 熔断器错误率超阈值后 Open 状态：直接返回错误，避免雪崩。

选择请求场景

共有 5 种场景：正常请求、Auth 失败、限流触发、熔断器 OPEN、正常路由到不同后端。

Gateway 实现
主流方案
Kong：Nginx + Lua 插件，声明式配置，生产最广泛
APISIX：etcd 动态路由，支持 Python/Go 插件
Envoy：L7 代理，Istio 数据面，支持 xDS 动态配置
AWS APIGW：托管方案，自动扩缩，适合 Serverless
熔断器状态机
CLOSED → (错误率↑) → OPEN
OPEN → (等待窗口) → HALF-OPEN
HALF-OPEN → (试探成功) → CLOSED
HALF-OPEN → (试探失败) → OPEN

与反向代理的区别

  • 反向代理（Nginx）：主要做负载均衡和 TLS 终止，逻辑简单
  • API Gateway：在代理之上增加认证、限流、熔断、转换、监控等业务逻辑
  • 服务网格（Istio）：下沉到每个 Pod 的 Sidecar，解决 East-West 流量；Gateway 负责 North-South（外部流量入口）
  • BFF（Backend for Frontend）：为不同终端（App/Web/Partner）定制聚合的特化 Gateway

性能关键点

  • 认证缓存：JWT 签名验证 CPU 密集，用短期 Token 缓存避免每次重验
  • 限流 Redis：分布式限流用 Lua 脚本保证 Redis 原子性，避免竞态
  • 连接池：到后端服务使用长连接池（keep-alive），避免每次请求新建 TCP
  • 异步日志：请求日志异步写入，不阻塞响应路径
  • Gateway 本身应无状态，方便水平扩展；有状态数据（限流计数、熔断状态）放 Redis

限流算法对比

  • 令牌桶：固定速率添加令牌，允许突发（令牌积累）。适合正常流量有短时峰值的场景。
  • 漏桶：固定速率处理请求，严格平滑，不允许突发。适合对后端保护要求严格的场景。
  • 固定窗口：统计固定时间窗口内的请求数，边界处可能有 2x 突发（窗口切换问题）。
  • 滑动窗口：精确统计任意时间窗口，无边界问题，但内存开销稍大。

网关的 12-Factor 设计

  • 路由规则动态加载：不需要重启 Gateway 即可新增/修改路由（etcd Watch / Admin API）
  • Plugin 化：认证/限流/日志每个都是独立插件，可配置，可热插拔
  • 灰度路由：通过 Header/Cookie/IP 将部分流量路由到金丝雀版本
  • 可观测性：每个请求记录 TraceID（注入 traceparent Header），方便跨服务追踪
  • 优雅降级：后端不可用时可返回缓存/兜底数据，而不是直接 502
