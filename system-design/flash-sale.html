System Design
秒杀系统
流量漏斗 · 预扣库存 · 异步下单 · 降级
步骤说明
选择场景，了解秒杀系统如何在高并发下保证库存准确和用户体验。
流量漏斗

多级过滤

秒杀流量的核心是把 99% 的请求挡在真正的库存操作之外：CDN 静态页 → Nginx 限流 → 黑名单过滤 → 验证码 → Redis 预检 → 业务层处理。

关键原则：越靠前的过滤成本越低，越靠后的节点处理的请求越少。让数据库只看到 1% 的真实流量。
库存设计

Redis 预扣库存

活动开始前将库存预热到 Redis（SETNX stock:item_1 100），用 Lua 脚本原子扣减：check → decr → return。避免超卖。

DB 最终扣减

Redis 预扣成功后将订单写入 Kafka 队列，Consumer 异步在 DB 执行最终库存扣减和订单创建，并用乐观锁兜底：UPDATE ... WHERE stock > 0。

幂等保证

订单使用 user_id + item_id + activity_id 的唯一索引，重复请求会触发唯一键冲突，保证一个用户只能抢到一件。

降级策略

Redis 不可用

Redis 集群故障时，直接返回"系统繁忙，请稍后再试"，不穿透到 DB。宁可损失部分购买体验，也不能让 DB 被打垮。

Kafka 积压

订单 Consumer 积压时，增加 Consumer 实例水平扩容，或对积压超时的订单直接标记失败并退款（配合用户通知）。

库存提前售罄

Redis 库存扣为 0 时，在内存 flag 中标记"已售罄"，后续请求直接在最外层拦截，不再访问 Redis，进一步降低压力。
