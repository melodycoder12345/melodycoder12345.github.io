搜索自动补全

搜索自动补全需要在 100ms 内返回相关候选词。理解前缀索引、排名策略和实时更新，是构建低延迟补全系统的核心。

Trie前缀匹配Redis实时更新
核心术语
  • Trie（前缀树）按字符前缀组织候选词，支持 O(k) 前缀查找，k 是查询长度。每个节点存子节点映射和 Top-N 热词缓存。
  • Score（排分）候选词按搜索频率、点击率和时效性综合排分，非简单字频排序。CTR 高的词会排在频率较低但 CTR 差的词前面。
  • Aggregation（聚合）近期热门搜索从日志流聚合，Flink 窗口计算后周期写入 Redis，通常有 1~5 分钟延迟，不是真实时。

背景与机制

Google、百度、淘宝每次击键都触发补全请求，要求 P99 < 100ms。核心路径是：前缀命中 CDN 边缘缓存 → 透传到 Suggest 服务 → 查询 Redis sorted set（用 ZRANGEBYLEX 做前缀匹配） → Ranking 服务综合打分 → 返回 Top-10 候选词。后台异步路径：搜索日志 → Kafka → Flink 实时聚合 → 周期更新 Redis。

常见误区

  • Trie 树不一定比 Redis sorted set 快，Redis ZRANGEBYLEX 在内存中做前缀匹配，延迟 < 1ms。
  • 候选词排序不能只按频率，CTR（点击率）和时效性（近 7 天权重 > 历史总量）同样重要。
  • 多语言补全需要单独处理分词边界，中文按字前缀，日文按假名，不能统一用 ASCII 前缀逻辑。
  • CDN 缓存补全结果时，缓存键应包含用户语言和地区，避免中英文补全结果混用。

工程场景

  • Redis ZRANGEBYLEX：key 存"词:score"编码，按字典序范围查找前缀匹配词
  • CDN 缓存：常见短前缀（2~4 字符）的补全结果 TTL=60s，边缘命中率 > 80%
  • Flink 窗口：5 分钟滚动窗口聚合搜索量，topN 词写入 Redis ZSet，score=频次×CTR×时效权重
  • 防穿透：Bloom Filter 过滤无效前缀，减少对 Trie 的无效查询

边界与恢复

  • 缓存过期穿透：CDN 过期瞬间大量请求打到 Suggest 服务，需限流 + 互斥重建
  • 热词突发：突发热词（如热搜事件）需要 Flink 实时窗口 + 手动推送干预通道
  • 索引更新：词表每天全量重建 + 增量实时更新，灰度发布避免批量更新抖动
  • 恶意输入：前缀长度限制（最多 50 字符）+ 速率限制（每 IP 10 QPS）
