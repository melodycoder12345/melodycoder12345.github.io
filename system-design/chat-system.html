即时通讯系统

IM 系统的核心挑战是长连接管理、消息顺序和未读计数。理解连接层、存储层和消息路由的设计，是构建低延迟、高可靠聊天系统的基础。

核心术语
  • Connection（长连接）每个在线用户持有一个 WebSocket 长连接，连接层需要处理海量并发连接，connId → userId 的路由映射存 Redis。
  • Message Sequence（消息序）每条消息有全局或会话级单调递增 ID，保证排序和去重，Snowflake 或 Redis INCR 实现。
  • Inbox（收件箱）每个用户有收件箱，支持未读计数、已读状态和跨设备同步，通常用 Redis + MySQL 双写。

背景与机制

微信、Slack、钉钉都面对同样的核心问题：海量长连接管理 + 消息可靠性。WS 网关负责维护连接状态（connId→userId 存 Redis），MsgRouter 负责找到对方的连接并推送。消息必须持久化到 DB，客户端 ACK 后才标记已投递。

常见误区

  • WebSocket 不等于可靠投递，网络丢包或进程崩溃会导致消息丢失，必须有客户端 ACK + 服务端重试。
  • 消息 ID 只用 DB 自增主键不够，分布式场景下 Snowflake 才能保证全局有序。
  • 群消息不能同步扇出到所有成员，需要 Kafka 异步写各成员收件箱。
  • 离线推送（APNs/FCM）到达率不保证 100%，用户重新上线需拉取未读消息。

工程场景

  • Netty 长连接网关：一台机器可维持 10万+ WebSocket 连接，心跳 30s
  • Redis：HSET online:{userId} connId gateway_ip，快速查找目标用户在哪台 GW
  • HBase：按 conversation_id + msg_id 存消息历史，支持范围查询
  • MySQL：inbox 表存 userId、convId、lastMsgId、unreadCount

边界与恢复

  • 断线重连：客户端重连后拉取 lastMsgId 之后的所有未读消息，补全消息序列
  • 消息去重：客户端生成 clientMsgId，服务端幂等检查防止重发产生重复
  • 顺序保证：同一会话的消息路由到同一 Kafka partition，保证消费顺序
  • 大群优化：群成员 > 500 时，改用读扩散模式，避免写收件箱风暴
