支付系统

支付系统以账务守恒、可追溯和可恢复为目标。预扣（冻结余额）+ 确认（实际扣减）状态机、幂等键、不可变账务流水与对账补偿共同缩小差错窗口；任一机制都不能单独承诺绝不多扣或少扣。

预扣 / Authorize确认 / Capture幂等对账Outbox 模式
核心术语
  • 预扣 + 确认（两阶段）冻结余额但不扣减 → 银行确认后实际扣减。
  • 幂等 Keyorder_id 作为幂等凭证，重复请求直接返回已有结果。
  • 对账任务定时扫描超时未确认记录，主动向银行查询状态，修复数据。
  • 回滚补偿银行拒绝或超时后，释放冻结金额，恢复可用余额。

准备发起支付

选择场景：正常支付、银行拒绝、网络超时+对账。

核心代码逻辑
// 创建支付（幂等）
func CreatePayment(req PayReq) {
  // 1. 检查幂等 key
  if exists(req.OrderID) {
    return getResult(req.OrderID)
  }
  // 2. 预扣余额（DB事务）
  tx.Begin()
  account.Frozen += req.Amount
  account.Available -= req.Amount
  payment.Status = AUTHORIZED
  tx.Commit()

  // 3. 调用银行 API
  result = bank.Charge(req)

  // 4. 确认或回滚
  if result.OK {
    account.Balance -= req.Amount
    account.Frozen -= req.Amount
    payment.Status = CAPTURED
  } else {
    account.Frozen -= req.Amount
    account.Available += req.Amount
    payment.Status = FAILED
  }
}

为什么需要两阶段？

  • 直接扣款的问题：调用银行 API 失败，但余额已扣，需要补偿回滚
  • 两阶段：预扣冻结余额（快速），等银行返回成功后再真正扣减（确认），银行拒绝则直接解冻
  • AUTHORIZE 状态：余额冻结但未扣，用户看到可用余额减少，防止超额支付
  • 对账弥补网络超时：银行 API 可能超时，不代表失败，对账任务主动查询结果

幂等性设计

  • order_id 作为幂等 key，每笔订单只能支付一次
  • DB 唯一索引：UNIQUE KEY(order_id)，重复插入失败
  • Lua 脚本 / SELECT ... FOR UPDATE：在 Redis 做幂等检查时保证原子性
  • 幂等 key 有效期：设置 TTL，防止无限期占用资源
  • 网络重试必须携带相同幂等 key，否则视为新请求

对账与数据一致性

  • 定时对账：每分钟扫描 status=AUTHORIZED 且超过 N 秒的记录
  • 主动查询：调用银行查单接口（QueryOrder），不依赖银行回调
  • 三态处理：已扣成功（→CAPTURED）/ 已拒绝（→FAILED+解冻）/ 处理中（继续等待）
  • 银行回调补充：回调来了也处理，但不是唯一来源，防止回调丢失
  • 资金对账报表：T+1 与银行流水对账，确保账面和实际资金一致

分布式支付挑战

  • 分布式事务：用户账户和订单状态在不同服务，用 Saga 模式而非 2PC
  • 超卖防护：秒杀场景下余额扣减用 Redis DECR + 定期同步
  • 货币精度：使用整数（分为单位）或 Decimal 类型，避免浮点数误差
  • 跨境支付：汇率实时查询，手续费分摊，本地支付方式（支付宝/微信/PayPal）
  • PCI DSS 合规：卡号数据加密/脱敏，安全审计日志，禁止明文存储
