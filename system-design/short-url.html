核心设计

编码方案：Base62

用 [0-9a-zA-Z] 62个字符对自增 ID 或哈希值编码，6 位 Base62 可表示 62⁶ ≈ 568 亿条记录，满足大多数业务需求。

ID 生成策略

推荐使用数据库自增主键，比随机哈希更稳定且无碰撞。高并发下可换用 Snowflake 分布式 ID。

重定向方式

301 永久重定向，浏览器缓存，减少服务器压力，但难以统计点击。302 临时重定向，每次都经过服务器，便于统计分析。

数据模型
short_codeVARCHAR(8) PK
long_urlTEXT NOT NULL
user_idBIGINT
created_atTIMESTAMP
expires_atTIMESTAMP NULL
click_countBIGINT DEFAULT 0
缓存策略

Redis 结构

Key: url:{short_code}
Value: 原始长链接
TTL: 与业务过期时间一致，或永不过期（高频 key）

⚠️ 缓存穿透：不存在的短码每次都打到 DB。防护方案：对不存在的 key 也写入空值（TTL 较短），或使用 Bloom Filter 前置拦截。
扩展考量

读多写少特性

短链跳转 QPS 远大于创建 QPS，可在 Redis 前再加 CDN 边缘缓存，热点短链的 302 响应直接从边缘节点返回。

分库分表

以 short_code 哈希分片，保证同一短码的读写落在同一分片。避免用自增主键分片，会产生写热点。
