分布式任务调度

分布式任务调度需要保证任务准时触发、幂等执行、失败重试和分布式去重。时间轮高效管理定时任务，分片策略让调度横向扩展。

时间轮幂等分片失败重试
核心术语
  • Time Wheel（时间轮）O(1) 复杂度的定时管理结构，任务按截止时间槽位放置，指针周期移动触发到期任务，比最小堆更高效。
  • Idempotency（幂等）任务重试时不产生副作用，通常通过任务 ID + 状态机（PENDING→RUNNING→SUCCESS/FAILED）保证。
  • Shard（分片）任务按 task_id % shard_count 分配到不同调度节点，每个节点负责一部分任务，水平扩展调度容量。

背景与机制

定时任务是最常见的后台需求（报表生成、订单超时、消息重推），但分布式环境下最难保证的是：（1）准时触发—时钟漂移 + 节点宕机；（2）不重复执行—多个调度节点同时触发同一任务；（3）失败重试—指数退避而不是无限重试。时间轮 + 分布式锁 + 状态机是标准解法。

常见误区

  • 用 SELECT ... WHERE next_exec_time <= NOW() 扫表调度，数据量大时全表扫描性能极差，应用时间轮或优先队列。
  • 仅用数据库行锁（FOR UPDATE）做去重，高并发下锁争抢严重，应用 Redis SETNX 分布式锁先行过滤。
  • 重试不加指数退避，频繁重试可能加剧下游压力，首次 1s → 2s → 4s → ... → 最大 1h。
  • 任务状态没有 RUNNING 中间态，会导致节点宕机后任务永久卡住，需要心跳超时自动释放。

工程场景

  • 时间轮实现：环形数组，槽位数=轮周期/精度（如 60s÷100ms=600槽），指针每 100ms 前进一格
  • XXL-Job：开源分布式调度框架，Executor 注册到注册中心，Admin 分配任务和监控
  • Redis 分布式锁：SET lock:{taskId} uuid NX EX 30，加锁成功才执行，超时自动释放
  • 分片策略：taskId % schedulerCount，每个 Scheduler 只负责自己分片的任务

边界与恢复

  • Scheduler 宕机：其他节点检测到心跳超时，接管宕机节点的分片任务（重新选主）
  • 时钟漂移：不同节点时钟差异导致同一任务提前或延迟触发，用 NTP 同步 + 100ms 容忍窗口
  • DEAD 任务：超过最大重试次数（如 5 次）标记为 DEAD，发告警，人工干预或写入死信队列
  • 幂等检查：任务开始时读取 DB 状态，若已 RUNNING/SUCCESS 则跳过（乐观锁 + 版本号）
