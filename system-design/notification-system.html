通知系统

通知系统将业务事件转化为多渠道（Push/短信/邮件）的并行投递。优先级队列保证高优先级通知（支付成功）不被低优先级（活动推荐）阻塞；幂等 key 防止网络重试导致重复通知；失败渠道独立重试，不影响其他渠道。

优先级队列多渠道扇出幂等 Key重试死信队列 DLQ
核心术语
  • 优先级队列高/中/低三档优先级，高优通知优先从队列取出投递。
  • 多渠道扇出Push + SMS + Email 并行发送，渠道间互不依赖。
  • 幂等 Key消息头部携带 idempotency_key，重复投递时服务端去重。
  • 指数退避重试失败后 1s→2s→4s→8s 重试，超限转 DLQ。

架构要点
用户偏好过滤
用户可关闭特定渠道（如只保留 Push，不要短信）。Dispatcher 读取用户配置后，只向已开启的渠道扇出。
第三方限制
短信运营商有 QPS 限制（如 100条/s），Email 有日发送上限。各渠道 Worker 维护独立限速器，不因一个渠道拥堵影响其他渠道。
监控指标
发送成功率、各渠道延迟 P99、DLQ 积压量、幂等命中率。

推送（Push）渠道

  • iOS：APNs (Apple Push Notification Service)，HTTP/2 协议，需证书认证
  • Android：FCM (Firebase Cloud Messaging)，支持优先级（high/normal）
  • Web Push：Vapid 协议，依赖 Service Worker 接收推送
  • 连接管理：用 device_token 标识设备，失效 token 需及时清理（APNs 返回 410 时删除）
  • 离线设备：消息暂存，上线后推送；超时后消息过期不发，避免发送过期信息

可靠性保证

  • At-Least-Once：Kafka Consumer 提交 Offset 在 ACK 发送之后，保证至少投递一次
  • 幂等 Key：消费者幂等处理，同一 key 重复到达时跳过，防止重复通知
  • 事务性发件箱（Transactional Outbox）：业务事件和通知记录在同一 DB 事务，由 CDC 进程读取后投递，彻底避免消息丢失
  • DLQ：死信队列记录重试耗尽的消息，人工或定时任务处理

大规模通知

群发通知（如全量用户促销推送）不同于实时通知：

  • 批量模式：从用户数据库分批读取（每批 10万），写入消息队列，避免一次性占满内存
  • 背压控制：Consumer 处理速率通过 Kafka Consumer Group 分区扩展
  • 发送窗口：避开用户睡眠时间（根据时区），提高打开率，降低运营商投诉率
  • A/B 测试：将用户分组，测试不同文案的点击率

通知系统常见问题

  • 重复通知：网络重试导致，幂等 key 是唯一解
  • 通知风暴：大量事件同时触发，用优先级队列和限速保护第三方
  • 设备 Token 失效：定期 ping 验证，失效后从 DB 删除，避免无效调用
  • 用户退订：需要统一管理用户偏好（per-user per-channel per-category）
  • 监控盲区：第三方推送平台不保证实时回调，需主动拉取投递结果
