令牌桶 · 滑动窗口 · 分布式限流

算法对比
🪣 令牌桶（Token Bucket）
桶中有令牌才能通过，令牌按固定速率补充。支持突发流量，是最常见的限流方式。适合 API 限流。
🚿 漏桶（Leaky Bucket）
请求进入桶，以固定速率流出。完全平滑输出，不允许突发。适合需要严格均匀速率的场景（如网络带宽）。
🪟 滑动窗口（Sliding Window）
记录每个请求的时间戳，统计滑动时间窗口内的请求数。精度高，内存占用较大，适合精细限流。
🔢 固定窗口（Fixed Window）
每个时间窗口内计数，超过阈值则拒绝。实现简单，但存在边界突刺问题（两个窗口交界处可能有 2x 突发）。
分布式限流

Redis + Lua 原子扣减

将令牌桶的 tokens 存储在 Redis 中，用 Lua 脚本原子地执行：检查令牌数 → 补充令牌 → 扣减令牌，避免并发竞争。

Lua 脚本在 Redis 中是原子执行的，不会有并发问题。这是分布式限流最常用的实现方式。

Redis Key 设计

Key: ratelimit:{user_id}:{window}
或 ratelimit:{api_path}:{minute}
根据限流维度选择合适的 key 粒度。

降级策略

多级限流

通常在多个层次设置限流：Nginx 层（连接数/IP 限流）→ API Gateway（接口级别）→ 服务内（用户/租户级别）→ 数据库连接池。

拒绝后的处理

返回 429 Too Many Requests，响应头附带 Retry-After 和 X-RateLimit-Remaining，让客户端知道何时可以重试。
