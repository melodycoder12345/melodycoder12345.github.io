信息流系统

信息流系统需要在低延迟和高吞吐之间权衡。推模式（写扩散）降低读延迟但写放大，拉模式（读扩散）减少写压力但读慢，混合模式用粉丝数阈值动态选择策略。

推模式拉模式扇出Timeline
核心术语
  • Push（写扩散）写入时将内容推送到所有粉丝的 Feed Timeline，读取时 O(1) 但写放大 O(N followers)。
  • Pull（读扩散）读取时从所有关注者的内容源聚合，避免写放大但读 O(M followings)。
  • Timeline（时间线）用户的 Feed，通常存在 Redis sorted set，score=timestamp，按时间倒序读取。

背景与机制

微博、Twitter、抖音的 Feed 核心挑战是写扩散和读放大的权衡。大 V 用户（粉丝数百万）如果用纯推模式，每发一条帖子就要写入数百万 sorted set，写放大严重。普通用户粉丝少，用推模式读 O(1) 性价比高。混合策略：粉丝数 < 1000 用 Push，粉丝数 > 1M 用 Pull，中间区间可动态决策。

常见误区

  • 纯推模式在大 V 场景写放大严重，Kafka 消费者来不及处理会导致延迟堆积。
  • 纯拉模式在粉丝多时读聚合慢，需要合并排序 M 个关注者的最新 N 条，复杂度高。
  • Redis sorted set 并非无限大，需要设置 timeline 上限（如最近 1000 条），老数据 ZREMRANGEBYRANK 清除。
  • 混合模式的阈值不是一成不变的，应结合实时流量动态调整。

工程场景

  • Redis sorted set：ZADD feed:{uid} score postId，ZREVRANGE 读最新 N 条
  • Kafka：topic=post_created，FanoutService 按 partition 消费，控制并发度
  • MySQL：follow 表存粉丝关系，大表需要按 uid 分片
  • 冷用户（长时间不登录）不写 Redis，登录时按需从 DB 构建 timeline

边界与恢复

  • 大 V 阈值：一般设 1M~5M 粉丝为 Pull 策略分界点，可灰度测试
  • 扇出并发度：限制每个任务最多并发写 1000 个粉丝 Redis，避免 Redis 热点
  • Timeline 容量上限：sorted set 保留最新 800~1000 条，老数据定期 trim
  • 缓存穿透：冷用户 Redis 不存在时，加互斥锁回源 DB，避免雪崩
