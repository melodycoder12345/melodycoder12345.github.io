可观测性

Metrics（指标）、Logging（日志）、Tracing（链路追踪）是可观测性的三大支柱。Prometheus 负责时序指标采集和告警，OpenTelemetry 标准化链路传播，SLO/SLI 定义服务质量目标和 Error Budget 管理。

Prometheus

拉取模式（Scrape）采集 /metrics 端点，时序数据存入 TSDB（2h 内存块 + 压缩磁盘块），PromQL 做范围查询，Alertmanager 持续评估告警规则。

OpenTelemetry 追踪

traceparent HTTP 头在微服务间传播 traceId/spanId，每个服务创建子 Span 记录耗时，Span 批量上报到 Collector（OTLP），最终写入 Jaeger/Tempo。

SLO & Error Budget

SLO 定义服务质量目标（如 99.9% 可用性），SLI 是度量指标，Error Budget 是允许的故障预算。预算耗尽时冻结发布，恢复后解冻，平衡稳定性与迭代速度。

日志体系：ELK / Loki

Fluentd/Promtail 采集 Pod 日志，ELK 用倒排索引支持全文检索，Loki 用标签索引更轻量。Agent 崩溃从 checkpoint 续传不丢日志，洪峰时背压控制丢弃低优先级日志。

OpenTelemetry

统一 SDK 一次插桩采集 Trace/Metric/Log，Collector Pipeline 批量处理+多 Exporter 扇出，Tail Sampling 等整条 Trace 完成后再决定是否保留，三信号通过 TraceID 关联。

混沌工程

主动注入故障验证系统弹性：定义稳态假说 → 注入 Pod Kill/网络延迟/分区 → 观测偏差 → 修复薄弱点。假说被证伪比假说成立更有价值，提前发现生产隐患。

学习路径建议

先看 Prometheus（Metrics 采集和存储基础）→ Grafana 与告警（将指标可视化并配置告警）→ SLO & Error Budget（指标转化为工程决策）→ 日志体系（日志采集和检索）→ OpenTelemetry（统一三大信号并实现三信号关联）→ 混沌工程（主动验证可观测性覆盖的有效性）。与 System Design 模块的监控系统页面互补，前者偏架构，本模块偏实现机制。
