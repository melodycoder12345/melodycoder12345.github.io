heap profile：alloc vs inuse

key

heap profile 有四个视图，容易混淆：

  • alloc_space：程序运行至今累计分配的总字节数（含已释放），反映 GC 压力
  • alloc_objects：累计分配的总对象数，找高频小对象
  • inuse_space：当前仍在使用的字节数，排查内存泄漏
  • inuse_objects：当前存活的对象数

诊断 GC 频繁看 alloc_space，诊断内存泄漏看 inuse_space。

# 切换 heap profile 视图
(pprof) sample_index = alloc_space
(pprof) sample_index = inuse_space
(pprof) top10

block / mutex profile 开启

adv

block 和 mutex profile 默认关闭，需在代码中显式开启采样率，否则 /debug/pprof/block 始终为空。

func main() {
    // 设为 1 = 所有阻塞事件都采样（开销大，仅调试用）
    // 建议生产设置 runtime.SetBlockProfileRate(10000)
    runtime.SetBlockProfileRate(1)

    // mutex: 1/n 概率采样，推荐 5
    runtime.SetMutexProfileFraction(5)

    // ... 程序逻辑
}

采集方式

net/http/pprof — HTTP 端点注册

core

最常用的方式，import 副作用自动注册路由到 DefaultServeMux。

import (
    "net/http"
    _ "net/http/pprof"  // 副作用导入，自动注册路由
)

func main() {
    // 独立端口，不与业务混用（重要！）
    go http.ListenAndServe("localhost:6060", nil)

    // ... 业务代码
}

注册后可访问的端点：

# 查看所有可用 profile

# 采集 30 秒 CPU profile（阻塞 30s）
http://localhost:6060/debug/pprof/profile?seconds=30

# 当前 heap snapshot
http://localhost:6060/debug/pprof/heap

# goroutine 全量栈（debug=2 输出完整格式）
http://localhost:6060/debug/pprof/goroutine?debug=2

runtime/pprof — 手动采集

core

适合 CLI 工具、批处理程序，或需要精确控制采集时间窗口的场景。

import (
    "os"
    "runtime/pprof"
)

func main() {
    // CPU profile
    f, _ := os.Create("cpu.prof")
    defer f.Close()
    pprof.StartCPUProfile(f)
    defer pprof.StopCPUProfile()

    // ... 需要分析的代码

    // Heap profile（在需要的时刻快照）
    hf, _ := os.Create("mem.prof")
    defer hf.Close()
    runtime.GC()              // 触发 GC，让 inuse 更准确
    pprof.WriteHeapProfile(hf)
}

benchmark 与优化工作流

标准优化循环

core

黄金法则：先度量，再优化，再度量，循环迭代。不要凭感觉优化。

// Step 1: 编写基准测试
func BenchmarkProcessData(b *testing.B) {
    data := generateTestData(10000)
    b.ResetTimer()        // 重置计时器，排除准备时间
    b.ReportAllocs()      // 等同 -benchmem，报告内存分配
    for i := 0; i < b.N; i++ {
        processData(data)
    }
}
# Step 2: 运行基准，采集 profile $ go test -bench=BenchmarkProcessData -benchmem -count=3 \ -cpuprofile=cpu.prof -memprofile=mem.prof ./pkg/...
# Step 3: 分析 CPU 热点 $ go tool pprof -http=:8080 cpu.prof
# Step 4: 分析内存分配 $ go tool pprof -alloc_space -http=:8081 mem.prof
# Step 5: 优化后对比（benchstat 对比多次结果） $ go test -bench=. -count=5 > after.txt $ benchstat before.txt after.txt

-benchmem 指标解读

core 
# 示例输出
BenchmarkFoo-8    500000    2345 ns/op    512 B/op    7 allocs/op
#                          ─────────     ──────────  ──────────────
#                          每次耗时       每次分配字节  每次分配次数

优化目标：减少 allocs/op 比减少 B/op 更重要，因为分配次数直接影响 GC 扫描频率。常见手段：

  • 对象复用：sync.Pool
  • 预分配切片：make([]T, 0, cap)
  • 值类型代替指针类型（逃逸分析）
  • strconv.AppendXxx 代替 FormatXxx

防止编译器消除基准代码

陷阱

如果基准函数的计算结果没有副作用，Go 编译器可能整体消除这段代码，导致基准结果为 0 ns/op（虚假的极快）。需要用 sink 变量保留结果。

// 错误：编译器可能消除 process() 的调用
func BenchmarkBad(b *testing.B) {
    for i := 0; i < b.N; i++ {
        process("data")  // 结果未使用，可能被消除
    }
}

// 正确：全局 sink 变量保留结果
var globalSink string

func BenchmarkGood(b *testing.B) {
    var s string
    for i := 0; i < b.N; i++ {
        s = process("data")
    }
    globalSink = s  // 赋值给全局变量，防止消除
}

testing.B 常用方法

adv 
func BenchmarkFull(b *testing.B) {
    // 并发基准
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            doWork()
        }
    })

    // 子基准（-bench=BenchmarkFull/small）
    b.Run("small", func(b *testing.B) {
        for i := 0; i < b.N; i++ { small() }
    })
    b.Run("large", func(b *testing.B) {
        for i := 0; i < b.N; i++ { large() }
    })

    // 自定义吞吐量指标
    b.SetBytes(1024)  // 报告 MB/s
}

面试题

CPU profile 和 heap profile 分别能诊断什么问题？ ▶
CPU profile 通过每秒 100 次信号中断采集当前调用栈，统计各函数被中断次数来估算 CPU 时间占比，适合诊断 计算热点（哪个函数最耗 CPU）。它不能诊断 I/O 等待、锁阻塞等"不占 CPU 的等待"。

Heap profile 按分配字节采样（默认每 512 KB 采一次），记录分配时的调用栈，适合诊断 内存分配热点、内存泄漏。看 alloc_space 诊断 GC 压力，看 inuse_space 诊断泄漏。
pprof 的采样对性能影响有多大？生产环境能用吗？ ▶
CPU profile 采样频率 100 Hz（10ms 一次），实测额外开销约 3-5%，可在生产使用，但建议按需开启，不要常驻。

Heap profile 按分配字节触发，开销极低（<1%），可长期开启。

需要特别注意的是 goroutine profile 会触发短暂 STW，goroutine 数量多（>10 万）时停顿可能达到毫秒级，在线上要谨慎调用频率。Block/mutex profile 开销取决于设置的采样率，生产环境建议 SetBlockProfileRate(10000)（万分之一采样）。
火焰图中横轴宽度代表什么？如何找到优化点？ ▶
横轴宽度代表该函数（及其所有子调用）在采样周期内占用 CPU 时间的比例，越宽越耗时。纵轴是调用深度，同一列的函数表示调用链。颜色无特殊含义，仅用于区分相邻函数。

找优化点的策略：①找最宽的顶部叶子函数（flat 耗时高，直接优化）；②找宽且"矮"的中间函数（cum 高但 flat 低，说明它调用了很多子函数，拆分后找哪个子调用最宽）；③关注 runtime.mallocgc 和 runtime.gcBgMarkWorker，宽则说明内存分配或 GC 是瓶颈。
alloc_objects 和 inuse_objects 有何区别？ ▶
alloc_objects 是程序启动至今 累计分配 的对象总数，无论是否已被 GC 回收。inuse_objects 是当前时刻 仍存活（未被 GC 回收）的对象数。

两者差值大意味着大量对象被频繁创建又销毁——这正是 GC 压力的来源。可以用 sync.Pool 复用这类短生命周期对象，降低 GC 频率。alloc_objects 高说明分配频繁，优先用 pool 或预分配；inuse_objects 持续增长说明内存泄漏。
如何用 go test 对某个函数做 CPU 性能分析？ ▶
三步走：①写 Benchmark 函数；②用 -bench + -cpuprofile 运行；③用 go tool pprof 分析。

go test -bench=BenchmarkMyFunc -benchmem -cpuprofile=cpu.prof -memprofile=mem.prof -benchtime=10s ./pkg/

-benchtime=10s 让采集时间更长，profile 更准确。然后 go tool pprof -http=:8080 cpu.prof 查看火焰图，用 list BenchmarkMyFunc 查看源码行级热点。注意：go test 会同时生成一个测试二进制，pprof 会自动使用它解析符号。

易错点

✗ 注册 net/http/pprof 但暴露在公网或业务端口
// 错误：pprof 挂到公网业务端口
import _ "net/http/pprof"

func main() {
    // 业务 handler
    http.HandleFunc("/", businessHandler)
    // pprof 也被注册到同一 mux
    http.ListenAndServe(":8080", nil)
}

任何人都能访问 /debug/pprof 获取堆栈信息、环境变量、内存内容，造成敏感数据泄露。

// 正确：独立端口 + 仅监听本地
import _ "net/http/pprof"

func main() {
    // pprof 只监听本地，独立端口
    go http.ListenAndServe(
        "127.0.0.1:6060", nil)

    // 业务使用独立 ServeMux
    mux := http.NewServeMux()
    mux.HandleFunc("/", businessHandler)
    http.ListenAndServe(":8080", mux)
}

通过 SSH 隧道或 kubectl port-forward 访问，永远不要对公网开放。

✗ 只看 inuse heap 误以为没有内存问题
// 现象：inuse_space 很小，但 GC 频繁
// 原因：alloc_space 很大，说明大量短生命
// 周期对象已被回收，但每秒分配数百 MB

# 错误排查方式
$ go tool pprof -inuse_space mem.prof
# 看起来正常，inuse 只有 50MB
# 误以为没有内存问题

GC 日志显示每秒触发数十次 GC，但只看 inuse 得出"内存没问题"的错误结论。

# 正确：同时看 alloc_space
$ go tool pprof -alloc_space mem.prof
(pprof) top10
# 发现 json.Marshal 累计分配 10 GB
# 优化：复用 encoder 或使用 json.NewEncoder

# 开启 GC trace 验证
$ GODEBUG=gctrace=1 ./myapp 2>&1 | head -20
# gc 1 @0.003s: ...  显示 GC 频率

分配频繁是 GC 的根本原因，要同时关注 alloc_space 和 alloc_objects。

✗ benchmark 没有防止编译器消除无副作用代码
// 错误：结果未使用，编译器消除
func BenchmarkHash(b *testing.B) {
    data := []byte("hello world")
    for i := 0; i < b.N; i++ {
        sha256.Sum256(data) // 结果丢弃！
    }
}
# 输出: 0.3 ns/op — 虚假的极快
// 正确：全局 sink 保留结果
var sink [32]byte

func BenchmarkHash(b *testing.B) {
    data := []byte("hello world")
    for i := 0; i < b.N; i++ {
        sink = sha256.Sum256(data)
    }
}
# 输出: 312 ns/op — 真实结果

全局变量赋值有副作用，编译器不会消除。sink 类型需与函数返回值匹配。
