Pool 基础

Get / Put / New

[核心]

sync.Pool 是一个临时对象池，用于缓存分配好的对象，减少 GC 压力。不保证对象持久存在，GC 时会被清空。

  • Get() — 从池中取对象，若池空则调用 New 创建
  • Put(x) — 将对象归还池，nil 被忽略
  • New func() any — 池空时的工厂函数，应返回同类型对象
  • Pool 是并发安全的，每个 P 有本地缓存，减少竞争
var bufPool = &sync.Pool{
    New: func() any {
        return bytes.NewBuffer(make([]byte, 0, 1024))
    },
}

func process(data []byte) {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()           // 重置状态
        bufPool.Put(buf)     // 归还
    }()
    buf.Write(data)
    // 使用 buf...
}

GC 清理时机

每次 GC 时 Pool 被清空

[进阶]

sync.Pool 中的对象在每次 GC 时会被全部清空（通过 poolCleanup 注册为 GC 清理函数），不能依赖 Pool 跨 GC 保存状态。

  • Go 1.13+ 优化：引入 victim cache，GC 时对象先移到 victim，下次 GC 才真正清除，减少抖动
  • Pool 不适合管理需要显式关闭的资源（连接、文件），那是连接池的职责
  • 高 GC 频率场景（内存紧张）下 Pool 效果会下降
// Pool 内部 GC 钩子（简化）
func init() {
    runtime.SetFinalizer(...) // 非实际 API
}
// 实际上通过 runtime.registerPoolCleanup
// 在每次 STW 开始时清空所有 Pool local 缓存
// Go 1.13+: local → victim → 释放（两个 GC 周期）

// 验证 Pool 对象被 GC 清空
p.Put(&obj{})
runtime.GC()              // 触发 GC
got := p.Get()            // 可能拿到 nil 或新对象

典型使用场景

[]byte buffer 与临时对象复用

[核心]

Pool 最适合生命周期短、分配频繁、同类型的临时对象，能显著降低 GC 压力（如 HTTP 处理时每个请求的序列化 buffer）。

  • fmt 包用 Pool 缓存格式化 buffer
  • encoding/json、net/http 内部大量使用 Pool
  • 与预分配对比：Pool 更灵活，预分配（slice）更可预测
  • 对象大小变化大时（有时 1KB 有时 1MB），Pool 可能导致内存占用升高
// 标准库的 fmt 包使用方式
var ppFree = sync.Pool{
    New: func() any { return new(pp) },
}

func newPrinter() *pp {
    p := ppFree.Get().(*pp)
    p.panicking = false
    p.erroring = false
    p.wrapErrs = false
    p.fmt.init(&p.buf)
    return p
}

反模式

不应使用 Pool 的场景

[核心]

Pool 是临时缓存，不是通用对象池或连接池，以下场景不应使用 Pool。

  • 长生命周期对象：数据库连接、gRPC 连接，应用连接池（有 MaxIdle、健康检查等）
  • 有状态对象归还前未 Reset：下一个 Get 会拿到脏数据
  • 需要固定数量限制：Pool 大小不可控；用 buffered channel 做令牌池
  • 跨请求传递上下文：Pool 对象可能被任意 goroutine 取走
// 固定大小的工作者池（用 channel）
type WorkerPool struct {
    tokens chan struct{}
}
func NewWorkerPool(n int) *WorkerPool {
    ch := make(chan struct{}, n)
    for i := 0; i < n; i++ { ch <- struct{}{} }
    return &WorkerPool{tokens: ch}
}
func (p *WorkerPool) Acquire() { <-p.tokens }
func (p *WorkerPool) Release() { p.tokens <- struct{}{} }

面试问答

Pool 里的对象什么时候被 GC？▶
每次 GC 触发时，runtime 会调用所有已注册 Pool 的清理函数。Go 1.13+ 使用 victim cache 机制：第一次 GC 时，Pool 的 local 缓存移到 victim；第二次 GC 时 victim 才被真正清空。这样两次 GC 之间对象有机会被重新取出，减少了短暂 GC 抖动导致的对象重建开销。
Get 时没有可用对象怎么办？▶
若 Pool 为空（本地缓存和 victim 均无对象），Get 会调用 Pool.New 函数创建新对象。若 New 为 nil，Get 返回 nil。因此推荐始终设置 New 函数，且 Get 后需做类型断言。Get 的查找顺序：当前 P 的本地缓存 → 其他 P 的缓存（steal）→ victim cache → 调用 New。
Pool 适合哪些场景，不适合哪些场景？▶
适合：短生命周期、分配频繁、对象大小稳定的临时对象，如序列化 buffer、格式化 buffer、临时 struct。不适合：需要固定数量限制（用 buffered channel）；有外部资源的对象（连接、文件，用专门的连接池）；需要跨请求保存状态的对象；对象大小变化极大的场景（可能造成内存占用暴涨）。
Pool 的底层实现是怎样的？▶
每个 P（处理器）有一个 poolLocal，包含本地 private 缓存（单对象，无锁）和 shared 双端队列（可被其他 P 偷取）。Get 优先从 private 取，其次从本地 shared 取，再从其他 P 的 shared 偷取，最后从 victim 取。Put 优先放入 private，若 private 已有则放 shared。这种分 P 的设计避免了全局锁竞争。
如何正确使用 Pool 避免内存泄漏？▶
关键三点：1) 只有对象适合复用时才 Put 回；Put 不是 Get 后的强制配对操作，过大或不再需要的对象可直接丢弃；2) 决定 Put 时先 Reset 对象状态；3) 不要 Put 持有外部资源引用的对象。若对象持有大 buffer 且场景稀疏，可不归还或限制容量，避免 Pool 持有大内存。

常见陷阱

❌ Put 了带状态的对象（vs ✅ Reset 后再 Put）
func handle() {
    buf := pool.Get().(*bytes.Buffer)
    buf.WriteString("secret data")
    respond(buf)
    pool.Put(buf) // 带有 "secret data"！
}
// 下个请求 Get 到同一 buf
// 内含上次的数据，可能信息泄露

未 Reset 直接 Put，下一个取走者会读到脏数据，甚至造成信息泄露。

func handle() {
    buf := pool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()      // 先清空
        pool.Put(buf)  // 再归还
    }()
    buf.WriteString("secret data")
    respond(buf)
}

defer 中先 Reset 再 Put，保证归还的对象是干净状态。

❌ 依赖 Pool 保存长期对象（vs ✅ 用连接池）
// 错误：依赖 Pool 缓存 DB 连接
var connPool = &sync.Pool{
    New: func() any {
        c, _ := sql.Open("mysql", dsn)
        return c
    },
}
// GC 后所有连接丢失，
// 下次请求重新建连，延迟剧增

GC 会清空 Pool，连接资源丢失，且连接不会被 Close，造成资源泄漏。

// 正确：用 database/sql 自带连接池
db, _ := sql.Open("mysql", dsn)
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(10)
db.SetConnMaxLifetime(5 * time.Minute)
// database/sql 管理连接生命周期

数据库、HTTP、gRPC 连接应使用专门的连接池管理，有完整的生命周期控制。

❌ Pool 中存储大 buffer 后不缩容（vs ✅ 检查 cap 再归还）
// 某次请求分配了 100MB buffer
func handle(big []byte) {
    buf := pool.Get().([]byte)
    buf = append(buf, big...) // 扩容到 100MB
    use(buf)
    pool.Put(buf[:0])  // 归还 100MB slice
}

100MB 的 slice 被 Pool 持有，即使只需要 1KB，Pool 也一直占用大内存。

// 超过阈值则丢弃，不归还
func handle(big []byte) {
    buf := pool.Get().([]byte)
    buf = append(buf, big...)
    use(buf)
    if cap(buf) < 64<<10 { // 64KB 以下
        pool.Put(buf[:0])
    }
    // 超大的 buf 直接丢弃，让 GC 回收
}

对超出阈值的大 buffer 不归还，防止 Pool 长期持有大量内存。
