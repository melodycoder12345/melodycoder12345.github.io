面试题

什么是数据竞争（data race）？▶
当两个 goroutine 并发访问同一内存位置，且至少一个是写操作，且没有同步机制（mutex、channel、atomic）时，发生数据竞争。数据竞争是未定义行为——结果不可预测，可能读到任何值，甚至破坏内存。用 go run -race 或 go test -race 检测（race detector）。
happens-before 关系是什么？▶
Go 内存模型定义：如果事件 A happens-before 事件 B，则 B 能看到 A 的所有内存写入。建立 happens-before 的机制：
① 同一 goroutine 内的语句顺序
② channel send happens-before receive
③ sync.Mutex Unlock happens-before Lock
④ sync.WaitGroup Wait happens-before Done 的 goroutine 结束
⑤ init 函数 happens-before main
sync/atomic 和 mutex 如何选择？▶
使用 atomic：操作是单个 int/uint/pointer 的读写，适合计数器、标志位、状态机。
使用 mutex：操作涉及多个字段的复合更新（需要原子性地更新一组值），或需要保护复杂数据结构（map、slice）。
经验法则：简单计数器/标志用 atomic，复合操作/保护结构体用 mutex。不要为了追求性能滥用 atomic——错误使用比 mutex 更难调试。
为什么需要 sync/atomic.StoreInt64 而不直接赋值？▶
在 64 位平台，64 位整数的读写通常是原子的，但：① 不是所有平台都保证（32 位平台 int64 可能需要两次内存操作）；② 编译器/CPU 可能对内存访问重排序（指令重排、store buffer）；③ 没有 happens-before 保证，其他 goroutine 可能看不到最新值。atomic.Store/Load 提供内存屏障，确保可见性和有序性。

易错点

❌ 以为 Go 的 i++ 是原子的
var counter int
for i := 0; i < 1000; i++ {
    go func() {
        counter++ // 数据竞争！
        // 读-改-写 三步非原子
        // 并发执行会丢失更新
    }()
}
// 最终 counter 通常 < 1000
// 方案1: atomic
var counter atomic.Int64
go func() { counter.Add(1) }()

// 方案2: mutex
var mu sync.Mutex
var counter int
go func() {
    mu.Lock()
    counter++
    mu.Unlock()
}()

i++ 是读-改-写三步操作，不是原子的，必须用 atomic 或 mutex 保护。

❌ 用普通变量做并发标志
var done bool  // 普通变量！

go func() {
    work()
    done = true  // 写（无 happens-before）
}()

for !done {     // 读（可能看不到写）
    time.Sleep(time.Millisecond)
    // CPU 可能把 !done 优化成 for true
    // 因为它"知道"本 goroutine 没改变 done
}
// 方案1: atomic.Bool (Go 1.19+)
var done atomic.Bool
go func() { work(); done.Store(true) }()
for !done.Load() { runtime.Gosched() }

// 方案2: channel（推荐）
done := make(chan struct{})
go func() { work(); close(done) }()
<-done  // 等待，不忙等

并发标志必须用 atomic 或 channel，否则可能产生数据竞争或对编译器优化不可见。
