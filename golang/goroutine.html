面试题

goroutine 和 OS 线程的区别？▶
goroutine 是用户态轻量线程：初始栈 2KB（线程 ~2MB），可按需增长到 1GB；调度由 Go runtime 管理，不需要系统调用；切换代价 ~100ns（线程 ~1μs）。单个 Go 程序可轻松运行百万 goroutine。
goroutine 泄漏的常见原因有哪些？▶
① channel 阻塞：发送/接收无对端且没有退出路径
② 死锁：多 goroutine 互相等待
③ select 无 default/无 done channel
④ sync.WaitGroup 未调用 Done
⑤ 无限循环没有退出条件

诊断工具：runtime.NumGoroutine()，pprof goroutine 分析，go tool trace。
如何优雅地停止一个 goroutine？▶
不能从外部强制终止（没有 goroutine ID 和 kill 接口）。正确方式：
① context.WithCancel：传入 ctx，定期检查 ctx.Done()
② done channel：发送信号，goroutine 选择退出
③ 关闭 input channel：goroutine range 自动退出
设计原则：goroutine 的创建者负责确保它能退出。
goroutine 的栈如何增长和收缩？▶
初始栈 2KB，编译器在每个函数调用处插入栈检查代码。栈不够时申请 2 倍大的新栈，将旧栈内容复制过去（"栈拷贝"策略，已替换旧的"分段栈"）。GC 时栈会检查是否可以缩减至 1/4 大小（若实际使用远小于当前大小）。
context.WithCancel 和 context.WithTimeout 的区别？▶
WithCancel：手动调用 cancel() 取消，适合主动控制生命周期。
WithTimeout(d)：d 时间后自动取消，等效于 WithDeadline(time.Now().Add(d))。
两者都会向整个 context 树传播取消信号，子 context 也会被取消。
最佳实践：defer cancel() 防止资源泄漏（即使 context 已超时，也需要 cancel 释放关联资源）。
GOMAXPROCS 是什么？如何设置？▶
GOMAXPROCS 控制同时执行 Go 代码的 OS 线程数（即 P 的数量）。默认等于 CPU 核心数。设置方式：runtime.GOMAXPROCS(n) 或环境变量 GOMAXPROCS=n。对于 CPU 密集型任务，等于核数最优；IO 密集型任务，可以适当调大；容器环境下需注意 cgroup CPU 限制与物理核心数的差异（推荐 automaxprocs 库）。

易错点

❌ 循环变量捕获（经典陷阱）
for i := 0; i < 5; i++ {
    go func() {
        fmt.Println(i) // 捕获的是 i 的引用
        // 可能全部打印 5
    }()
}
time.Sleep(time.Second)
for i := 0; i < 5; i++ {
    i := i // 创建副本
    go func() {
        fmt.Println(i) // 捕获副本
    }()
}
// 或 Go 1.22+ 循环变量语义变更，
// 每次迭代自动创建新变量

Go 1.22 起 for 循环变量语义已修正，每次迭代创建新变量，旧代码注意兼容性。

❌ 未等待 goroutine 完成就返回
func process(items []Item) {
    for _, item := range items {
        go handle(item)
    }
    // main 函数 return，goroutine 被强制终止
    return
}
func process(items []Item) {
    var wg sync.WaitGroup
    for _, item := range items {
        wg.Add(1)
        go func(it Item) {
            defer wg.Done()
            handle(it)
        }(item)
    }
    wg.Wait() // 等所有 goroutine 完成
}

用 sync.WaitGroup 或 errgroup.Group 等待所有 goroutine 完成。

❌ 忘记 defer cancel() 导致 context 泄漏
func doWork() {
    ctx, cancel := context.WithTimeout(
        context.Background(), 5*time.Second)
    // 忘记 cancel()
    // context 资源直到超时才释放
    result := fetch(ctx)
    return result
}
func doWork() {
    ctx, cancel := context.WithTimeout(
        context.Background(), 5*time.Second)
    defer cancel() // 始终调用！
    // 即使提前 return 也会释放资源
    result := fetch(ctx)
    return result
}

WithCancel/WithTimeout 创建的 cancel 函数必须调用，否则 context 相关的 goroutine 和 timer 资源不会释放。

❌ goroutine 中 panic 未被 recover
func main() {
    go func() {
        panic("boom") // 终止整个程序！
    }()
    // 主 goroutine 无法 recover
    // 子 goroutine 的 panic
    time.Sleep(time.Second)
}
func safeGo(f func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("recovered: %v", r)
            }
        }()
        f()
    }()
}

// 使用
safeGo(func() { /* 业务逻辑 */ })

每个 goroutine 需要自己 recover。可封装 safeGo 工具函数统一处理。
