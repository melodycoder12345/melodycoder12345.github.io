go.mod 基础

module 路径、Go 版本、require

[核心]

go.mod 是模块的清单文件，定义模块路径、Go 版本要求和直接依赖。go.sum 存储依赖的加密哈希，两者都必须提交到版本控制。

  • module — 当前模块的规范导入路径（通常为代码仓库 URL）
  • go — 指定最低 Go 版本，影响语言特性和工具链行为
  • require — 直接和间接依赖（间接依赖有 // indirect 注释）
  • replace — 替换模块路径或版本，用于本地开发
  • exclude — 排除特定版本（有已知 bug 时使用）
// go.mod 示例
module github.com/myorg/myapp

go 1.22

require (
    github.com/gin-gonic/gin v1.9.1
    golang.org/x/sync v0.6.0
    github.com/stretchr/testify v1.9.0 // indirect
)

replace github.com/myorg/shared => ../shared

版本语义

Semver、v2+ 路径、间接依赖

[核心]

Go modules 使用语义化版本（semver）。v2 及以上的模块需要在 import 路径中加 /v2 后缀，这是重大设计决定（Import Compatibility Rule）。

  • v1.2.3 — major.minor.patch；major 变化表示不兼容
  • v2+ 模块：module github.com/foo/bar/v2，导入时也加 /v2
  • 最小版本选择（MVS）：Go 选择满足所有要求的最低版本，而非最新版
  • 间接依赖：不在本模块代码中直接 import，但被依赖的依赖所需要
  • 伪版本：v0.0.0-20230101120000-abcdef012345 用于没有 tag 的 commit
// 使用 v2 模块
import "gopkg.in/yaml.v3"
import "github.com/go-redis/redis/v9"

// 查看依赖图
$ go mod graph
$ go list -m all          # 查看所有依赖版本
$ go list -m -versions github.com/gin-gonic/gin
                          # 查看可用版本

常用命令

go get / go mod tidy / go mod vendor

[核心]

日常开发最常用的 module 管理命令，每个都有明确职责。

  • go get pkg@v1.2.3 — 添加/升级依赖到指定版本；@latest 获取最新
  • go get pkg@none — 移除依赖
  • go mod tidy — 添加缺失依赖、删除无用依赖，更新 go.sum；应在 CI 中验证
  • go mod vendor — 将依赖复制到 vendor/，用于离线构建或审计
  • go mod download — 下载依赖到本地缓存（不修改 go.mod）
  • go mod verify — 验证依赖的 hash 与 go.sum 一致
# 添加新依赖
$ go get github.com/pkg/errors@v0.9.1

# 升级所有直接依赖到最新 minor/patch
$ go get -u ./...

# 仅升级 patch 版本
$ go get -u=patch ./...

# 清理 go.mod 和 go.sum
$ go mod tidy

# CI 验证 go.mod 是否是最新的
$ go mod tidy && git diff --exit-code go.mod go.sum

Workspace 模式

go.work 与多模块本地开发

[进阶]

Go 1.18+ 引入 workspace 模式（go.work），解决本地同时开发多个相互依赖模块时，需要频繁修改 replace 指令的痛点。

  • go work init [./mod1 ./mod2] — 创建 go.work 文件
  • go work use ./newmod — 添加模块到 workspace
  • go.work 文件不应提交到版本控制（仅用于本地开发）
  • 设置 GOWORK=off 禁用 workspace 模式
  • workspace 中的模块互相引用时使用本地版本，无需 replace
// go.work 示例
go 1.22

use (
    ./myapp
    ./shared-lib
    ./another-service
)

// 使用方法
$ cd ~/projects
$ go work init ./myapp ./shared-lib
// 现在 myapp 对 shared-lib 的 import
// 会使用本地版本，无需在 go.mod 中 replace

// .gitignore 中添加：
// go.work
// go.work.sum

面试问答

replace 指令的作用？什么情况下使用？▶
replace 将一个模块（或特定版本）替换为另一个路径或版本。用途：1) 本地开发：将依赖的远程模块替换为本地目录（调试时修改依赖）；2) Fork 修复：将问题模块替换为自己 fork 的版本；3) 私有镜像：将公开模块路径替换为内部仓库。注意：replace 对依赖的依赖不生效（只对当前模块有效）；replace 到本地路径不应合并到生产分支，应在开发完成后提交 PR 到上游再去掉 replace。
go mod tidy 做了什么？▶
go mod tidy 做两件事：1) 扫描当前模块所有 .go 文件的 import，添加缺失的依赖到 go.mod；2) 删除 go.mod 中有但代码中未使用的依赖。同时更新 go.sum（添加新依赖的 hash，移除无用 hash）。最佳实践：每次添加/删除 import 后运行 tidy，在 CI 中验证 go.mod 和 go.sum 是最新状态（go mod tidy && git diff --exit-code）。
间接依赖是什么？为什么出现在 go.mod 中？▶
间接依赖（// indirect）是本模块代码没有直接 import，但依赖链中需要的模块。出现在 go.mod 有两种情况：1) 依赖模块的 go.mod 不完整（如老版本格式），Go 工具链需要在当前 go.mod 中显式记录版本；2) 为了确保版本选择的确定性，某些情况下需要固定间接依赖的版本。运行 go mod tidy 会将真正不需要的间接依赖移除，并补全必要的间接依赖。
Go modules 的最小版本选择（MVS）是什么？▶
MVS（Minimum Version Selection）是 Go 选择依赖版本的算法：在所有依赖（直接和间接）声明的版本要求中，选择满足所有要求的最低版本。例如 A 要求 C v1.2，B 要求 C v1.3，则选 C v1.3（最低满足所有要求的版本）。这与 npm 等工具的"选最新"策略不同，MVS 保证了构建的可重现性：同样的 go.mod 产生同样的依赖图，不受新版本发布影响，除非显式 go get 升级。
go.sum 的作用是什么？可以删除重新生成吗？▶
go.sum 存储每个依赖模块的加密哈希（SHA-256），用于验证下载内容与预期一致，防止供应链攻击（模块内容被篡改）。go.sum 必须提交到版本控制，否则其他开发者和 CI 无法验证依赖完整性。可以删除后重新生成（go mod download 或 go mod tidy），但这会重新从网络获取 hash，期间存在（极小的）风险。正确做法：永远不要手动删除 go.sum，若内容损坏，确认来源安全后再重新生成。

常见陷阱

❌ 删除 go.sum 后重新生成（vs ✅ 提交并维护 go.sum）
# 在 .gitignore 中添加了 go.sum
# 或手动删除后重新生成
$ rm go.sum
$ go mod tidy
# go.sum 内容依赖当时的网络状态
# 不同时间生成可能不同
# 失去了供应链保护

go.sum 是安全校验文件，删除会失去对依赖内容变化的检测能力。

# 正确：始终提交 go.sum
$ git add go.mod go.sum
$ git commit -m "add dependency"

# CI 验证 go.sum 完整
$ go mod verify
all modules verified

# 若需要更新，明确运行
$ go mod tidy && git add go.sum

go.sum 必须随 go.mod 一起提交，CI 用 go mod verify 验证完整性。

❌ replace 指令遗留在生产代码中（vs ✅ 仅用于本地开发）
// go.mod 提交了本地 replace
replace (
    github.com/myorg/lib => ../lib
)
// CI 构建失败：找不到 ../lib
// 其他开发者克隆后无法构建

指向本地相对路径的 replace 提交到代码库，导致他人和 CI 构建失败。

// 方案1：用 workspace 替代 replace（本地开发）
$ go work init . ../lib
// go.work 加入 .gitignore

// 方案2：replace 指向版本化路径（可提交）
replace github.com/bad/pkg v1.0.0 =>
    github.com/myfork/pkg v1.0.1-fix

用 workspace 处理本地开发；replace 只在指向远程仓库时才可提交。

❌ go.mod 中 go 版本过低导致行为差异（vs ✅ 及时更新 go 指令）
// go.mod 仍声明 go 1.16
module myapp

go 1.16

// 但代码使用了 Go 1.21+ 特性
// 或期望 Go 1.22 的循环变量语义
// 构建成功，但行为与预期不同

go 指令版本过低，无法获得新版本的语言特性（如 1.22 的循环变量语义）。

// 更新到团队实际使用的 Go 版本
module myapp

go 1.22

// 使用 toolchain 指令（Go 1.21+）
// 指定推荐的工具链版本
toolchain go1.22.3

// 定期更新：
$ go get go@1.22

go 指令应与团队实际使用的版本一致；Go 1.21+ 可用 toolchain 指令精确指定。
