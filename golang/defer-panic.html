defer 执行顺序

LIFO + 参数在 defer 处求值

核心

defer 语句将函数调用压入一个栈（LIFO）。函数返回时，defer 按后进先出的顺序执行。defer 语句中的函数参数在 defer 登记时立即求值。

func demo() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
    fmt.Println("executing")
}
// 输出：executing → 3 → 2 → 1

// 参数求值时机：defer 处立即求值
x := 0
defer fmt.Println(x)  // x 此时为 0，打印 0
x = 5
// 函数返回时执行 defer，打印 0（已记录的值）

// 闭包：捕获引用，执行时求值
y := 0
defer func() { fmt.Println(y) }()  // 打印 5
y = 5

defer 常见用法

资源清理、解锁、计时

核心

defer 最常用于确保资源释放，即使发生错误也能正确清理。

// 1. 关闭文件
f, err := os.Open("file.txt")
if err != nil { return err }
defer f.Close()  // 保证关闭

// 2. 解锁 mutex
mu.Lock()
defer mu.Unlock()

// 3. 计时函数
func timeFunc(name string) func() {
    start := time.Now()
    return func() {
        fmt.Printf("%s took %v\n", name, time.Since(start))
    }
}
defer timeFunc("myFunc")()  // 注意两个括号！

// 4. 修改命名返回值
func doWork() (err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("doWork: %w", err)
        }
    }()
    return riskyOp()
}

panic 传播

栈展开与终止程序

核心

panic 触发后，运行时开始展开（unwind）当前 goroutine 的调用栈：

1
当前函数停止执行，运行所有已注册的 defer
2
调用方同样停止，运行其 defer，继续向上展开
3
如果某个 defer 中调用了 recover()，panic 被捕获，程序继续
4
如果到达 goroutine 顶端仍未被 recover，打印 panic 信息和堆栈，程序终止
// panic 接受任意类型
panic("something went wrong")
panic(fmt.Errorf("error: %v", err))
panic(42)  // 任意类型

// 运行时 panic（自动触发）
// - 数组/slice 越界
// - nil 指针解引用
// - 向关闭的 channel 发送数据
// - 类型断言失败（单值形式）
// - 除以零（整数）

panic + recover

recover 的使用限制与 safeGo 模式

进阶

recover 的关键限制：只能在 defer 函数中直接调用才有效，且只对当前 goroutine 的 panic 有效。跨 goroutine 的 panic 无法被 recover。

// recover 必须在 defer 内直接调用
func safeRun(f func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    f()
    return nil
}

// safeGo 模式：保护 goroutine 不因 panic 崩溃
func safeGo(f func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("goroutine panic: %v\n%s", r,
                    debug.Stack())
            }
        }()
        f()
    }()
}

// ❌ 跨 goroutine 无法 recover
func main() {
    defer func() {
        if r := recover(); r != nil {
            // 无法捕获子 goroutine 的 panic
        }
    }()
    go func() { panic("goroutine panic") }()
    time.Sleep(time.Second)
    // 程序仍然崩溃！
}

面试题

defer 在 return 前还是后执行？▶
精确说法：defer 在函数设置返回值之后、实际返回调用方之前执行。

Go 的 return 语句拆解为两个步骤：
1. 将返回值写入返回值变量
2. 执行所有 defer
3. 实际跳转返回（携带返回值）

这就是为什么 defer 可以修改命名返回值：
func f() (result int) { defer func() { result++ }(); return 1 }
这里 return 1 先把 result 设为 1，然后 defer 把 result 改为 2，函数返回 2。
defer 如何修改命名返回值？▶
只有命名返回值可以被 defer 中的闭包修改。工作原理：
• 命名返回值是一个具名变量，存在于函数的作用域中
• defer 中的闭包捕获了这个变量的引用
• 由于 defer 在 return 设置返回值之后执行，所以可以修改最终返回的值

典型用法：统一添加错误上下文、panic recovery 转换为 error：
func doWork() (err error) {
  defer func() { if err != nil { err = fmt.Errorf("wrap: %w", err) } }()
  ...}
recover 的使用场景和注意事项？▶
使用场景：
1. HTTP 服务器：防止某个 handler 的 panic 导致整个服务崩溃
2. 测试框架：捕获测试代码中的 panic
3. 插件系统：隔离第三方代码的 panic
4. 库边界：将内部 panic 转换为 error 暴露给调用方

注意事项：
• recover 只能在 defer 函数内直接调用，defer recover() 是无效的（没有赋值操作）
• 只对当前 goroutine 有效，跨 goroutine 无法捕获
• recover 的返回值是 panic 时传入的值，类型是 interface{}
• 捕获后要记录日志/堆栈信息，避免静默吞掉错误
defer 在循环中调用有什么问题？▶
循环中的 defer 会累积到整个函数返回时才执行，不是每次迭代后执行。这可能导致：
1. 资源占用：循环 1000 次打开文件，所有文件在循环结束后才关闭，同时持有 1000 个文件描述符
2. 内存占用：defer 参数/闭包被暂存

解决方案：
1. 将循环体提取为独立函数，在函数中 defer
2. 改为显式关闭：不用 defer，在每次迭代末尾手动调用 Close()

for _, file := range files {
  func() { f, _ := os.Open(file); defer f.Close(); process(f) }()
}
panic(nil) 和 panic(error) 有什么区别？（Go 1.21 新变化）▶
Go 1.21 之前：panic(nil) 后，recover() 返回 nil，无法区分"没有 panic"和"panic(nil)"这两种情况。

Go 1.21+：引入 runtime/panicdepth 机制，recover() 在捕获 panic(nil) 时返回一个 *runtime.PanicNilError，而不是 nil，从而可以区分。

检查是否有 panic：if r := recover(); r != nil { ... } 在 Go 1.21+ 可以可靠地检测到所有 panic（包括 panic(nil)）。

建议：避免使用 panic(nil)，改用 panic(errors.New("..."))，语义更清晰。

易错点

❌ 循环中 defer 资源泄漏
func processFiles(files []string) {
    for _, name := range files {
        f, err := os.Open(name)
        if err != nil { continue }
        defer f.Close()  // ❌ 不会每次迭代执行
        process(f)
    }
    // 函数返回时才关闭所有文件
    // 循环中同时持有所有文件句柄
}

defer 属于函数级别，不是循环级别。循环内所有 defer 到函数返回才执行。

func processFiles(files []string) {
    for _, name := range files {
        // ✓ 提取为独立函数
        if err := processFile(name); err != nil {
            log.Println(err)
        }
    }
}
func processFile(name string) error {
    f, err := os.Open(name)
    if err != nil { return err }
    defer f.Close()  // ✓ 函数返回时关闭
    return process(f)
}

将循环体提取为独立函数，每次调用后 defer 正确执行。

❌ defer 参数求值时机误解
func bad() {
    start := time.Now()
    defer log.Println(
        "elapsed:", time.Since(start))
    // time.Since(start) 在 defer 语句
    // 处被求值（约 0ns），而非返回时
    time.Sleep(100 * time.Millisecond)
}

defer 的函数参数（非闭包）在 defer 语句处立即求值，不是函数返回时。

func good() {
    start := time.Now()
    defer func() {
        log.Println(
            "elapsed:", time.Since(start))
        // 函数返回时才执行，计时正确
    }()
    time.Sleep(100 * time.Millisecond)
    // 打印约 100ms
}

需要在函数返回时才求值的逻辑，用 defer func() { ... }() 包装成闭包。

❌ recover 在非 defer 直接调用中无效
func bad() {
    defer recover()  // ❌ 无效！
    // recover() 的返回值被丢弃
    // 等价于 defer func(){ recover() }()
    // 但即使这样写也有问题

    defer myRecovery()  // ❌ 间接调用无效
    panic("oops")       // 仍然会崩溃
}
func myRecovery() { recover() }  // 间接调用

recover 必须在 defer 内直接调用才能捕获 panic，间接调用无效。

func good() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("recovered: %v", r)
        }
    }()  // ✓ defer 内直接调用 recover
    panic("oops")  // 被捕获，程序继续
}

// recover 返回 panic 传入的值
// 可以进一步转换为 error

recover 必须 defer func() { if r := recover(); r != nil { ... } }() 这种模式。
