errgroup 基础

Group.Go / Group.Wait

[核心]

errgroup 是 golang.org/x/sync 包提供的结构化并发工具，在 WaitGroup 基础上增加了错误收集和context 取消能力。

  • g.Go(func() error) — 启动 goroutine，自动计数
  • g.Wait() — 等待所有 goroutine 完成，返回第一个非 nil error
  • 发生第一个错误时，context 被取消（需用 WithContext）
  • 其他 goroutine 应通过 ctx 感知取消并提前退出
import "golang.org/x/sync/errgroup"

g := new(errgroup.Group)

g.Go(func() error {
    return fetchUserData()
})
g.Go(func() error {
    return fetchOrderData()
})

if err := g.Wait(); err != nil {
    return fmt.Errorf("fetch failed: %w", err)
}

与 WaitGroup 对比

错误传播与代码简洁性

[核心]

WaitGroup 不提供错误传播机制，需要额外的 channel 或 mutex 收集错误；errgroup 将这些模式封装好了。

  • WaitGroup：需手动 Add/Done，需 channel 收集错误，需检查 channel
  • errgroup：自动 Add/Done，Wait 直接返回第一个错误，代码更简洁
  • errgroup 只返回第一个错误，若需要所有错误则仍需自定义收集
// WaitGroup 版本（繁琐）
var wg sync.WaitGroup
errc := make(chan error, 2)
wg.Add(2)
go func() { defer wg.Done(); errc <- f1() }()
go func() { defer wg.Done(); errc <- f2() }()
wg.Wait()
close(errc)
for err := range errc {
    if err != nil { return err }
}

context 传播

errgroup.WithContext

[进阶]

使用 errgroup.WithContext 获得可取消的 context，任何一个 goroutine 返回错误时，ctx 会被 cancel，其他 goroutine 可通过 ctx.Done() 感知并提前退出。

  • ctx 在 Wait 返回后无论成功还是失败都会被 cancel（cleanup）
  • goroutine 内应将 ctx 传给所有 I/O 操作（http.NewRequestWithContext 等）
  • 父 ctx 被 cancel 时，衍生的 errgroup ctx 也会取消
g, ctx := errgroup.WithContext(context.Background())

urls := []string{"http://a.com", "http://b.com"}
for _, url := range urls {
    url := url // 捕获循环变量
    g.Go(func() error {
        req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
        resp, err := http.DefaultClient.Do(req)
        if err != nil { return err }
        defer resp.Body.Close()
        return process(resp)
    })
}
return g.Wait()

实际应用模式

并行请求与限流

[进阶]

errgroup 本身不限制并发数，需要搭配 semaphore（信号量）实现并发限流。

  • 用 golang.org/x/sync/semaphore 限制最大并发 goroutine 数
  • 或用 buffered channel 作为简单信号量
  • 结构化并发：所有 goroutine 的生命周期都被 Wait 管理，不泄漏
// 限制最多 3 个并发
g, ctx := errgroup.WithContext(parentCtx)
sem := make(chan struct{}, 3)

for _, item := range items {
    item := item
    sem <- struct{}{}     // 获取令牌（阻塞）
    g.Go(func() error {
        defer func() { <-sem }() // 释放令牌
        return process(ctx, item)
    })
}
return g.Wait()

面试问答

errgroup 和 WaitGroup 的主要区别？▶
主要有三点区别：1) 错误处理：WaitGroup 无内建错误传播，errgroup 的 Wait() 返回第一个错误；2) Context 集成：errgroup.WithContext 在首个错误发生时自动取消 ctx，WaitGroup 没有这个功能；3) API 简洁性：errgroup.Go 自动管理计数，无需手动 Add/Done。缺点：errgroup 只保留第一个错误，若需要收集所有错误需要自定义。
errgroup.Wait 返回什么错误？如果多个 goroutine 都返回了错误呢？▶
Wait 只返回所有 goroutine 中第一个返回的非 nil 错误。若多个 goroutine 都返回了错误，后续的错误会被丢弃。这是通过 sync.Once 实现的：第一个错误触发 once.Do，后续错误不再更新。如果业务需要所有错误，可以在闭包外用 slice + mutex 自行收集，然后 g.Go 返回 nil 或哨兵错误。
如何用 errgroup 限制并发数？▶
errgroup 本身不支持并发限制。常用两种方案：1) buffered channel 作信号量：在循环中先向 channel 发送令牌（阻塞），goroutine 完成时从 channel 取出令牌；2) golang.org/x/sync/semaphore.Weighted：sem.Acquire(ctx, 1) 获取，sem.Release(1) 释放，支持带权重的获取和 context 取消。
errgroup 的 ctx 什么时候会被 cancel？▶
使用 errgroup.WithContext 时，派生的 ctx 在以下情况被 cancel：1) 任何一个 g.Go 的函数返回非 nil 错误时立即 cancel；2) 所有 goroutine 完成后，Wait 返回前也会 cancel（cleanup）。因此不管成功还是失败，Wait 返回后 ctx 一定是已取消状态。如果只需要在错误时取消，直接使用 WithContext；不需要的话用 new(errgroup.Group)。
errgroup 中的 goroutine panic 会怎样？▶
errgroup 的 Go 方法不做 recover，goroutine 内的 panic 会直接传播导致程序崩溃（与普通 goroutine panic 行为相同）。如果需要 panic 安全，需要在传给 g.Go 的函数内自行 recover，将 panic 转换成 error 返回。这是与某些第三方库（如 go-errgroup）的区别，标准 errgroup 有意不处理 panic，认为 panic 表示不可恢复的错误。

常见陷阱

❌ 忘记检查 Wait 返回的 error（vs ✅ 始终处理错误）
g.Go(func() error {
    return riskyOp()
})
g.Wait() // 忘记检查 error！
// 以为成功了，实则有错误被忽略
useResults() // 可能用了不完整的数据

g.Wait() 的 error 必须检查，否则静默失败，使用不完整数据。

g.Go(func() error {
    return riskyOp()
})
if err := g.Wait(); err != nil {
    return fmt.Errorf("group failed: %w", err)
}
useResults() // 安全：确认无错误

始终检查 Wait 的 error，有错误时提前返回，避免使用部分数据。

❌ goroutine 中捕获循环变量（vs ✅ 每次循环创建副本）
for _, url := range urls {
    g.Go(func() error {
        // url 是循环变量，所有 goroutine
        // 共享同一个 url 的最终值
        return fetch(url) // 竞态！
    })
}

所有 goroutine 捕获的是同一个 url 变量，执行时可能都是最后一个 URL。

for _, url := range urls {
    url := url // 创建副本（Go 1.22前必须）
    g.Go(func() error {
        return fetch(url)
    })
}
// Go 1.22+ 循环变量每次迭代独立，无需此操作

在闭包外重新声明变量创建副本，Go 1.22+ 的新循环语义自动解决此问题。

❌ 不限并发数导致资源耗尽（vs ✅ 信号量限流）
// 100万条数据全部并发处理
for _, item := range millionItems {
    item := item
    g.Go(func() error {
        return httpFetch(item)
    })
}
// 100万个 goroutine + 连接，OOM

无限制启动 goroutine，内存和 fd 耗尽，程序崩溃。

sem := make(chan struct{}, 50) // 最多 50 并发
for _, item := range millionItems {
    item := item
    sem <- struct{}{}
    g.Go(func() error {
        defer func() { <-sem }()
        return httpFetch(item)
    })
}

信号量确保最多 50 个并发 goroutine，避免资源耗尽。
