sync.Mutex

互斥锁基础

[核心]

Mutex 是 Go 中最基本的互斥锁，保证同一时刻只有一个 goroutine 访问临界区。不可重入：同一 goroutine 二次加锁会死锁。

  • Lock() — 加锁，若已锁则阻塞等待
  • Unlock() — 解锁，必须由加锁的 goroutine 调用
  • 总是用 defer mu.Unlock() 防止忘记解锁
  • 零值可用，不需要初始化；但不可复制（go vet 会检测）
var mu sync.Mutex
var counter int

func increment() {
    mu.Lock()
    defer mu.Unlock()  // 始终用 defer
    counter++
}

sync.RWMutex

读写锁

[进阶]

RWMutex 允许多个读者并发，但写者独占。适合读多写少场景（如配置缓存、路由表）。

  • RLock() / RUnlock() — 读锁，允许多个并发读
  • Lock() / Unlock() — 写锁，独占
  • 写锁等待时会阻止新读锁，防止写饥饿
  • 若读操作很快，Mutex 可能比 RWMutex 更快（无额外开销）
var rw sync.RWMutex
var cache = map[string]string{}

func read(key string) string {
    rw.RLock()
    defer rw.RUnlock()
    return cache[key]
}

func write(key, val string) {
    rw.Lock()
    defer rw.Unlock()
    cache[key] = val
}

sync.WaitGroup

等待一组 goroutine

[核心]

WaitGroup 让主 goroutine 等待一组 goroutine 完成。Add 必须在 goroutine 启动之前调用，否则存在竞态。

  • Add(n) — 增加计数，在启动 goroutine 前调用
  • Done() — 计数减 1，通常 defer wg.Done()
  • Wait() — 阻塞直到计数归零
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)        // 在 goroutine 外 Add
    go func(id int) {
        defer wg.Done()
        doWork(id)
    }(i)
}
wg.Wait()

sync.Once

单次初始化

[核心]

Once 保证某个函数只执行一次，无论多少 goroutine 并发调用。适合懒加载单例、全局初始化。

  • 与 init() 区别：Once 可延迟到真正需要时执行，且可按条件跳过
  • 内部用原子操作 + Mutex 实现快速路径
  • 若 Do 内 panic，Once 不会重试；下次调用不执行
var (
    once     sync.Once
    instance *DB
)

func GetDB() *DB {
    once.Do(func() {
        instance = connectDB()
    })
    return instance
}

sync.Cond

条件变量

[高级]

Cond 允许 goroutine 等待某个条件成立。必须与 Mutex 或 RWMutex 配合使用。

  • Wait() — 原子释放锁并挂起，被唤醒后重新获取锁
  • Signal() — 唤醒一个等待的 goroutine
  • Broadcast() — 唤醒所有等待的 goroutine
  • 虚假唤醒：Wait 必须在循环中检查条件
var mu sync.Mutex
cond := sync.NewCond(&mu)
var ready bool

// 等待方
mu.Lock()
for !ready {   // 用 for 而非 if，防止虚假唤醒
    cond.Wait()
}
mu.Unlock()

// 通知方
mu.Lock()
ready = true
cond.Broadcast()
mu.Unlock()

面试问答

Mutex 不可重入是什么意思？▶
Go 的 Mutex 不记录是哪个 goroutine 持有锁。若同一 goroutine 在已持有锁时再次调用 Lock()，会永久阻塞造成死锁。这是设计决策：实现可重入锁需要保存 goroutine ID，增加开销且鼓励不良设计（持锁调用复杂函数）。解决方案：重构代码提取无锁内部函数，或使用 channel 替代。
WaitGroup 为什么必须在 goroutine 外部调用 Add？▶
若在 goroutine 内部调用 Add(1)，主 goroutine 可能在 Add 执行前就调用了 Wait()，此时计数仍为 0，Wait 立即返回，后续 goroutine 继续执行时程序已经退出。正确做法：先 wg.Add(n)，再启动 goroutine，确保 Wait 在所有 Add 完成后才可能返回零。
sync.Once 的实现原理？▶
Once 内部有一个 uint32 的 done 标志和一个 Mutex。快速路径：用 atomic.LoadUint32 检查 done，若已为 1 直接返回（无锁开销）。慢速路径：加 Mutex 后再次检查 done（double-check），执行函数后 atomic.StoreUint32 置 1。这保证了并发安全且对已完成的情况只有原子读的代价。
RWMutex 相比 Mutex 什么时候更快？▶
RWMutex 仅在读操作远多于写操作时有优势（如读写比 > 10:1）。若读操作极快（几十纳秒），RWMutex 的额外开销反而使其更慢。基准测试结论：读比例 >80%、读操作耗时较长（有 I/O 或计算）时，RWMutex 才有明显优势。短路径的频繁加锁用 Mutex 更简单高效。
sync.Cond 和 channel 如何选择？▶
Channel 适合一次性信号或数据传递；Cond 适合多个 goroutine 等待同一条件变化，且条件可反复进入等待状态。例如：连接池空时多个请求等待可用连接，有连接归还时 Broadcast 唤醒所有等待者。用 channel 模拟需要额外维护 goroutine 数量，较为繁琐。

常见陷阱

❌ Mutex 加锁后忘记 Unlock（vs ✅ defer 解锁）
// 错误：panic 时锁泄漏
func bad() {
    mu.Lock()
    doSomething()  // 若 panic
    mu.Unlock()    // 不会执行
}

panic 或提前 return 时 Unlock 不执行，导致死锁。

// 正确：defer 保证解锁
func good() {
    mu.Lock()
    defer mu.Unlock()
    doSomething()
}

defer 在函数返回时（含 panic）始终执行，保证解锁。

❌ WaitGroup Add 在 goroutine 内部（vs ✅ 外部 Add）
// 竞态：Wait 可能在 Add 前返回
for i := 0; i < 3; i++ {
    go func() {
        wg.Add(1) // 危险！
        defer wg.Done()
        work()
    }()
}
wg.Wait()

主 goroutine 执行 Wait 时，goroutine 可能尚未 Add，Wait 立即返回。

// 正确：先 Add 再启动
for i := 0; i < 3; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        work()
    }()
}
wg.Wait()

Add 在 goroutine 启动前调用，Wait 一定能正确等待。

❌ Cond.Wait 用 if 检查条件（vs ✅ for 循环检查）
// 错误：if 无法防虚假唤醒
mu.Lock()
if !ready {
    cond.Wait()
}
// ready 可能仍为 false！
process()
mu.Unlock()

虚假唤醒时条件未满足，用 if 会错误继续执行。

// 正确：for 循环确保条件满足
mu.Lock()
for !ready {
    cond.Wait()
}
// 到此 ready 一定为 true
process()
mu.Unlock()

for 循环在每次 Wait 返回后重新检查条件，保证正确性。
