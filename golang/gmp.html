面试题

GMP 中 G、M、P 各自的职责是什么？▶
G（Goroutine）：用户态执行单元，包含函数栈（初始 2KB）和调度状态。
M（Machine）：OS 线程，与内核直接交互，执行 G 的代码，数量上限默认 10000。
P（Processor）：逻辑处理器，持有本地 runq（最多 256 个 G）和内存缓存（mcache）。M 必须持有 P 才能执行 G。P 的数量默认等于 CPU 核数（GOMAXPROCS）。
什么是 work-stealing？为什么需要它？▶
当一个 P 的本地 runq 为空时，它会随机选择另一个 P，从其 runq 后半段偷走一半 G（最多 128 个）放入自己的 runq。
目的：平衡 CPU 负载，防止部分 CPU 空转而其他 CPU 积压。让整体吞吐接近最优，无需中央调度器协调。
代价：偷取时需要持有目标 P 的 runq 锁（短暂），多核下很少成为瓶颈。
goroutine 阻塞在网络 I/O 时，M 会阻塞吗？▶
不会。Go 使用 netpoller（基于 epoll/kqueue/iocp）。当 goroutine 调用 net.Read/Write 时：
1. 运行时将其注册到 netpoller，G 进入等待状态
2. M 立即释放该 G，从 runq 取下一个 G 继续执行
3. I/O 就绪时，netpoller 把 G 重新放入 runq
这让 Go 用少量 OS 线程承载大量并发网络连接。
blocking syscall 和网络 I/O 阻塞有什么区别？▶
网络 I/O 走 netpoller，M 不阻塞。Blocking syscall（如 syscall.Read 直接调用）无法被 netpoller 接管：
1. M 调用 syscall，陷入内核，P 与 M 解绑
2. P 被其他空闲 M（或新建 M）接管，继续执行其他 G
3. syscall 返回时，原 M 尝试取回 P；失败则 G 进入全局 runq，M 进入休眠
避免大量 blocking syscall：会创建大量 M，增加上下文切换开销。
GOMAXPROCS 设为 1 时，Go 还有并发吗？▶
有并发，但没有并行。GOMAXPROCS=1 时只有一个 P，所有 G 串行执行（M 时间片轮流运行 G）。
协作式切换点：channel 操作、syscall、runtime.Gosched()、函数调用（抢占检查）。
Go 1.14+ 使用异步抢占，即使没有切换点也能强制抢占长时间运行的 goroutine（通过信号 SIGURG）。
全局 runq 和本地 runq 的区别？▶
本地 runq（P.runq）：每个 P 独有，容量 256，无锁 FIFO 环形队列，入队出队都是原子操作，访问极快。
全局 runq（sched.runq）：有全局锁，访问较慢。溢出时（本地 runq 满）G 批量迁移到这里。
调度优先级：本地 runq → 全局 runq（每 61 次调度强制检查一次）→ work-stealing → netpoller。
新建 G 为什么优先放入当前 P 的本地队列？▶
放入当前 P 的本地 runq 有两个优势：
1. 局部性：新 G 通常与创建它的 G 共享数据（channel 通信等），放在同一 P 上减少跨核缓存失效。
2. 无锁操作：本地队列无锁，入队 O(1) 且极快；全局队列需持锁，代价高。
特殊地，新 G 会先尝试占用 P.runnext 槽（下次立即执行），而非队尾，进一步降低调度延迟。
M 的数量如何动态调整？上限是多少？▶
增加 M：当 P 因 G 阻塞（blocking syscall、CGO）而空闲，runtime 先从 idle M 池取 M；若池空则通过 clone 系统调用创建新 OS 线程。
减少 M：M 若长时间无 G 可运行，调用 stopm() 进入休眠放入 idle M 池；极长时间空闲的 M 会被回收（线程退出）。
上限：默认 10000 个 M，可通过 runtime.SetMaxThreads(n) 调整。超出上限时新建 M 会触发 panic。

易错点

❌ goroutine 泄漏：没有退出路径
func leak() {
    go func() {
        for {
            // 永远不退出
            doWork()
        }
    }()
}
func safe(ctx context.Context) {
    go func() {
        for {
            select {
            case <-ctx.Done():
                return // 有退出路径
            default:
                doWork()
            }
        }
    }()
}

规则：每个 goroutine 启动时就要设计好退出条件。

❌ GOMAXPROCS 在容器中可能取错
// 默认读宿主机 CPU 数
// 容器限制 2 核，宿主 64 核
// GOMAXPROCS = 64（错误！）
// 导致过多 M 争抢 CPU

import "runtime"
runtime.GOMAXPROCS(runtime.NumCPU())
// 用 automaxprocs 自动读取
// cgroup 中的 CPU 配额
import (
    _ "go.uber.org/automaxprocs"
)

原因：runtime.NumCPU() 读宿主机 CPU 数，容器内不准确。

❌ 在 init() 或全局变量中启动 goroutine
var bg = startBackground()

func startBackground() chan struct{} {
    ch := make(chan struct{})
    go worker(ch) // 无法取消！
    return ch
}
type Service struct{ cancel func() }

func New() *Service { return &Service{} }

func (s *Service) Start(ctx context.Context) {
    ctx, s.cancel = context.WithCancel(ctx)
    go worker(ctx)
}
func (s *Service) Stop() { s.cancel() }

规则：goroutine 必须有明确的 owner，能通过 context 或 channel 控制停止。

❌ 误解"P 的数量 = 并发数"
// 常见误解：
// GOMAXPROCS=4 表示
// 最多同时运行 4 个 goroutine

// 实际上：
// 最多 4 个 G 并行执行
// 但有成千上万个 G 并发存在
// P 控制的是"并行"（同时在 CPU 上）
// 不影响"并发"（goroutine 总数）

// 阻塞在 I/O 的 G 不占 P
// 100万个网络连接可以只用少量 P
// 因为大多数 G 在等待 I/O

关键：P 数量只影响 CPU 密集任务的并行度，I/O 密集任务不受限。
