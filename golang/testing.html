Table-Driven 测试

结构体 slice + t.Run 子测试

[核心]

Table-driven 是 Go 社区标准测试模式：将测试用例整理成结构体 slice，用 t.Run 为每个用例创建子测试，便于单独运行和定位失败。

  • 子测试名会拼接到父测试名：TestAdd/positive_numbers
  • 用 go test -run TestAdd/positive 单独运行匹配的子测试
  • 子测试失败不会中止其他子测试的执行
  • 命名规范：用下划线分隔，避免空格（命令行需转义）
func TestAdd(t *testing.T) {
    cases := []struct{
        name    string
        a, b   int
        want    int
    }{
        {"positive", 2, 3, 5},
        {"negative", -1, -2, -3},
        {"zero", 0, 0, 0},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := Add(tc.a, tc.b)
            if got != tc.want {
                t.Errorf("got %d, want %d", got, tc.want)
            }
        })
    }
}

并行测试

t.Parallel() 与 TestMain

[进阶]

t.Parallel() 标记当前测试可与其他并行测试同时运行，可显著缩短 I/O 密集型测试的总时间。

  • 调用 t.Parallel() 后当前测试暂停，等待父测试函数返回后与其他并行测试同时运行
  • 并行测试中捕获循环变量需要特别注意（Go 1.22 前）
  • TestMain(m *testing.M) — 控制测试初始化和清理，调用 m.Run() 运行测试
  • 并行度：默认为 GOMAXPROCS，可用 -parallel n 控制
func TestDB(t *testing.T) {
    cases := []struct{ name, query string }{
        {"users", "SELECT * FROM users"},
        {"orders", "SELECT * FROM orders"},
    }
    for _, tc := range cases {
        tc := tc         // 捕获循环变量
        t.Run(tc.name, func(t *testing.T) {
            t.Parallel()   // 并行运行
            runQuery(t, tc.query)
        })
    }
}

// TestMain 示例
func TestMain(m *testing.M) {
    setupDB()
    code := m.Run()
    teardownDB()
    os.Exit(code)
}

Benchmark

b.N / b.ResetTimer / b.ReportAllocs

[进阶]

Benchmark 由 testing 框架反复调用，自动调整 b.N 直到结果稳定。运行命令：go test -bench=. -benchmem。

  • b.N — 框架控制的循环次数，不要手动设置
  • b.ResetTimer() — 排除初始化时间，在 setup 完成后调用
  • b.ReportAllocs() — 显示每次操作的内存分配数（等效于 -benchmem）
  • b.SetBytes(n) — 设置每次操作处理的字节数，输出 MB/s
  • 结果分析：benchstat 工具对比多次 benchmark 结果
func BenchmarkJSON(b *testing.B) {
    data := generateData()  // 初始化在循环外
    b.ResetTimer()           // 不计入初始化时间
    b.ReportAllocs()
    b.SetBytes(int64(len(data)))

    for i := 0; i < b.N; i++ {
        var v MyStruct
        if err := json.Unmarshal(data, &v); err != nil {
            b.Fatal(err)
        }
    }
}
// 运行：go test -bench=BenchmarkJSON -benchmem -count=5
// 对比：benchstat old.txt new.txt

测试工具

testify / gomock / httptest

[进阶]

标准库 testing 功能较基础，常用第三方工具提升测试效率和可读性。

  • testify/require — 断言失败立即停止测试（vs assert 继续）；require.Equal、require.NoError
  • testify/mock — 手动 mock；gomock 通过 mockgen 代码生成 mock
  • net/http/httptest — 测试 HTTP handler，无需启动真实服务器
  • go test -cover — 查看覆盖率；-coverprofile 生成报告
// httptest 测试 Handler
func TestHandler(t *testing.T) {
    req := httptest.NewRequest("GET", "/users/1", nil)
    w := httptest.NewRecorder()
    UserHandler(w, req)
    resp := w.Result()
    require.Equal(t, http.StatusOK, resp.StatusCode)
}

// gomock 使用示例
//go:generate mockgen -source=repo.go -destination=mock_repo.go
ctrl := gomock.NewController(t)
defer ctrl.Finish()
mockRepo := NewMockUserRepo(ctrl)
mockRepo.EXPECT().GetUser(1).Return(&User{}, nil)

面试问答

t.Run 子测试如何命名？有什么规范？▶
子测试名会附加到父测试名，如 TestFoo/case_1。命名建议：使用下划线替代空格（空格在命令行 -run 参数中需要转义为下划线），名称应描述测试场景而非实现细节（如 "empty_input" 而非 "test1"）。可以嵌套 t.Run（多级子测试），用 -run TestFoo/sub/nested 精确指定。t.Run 返回 bool，可检测是否成功。
benchmark 中 b.N 是什么，为什么不能手动设置？▶
b.N 是 testing 框架自动调整的循环次数。框架先以 b.N=1 运行，若运行时间过短则加倍 b.N 重新运行，直到运行时间达到目标（默认 1 秒）。b.N 由框架控制以获得稳定的时间测量。手动设置 b.N 会破坏这个机制。代码必须在 for i := 0; i < b.N; i++ 循环中执行待测代码，循环外做 setup，setup 完成后可调用 b.ResetTimer()。
如何测试私有函数？▶
有三种方案：1) 在同一 package 的 _test.go 文件中测试（不加 _test 后缀的包名），可直接访问私有函数，如 package foo 对应 foo_test.go 中也声明 package foo；2) 将私有函数提升为公开（重新考虑设计是否合理）；3) 通过测试公开 API 间接覆盖私有函数（黑盒测试，更推荐）。_test.go 文件只在测试时编译，不会进入生产二进制。
如何防止 benchmark 结果被编译器优化掉？▶
编译器可能将结果不被使用的计算优化掉，导致 benchmark 测量的是空循环。解决方案：1) 将结果赋给包级变量（var result = someFunc()）；2) 使用 testing.B.RunParallel 时框架有特殊处理；3) 将结果赋给局部变量再赋给黑洞变量（_ = result 不够，用包级 var sink any）。规范写法：var Sink any; func BenchmarkFoo(b *testing.B) { for i := 0; i < b.N; i++ { Sink = fn() } }
go test -race 的作用？使用场景？▶
-race 开启 Go 的竞态检测器（race detector），基于 ThreadSanitizer 实现。运行时监控内存访问，若检测到两个 goroutine 无同步地并发读写同一内存，报告竞态。使用场景：1) CI 流水线中运行测试，及早发现并发 bug；2) 本地排查疑似竞态问题；3) benchmark 不适合加 -race（约 5-10x 性能开销）。-race 只能检测运行时实际发生的竞态，无法覆盖所有路径，但实践中非常有效。

常见陷阱

❌ t.Parallel 中捕获循环变量（vs ✅ 每次迭代创建副本）
for _, tc := range cases {
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        // tc 是循环变量！
        // 并行运行时 tc 已经是最后一个值
        doTest(t, tc)
    })
}

并行子测试运行时，循环已结束，所有子测试共享 tc 的最终值。

for _, tc := range cases {
    tc := tc  // 每次迭代创建副本
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        doTest(t, tc) // 各自独立的 tc
    })
}
// Go 1.22+ 循环变量语义变更，无需此操作

内部重声明 tc := tc 创建局部副本，每个子测试捕获独立变量。

❌ Benchmark 结果被优化掉（vs ✅ 用 sink 变量防优化）
func BenchmarkMarshal(b *testing.B) {
    v := MyStruct{Name: "test"}
    for i := 0; i < b.N; i++ {
        json.Marshal(v) // 结果被丢弃
        // 编译器可能整体消除
    }
}

Marshal 返回值未使用，编译器可能将整个调用优化掉，结果不可信。

var benchSink []byte

func BenchmarkMarshal(b *testing.B) {
    v := MyStruct{Name: "test"}
    var out []byte
    for i := 0; i < b.N; i++ {
        out, _ = json.Marshal(v)
    }
    benchSink = out // 阻止优化
}

将结果赋给包级变量，编译器无法确定结果是否被使用，从而保留调用。

❌ 测试依赖执行顺序（vs ✅ 每个测试独立，用 setup/teardown）
var globalDB *DB

func TestCreate(t *testing.T) {
    globalDB.Create(...)  // 依赖上一个测试
}
func TestList(t *testing.T) {
    items := globalDB.List()  // 依赖 TestCreate
    // -shuffle=on 会让测试顺序随机，这里会失败
}

测试有执行顺序依赖，用 go test -shuffle=on 或并行执行时会随机失败。

func TestList(t *testing.T) {
    // 每个测试自己初始化所需数据
    db := setupTestDB(t)
    t.Cleanup(func() { db.Drop() })
    db.Create(...)   // 本测试自己准备数据
    items := db.List()
    // 测试完全独立，可并行
}

每个测试自己 setup 数据，用 t.Cleanup 清理，完全独立，可任意顺序运行。
