面试题

什么是逃逸分析？在哪个阶段执行？▶
逃逸分析是编译期静态分析，判断变量是否"逃逸"到堆（生命周期超过当前函数栈帧）。在 Go 编译器的 SSA 优化阶段执行。不逃逸的变量分配在栈，函数返回自动回收；逃逸的变量分配在堆，由 GC 管理。用 go build -gcflags="-m -m" 查看详细逃逸信息。
哪些情况会导致变量逃逸？▶
① 函数返回指针（生命周期超过函数）
② 赋值给接口变量（编译器无法确定具体类型大小）
③ 发送到 channel（接收方可能在不同 goroutine）
④ 闭包捕获变量（闭包生命周期可能更长）
⑤ 切片/map 动态增长（编译期大小未知）
⑥ 大对象（超过栈增长阈值）
⑦ 被外部指针引用
接口赋值为什么一定会逃逸？▶
接口（iface/eface）内部存储的是指针（itab + data pointer）。当具体类型的值被赋给接口时，如果值不是指针，编译器需要在堆上为其分配内存（因为接口只能存指针，不能内联存储任意大小的值）。例外：对于指针类型赋给接口，不一定额外分配（本身就是指针）。
如何避免不必要的逃逸？▶
① 避免返回局部变量的指针，改为传入指针参数（调用方分配）
② 减少接口的使用（具体类型比接口快，无逃逸）
③ 使用值类型传参（小 struct 值拷贝比堆分配更快）
④ 预分配 slice：make([]T, 0, n)
⑤ 使用 sync.Pool 复用堆对象
用 pprof 和逃逸分析信息来定位高频逃逸热点。
fmt.Println 为什么会导致参数逃逸？▶
fmt.Println 的参数类型是 ...interface{}。任何传入的具体类型值都会被自动转换为接口，触发逃逸。在性能敏感路径上，避免使用 fmt，改用 log（有相同问题）或 zerolog/zap（使用结构化日志避免接口转换）或直接操作 []byte。

易错点

❌ 以为 new() 一定在堆上
func sum(a, b int) *int {
    // new() 不一定在堆上
    // 这里 result 实际上逃逸了
    result := new(int)
    *result = a + b
    return result  // 返回指针 → 逃逸
}
// 不逃逸的例子
func process() {
    x := new(int) // 不逃逸！
    *x = 42
    use(*x)  // x 不超出函数，栈分配
}

// new() 和 & 的分配位置
// 完全由逃逸分析决定，不是语法决定

不要假设 new() 在堆，&local 在栈。逃逸分析才是最终裁判。

❌ 接口参数频繁逃逸
// 每次调用都导致 point 逃逸到堆
type Shaper interface {
    Area() float64
}
func printArea(s Shaper) {
    fmt.Println(s.Area())
}
// 调用：
printArea(Point{1, 2}) // 逃逸！
// 具体类型参数，无逃逸
func printPointArea(p Point) {
    fmt.Println(p.Area())
}

// 或只在必要时才用接口
// 接口最适合在模块边界使用
// 而不是内部高频调用路径

接口在模块边界使用，内部高频路径使用具体类型，减少逃逸和虚函数开销。

❌ 闭包捕获导致意外逃逸
func makeCounter() func() int {
    count := 0  // count 逃逸到堆！
    return func() int {
        count++  // 闭包捕获 count 引用
        return count
    }
    // 闭包生命周期超过函数 → count 必须堆分配
}
// 这是正确使用，逃逸是有意为之
// 若需要避免，改用显式状态
type Counter struct{ count int }
func (c *Counter) Inc() int {
    c.count++
    return c.count
}
// Counter 可以在调用方控制分配位置

闭包捕获引用是设计使然，理解逃逸的原因，而非盲目避免闭包。
