面试题

三色标记中，白、灰、黑分别代表什么？▶
白色：未被访问，GC 结束后仍为白色的对象会被回收。
灰色：已被发现（可达），但其引用的子对象还未全部扫描。放在"灰色工作队列"中。
黑色：已完全扫描，所有子对象已标记。黑色对象不会被回收，且不会被重新扫描。
为什么需要写屏障？不加会怎样？▶
GC 并发标记时，应用代码仍在运行，可能发生：黑色对象 A 新增对白色对象 C 的引用，同时灰色对象 B 删除了对 C 的引用——C 永远无法被扫描到，会被错误回收（悬挂指针）。
写屏障确保在并发标记期间，任何新建的指针引用都会被记录，C 会被重新标记为灰色，保证不漏掉活跃对象。
Go GC 有几次 STW？各做什么？▶
当前 Go GC 的标记周期包含两次主要 STW 转换：
1. Mark Setup STW：切换到标记阶段并开启写屏障；恢复执行后并发扫描根和可达堆对象，运行中的 goroutine 会为栈扫描被短暂挂起。
2. Mark Termination STW：完成剩余标记工作并切换到清扫阶段。
停顿时长取决于运行环境和负载，不应承诺固定小于 1ms。
如何降低 Go GC 的停顿时间？▶
1. 减少堆上对象数量：用 sync.Pool 复用临时对象，避免返回指针（逃逸到堆），优先用值类型。
2. 减少指针数量：写屏障开销与指针密度成正比，结构体中减少嵌套指针。
3. 调整 GOGC：提高触发阈值（如 GOGC=200）可降低频率，但会增加内存占用。
4. GOMEMLIMIT（Go 1.19+）：按内存上限软触发 GC，防止 OOM，比调 GOGC 更安全。
GOGC 控制什么？默认值是多少？▶
GOGC=100（默认）把下一周期新增堆预算设为约等于“存活堆 + GC roots”。更精确的目标是 live heap + (live heap + roots) × GOGC/100，并非始终恰好是存活堆的 2 倍。GOMEMLIMIT 是涵盖运行时内存的软限制，压力下可暂时超过以避免 GC thrashing。
什么是混合写屏障（hybrid write barrier）？▶
Go 1.8 引入混合写屏障，结合了 Dijkstra 插入写屏障和 Yuasa 删除写屏障：
· 插入时：新写入的目标指针参与标记保护
· 删除时：被覆盖的旧指针也参与标记保护
它消除了标记终止阶段重新扫描全部 goroutine 栈的需要。

不同情形的 GC 行为对比

场景 1：CPU 密集型▶
G 一直在运行，CPU 持续满载。
→ 并发标记与用户代码并发，GC mark worker 竞争 CPU 时间片。
→ STW 时间主要受 goroutine 数量影响（需扫描所有栈）。
→ 建议：适当调高 GOGC 降低 GC 频率，或用 GOMEMLIMIT 控制。
场景 2：I/O 密集型（G 阻塞多）▶
G 大量阻塞在网络/IO，P 空闲率高。
→ 并发标记可利用空闲 CPU 资源，几乎不影响用户代码延迟。
→ 整体吞吐更高，GC 对应用影响最小。
→ 建议：保持默认 GOGC=100 即可，不需要特别优化。
场景 3：内存分配激增▶
分配速率高 → 堆增长快 → 更频繁触发 GC。
→ GC 周期变短，STW 可能变多（每次都有 2 次 STW）。
→ 极端情况：分配速率 > 标记速率，触发 GC 辅助（mutator assist）。
→ 建议：用 sync.Pool 复用对象，调高 GOGC，使用 GOMEMLIMIT。
场景 4：大对象存活多▶
存活对象多 → 标记阶段工作量大，并发标记时间变长。
→ 可能造成 CPU 占用上升（mark worker 占用更多时间片）。
→ 如果存活对象包含大量指针，写屏障开销也会上升。
→ 建议：减少堆上指针数量，用值类型代替指针类型。
场景 5：P 数量变化▶
P 数量会影响应用与 GC 的并行度，但更多 P 不等于 STW 必然更短。Go 1.25+ 在 Linux 容器中默认感知 cgroup CPU 限制；较旧版本可显式设置 GOMAXPROCS 或使用 automaxprocs。

易错点

❌ 频繁创建大量小对象
func process(reqs []Request) {
    for _, r := range reqs {
        // 每次循环分配 buf
        buf := make([]byte, 4096)
        encode(r, buf)
    }
}
var pool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)
    },
}
func process(reqs []Request) {
    for _, r := range reqs {
        buf := pool.Get().([]byte)
        encode(r, buf)
        pool.Put(buf)
    }
}

原因：大量小对象增加堆对象数量，加重 GC 标记压力。

❌ 持有大对象引用导致 GC 无法回收
var cache = map[string][]byte{}

func load(k string, v []byte) {
    // 全局 map 持有引用
    cache[k] = v // 永不释放！
}
// 用 weak reference 或设置 TTL
// 或定期清理
func (c *Cache) Evict() {
    c.mu.Lock()
    defer c.mu.Unlock()
    for k, e := range c.items {
        if e.expired() {
            delete(c.items, k)
        }
    }
}

原因：全局变量持有引用让对象变成 GC root 的可达对象，永远不会被回收。

❌ finalizer 依赖 GC 时机
// 依赖 GC 释放资源
func NewConn() *Conn {
    c := &Conn{...}
    runtime.SetFinalizer(c, (*Conn).Close)
    // 问题：GC 时机不确定
    return c
}
// 显式关闭资源
func use() {
    c, _ := NewConn()
    defer c.Close() // 明确释放

    // 或用 context 控制
    c.RunUntil(ctx)
}

原因：Go GC 是按需触发，finalizer 执行时机不确定，不能用于时间敏感的资源释放。

❌ 在 STW 敏感场景中使用 runtime.GC()
// 手动触发 GC（慎用）
func afterBatch() {
    runtime.GC() // 强制执行 GC
    // 会触发 STW，影响延迟
}
// 在低峰期或非关键路径触发
func maintenance() {
    // 只在明确维护窗口内调用
    // 或通过 GOGC/GOMEMLIMIT 控制
    debug.FreeOSMemory() // 归还 OS
}

原则：相信 Go runtime 的自动 GC 策略，手动 GC 通常弊大于利。
