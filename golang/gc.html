面试题

三色标记中，白、灰、黑分别代表什么？▶
白色：未被访问，GC 结束后仍为白色的对象会被回收。
灰色：已被发现（可达），但其引用的子对象还未全部扫描。放在"灰色工作队列"中。
黑色：已完全扫描，所有子对象已标记。黑色对象不会被回收，且不会被重新扫描。
为什么需要写屏障？不加会怎样？▶
GC 并发标记时，应用代码仍在运行，可能发生：黑色对象 A 新增对白色对象 C 的引用，同时灰色对象 B 删除了对 C 的引用——C 永远无法被扫描到，会被错误回收（悬挂指针）。
写屏障确保在并发标记期间，任何新建的指针引用都会被记录，C 会被重新标记为灰色，保证不漏掉活跃对象。
Go GC 有几次 STW？各做什么？▶
Go GC 有 2 次 STW（通常总共 <1ms）：
1. Mark Setup STW：开启写屏障，扫描根对象（goroutine 栈、全局变量），启动并发标记。
2. Mark Termination STW：关闭写屏障，处理最后一批写屏障日志，确保三色不变性，进入并发清扫。
之后的清扫（sweep）与应用并发执行，不需要 STW。
如何降低 Go GC 的停顿时间？▶
1. 减少堆上对象数量：用 sync.Pool 复用临时对象，避免返回指针（逃逸到堆），优先用值类型。
2. 减少指针数量：写屏障开销与指针密度成正比，结构体中减少嵌套指针。
3. 调整 GOGC：提高触发阈值（如 GOGC=200）可降低频率，但会增加内存占用。
4. GOMEMLIMIT（Go 1.19+）：按内存上限软触发 GC，防止 OOM，比调 GOGC 更安全。
GOGC 控制什么？默认值是多少？▶
GOGC=100（默认）表示：当堆内存达到上次 GC 后存活对象大小的 2 倍时触发下一次 GC（100% 增长）。
GOGC=200：堆翻 3 倍才触发，GC 频率更低，但内存占用更高。
GOGC=off：完全关闭 GC（危险，仅用于极短暂的批处理任务）。
Go 1.19+ 推荐用 GOMEMLIMIT 配合 GOGC 使用，更精确。
什么是混合写屏障（hybrid write barrier）？▶
Go 1.14 引入，结合了 Dijkstra 插入写屏障和 Yuasa 删除写屏障：
· 插入时：新写入的目标指针标记为灰色
· 删除时：被覆盖的旧指针也标记为灰色
优点：不需要在 STW 时重新扫描 goroutine 栈（Go 1.13 之前需要），显著缩短 mark termination STW 时间。

易错点

❌ 频繁创建大量小对象
func process(reqs []Request) {
    for _, r := range reqs {
        // 每次循环分配 buf
        buf := make([]byte, 4096)
        encode(r, buf)
    }
}
var pool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)
    },
}
func process(reqs []Request) {
    for _, r := range reqs {
        buf := pool.Get().([]byte)
        encode(r, buf)
        pool.Put(buf)
    }
}

原因：大量小对象增加堆对象数量，加重 GC 标记压力。

❌ 持有大对象引用导致 GC 无法回收
var cache = map[string][]byte{}

func load(k string, v []byte) {
    // 全局 map 持有引用
    cache[k] = v // 永不释放！
}
// 用 weak reference 或设置 TTL
// 或定期清理
func (c *Cache) Evict() {
    c.mu.Lock()
    defer c.mu.Unlock()
    for k, e := range c.items {
        if e.expired() {
            delete(c.items, k)
        }
    }
}

原因：全局变量持有引用让对象变成 GC root 的可达对象，永远不会被回收。

❌ finalizer 依赖 GC 时机
// 依赖 GC 释放资源
func NewConn() *Conn {
    c := &Conn{...}
    runtime.SetFinalizer(c, (*Conn).Close)
    // 问题：GC 时机不确定
    return c
}
// 显式关闭资源
func use() {
    c, _ := NewConn()
    defer c.Close() // 明确释放

    // 或用 context 控制
    c.RunUntil(ctx)
}

原因：Go GC 是按需触发，finalizer 执行时机不确定，不能用于时间敏感的资源释放。

❌ 在 STW 敏感场景中使用 runtime.GC()
// 手动触发 GC（慎用）
func afterBatch() {
    runtime.GC() // 强制执行 GC
    // 会触发 STW，影响延迟
}
// 在低峰期或非关键路径触发
func maintenance() {
    // 只在明确维护窗口内调用
    // 或通过 GOGC/GOMEMLIMIT 控制
    debug.FreeOSMemory() // 归还 OS
}

原则：相信 Go runtime 的自动 GC 策略，手动 GC 通常弊大于利。
