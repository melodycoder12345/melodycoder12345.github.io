error 接口

内置 error 接口与惯用模式

核心

Go 内置的 error 接口只有一个方法。函数通过多返回值返回错误，调用方立即检查错误。

// error 接口定义
type error interface {
    Error() string
}

// 惯用返回模式：(value, error)
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, fmt.Errorf("division by zero")
    }
    return a / b, nil
}

// 调用方立即处理错误
result, err := divide(10, 0)
if err != nil {
    log.Printf("error: %v", err)
    return
}
fmt.Println(result)

Go 的错误处理是显式的。errors.New 创建简单错误，fmt.Errorf 创建带格式的错误，两者都返回 error 接口值。

Sentinel Error（哨兵错误）

预定义错误值与 errors.Is 比较

核心

Sentinel error 是包级别的预定义错误变量，代表特定的错误状态。使用 errors.Is 而非 == 来检查（因为错误可能被包装）。

// 标准库中的 sentinel errors
io.EOF              // 正常的文件结束
io.ErrUnexpectedEOF  // 非预期的 EOF
os.ErrNotExist      // 文件不存在
sql.ErrNoRows       // 查询无结果
context.Canceled   // context 被取消

// 定义自己的 sentinel error
var ErrNotFound = errors.New("not found")
var ErrPermission = errors.New("permission denied")

// 比较：用 errors.Is，而不是 ==
err := someFunc()
if errors.Is(err, ErrNotFound) {
    // 处理 not found 情况
}

// 读取直到 EOF
for {
    n, err := reader.Read(buf)
    if err == io.EOF { break }
    if err != nil { return err }
    process(buf[:n])
}

错误包装（Error Wrapping）

%w、Unwrap、errors.Is 与 errors.As

核心

Go 1.13 引入标准的错误链，使用 %w 包装错误，保留原始错误的同时添加上下文信息。

DatabaseErr
"db: connection refused"
← Unwrap
ServiceErr
"service: query failed"
← Unwrap
HandlerErr
"handler: internal error"
// 包装错误：%w 保留错误链
func queryUser(id int) (User, error) {
    u, err := db.Get(id)
    if err != nil {
        // %w 包装，保留原始错误
        return User{}, fmt.Errorf("queryUser(%d): %w", id, err)
    }
    return u, nil
}

// errors.Is：递归解包，检查错误链中是否包含目标错误
err := queryUser(42)
if errors.Is(err, sql.ErrNoRows) {
    // 即使 err 被多层包装，也能找到 sql.ErrNoRows
}

// errors.As：提取特定类型的错误
var pathErr *os.PathError
if errors.As(err, &pathErr) {
    fmt.Println("path:", pathErr.Path)
}

// errors.Unwrap：解开一层包装
cause := errors.Unwrap(err)

自定义错误类型

带上下文信息的错误类型

进阶

自定义错误类型可以携带更多上下文（如错误码、操作类型、请求 ID），并通过实现 Unwrap 支持错误链。

// 带上下文的自定义错误
type AppError struct {
    Code    int
    Message string
    Err     error  // 原始错误
}

func (e *AppError) Error() string {
    if e.Err != nil {
        return fmt.Sprintf("[%d] %s: %v", e.Code, e.Message, e.Err)
    }
    return fmt.Sprintf("[%d] %s", e.Code, e.Message)
}

// 实现 Unwrap 支持 errors.Is/As
func (e *AppError) Unwrap() error { return e.Err }

// 使用
var ae *AppError
if errors.As(err, &ae) {
    fmt.Println("error code:", ae.Code)
}

面试题

errors.Is 和 == 的区别是什么？▶
==：直接比较两个错误值是否相等（指针相等或值相等），无法处理被包装的错误。

errors.Is(err, target)：递归解包错误链，检查链中是否有某个错误 == target 或实现了 Is(error) bool 方法返回 true。

示例：如果 err 是 fmt.Errorf("wrap: %w", sql.ErrNoRows)，则 err == sql.ErrNoRows 为 false，但 errors.Is(err, sql.ErrNoRows) 为 true。

结论：使用 errors.Is 来比较错误，不要用 ==（除非明确不涉及包装错误的场景，如比较 io.EOF）。
如何判断并提取特定类型的错误？▶
使用 errors.As(err, &target)，它会遍历错误树，尝试将某个错误赋值给 target。target 必须是非 nil 指针，指向实现 error 的类型或任意接口类型：

var pathErr *os.PathError
if errors.As(err, &pathErr) { fmt.Println(pathErr.Path) }

errors.As vs errors.Is：
• Is：比较特定的错误实例（sentinel error）
• As：提取特定类型的错误值，可以访问其字段
panic 和 error 什么时候分别使用？▶
使用 error（推荐，绝大多数情况）：
• 可预期的错误：文件不存在、网络超时、参数无效
• 业务错误：用户不存在、权限不足
• 可恢复的错误：数据库连接失败（可重试）

使用 panic（谨慎，极少情况）：
• 程序不变量被违反（如数组越界、nil 指针）：运行时自动 panic
• 初始化失败（如 regexp.MustCompile 传入无效正则）
• 表明代码有 bug，不应该发生的情况

库代码应该避免向外 panic（用 recover 转换为 error），让调用方自己决定如何处理。
%v 和 %w 在 fmt.Errorf 中的区别？▶
%v：将错误格式化为字符串嵌入新错误消息，不保留原始错误的引用。errors.Is/As 无法解包到原始错误。

%w：包装错误，保留原始错误的引用。新错误实现 Unwrap() error 方法返回原始错误，errors.Is/As 可以递归解包。

选择原则：
• 如果调用方需要识别原始错误类型 → 用 %w
• 如果只需要错误信息字符串，不需要识别原始类型 → 用 %v（不泄漏内部实现细节）
如何为自定义错误类型支持 errors.Is 自定义比较？▶
实现 Is(target error) bool 方法可以自定义 errors.Is 的匹配逻辑：

func (e *AppError) Is(target error) bool {
  t, ok := target.(*AppError)
  if !ok { return false }
  return e.Code == t.Code // 按 Code 匹配，不管 Message
}

这样 errors.Is(err, &AppError{Code: 404}) 会匹配所有 Code 为 404 的错误，而不需要精确的实例相等。

易错点

❌ 忽略 error 返回值
// ❌ 忽略错误，可能导致 f 为 nil
f, _ := os.Open("file.txt")
data, _ := io.ReadAll(f)
// 如果文件不存在，f == nil
// ReadAll 会 panic: nil pointer

用 _ 忽略 error 相当于祈祷不出错，后续操作可能产生更难调试的 panic。

f, err := os.Open("file.txt")
if err != nil {
    return fmt.Errorf("open: %w", err)
}
defer f.Close()
data, err := io.ReadAll(f)
if err != nil {
    return fmt.Errorf("read: %w", err)
}

每个 error 都要检查，用 %w 包装并添加上下文信息后向上传递。

❌ 用 == 比较被包装过的 sentinel error
err := queryDB()
// 底层是 fmt.Errorf("query: %w", sql.ErrNoRows)

// ❌ == 无法穿透包装层
if err == sql.ErrNoRows {
    // 永远不会执行！
}

wrapped error 用 == 比较一定是 false，因为包装后是不同的对象。

// ✓ errors.Is 递归解包比较
if errors.Is(err, sql.ErrNoRows) {
    // 正确处理
}

// 提取特定类型也用 errors.As
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) {
    fmt.Println(pgErr.Code)
}

始终用 errors.Is/As，而不是 == 来比较错误。

❌ 自定义 error 类型未实现 Unwrap，错误链断裂
type MyErr struct {
    Cause error
    Msg   string
}
func (e *MyErr) Error() string {
    return e.Msg
}
// ❌ 没有 Unwrap 方法

// errors.Is 无法找到 Cause
err := &MyErr{Cause: io.EOF, Msg: "wrapped"}
errors.Is(err, io.EOF)  // false！

没有 Unwrap 方法，errors.Is/As 无法解包到 Cause 错误。

type MyErr struct {
    Cause error
    Msg   string
}
func (e *MyErr) Error() string {
    return e.Msg
}
// ✓ 实现 Unwrap，暴露错误链
func (e *MyErr) Unwrap() error {
    return e.Cause
}

err := &MyErr{Cause: io.EOF}
errors.Is(err, io.EOF)  // true ✓

自定义错误类型如果持有 Cause，必须实现 Unwrap 方法让错误链可遍历。
