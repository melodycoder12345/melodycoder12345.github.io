为什么需要了解 Go 汇编？

四个核心应用场景

core
  • 理解编译器优化决策：内联（inlining）、逃逸（escape to heap）、边界检查消除（BCE）都在汇编层面体现。读懂汇编才能验证优化是否生效。
  • 调试 runtime 源码：goroutine 切换（runtime.gosched）、GC 写屏障（write barrier）、栈增长（runtime.morestack）等核心逻辑均由汇编实现。
  • 手写 SIMD 优化：Go 标准库的 crypto/sha256、encoding/base64、bytes.IndexByte 等高性能路径使用汇编+SIMD 指令（AVX2/SSE4.2）。
  • 读懂工具链输出：go tool objdump（反汇编二进制）、go build -gcflags=-S（输出汇编到 stdout）是性能调优的重要手段。
💡 不需要日常手写汇编，但能读懂编译器输出是 Go 性能工程师的基本素养。

查看汇编输出的方法

# 方法 2：反汇编已编译的二进制 $ go tool objdump -s 'main\.Add' ./myapp

Plan 9 汇编基础语法

数据类型后缀与指令集

core

Plan 9 汇编指令通过后缀表示操作数宽度，操作数顺序为 src → dst（与 Intel 语法的 dst, src 相反）。

后缀宽度示例说明
B1 字节MOVB AX, BXbyte，8-bit
W2 字节MOVW AX, BXword，16-bit
L4 字节MOVL AX, BXlong，32-bit
Q8 字节MOVQ AX, BXquad，64-bit（64位程序默认）
 
// Plan 9 汇编 vs Intel 语法 vs AT&T 语法对比
//
// 操作：将立即数 1 加到 AX 寄存器
// Plan 9:  ADDQ $1, AX        (src → dst，$前缀表示立即数)
// Intel:   ADD  RAX, 1        (dst, src)
// AT&T:    addq $1, %rax      (%前缀表示寄存器)
//
// 内存寻址：读取 [AX+8] 位置的值到 BX
// Plan 9:  MOVQ 8(AX), BX     (offset 在括号前)
// Intel:   MOV  RBX, [RAX+8]
// AT&T:    movq 8(%rax), %rbx

常用指令速查

ref
Plan 9 指令含义等价 C 操作
MOVQ src, dst64位移动dst = src
ADDQ src, dst加法dst += src
SUBQ src, dst减法dst -= src
IMULQ src, dst有符号乘dst *= src
XORQ src, dst异或dst ^= src
CMPQ a, b比较（设标志位）a - b（结果不保存）
JMP label无条件跳转goto label
JLT label小于则跳转if (a < b) goto label
JBE label低于等于则跳（无符号）常用于边界检查
CALL func(SB)函数调用func()
RET函数返回return
PUSHQ AX压栈*--sp = AX
POPQ AX出栈AX = *sp++

寻址模式

adv 
// 立即数（常量）：$前缀
MOVQ $42, AX          // AX = 42

// 寄存器直接
MOVQ AX, BX           // BX = AX

// 内存间接（寄存器作地址）
MOVQ (AX), BX         // BX = *AX（解引用）

// 带偏移量的内存寻址
MOVQ 8(AX), BX        // BX = *(AX + 8)
MOVQ -8(SP), BX       // BX = *(SP - 8)（本地变量）

// 带缩放的索引寻址（用于数组访问）
MOVQ (AX)(CX*8), BX   // BX = *(AX + CX*8)（[]int64 索引）

// 全局符号地址（SB 相对）
LEAQ myVar(SB), AX   // AX = &myVar（取全局变量地址）

函数定义格式

TEXT 指令与函数头

core

汇编函数用 TEXT 指令定义，格式：

// TEXT pkgname·FuncName(SB), FLAGS, $framesize-argssize
//      │              │          │    │            │
//      └─ 包名（可省略）└─ SB相对  │    │            └─ 参数+返回值总字节数
//                               │    └─ 本地变量栈帧大小（字节）

// 示例：Add(a, b int) int
TEXT ·Add(SB), NOSPLIT, $0-24
//                           │    │    └─ 参数字节：a(8)+b(8)+ret(8) = 24
//                           │    └─ 本地变量 0 字节
//                           └─ NOSPLIT: 不触发栈增长检查（小函数用）
Flag含义使用场景
NOSPLIT跳过栈溢出检查（morestack 不调用）小叶函数，栈用量已知且小
NOFRAME不分配栈帧，不保存 BP极简叶函数，配合 NOSPLIT
NEEDCTXT函数使用闭包上下文（DX 寄存器）闭包汇编实现
WRAPPERwrapper 函数，不计入 traceback 帧接口 dispatch wrapper

Go 1.17+ 寄存器调用约定（ABI Internal）

adv

Go 1.17 引入基于寄存器的 ABI。下面仅展示 amd64 工具链实现的概念示意；实际寄存器分配还受参数类型、聚合拆分、返回值和工具链版本影响，不能作为 Go 语言级调用约定依赖：

// 整型参数寄存器顺序（AMD64）
// 第 1 个参数 → AX
// 第 2 个参数 → BX
// 第 3 个参数 → CX
// 第 4 个参数 → DI
// 第 5 个参数 → SI
// 第 6 个参数 → R8
// 第 7 个参数 → R9
// 第 8 个参数 → R10
// 第 9 个参数 → R11
// 寄存器预算不足的参数会使用栈；不能简单按“第 10 个参数”判断
//
// 浮点参数寄存器：X0-X14（15 个）
// 返回值同样使用寄存器
//
// 注意：手写汇编文件若用 ABI0（老约定），
// Go 编译器会自动生成 ABI0→ABI Internal 的 wrapper
⚠️ 手写汇编使用旧的 ABI0（栈传参），Go 编译器自动生成 shim 函数桥接两个 ABI。这意味着手写汇编调用有一次额外的寄存器↔栈拷贝开销，在热路径上需注意。

伪寄存器与栈帧布局

四个伪寄存器详解

core
伪寄存器全称指向典型用法
SBStatic Base程序静态数据段基址myVar(SB) 访问全局变量
SPStack Pointer（虚拟）本地栈帧顶部（比硬件 SP 低 8 字节）x-8(SP) 访问本地变量
FPFrame Pointer（虚拟）函数参数区域（调用者栈帧）a+0(FP) 访问第 1 个参数
PCProgram Counter当前指令地址（等价 IP/RIP）用于分支跳转目标
⚠️ 关键区分：Go 汇编中 SP 是虚拟 SP，指向本地变量顶部（帧顶）；访问本地变量用 name-N(SP)（负偏移）。硬件 SP 比虚拟 SP 高 8 字节（存放返回地址）。

典型栈帧布局（ABI0）

adv

调用 func Foo(a, b int) int 时的栈帧布局（高地址在上）：

caller 的栈帧高地址
a+0(FP) → 参数 a（8 字节）FP+0
b+8(FP) → 参数 b（8 字节）FP+8
ret+16(FP) → 返回值（8 字节）FP+16
返回地址（CALL 压入）硬件 SP+0
x-8(SP) → 本地变量 x（8 字节）虚拟 SP-8
y-16(SP) → 本地变量 y（8 字节）虚拟 SP-16
栈增长方向（向低地址）↓低地址
// 参数引用：用 FP 伪寄存器（带变量名，方便调试）
MOVQ a+0(FP), AX     // 读取参数 a
MOVQ b+8(FP), BX     // 读取参数 b

// 本地变量：用 SP 伪寄存器（负偏移）
MOVQ AX, x-8(SP)      // 写本地变量 x

// 写返回值
ADDQ AX, BX
MOVQ BX, ret+16(FP)  // 写入返回值
RET

// 文件：math_amd64.s — AMD64 汇编实现（ABI0 栈传参）
// Go 编译器自动生成 ABI wrapper，调用方无感知

#include "textflag.h"

// func Sum(a, b int) int
// 参数通过栈传递（ABI0）：
//   a at a+0(FP)      8 字节
//   b at b+8(FP)      8 字节
//   ret at ret+16(FP) 8 字节
TEXT ·Sum(SB), NOSPLIT, $0-24
    MOVQ    a+0(FP), AX      // AX = a
    MOVQ    b+8(FP), BX      // BX = b
    ADDQ    BX, AX            // AX = a + b
    MOVQ    AX, ret+16(FP)   // 写返回值
    RET                        // 返回

完整示例：MaxInt64（对比编译器输出）

adv 
// Go 源码（编译器会内联此函数）
func MaxInt64(a, b int64) int64 {
    if a > b {
        return a
    }
    return b
}

// 对应汇编（go build -gcflags=-S 输出，简化）：
TEXT ·MaxInt64(SB), NOSPLIT, $0-24
    MOVQ    a+0(FP), AX      // AX = a
    MOVQ    b+8(FP), BX      // BX = b
    CMPQ    AX, BX            // 比较 a 和 b
    JLE     retB               // a <= b → 跳到 retB
    MOVQ    AX, ret+16(FP)   // 返回 a
    RET
retB:
    MOVQ    BX, ret+16(FP)   // 返回 b
    RET

// 构建命令：
// go build ./...   — 自动使用 math_amd64.s
// go vet ./...     — 验证汇编声明与实现签名匹配

SIMD 汇编示例（SSE4.2 字节搜索）

adv

Go 标准库 bytes.IndexByte 的实现使用 SSE4.2 的 PCMPESTRI 指令并行比较 16 字节，展示手写汇编的真实价值。

// 简化示意：用 SSE4.2 PCMPEQB 加速字节搜索
// 每次处理 16 字节，比纯 Go 快 10-16x
TEXT ·IndexByteFast(SB), NOSPLIT, $0-40
    // 加载 needle（目标字节）广播到 XMM0 的 16 个位置
    MOVBLZX c+24(FP), AX
    MOVD    AX, X0
    PSHUFB  X1, X0            // 广播到 16 字节

    // 加载 16 字节数据，与 X0 比较
    MOVOU   (SI), X2          // X2 = 16 bytes from s
    PCMPEQB X0, X2           // 按字节比较
    PMOVMSKB X2, AX          // 提取比较结果位掩码
    BSFL    AX, AX            // 找最低位 1（最近匹配）
    RET

面试题

Go 汇编中的虚拟 SP 和硬件 SP 有什么区别？ ▶
硬件 SP：CPU 实际的栈指针寄存器（AMD64 的 RSP），始终指向栈顶（当前有效数据的最低地址），CALL 指令压入返回地址时 RSP-=8。

虚拟 SP：Go 汇编中 SP 伪寄存器，指向当前函数帧的"顶部"（本地变量区的顶端）。它比硬件 SP 高 8 字节（隔开了 CALL 压入的返回地址）。用 name-N(SP)（负偏移）访问本地变量。

在没有本地变量（$0 帧大小）的叶函数中，虚拟 SP 等于硬件 SP。在 Go 汇编中，带变量名前缀的 SP 引用（x-8(SP)）总是指虚拟 SP；不带前缀的 0(SP) 则是硬件 SP。
NOSPLIT flag 的作用是什么？什么情况下应该使用它？ ▶
NOSPLIT 指示编译器不在函数入口生成栈溢出检查代码（即不插入 CALL runtime.morestack）。正常函数每次调用时检查栈是否有足够空间，不足则扩容。

使用 NOSPLIT 的场景：①叶函数（不调用其他函数）且栈用量明确很小；②runtime 内部关键路径（morestack 本身是 NOSPLIT，否则无限递归）；③帧大小为 0（$0）的简单函数。

不当使用 NOSPLIT 的后果：如果函数实际栈用量超过 goroutine 栈剩余空间，会触发栈溢出 panic（无法恢复）。vet 工具会检查 NOSPLIT 函数的栈用量。
Go 1.17 引入寄存器传参后，手写汇编如何适配？ ▶
Go 1.17+ 引入了两套 ABI：ABI Internal（新，寄存器传参，Go 函数间调用使用）和 ABI0（旧，栈传参，汇编函数使用）。

普通包中的手写汇编使用 ABI0，工具链在需要时生成 ABI0 与 ABIInternal 之间的适配包装器，因此通过伪 FP 访问参数的既有写法仍可工作。ABIInternal 是不稳定的工具链内部接口，普通包不能用 //go:linkname 把它当成受支持的优化入口；应以目标版本的汇编输出和 benchmark 验证性能。
如何在汇编中实现跨平台支持？ ▶
Go 使用文件名约定区分平台汇编文件：file_amd64.s（只在 AMD64 编译）、file_arm64.s（只在 ARM64 编译），类似 .go 文件的 build constraint。

跨平台策略：①为每个支持的 GOOS/GOARCH 组合提供对应 .s 文件；②提供通用 Go 实现作为降级（file_generic.go 用 build tag //go:build !amd64）；③标准库 bytes、crypto/sha256 等均采用此策略。

也可在 .s 文件内用宏区分：#ifdef GOARCH_amd64，但一般推荐分文件更清晰。

易错点

✗ Go 汇编的 SP 偏移计算错误
// 错误：帧大小 $16 但偏移写错
TEXT ·Bad(SB), NOSPLIT, $16-8
    // 本地变量 a 应在 a-8(SP)
    // 但错误写成 a+8(SP)（正偏移访问 FP 区域）
    MOVQ    AX, a+8(SP)  // BUG!

正偏移 SP 访问的是参数/返回值区域（FP 区域），本地变量应用负偏移。

// 正确：本地变量用负偏移
TEXT ·Good(SB), NOSPLIT, $16-8
    // 帧大小 $16 → 有 16 字节本地空间
    // 本地变量 a: a-8(SP)
    // 本地变量 b: b-16(SP)
    MOVQ    AX, a-8(SP)   // 正确

运行 go vet ./... 会检测此类错误（vet 理解 Plan 9 汇编）。

✗ 忘记在 .go 声明文件中省略函数体
// 错误：有函数体，汇编实现会被忽略
package mymath

func Sum(a, b int) int {
    return 0  // 这会覆盖汇编实现！
}
// 编译错误：duplicate symbol 或静默使用 Go 实现
// 正确：声明无函数体（无花括号）
package mymath

// Sum returns the sum of a and b.
func Sum(a, b int) int
// 链接器会去 .s 文件找实现

// 同目录下需有：math_amd64.s（或 math.s）
// 否则编译报：missing function body
