Slice 底层结构

SliceHeader 三字段

核心

Slice 在运行时由 reflect.SliceHeader 表示，24 字节，包含三个字段：

SliceHeader
Datauintptr
Lenint
Capint
→
[0] [1] [2] [3] [4] [5] ...
  • Data：指向底层数组的指针
  • Len：当前有效元素数量（len(s)）
  • Cap：底层数组的总容量（cap(s)）
s := []int{1, 2, 3, 4, 5}
t := s[1:3]  // len=2, cap=4，共享底层数组
fmt.Println(len(t), cap(t))  // 2 4
t[0] = 99
fmt.Println(s)  // [1 99 3 4 5]：s[1] 也变了

Slice 扩容策略

append 触发扩容的规则

核心

当 append 导致 len > cap 时，Go 运行时会分配新的底层数组，将原数据拷贝过去，返回指向新数组的新 slice。

Go 1.18 之前：容量 < 1024 时翻倍，>= 1024 时每次增加 25%。

Go 1.18+：改为更平滑的增长策略，避免在 1024 处出现突变，综合考虑元素类型对齐等因素。

s := make([]int, 0, 3)  // len=0, cap=3
s = append(s, 1, 2, 3)  // len=3, cap=3，不扩容
s = append(s, 4)        // len=4，发生扩容；新 cap 由实现决定
// 原底层数组被废弃，s 指向新数组

// 扩容前保存的子切片不受影响（指向旧数组）
a := []int{1, 2, 3}
b := a               // b 和 a 共享底层数组
a = append(a, 4)   // a 扩容，指向新数组
a[0] = 99
fmt.Println(b[0])  // 1，b 仍指向旧数组

Map 底层结构

Go 1.24+ Swiss Table 实现

进阶

map 的语言契约是无序键值集合，具体布局属于运行时实现细节。Go 1.24 起，默认实现改为基于 Swiss Table 的开放寻址哈希表；旧版 hmap/bmap 描述不再代表当前默认实现。

  • group：8 个键值槽位配合控制字，记录空闲、删除或占用状态及哈希低 7 位
  • table / directory：使用探测序列处理冲突；大型 map 通过目录选择多个 table，并按 table 扩容或分裂
// 当前实现：开放寻址 + group 控制字并行匹配
// 小表整体扩容；大表通过目录进行局部 table 分裂
// 这些实现细节可能随 Go 版本继续变化

注意：规范只保证 map 迭代顺序未指定，且不保证两次遍历顺序相同；业务逻辑不能依赖所谓“随机顺序”。

Map 使用

初始化、操作与并发安全

核心
// 创建：make 可以预分配容量，减少 rehash
m := make(map[string]int, 100)  // 预分配 100 个槽位

// 读取（两值形式检查 key 是否存在）
v, ok := m["key"]  // ok=false 说明 key 不存在
v = m["missing"]  // 不存在时返回零值，不 panic

// 删除
delete(m, "key")  // key 不存在时是 no-op

// 迭代（顺序未指定）
for k, v := range m { ... }

// 并发不安全！多 goroutine 读写需要保护
var mu sync.RWMutex
mu.Lock()
m["k"] = 1
mu.Unlock()

// 或使用 sync.Map（读多写少场景）
var sm sync.Map
sm.Store("k", 1)
v, _ = sm.Load("k")

面试题

append 后原 slice 元素还能访问吗？▶
分两种情况：
1. 未发生扩容（len+n <= cap）：append 直接在原底层数组写入，原 slice 变量的 len/cap 不变，但内存已修改。如果有子 slice 或引用，仍能访问到新写入的数据。

2. 发生了扩容（len+n > cap）：Go 分配新数组，拷贝数据，原底层数组不再被新 slice 引用。此时原 slice 变量仍指向旧数组，可以读取原有数据，但新旧已经独立，修改互不影响。

关键：append 总是返回新的 slice header，必须用返回值，不能忽略。
map 的并发读写会发生什么？如何解决？▶
未同步的 map 并发读写属于数据竞争，程序不正确；当前运行时经常会以 concurrent map read and map write 或 concurrent map writes 致命终止，但不能把它当作同步或完整的竞争检测。应使用 -race 辅助检查。

解决方案：
1. sync.RWMutex：读操作用 RLock，写操作用 Lock，适合读多写少
2. sync.Map：适合读极多写少的场景，内部用两个 map（read/dirty）减少锁竞争
3. 分片锁（sharding）：将 map 按 key hash 分成多个 segment，每个 segment 独立加锁
4. channel 串行化：通过 channel 将 map 操作序列化到单个 goroutine
slice 和 array 的核心区别？▶
主要区别：
• 长度：array 长度是类型的一部分（[3]int != [4]int），编译时固定；slice 长度动态可变
• 值/引用：array 是值类型，赋值拷贝整个数组；slice 是引用类型，赋值只拷贝 header
• 内存：array 与 slice 的底层数组位于栈还是堆，由逃逸分析和编译器实现决定
• 传参：array 传参是拷贝（大数组建议传指针）；slice 传参只拷贝 header（三个字段）
• comparable：array 可以用 == 比较；slice 不能用 == 比较（只能与 nil 比较）
map 的 key 有什么限制？▶
map 的 key 必须是可比较（comparable）类型，即支持 == 和 != 操作的类型。

可以作为 key 的类型：bool、整数、浮点、复数、string、pointer、channel、interface、array（元素类型需可比较）、struct（所有字段需可比较）。

不能作为 key 的类型：slice、map、func（这些类型不支持 ==）。

小技巧：如果需要用 slice 作为 key，可以先 fmt.Sprint 或 strings.Join 转为 string；如果需要用 struct 作为 key，确保所有字段都可比较。
如何高效地从 slice 中删除某个元素？▶
几种方法：
1. 保持顺序（O(n)）：s = append(s[:i], s[i+1:]...)
2. 不保持顺序（O(1)）：s[i] = s[len(s)-1]; s = s[:len(s)-1]（用最后一个元素覆盖要删除的元素）
3. Go 1.21 slices 包：slices.Delete(s, i, i+1)

注意：删除后原 slice 末尾可能仍持有旧元素的引用（对于引用类型元素），需要手动置 nil 防止内存泄漏：s[len(s):len(s)+1][0] = nil 或在删除后清零尾部。

易错点

❌ 忽略 append 的返回值
func addElem(s []int) {
    append(s, 1)  // ❌ 编译错误
    // 即使不报错，s 也没有变化
}

// 调用者看到的 s 没有新元素
s := []int{1, 2}
addElem(s)
fmt.Println(s)  // [1 2]

append 返回新的 slice header，不接收返回值则白做。

// 正确：接收 append 的返回值
s := []int{1, 2}
s = append(s, 3)  // ✓

// 如果需要在函数内修改，传指针或返回新 slice
func addElem(s []int) []int {
    return append(s, 1)
}
s = addElem(s)  // ✓

append 必须赋值给变量（通常是原变量），函数传参 slice 时要返回修改后的版本。

❌ sub-slice 共享底层数组，修改一个影响另一个
a := []int{1, 2, 3, 4, 5}
b := a[1:3]  // [2 3]，共享底层数组
b[0] = 99
fmt.Println(a)  // [1 99 3 4 5]！a 也变了

// append 如果未超出 cap 也会影响原 slice
b = append(b, 88)
fmt.Println(a)  // [1 99 3 88 5]！

子切片与原切片共享内存，append 如未触发扩容仍会写入原数组。

a := []int{1, 2, 3, 4, 5}

// 用 copy 创建独立副本
b := make([]int, 2)
copy(b, a[1:3])  // b 独立
b[0] = 99
fmt.Println(a)   // [1 2 3 4 5]，a 不变 ✓

// Go 1.21 slices.Clone
import "slices"
b = slices.Clone(a[1:3])

需要独立副本时用 copy 或 slices.Clone，不要直接切片赋值。

❌ 未初始化的 map 写入 panic
var m map[string]int  // nil map

// 读可以（返回零值）
v := m["key"]  // v = 0，不 panic

// 写 panic！
m["key"] = 1
// panic: assignment to entry in nil map

声明但未用 make 初始化的 map 是 nil，写入操作会 panic。

// 正确：用 make 初始化
m := make(map[string]int)
m["key"] = 1  // ✓

// 或字面量初始化
m2 := map[string]int{
    "a": 1,
    "b": 2,
}

// struct 中的 map 字段也需要初始化
type Foo struct{ M map[string]int }
f := Foo{M: make(map[string]int)}

始终用 make 或字面量初始化 map，struct 中的 map 字段尤其容易忘记。

❌ 大 slice 子切片导致内存泄漏
// 读取大文件内容
big, _ := os.ReadFile("huge.log")
// 只取前 10 字节，但持有整个 big 的引用
header := big[:10]
// big（可能 1GB）无法被 GC 回收
// 因为 header 还在引用底层数组

小的子切片持有大的底层数组引用，导致大内存无法释放。

big, _ := os.ReadFile("huge.log")
// 用 copy 创建独立小切片
header := make([]byte, 10)
copy(header, big)
// big 可以被 GC 回收了
big = nil

// 或使用 bytes.Clone（Go 1.20+）
header = bytes.Clone(big[:10])

长期持有的子切片要用 copy 复制出来，让原大切片能被 GC 释放。
