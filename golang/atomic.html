基本原子操作

Add / Load / Store

[核心]

sync/atomic 包提供无锁的原子读写操作，底层映射到 CPU 原子指令（如 LOCK XADD）。Go 1.19+ 推荐使用类型安全的新 API。

  • atomic.AddInt64(&n, delta) — 原子加减，返回新值
  • atomic.LoadInt64(&n) — 原子读取
  • atomic.StoreInt64(&n, val) — 原子写入
  • Go 1.19+ 新 API：atomic.Int64、atomic.Bool、atomic.Pointer[T]
// Go 1.19+ 推荐写法
var counter atomic.Int64

counter.Add(1)
val := counter.Load()
counter.Store(0)

// 旧 API（兼容写法）
var n int64
atomic.AddInt64(&n, 1)
v := atomic.LoadInt64(&n)

CompareAndSwap

CAS 语义与 ABA 问题

[进阶]

CAS（Compare-And-Swap）原子地比较内存值与期望值，相等才写入新值，返回是否成功。是无锁数据结构的基础。

  • ABA 问题：值从 A 改为 B 再改回 A，CAS 认为未变化，实则状态已改变
  • 解决 ABA：引入版本号（stamp），Go 的 atomic.Pointer 或结合时间戳
  • 自旋锁：CAS 失败则重试，适合极短临界区
// CAS 自旋直到成功
var state atomic.Int32

func spinLock() {
    for !state.CompareAndSwap(0, 1) {
        runtime.Gosched() // 让出 CPU
    }
}

func spinUnlock() {
    state.Store(0)
}

// 带版本号防 ABA
type Stamped struct {
    val   int64
    stamp uint64
}

内存顺序

顺序一致性与 happens-before

[高级]

Go 的 atomic 操作提供顺序一致性（Sequential Consistency）保证，所有 CPU 观察到原子操作的顺序一致。

  • atomic 操作之间有 happens-before 关系，普通变量读写没有
  • 用 atomic 做"发布"标志：写 atomic 前的普通写对读 atomic 后的读可见
  • 与 Mutex 比较：Mutex 有上下文切换开销；atomic 无调度，但只保护单个值
  • 何时用 atomic：简单计数器、flag、单值状态机；复合状态仍需 Mutex
// 用 atomic 发布初始化结果
var (
    data     []byte
    ready   atomic.Bool
)

func init() {
    data = loadData()   // 普通写
    ready.Store(true)   // 原子发布
}

func handler() {
    if !ready.Load() { return }
    // data 此时可见（happens-before 保证）
    use(data)
}

atomic.Value

原子存储任意类型

[进阶]

atomic.Value 可原子存取 interface{}，适合 copy-on-write 模式：读多写少，每次写创建新副本，原子替换指针。

  • 第一次 Store 后，后续 Store 必须存相同类型，否则 panic
  • Store 的值不能为 nil
  • 典型用途：原子替换配置、路由表、白名单等只读快照
var configVal atomic.Value

type Config struct { Timeout int }

func updateConfig(c *Config) {
    configVal.Store(c) // 原子替换
}

func getConfig() *Config {
    return configVal.Load().(*Config)
}

// copy-on-write 更新
func patchConfig(timeout int) {
    old := getConfig()
    newC := *old           // 复制
    newC.Timeout = timeout
    updateConfig(&newC)
}

面试问答

atomic 和 mutex 的区别？各自适用场景？▶
atomic 基于 CPU 原子指令，无系统调用，无上下文切换，延迟约 1-5ns；mutex 在争用时涉及 goroutine 挂起和调度，延迟可达微秒级。atomic 适合单个整数/指针的原子更新（计数器、标志位）；mutex 适合保护复合操作或多个相关变量的一致性更新。
CAS 的 ABA 问题是什么，Go 中如何解决？▶
ABA 问题：线程读到值 A，被抢占后另一线程将 A→B→A，原线程 CAS(A, new) 成功，但中间状态变化被忽略。在链表等结构中可能导致节点已被删除重用但 CAS 仍然成功，引发悬挂指针。Go 中解决方案：使用版本号（将值和版本打包成 struct 用 128bit CAS），或直接使用带 GC 的安全指针（GC 保证不会重用地址），多数场景下 Go GC 已经规避此问题。
int32 和 int64 在 32 位平台的原子性问题？▶
在 32 位平台，64 位的原子操作（atomic.LoadInt64 等）要求变量8字节对齐。若 int64 变量在结构体中不对齐（如位于奇数偏移），原子操作会 panic。解决：将 int64 字段放在结构体的首位，或使用 atomic.Int64（Go 1.19+，内部保证对齐）。int32 在 32 位平台天然是原子的，无此问题。
atomic.Value 为什么要求每次 Store 相同类型？▶
atomic.Value 内部存储 interface{} （包含类型指针和数据指针）。若允许不同类型，Load 时类型断言就无法确定应该断言成什么类型，使用者无法安全读取。强制相同类型是为了让使用者可以放心地进行类型断言而不需要额外的类型检查逻辑。Go 1.17+ 引入了 atomic.Pointer[T]，通过泛型在编译期保证类型安全，是更好的选择。
什么情况下 atomic 操作仍然存在竞态？▶
atomic 只保证单次操作的原子性，不保证多步操作的原子性。例如：先 Load 再 Store（read-modify-write）两步之间仍有窗口，其他 goroutine 可以修改值。需要用 CAS 循环替代，或使用 Mutex 保护整个 read-modify-write 序列。检测工具：go test -race（Go race detector）能发现此类竞态。

常见陷阱

❌ 用 atomic 保护复合操作仍有竞态（vs ✅ CAS 循环或 Mutex）
// 竞态：Load 和 Store 不是原子的整体
var n atomic.Int64

func doubleIfPositive() {
    v := n.Load()      // 读
    if v > 0 {
        n.Store(v * 2) // 写：窗口期内可被修改
    }
}

两步之间另一 goroutine 可能修改 n，Store 会覆盖其修改。

// 正确：CAS 循环
func doubleIfPositive() {
    for {
        v := n.Load()
        if v <= 0 { return }
        if n.CompareAndSwap(v, v*2) {
            return
        }
        // CAS 失败则重试
    }
}

CAS 失败说明值已被修改，重新读取并重试，保证原子性。

❌ atomic.Value 存不同类型导致 panic（vs ✅ 固定类型或用泛型指针）
var v atomic.Value
v.Store("hello")    // string
v.Store(42)           // int: panic!
// panic: sync/atomic:
// store of inconsistently
// typed value into Value

第二次 Store 类型与第一次不同，运行时 panic。

// 方案1：固定存指针
var v atomic.Value
v.Store((*Config)(nil)) // 不行，nil panic

// 方案2：Go 1.19+ 泛型指针
var p atomic.Pointer[Config]
p.Store(&Config{})
cfg := p.Load() // *Config, 编译期类型安全

使用 atomic.Pointer[T] 获得泛型类型安全，无运行时 panic 风险。

❌ 64位原子变量在结构体中未对齐（vs ✅ 放在首字段或用新 API）
// 32位平台可能 panic
type Bad struct {
    flag bool   // 1 byte
    // 3 bytes padding
    count int64 // offset=4: 未对齐!
}
var b Bad
atomic.AddInt64(&b.count, 1) // panic

在 32 位平台，int64 原子操作要求 8 字节对齐。

// 正确：int64 放首位或用新 API
type Good struct {
    count int64 // 首字段，保证对齐
    flag  bool
}

// 或直接用 Go 1.19+ 类型
type Better struct {
    count atomic.Int64 // 内部对齐
    flag  bool
}

atomic.Int64 内部保证对齐，是最安全的做法。
