Functional Options 模式

问题：构造函数参数爆炸

核心

当一个结构体有多个可选参数时，传统做法要么用一个胖构造函数（调用者被迫传大量零值），要么单独暴露 setter（不利于链式初始化、并发安全）。Functional Options 把每个配置项封装成 func(*Server) 类型的函数，调用方按需传入，缺省值由构造函数设置。

// 选项类型
type Option func(*Server)

// 服务器结构体
type Server struct {
    addr     string
    timeout  time.Duration
    maxConns int
    tls      bool
}

// 选项函数
func WithTimeout(d time.Duration) Option {
    return func(s *Server) { s.timeout = d }
}

func WithMaxConn(n int) Option {
    return func(s *Server) { s.maxConns = n }
}

func WithTLS() Option {
    return func(s *Server) { s.tls = true }
}

// 构造函数：先设默认值，再应用选项
func NewServer(addr string, opts ...Option) *Server {
    s := &Server{
        addr:     addr,
        timeout:  30 * time.Second,
        maxConns: 100,
    }
    for _, opt := range opts { opt(s) }
    return s
}

// 调用方：只传关心的参数
s := NewServer(":8080",
    WithTimeout(10*time.Second),
    WithMaxConn(200),
    WithTLS(),
)

接口扩展无破坏性变更

进阶

新增选项只需新增一个 WithXxx 函数，不改变 NewServer 签名，已有调用方代码零改动。这是 Functional Options 对比 Config Struct 的最大优势——Config Struct 新增字段后，若调用方使用字面量初始化会触发编译错误。

对比维度Config StructFunctional OptionsBuilder
新增参数向后兼容❌ 字面量初始化报错✅ 只加新函数✅ 加新方法

链式调用❌✅ 变参传入✅ 方法链
可测试性高高高
Go 惯用度中⭐ 最高中

Middleware / 装饰器模式

HTTP Handler 包装链

核心

Go 的 http.Handler 接口只有一个方法，天然适合函数式包装。中间件接收一个 Handler、返回一个 Handler，通过嵌套调用形成洋葱模型——请求从外向内穿透，响应从内向外冒泡。

// 中间件类型别名（可读性）
type Middleware func(http.Handler) http.Handler

// Logging 中间件
func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s %v", r.Method, r.URL, time.Since(start))
    })
}

// Auth 中间件
func Auth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") == "" {
            http.Error(w, "unauthorized", 401)
            return
        }
        next.ServeHTTP(w, r)
    })
}

// Recover 中间件（必须最外层）
func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rv := recover(); rv != nil {
                http.Error(w, "internal error", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

函数式组合 Chain

进阶

Chain 工具函数把中间件列表折叠成单个包装，调用顺序是从左到右（第一个中间件最外层，最后执行 handler）。Recover 放第一位保证能捕获所有 panic。

// Chain 按顺序叠加中间件：Chain(h, m1, m2) == m1(m2(h))
func Chain(h http.Handler, mws ...Middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

// 组装：Recover → Logging → Auth → 业务Handler
handler := Chain(
    http.HandlerFunc(myHandler),
    Recover,   // 最外层：能捕获后续所有 panic
    Logging,   // 记录整个请求耗时
    Auth,      // 最靠近 handler：验证通过才执行
)
http.ListenAndServe(":8080", handler)

常用惯用法

Table-Driven 测试

核心

用结构体切片描述测试用例，一个循环驱动所有断言。新增用例只加一行数据，测试逻辑复用，失败信息带名字易定位。

func TestAdd(t *testing.T) {
    tests := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"正数", 1, 2, 3},
        {"负数", -1, -2, -3},
        {"零", 0, 0, 0},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := Add(tt.a, tt.b); got != tt.expected {
                t.Errorf("got %d, want %d", got, tt.expected)
            }
        })
    }
}

done channel 信号 + Context 透传

核心

用 chan struct{} 通知 goroutine 退出（关闭即广播）；生产级代码改用 context.Context 透传取消信号、截止时间和请求范围值，两者可结合使用。

// done channel 模式
done := make(chan struct{})
go func() {
    for {
        select {
        case <-done:
            return                // 收到关闭信号，退出
        case job := <-jobCh:
            process(job)
        }
    }
}()
close(done)  // 广播给所有监听者

// context 透传模式（推荐）
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()  // 务必 defer cancel，防止泄漏

go func(ctx context.Context) {
    select {
    case <-ctx.Done():
        log.Println("cancelled:", ctx.Err())
        return
    case result := <-doWork(ctx):
        handleResult(result)
    }
}(ctx)

错误 Sentinel + %w 包装

核心

包级 sentinel 错误用 errors.New 定义，调用方用 errors.Is 匹配；fmt.Errorf("...: %w", err) 包装错误链，保留原始错误可被 errors.Unwrap 拆解。

// 定义 sentinel
var (
    ErrNotFound  = errors.New("not found")
    ErrForbidden = errors.New("forbidden")
)

// 包装：保留错误链
func GetUser(id int) (*User, error) {
    u, err := db.Find(id)
    if err != nil {
        return nil, fmt.Errorf("GetUser(%d): %w", id, ErrNotFound)
    }
    return u, nil
}

// 匹配：不管包装了多少层
err := GetUser(42)
if errors.Is(err, ErrNotFound) {
    // 处理 404
}

// 自定义错误类型用 errors.As 提取
var ve *ValidationError
if errors.As(err, &ve) {
    log.Println(ve.Field, ve.Message)
}

常见陷阱集

goroutine 泄漏：忘记取消

高频

启动 goroutine 后没有提供退出路径，goroutine 永久阻塞在 channel 接收或无限循环，内存持续增长。常见于：HTTP 请求超时但 goroutine 还在等 DB 响应。

// ❌ 泄漏：goroutine 会一直等待 ch，永不退出
func leak() {
    ch := make(chan int)
    go func() {
        val := <-ch     // 永远阻塞
        process(val)
    }()
    // ch 从未被写入，goroutine 泄漏
}

// ✅ 修复：使用 context 控制生命周期
func noLeak(ctx context.Context) {
    ch := make(chan int, 1)
    go func() {
        select {
        case val := <-ch:
            process(val)
        case <-ctx.Done():
            return    // 退出路径
        }
    }()
}

map 并发写 panic

高频

Go 内建 map 不是并发安全的，多 goroutine 同时写（或一读一写）会触发 concurrent map writes panic。使用 sync.RWMutex 或 sync.Map（读多写少场景）保护。

// ❌ panic：并发写 map
m := map[string]int{}
go func() { m["a"] = 1 }()
go func() { m["b"] = 2 }()

// ✅ 方案一：sync.RWMutex 包装
type SafeMap struct {
    mu sync.RWMutex
    m  map[string]int
}
func (s *SafeMap) Set(k string, v int) {
    s.mu.Lock(); defer s.mu.Unlock()
    s.m[k] = v
}

// ✅ 方案二：sync.Map（读远多于写）
var sm sync.Map
sm.Store("a", 1)
v, ok := sm.Load("a")

循环变量闭包捕获

高频

Go 1.22 之前，for range 的循环变量是同一个内存地址，goroutine 闭包捕获的是引用而非值，所有 goroutine 可能读到循环结束后的同一个值。

// ❌ Go 1.21 及以前：全部打印最后一个值
for _, v := range []int{1, 2, 3} {
    go func() { fmt.Println(v) }()  // 捕获了变量 v 的地址
}

// ✅ 修复一：局部变量遮蔽
for _, v := range []int{1, 2, 3} {
    v := v  // 新建局部变量，捕获值拷贝
    go func() { fmt.Println(v) }()
}

// ✅ 修复二：通过参数传值
for _, v := range []int{1, 2, 3} {
    go func(n int) { fmt.Println(n) }(v)
}

// Go 1.22+ 循环变量语义已修正，每次迭代独立

interface nil 陷阱

进阶

接口由 (type, value) 两字段构成。把 nil 指针赋给接口变量，接口的 type 字段非 nil，接口本身不等于 nil。

type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

// ❌ 陷阱：返回 nil 指针包装进 error 接口
func getError(fail bool) error {
    var err *MyError  // nil *MyError
    if fail { err = &MyError{"oops"} }
    return err        // 即使 fail=false，返回的 error != nil！
}

err := getError(false)
fmt.Println(err == nil) // false ← 反直觉

// ✅ 修复：直接返回 nil（不通过具体类型）
func getError(fail bool) error {
    if fail { return &MyError{"oops"} }
    return nil  // 直接返回 nil，接口两字段都为零值
}

面试题

Functional Options 模式解决了什么问题？和 Builder 模式有何区别？▶
Functional Options 解决了构造函数参数爆炸和向后兼容扩展两个问题：可选参数多时调用方不必传大量零值；新增参数不改变函数签名，已有代码无需修改。

与 Builder 模式的区别：Builder 需要额外的 Builder 类型和 Build() 终结方法，适合参数之间有复杂依赖关系、需要统一验证的场景；Functional Options 更轻量，是 Go 社区的惯用法，配置项之间独立、各自验证时首选。两者都实现了"不传则用默认值"，但 Functional Options 在 Go 中对泛型/接口更友好。
Go 中如何实现 HTTP 中间件链？为何不用继承？▶
中间件是 func(http.Handler) http.Handler 类型的函数。通过嵌套调用（或 Chain 工具函数反向折叠）形成洋葱模型：请求从最外层中间件流入，最后到达业务 Handler，响应原路返回。

Go 不用继承因为接口+组合更灵活：中间件无需感知彼此的实现，只依赖 http.Handler 接口；可以在运行时动态组合；复用粒度更细。继承会导致深层次类型耦合，Go 的设计哲学是"组合优于继承"。
如何优雅地处理 goroutine 的生命周期？▶
核心原则：启动者负责回收。具体手段：
1. 传入 context.Context，goroutine 监听 ctx.Done() 退出；
2. 用 sync.WaitGroup 等待所有 goroutine 完成；
3. 用带缓冲 channel 或 errgroup（golang.org/x/sync）收集错误；
4. 服务关闭时调用 cancel()，给 goroutine 合理的清理时间（context.WithTimeout）。

避免：无限制地启动 goroutine（用 worker pool 限流）；goroutine 内 panic 未 recover（中间件层统一兜底）。
为什么 Go 中"不要过早抽象"？举例说明▶
Go 接口是隐式实现，接口应该在使用方定义，而非实现方强加。过早定义宽接口（大量方法）会让实现方和测试方都变得臃肿；只有当有两个以上实现、或需要 mock 测试时，才有必要提取接口。

例：一开始就定义 UserRepository interface { FindByID; FindByEmail; Create; Update; Delete; List; Count }，真实实现和 mock 都要实现 6 个方法。更好的做法是：各调用处只定义自己需要的小接口（interface{ FindByID(int) (*User, error) }），测试时只需 mock 这一个方法，后续合并也很容易。
context.WithValue 的 key 为什么要用自定义类型而不是字符串？▶
context.Value 的 key 比较用 ==，如果用字符串，不同包使用相同字符串作 key 会产生隐式冲突——A 包存的值可能被 B 包读到，造成数据泄漏或类型断言 panic。

使用包私有的自定义类型（如 type contextKey int 或 type contextKey struct{}），即使 key 的值相同，类型不同则 == 结果不同，天然隔离各包的命名空间。Go 官方文档也明确建议：不要用内建类型做 context key。

易错点

⚠ 易错 1：循环中启动 goroutine 捕获循环变量引用
// ❌ 所有 goroutine 看到最后一个值
funcs := make([]func(), 3)
for i := 0; i < 3; i++ {
    funcs[i] = func() {
        fmt.Println(i)  // 捕获引用
    }
}
for _, f := range funcs {
    go f()  // 打印三个 3
}

循环结束后 i=3，所有闭包访问同一地址，输出全为 3（Go 1.21 及以前）。

// ✅ 每次迭代创建新局部变量
funcs := make([]func(), 3)
for i := 0; i < 3; i++ {
    i := i  // 局部变量遮蔽
    funcs[i] = func() {
        fmt.Println(i)  // 捕获副本
    }
}
for _, f := range funcs {
    go f()  // 0 1 2（顺序不定）
}

Go 1.22+ 循环变量语义已自动修正，每次迭代有独立变量，但旧代码仍需注意。

⚠ 易错 2：middleware 链顺序错误（recover 未置最外层）
// ❌ Recover 在 Logging 内层
handler := Chain(h,
    Logging,   // 最外层
    Auth,
    Recover,   // ❌ 只能捕获 Auth 之后的 panic
)
// Logging 中间件 panic 无法被捕获

Recover 只能捕获其内部（靠近 handler 侧）的 panic，外层中间件的 panic 不在覆盖范围内。

// ✅ Recover 必须最外层
handler := Chain(h,
    Recover,   // ✅ 最外层，覆盖所有后续 panic
    Logging,
    Auth,
)
// 任意中间件或 handler panic
// 都能被 Recover 捕获并返回 500

中间件顺序决定执行顺序，Recover 放最前（最外层）才能保护整个链路。

⚠ 易错 3：包装了 nil 指针的接口变量不等于 nil
type Conn interface { Close() error }

func openConn(ok bool) Conn {
    var c *TCPConn  // nil 具体类型
    if ok { c = dial() }
    return c  // ❌ 接口有 type 字段！
}

conn := openConn(false)
// conn != nil，调用 Close() 会 panic
if conn != nil { conn.Close() }

接口 = (type=*TCPConn, value=nil)，type 不为零，故 conn != nil。

func openConn(ok bool) Conn {
    if !ok {
        return nil  // ✅ 直接返回 nil
    }
    return dial()
}

// 或者在需要判断时用 reflect：
func isNil(i interface{}) bool {
    if i == nil { return true }
    v := reflect.ValueOf(i)
    return v.Kind() == reflect.Ptr &&
           v.IsNil()
}

函数返回接口类型时，nil 具体指针要显式 return nil，不能通过具体类型变量间接返回。
