Handler 接口

ServeHTTP 与 HandlerFunc

[核心]

net/http 的核心是 http.Handler 接口，只有一个方法。HandlerFunc 是函数类型适配器，让普通函数实现 Handler。

  • ServeHTTP(w http.ResponseWriter, r *http.Request) — 处理一个 HTTP 请求
  • http.HandlerFunc(fn) — 将函数转为 Handler
  • 每个请求在独立 goroutine 中处理，Handler 必须是并发安全的
  • 写响应后调用 return，不会自动停止处理
// 实现 Handler 接口
type HelloHandler struct{ msg string }
func (h *HelloHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintf(w, "%s", h.msg)
}

// HandlerFunc：函数直接用作 Handler
http.HandleFunc("/hello", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    fmt.Fprintln(w, "Hello, Go!")
})

ServeMux 路由

路径匹配与路由注册

[核心]

http.ServeMux 是标准库路由器。Go 1.22+ 增强了路径匹配，支持方法和路径参数。DefaultServeMux 是全局实例，生产环境建议创建独立实例。

  • 精确匹配：/foo 只匹配 /foo
  • 树匹配：/foo/（以 / 结尾）匹配 /foo/ 开头的所有路径
  • Go 1.22+：GET /users/{id} 支持方法和路径参数，r.PathValue("id")
  • 第三方路由：chi、gorilla/mux 提供更丰富的功能（中间件链、正则等）
// Go 1.22+ 增强路由
mux := http.NewServeMux()
mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")
    fmt.Fprintf(w, "user: %s", id)
})
mux.HandleFunc("POST /users", createUser)

srv := &http.Server{
    Addr:    ":8080",
    Handler: mux,
}

Middleware 链

Handler 包装模式

[进阶]

Go 中间件是接受并返回 http.Handler 的函数，通过包装实现横切关注点。

  • 包装顺序即执行顺序：最外层先执行请求前逻辑，最后执行响应后逻辑
  • 常见中间件：日志、认证、限流、panic 恢复、超时
  • 可用 http.TimeoutHandler(h, dur, msg) 为 handler 设置超时
// 日志中间件
func Logger(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

// 认证中间件
func Auth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !isAuthorized(r) {
            http.Error(w, "Unauthorized", http.StatusUnauthorized)
            return
        }
        next.ServeHTTP(w, r)
    })
}

// 链式组合
handler := Logger(Auth(mux))

http.Client 与 Transport

复用连接与超时设置

[进阶]

http.Client 内含 Transport，负责 TCP 连接管理和复用。生产环境必须配置超时，不能用默认 Client。

  • http.DefaultClient 无超时，可能永久挂起
  • Client.Timeout 是端到端超时（含连接、等待、读取 Body）
  • Transport.DialContext 控制连接超时；ResponseHeaderTimeout 控制等待响应头超时
  • MaxIdleConns、MaxIdleConnsPerHost 控制连接池大小，避免频繁建连
var httpClient = &http.Client{
    Timeout: 30 * time.Second,
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   5 * time.Second,
            KeepAlive: 30 * time.Second,
        }).DialContext,
        MaxIdleConnsPerHost:   100,
        IdleConnTimeout:       90 * time.Second,
        ResponseHeaderTimeout: 10 * time.Second,
        TLSHandshakeTimeout:   10 * time.Second,
    },
}

面试问答

为什么不要用默认的 http.DefaultClient 做生产请求？▶
http.DefaultClient 的 Timeout 为零，表示无超时。在生产环境中，若目标服务响应缓慢或挂起，goroutine 会永久阻塞，最终耗尽资源。此外 DefaultTransport 的连接池参数（MaxIdleConns=100、MaxIdleConnsPerHost=默认2）可能不适合高并发场景。生产环境应创建自定义 http.Client，明确设置所有超时参数。
Handler 是否并发安全？如何保证？▶
每个 HTTP 请求在独立 goroutine 中调用 Handler.ServeHTTP，因此多个请求可能同时执行同一个 Handler。Handler 本身不保证并发安全——需要开发者保证：1) Handler 不持有可变状态，或状态由 Mutex/atomic 保护；2) 函数本地变量是栈上的，天然安全；3) 共享的 DB 连接池、缓存等本身应并发安全；4) ResponseWriter 不应在 ServeHTTP 返回后继续使用。
http.Server 有哪些超时设置，各自作用？▶
Server 有四个超时：1) ReadTimeout：读取完整请求（含 body）的最大时间；2) ReadHeaderTimeout：只读请求头的超时，比 ReadTimeout 更精确，防止 Slowloris 攻击；3) WriteTimeout：写响应的最大时间（从请求头读完后开始计时）；4) IdleTimeout：Keep-Alive 连接等待下一个请求的超时。推荐设置 ReadHeaderTimeout + WriteTimeout，并为每个 Handler 用 http.TimeoutHandler 设置业务超时。
什么是 ResponseWriter 的写入顺序要求？▶
HTTP 响应结构是：状态码 → 响应头 → 响应体。一旦开始写 Body（调用 Write），状态码和 Header 就被锁定发送出去。正确顺序：1) 先调用 w.Header().Set() 设置响应头；2) 调用 w.WriteHeader(code) 发送状态码（若不调用，第一次 Write 自动发送 200）；3) 调用 w.Write() 写 Body。WriteHeader 之后不能再修改 Header，Write 之后不能再 WriteHeader。
http.Transport 为什么不能在每次请求时重新创建？▶
Transport 内部维护连接池（idle connections），复用已建立的 TCP 连接，避免每次 DNS 解析、TCP 握手、TLS 握手。若每次请求重新创建 Transport，连接池丢失，每次都要重新建连，延迟增加 10-100 倍（尤其 TLS）。Transport 应作为包级变量或结构体字段，全局共享。同样，http.Client 也应全局复用，不要在 handler 内部创建。

常见陷阱

❌ 不读完 Body 导致连接不复用（vs ✅ 读完或 Discard）
resp, _ := client.Do(req)
defer resp.Body.Close()
if resp.StatusCode != 200 {
    return errBadStatus
    // Body 未读完就 return，
    // Close 后连接直接关闭不复用
}

仅 Close 未读完的 Body 会关闭底层连接，无法复用，影响性能。

resp, _ := client.Do(req)
defer func() {
    io.Copy(io.Discard, resp.Body)
    resp.Body.Close()
}()
if resp.StatusCode != 200 {
    return errBadStatus
}

Discard 耗尽剩余 Body 后 Close，连接可以被复用。

❌ 默认 Client 无超时（vs ✅ 自定义 Client 设置超时）
// http.DefaultClient 无超时！
resp, err := http.Get(slowURL)
// 若 slowURL 挂起，goroutine
// 永久阻塞，积累会耗尽资源

// http.Get 等价于：
// http.DefaultClient.Get(url)

生产环境绝不能用 http.DefaultClient 或 http.Get/Post 包级函数。

var client = &http.Client{
    Timeout: 10 * time.Second,
}

// 或带 context 的精细控制
ctx, cancel := context.WithTimeout(
    r.Context(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := client.Do(req)

全局自定义 Client 设置 Timeout，或用 context 控制单次请求超时。

❌ WriteHeader 后继续设置 Header（vs ✅ 先设 Header 再 WriteHeader）
func handler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    // WriteHeader 后设置 Header 无效！
    w.Header().Set("Content-Type", "application/json")
    w.Write(jsonData)
}

WriteHeader 后响应头已发送，再设置 Header 无效，日志会有 "superfluous response.WriteHeader" 警告。

func handler(w http.ResponseWriter, r *http.Request) {
    // 1. 先设置响应头
    w.Header().Set("Content-Type", "application/json")
    // 2. 再写状态码（或省略，Write 自动发 200）
    w.WriteHeader(http.StatusCreated)
    // 3. 写 Body
    w.Write(jsonData)
}

响应头必须在 WriteHeader 或首次 Write 之前设置。
