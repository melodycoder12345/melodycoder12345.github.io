基础概念

01

🏛️冯·诺依曼架构

现代计算机的基础由四大部件构成：
· CPU — 控制单元 + ALU + 寄存器，执行指令
· 内存（RAM） — 存储程序与数据，CPU 可直接寻址
· I/O 设备 — 磁盘、网卡、键鼠，通过总线与 CPU 交互
· 总线 — 地址线 / 数据线 / 控制线，连接所有部件
程序存储原则：指令与数据同存于内存，统一编址。

⚡性能瓶颈与优化思路

· 内存墙：CPU GHz 级，内存 ns 级，Cache 弥合延迟差
· 流水线：指令级并行提吞吐，一个周期推进一阶段
· 局部性：时间 / 空间局部性决定 Cache 命中率
· TLB：虚实地址转换的快表，命中则免页表遍历
· DMA：绕过 CPU 完成大块 I/O，释放 CPU 算力
· 内存屏障：阻止乱序执行破坏多核可见性

六条核心结论
⚙️ 流水线
流水线提吞吐不降延迟，单条指令仍需 5 个阶段。数据冒险 / 控制冒险是主要瓶颈，forwarding 和分支预测是补救手段。
🗄️ 缓存
L1 命中 ~4 周期，RAM ~200 周期，差距 50×。局部性是性能的核心杠杆。false sharing 让独立变量竞争同一缓存行，是隐性性能杀手。
🗺️ TLB
TLB 命中只需 ~1 周期额外开销，miss 则触发 4 级页表遍历（4 次内存访问）。TLB 是内核/进程性能的关键，hugepage 减少 TLB 压力。
🔌 DMA
DMA 将 I/O 的 CPU 代价从 O(n) 降为 O(1)。轮询=CPU 忙等，中断=CPU 被抢占，DMA=CPU 只参与配置和完成中断，最适合大块数据传输。
🚧 内存屏障
编译器和 CPU 都会重排指令。内存屏障阻止重排，保证多核可见性顺序。Go 的 sync/atomic 操作隐含全屏障语义，是 Go 内存模型的硬件根基。
⚛️ 原子指令
CAS（Compare-And-Swap）是 lock-free 算法的基石。x86 用 LOCK 前缀锁缓存行，ARM 用 LL/SC 监控器。高竞争场景自旋代价大，不如 mutex。
高频 Q & A
为什么要关心缓存行大小？Go 代码里如何避免 false sharing？
缓存以 64 字节为单位读写。两个变量若落在同一缓存行，不同 CPU Core 修改时会互相使对方缓存失效（MESI Invalidate），即使逻辑上无关联。Go 中常见修复：在 struct 字段间填充 _ [56]byte 让热变量独占缓存行，或用 sync.Mutex（已内置 padding）。
CPU 乱序执行为什么不会破坏单线程语义？多线程怎么会出问题？
CPU 保证单线程程序顺序语义——通过 ROB（重排序缓冲区）按原始程序序提交结果，外部不可见。但多线程时，另一个 Core 看到的写入顺序可能与程序序不同（Store Buffer 异步刷写），这就是为什么需要内存屏障来约束跨核可见顺序。
内存屏障与 Go 内存模型是什么关系？
Go 内存模型定义了 happens-before 规则（哪些操作在另一操作之前可见），这是语言层语义。硬件层用内存屏障（mfence/sfence）实现这些规则。atomic.Store 在 x86 编译为 LOCK XCHG，sync.Mutex.Unlock() 包含 store 屏障，保证临界区写对后续加锁者可见。
0.1 + 0.2 为什么不等于 0.3？实际项目如何处理？
IEEE 754 用二进制分数表示小数，0.1 和 0.2 都是无限循环二进制小数，存储时截断引入误差，两者相加结果为 0.30000000000000004。处理方案：金融场景用整数（分而非元）或 math/big.Float；比较时用 math.Abs(a-b) < 1e-9 而非  ==。
