NUMA

Non-Uniform Memory Access（非一致性内存访问）常见于多路服务器。处理器访问本地与远端内存的延迟和带宽不同，但差距不是固定倍数，取决于平台拓扑、互联、内存配置和并发负载。理解实际拓扑与测量结果是性能调优的前提。

核心术语
  • NUMA Node一组处理器和相对本地的内存；本地/远端成本需按目标机器测量。
  • NUMA Affinity绑定进程到节点，确保内存从同一节点分配。
  • False Sharing不同核修改同一 cache line，引发跨核失效风暴。
  • NUMA Balancing内核自动迁移页/进程减少远端访问。

NUMA 架构基础

  • UMA（一致性内存）：所有 CPU 通过共享总线访问统一内存，延迟相同，但带宽竞争随核数增加而恶化
  • NUMA 的优势：每个 socket 有本地内存总线，扩展核数时带宽随之扩展，无总线瓶颈
  • QPI/UPI 互联：Intel 用 QPI（QuickPath Interconnect，后改名 UPI）连接多个 socket，带宽约 50-100 GB/s，但仍低于本地 DDR5 内存带宽（~200 GB/s/channel）
  • 典型配置：双路服务器 2 个 NUMA 节点，四路服务器 4 个节点，访问延迟随 hop 数增加
  • 查看 NUMA 拓扑：numactl --hardware 或 lstopo

NUMA 内存分配策略

  • local（默认）：在当前 CPU 所在节点分配内存，最优策略
  • bind：强制从指定节点分配，若不足则 OOM，不跨节点
  • preferred：优先从指定节点分配，不足时可跨节点
  • interleave：轮询各节点分配，适合内存总带宽敏感（如大型内存映射文件）
# 查看 NUMA 拓扑 numactl --hardware # node 0 cpus: 0-23 node 1 cpus: 24-47 # node distances: 0-0:10 0-1:21 # 绑定到 node 0，内存也从 node 0 分配 numactl --cpunodebind=0 --membind=0 ./redis-server # 查看进程 NUMA 内存分布 numastat -p redis-server

False Sharing

⚠ 64 字节是 CPU cache line 的大小。若两个频繁写入的变量在同一个 cache line 中，它们会相互驱逐彼此的缓存，即使它们从不互相依赖。
// 糟糕：counter_a 和 counter_b 在同一 cache line struct BadCounters { int64_t counter_a; // 8 bytes int64_t counter_b; // 8 bytes，同一 cache line! }; // 正确：用 padding 隔离到不同 cache line struct GoodCounters { alignas(64) int64_t counter_a; alignas(64) int64_t counter_b; }; // Go 中的对齐 type Counter struct { _ [64]byte // padding v int64 _ [56]byte // padding }

NUMA 对数据库的影响

  • MySQL / PostgreSQL：默认不做 NUMA 绑定，内存可能分配在远端节点，建议：numactl --interleave=all mysqld（均匀利用多节点内存带宽）
  • Redis：单线程，优先绑定到单 NUMA 节点（numactl --cpunodebind=0 --membind=0），避免远端访问
  • JVM（Java）：G1/ZGC 有 NUMA-aware 内存分配（-XX:+UseNUMA），各 GC 线程倾向分配本地节点的 region
  • Kafka：JVM 进程，启用 -XX:+UseNUMA 即可，page cache 效果好于 JVM heap 调优
  • 大内存服务（>= 128GB 使用量）NUMA 调优收益最显著

Linux NUMA Balancing

  • 内核周期性地将进程的内存页标记为 PROT_NONE，触发 page fault 时记录访问来自哪个 CPU
  • 若发现进程频繁从远端节点访问内存，内核会迁移内存页到本地节点
  • 或者迁移进程线程到内存所在节点（task migration）
  • 可通过 /proc/sys/kernel/numa_balancing 开关，对于已 NUMA 绑定的服务建议关闭（减少 page fault 开销）
  • numastat 监控：watch numastat 观察 numa_miss（远端分配次数），优化目标是 miss 接近 0

Cache 层次与延迟参考

  • L1 Cache：~1ns，每核独占，64KB（指令+数据各 32KB）
  • L2 Cache：~4ns，每核独占，256KB~4MB
  • L3（LLC）Cache：~12ns，所有核共享，16-64MB
  • 本地 DRAM：~70ns，NUMA 本地节点内存
  • 远端 DRAM：~140-200ns，跨 NUMA 节点内存（2-3× 本地延迟）
  • NVME SSD 随机读：~100μs（1000× DRAM）
  • 理解这些延迟数字帮助判断性能优化方向：内存带宽瓶颈 vs NUMA 跨节点 vs cache miss
