面试题

x86 和 ARM 的内存一致性模型有什么不同？▶
x86 采用 TSO（Total Store Order）模型：store 操作通过 Store Buffer 异步写入，但所有 load 都能看到最新的 store（acquire 语义）。store 之间的顺序对其他核可见，只有 store-load 顺序可能被打乱。

ARM 采用弱内存模型（Weakly Ordered）：store-store、load-load、load-store、store-load 四种顺序都可能被重排。需要显式 dmb（Data Memory Barrier）指令保序。因此在 ARM 上更容易触发并发 bug，同时也给了编译器/CPU 更大的优化空间。
Go 的 sync/atomic 操作能替代所有 mutex 使用吗？▶
不能。sync/atomic 适合单一变量的原子读写（如计数器、标志位），保证该变量的读写是原子的且有内存顺序语义。
必须用 mutex 的场景：
• 多变量一致性（如更新多个相关字段需要保持一致）
• 复杂的 read-modify-write 操作（如 map 操作）
• 需要条件等待（配合 sync.Cond）
• 保护不可原子操作的数据结构（slice、map 等）
滥用 atomic 代替 mutex 往往导致代码难以理解且容易出错。
volatile 关键字（C/Java）能否代替内存屏障？▶
不能，两者语义不同：

C volatile：仅告诉编译器"每次都从内存读取，不要缓存到寄存器"，阻止编译器优化，但不阻止 CPU 乱序执行，也不保证多核可见性。在多线程中使用 volatile 是不够的。

Java volatile：语义强得多，等价于加了 acquire/release 屏障：写入 volatile 变量有 release 语义，读取有 acquire 语义，保证可见性和 happens-before。但仍不保证复合操作的原子性（如 i++）。

结论：C volatile 不能替代屏障；Java volatile 可以替代部分屏障用途，但不是全内存屏障（mfence）。
Go 内存模型中的 happens-before 如何通过 channel 建立？▶
Go 内存模型规定：
• 无缓冲 channel：第 n 次接收 happens-before 第 n 次发送完成。即接收方解阻塞意味着发送方已完成写入。
• 有缓冲 channel：第 n 次发送 happens-before 第 n 次接收完成。缓冲区容量 c，第 n 次接收 happens-before 第 n+c 次发送。
• close 操作：channel 关闭 happens-before 接收到零值。

实践：通过 channel 传递数据，发送前的所有写操作都 happens-before 接收后的所有读操作，无需额外 mutex/atomic。这是 Go 推荐的同步方式。

易错点

❌ Double-Checked Locking 反模式
// 错误！flag 的写可能在 init()
// 之前被其他核看到（重排序）
var flag int32
var obj *Object

func getInstance() *Object {
    if flag == 0 {      // 第1次检查
        lock()
        if flag == 0 {  // 第2次检查
            obj = &Object{}
            init(obj)
            flag = 1   // 可能被重排到
                       // init() 之前！
        }
        unlock()
    }
    return obj  // 可能返回未初始化的 obj
}
// 正确：使用 sync.Once
// 内部用 atomic 实现正确的
// double-checked locking
var once sync.Once
var obj *Object

func getInstance() *Object {
    once.Do(func() {
        obj = &Object{}
        init(obj)
    })
    return obj
}

// 或者用 atomic.Pointer（Go 1.19+）
var ptr atomic.Pointer[Object]

原则：sync.Once 是 Go 中 lazy initialization 的标准做法，底层已正确处理内存屏障。

❌ 用普通变量做并发标志位
// 错误！普通变量无内存顺序保证
var ready bool
var data int

// Thread 0
func writer() {
    data = 42
    ready = true  // 可能被重排到
                  // data=42 之前！
}

// Thread 1
func reader() {
    for !ready {}  // 可能永远看不到
                   // ready=true（寄存器缓存）
    use(data)  // data 可能仍是 0
}
// 正确：使用 atomic
var ready atomic.Bool
var data int

// Thread 0
func writer() {
    data = 42
    // StoreInt32 有 release 语义
    // 保证 data=42 在 ready=true 之前可见
    ready.Store(true)
}

// Thread 1
func reader() {
    // Load 有 acquire 语义
    for !ready.Load() {}
    use(data)  // 保证看到 data=42 ✓
}

原则：多 goroutine 共享的标志变量必须用 sync/atomic 或 channel，普通变量赋值没有可见性保证。
