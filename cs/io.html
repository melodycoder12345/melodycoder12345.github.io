面试题

中断与异常（Exception）的区别？▶
中断（Interrupt）是异步的，由外部硬件设备触发（如磁盘完成、网卡收包、时钟），与当前指令无关，CPU 完成当前指令后响应。异常（Exception）是同步的，由当前指令触发（如缺页 #PF、除零 #DE、非法指令 #UD），必须在当前指令处理完之前响应。两者统称"中断向量"，x86 通过 IDT（Interrupt Descriptor Table）统一分发，0-31 号为异常，32-255 号为外部中断和软中断（int 指令）。
为什么 DMA 需要 cache coherency 支持？▶
DMA 直接写内存（绕过 CPU Cache）。如果 CPU Cache 中有该内存区域的旧数据（stale），CPU 读到的是 Cache 中的旧值而非 DMA 写入的新值（Cache 一致性问题）。解决方案：1. Cache invalidate：DMA 写完后，OS 使对应 Cache line 失效，CPU 下次读时从内存取；2. Non-cacheable memory：DMA 缓冲区标记为不可缓存（WC/UC），性能差但简单；3. IOMMU + coherent DMA：现代 SoC 通过 IOMMU 保证 DMA 访问经过 Cache 一致性协议（CCI/CCN）。
Go runtime 中的网络 I/O 是用哪种模型？netpoller 工作原理？▶
Go 使用非阻塞 I/O + I/O 多路复用（Linux: epoll，macOS: kqueue，Windows: IOCP）。
netpoller 工作原理：
1. goroutine 调用 net.Read()，底层 syscall 设置 non-blocking；
2. 若 EAGAIN（数据未就绪），将 goroutine 挂起（gopark），M 线程不阻塞；
3. 专用 sysmon 线程或 findrunnable 调用 epoll_wait，fd 就绪时唤醒对应 goroutine（goready）；
4. goroutine 被调度到某个 P 上继续执行，完成读操作。
效果：用户层感觉是同步阻塞（goroutine 挂起），底层是非阻塞，M 线程不被占用。
软中断和硬中断的区别？NAPI 是什么？▶
硬中断：硬件直接触发，ISR 在中断上下文运行，不可睡眠，时间极短（微秒级）。软中断（softirq）：由硬中断 ISR 触发（raise_softirq），在中断返回时或 ksoftirqd 内核线程中执行，可处理耗时较长的任务（如 TCP/IP 协议栈处理）。
NAPI（New API）是 Linux 网络驱动的混合模型：高负载时，网卡触发一次硬中断后关闭后续中断，改为软中断轮询（budget 机制）处理积压的收包，避免中断风暴（interrupt storm）；低负载时恢复中断模式。这是中断 + 轮询的自适应组合。

易错点

⚠ Go goroutine 阻塞在 syscall
// 普通阻塞 syscall（如文件读写）
// goroutine G 调用 os.File.Read()
// → 触发阻塞 syscall
// → M 线程陷入内核等待
// → G 和 P 解绑
// → runtime 从 P 队列调度新的 M
//    (entersyscall / exitsyscall)

// 问题：
// 大量 goroutine 阻塞在文件 I/O
// → 大量 M 线程被创建
// → 线程数可达 GOMAXPROCS×n
// → 内存和调度开销激增
// 网络 I/O（netpoller 非阻塞模型）
// goroutine G 调用 net.Conn.Read()
// → 底层 syscall 设为 non-blocking
// → EAGAIN → G 挂起（gopark）
// → M 线程释放，继续跑其他 G
// → epoll_wait 检测 fd 就绪
// → goready(G) → G 重新调度

// 对比：
// 文件 I/O：M 阻塞，需更多 M
// 网络 I/O：M 不阻塞，高并发
// 解法：对文件 I/O 用 goroutine
//        + sync.WaitGroup 控制并发数

Go 的 netpoller 只对网络 socket 生效，普通文件 I/O 仍是阻塞 syscall，高并发文件读写需限制并发 goroutine 数量。

⚠ DMA 与 Cache 一致性
// 错误做法：直接用普通内存做 DMA
char buf[4096];
// CPU 预先读了 buf → 在 Cache 中
// 启动 DMA 写入 buf
dma_start(buf, 4096);
dma_wait();
// CPU 读 buf → 读到 Cache 旧数据！
// DMA 写的新数据不可见（stale）
printf("%s\n", buf); // 可能是旧数据
// 正确做法：Cache 一致性 DMA
// 1. 分配 DMA 一致性内存
buf = dma_alloc_coherent(dev,
        4096, &dma_addr, GFP_KERNEL);
// CPU 和 DMA 都看到同一份数据

// 2. 或者流式 DMA + 同步操作
dma_sync_single_for_device(...);
dma_start(dma_addr, 4096);
dma_wait();
dma_sync_single_for_cpu(...); // 失效Cache
// 现在 CPU 读到的是 DMA 写入的新数据

ARM/非 x86 平台的 DMA 一致性问题更常见，x86 因硬件一致性协议（MESI）通常自动处理，但仍需正确使用 DMA API。
