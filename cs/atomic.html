面试题

CAS 操作是原子的，为什么还需要 for 循环重试？▶
CAS 是"比较并交换"的单次原子操作——它保证 compare 和 swap 之间不被打断，但不保证一定成功。当多个 goroutine 并发修改同一变量时，某个 goroutine 的 CAS 可能因为 expected != *addr 而失败。失败说明有其他 goroutine 先完成了写入，当前 goroutine 需要重新读取最新值再尝试，这就是 CAS 自旋循环的本质：乐观锁 + 重试。
ABA 问题是什么？在什么场景下会产生实际危害？Go 如何解决？▶
ABA 问题：goroutine G1 读取 old=A，此时 G2 将值改为 B 再改回 A，G1 的 CAS(A,new) 成功，但中间经历了 B 状态被忽略。对计数器（单调递增）无害，但对无锁链表 pop 有害：弹出 A 后链表结构已变，再次匹配 A 指针会操作已释放的内存。Go 解决方案：sync/atomic.Pointer[T] 用带版本号思路比较；或用 sync.Mutex；链表 pop 场景推荐用 channel 替代。
x86 的 LOCK CMPXCHG 和 ARM 的 LDREX/STREX 有什么本质区别？性能上有什么影响？▶
x86 用 LOCK 前缀锁定总线/缓存行，在操作期间阻止其他 CPU 访问该地址，是一种"悲观锁"硬件实现，代价是总线仲裁延迟。ARM 用独占监控器（Exclusive Monitor）—— LDREX 标记监视，STREX 检查监控器是否仍有效，不锁总线，是"乐观"方式。性能上：ARM LL/SC 在低竞争时开销更小（不锁总线），高竞争时 STREX 失败率高导致更多重试；x86 LOCK 延迟固定但在超高并发下总线争用明显。现代 x86 已用 MESI 缓存一致性协议优化，很少真正锁总线。
sync/atomic.AddInt64 和手写 CAS 循环，各自适合什么场景？▶
atomic.AddInt64 底层是单条原子指令（x86: LOCK XADD，ARM: LDADDAL），适合简单的加减操作，开销最小。手写 CAS 循环适合：1) 需要"先读取再条件写"的复合逻辑（如 if val > threshold { val = newVal }）；2) 更新非数值类型（指针、复合结构）；3) 实现自定义无锁数据结构。原则：能用 atomic.Add/Swap/Load/Store 解决的不要用 CAS 循环，CAS 循环能解决的不要用 mutex。
无锁数据结构（lock-free）一定比有锁更快吗？什么情况下 mutex 反而更好？▶
不一定。lock-free 在低竞争、短临界区时优势明显（避免内核陷入、上下文切换）。但以下场景 mutex 更好：1) 高竞争：大量 goroutine 争同一地址，CAS 失败率 > 50% 时自旋浪费 CPU；2) 临界区操作复杂：多个变量需要原子更新时，CAS 无法保证跨变量原子性；3) 需要等待而非自旋：mutex 在等待时让出 CPU，CAS 自旋持续占用。Go runtime 的 sync.Mutex 在有竞争时会先自旋再进入 futex 等待，比纯 CAS 自旋更节能。

易错点

❌ 原子操作组合不是原子事务
// 错误：两个原子操作的组合不是原子的
if atomic.LoadInt64(&x) > 0 {
    // 这里 x 可能已被其他 goroutine 修改
    atomic.AddInt64(&x, -1) // 可能变负！
}
// 正确：用 CAS 循环或 mutex 保护
for {
    old := atomic.LoadInt64(&x)
    if old <= 0 { break }
    if atomic.CompareAndSwapInt64(
        &x, old, old-1) {
        break
    }
}

原则：atomic.AddInt64 是原子的，但多个 atomic 操作的组合不是原子的，需要 mutex 或 CAS 循环保护。

❌ CAS 自旋在高竞争下浪费 CPU
// 1000 个 goroutine 争同一计数器
// CAS 失败率极高，99% 时间在自旋
func inc(c *int64) {
    for {
        old := atomic.LoadInt64(c)
        if atomic.CompareAndSwapInt64(
            c, old, old+1) { return }
        // 高竞争下此处反复循环
    }
}
// 高竞争下直接用 atomic.AddInt64
// 或 sync.Mutex 效率更高
var mu sync.Mutex
var counter int64

func inc() {
    // 方案1：内置原子加（推荐）
    atomic.AddInt64(&counter, 1)
    // 方案2：复杂逻辑用 mutex
    mu.Lock()
    counter++
    mu.Unlock()
}

原则：大量 goroutine 争同一地址时，mutex（内核级 futex）让出 CPU 更省电，CAS 自旋持续占用核心。

❌ Go 没有暴露弱内存序（有意为之）
// 其他语言可以选择内存顺序：
// C++ std::atomic<int>
val.store(1, std::memory_order_relaxed)
val.load(std::memory_order_acquire)
// Go 没有这种选项——全部 SeqCst
// Go 的 sync/atomic 全部是顺序一致
// （Sequential Consistency），最强内存序
// 不如 Relaxed/Acquire/Release 性能好
// 但 Go 有意不暴露弱内存序，
// 因为弱内存序极易误用产生 subtle bug

// 正确：接受 Go 的设计，不要试图
// 用 unsafe 手动绕过内存屏障
atomic.StoreInt64(&flag, 1) // SeqCst

原则：Go 的 sync/atomic 默认顺序一致，这是有意为之的安全设计——不要用 unsafe 绕过，收益微乎其微，风险极高。
