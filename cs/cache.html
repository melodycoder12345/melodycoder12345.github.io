面试题

Cache line 大小通常是多少？为什么是这个大小？▶
现代 CPU（x86/ARM）的 Cache line 通常是 64 字节。这个大小是工程权衡的结果：
• 太小：空间局部性利用率低，tag 存储开销大；
• 太大：传输延迟增加，false sharing 概率上升，在 miss 时浪费带宽（加载了不需要的数据）。
64B 对应 DDR 内存总线一次突发传输（burst transfer）的典型大小，与内存子系统的物理特性匹配。
MESI 协议中 M→S 状态转换会发生什么？▶
当 Core0 持有 M（Modified，脏数据）状态的 cache line，而另一个 Core1 发出读请求时，会触发 write-back + share 流程：
1. Core0 通过总线嗅探（bus snooping）感知到 Core1 的读请求；
2. Core0 将脏数据写回（write-back）到内存；
3. Core0 的状态从 M 降为 S；
4. Core1 从内存读取数据，状态也设为 S。
最终两个核都持有干净的共享副本。
False Sharing 如何检测和修复？▶
检测：
• perf stat -e cache-misses,LLC-load-misses ./app
• perf c2c record ./app（Linux perf c2c 专门检测 cache-to-cache false sharing）
• Intel VTune Profiler 的 Memory Access 分析

修复：
• Padding 对齐：在变量间插入填充字节，使其分属不同 cache line；
• Go 中常用 _ [56]byte 或 _ [64-unsafe.Sizeof(x)]byte；
• 重新设计数据结构，将不同线程访问的字段分离到不同结构体。
为什么顺序遍历数组比随机访问快得多？▶
两个核心原因：
1. 空间局部性（Spatial Locality）：CPU 以 64B cache line 为单位加载数据，顺序访问时每次 cache miss 会预加载后续元素，命中率极高（L1 hit ~4 周期）。随机访问每个元素大概率触发新的 miss（L3 miss ~200 周期）。
2. 硬件预取（Hardware Prefetcher）：现代 CPU 检测到步长规律的访问模式后，会提前将数据从内存预取到 cache，顺序访问完美触发预取器。随机访问无规律，预取器失效。
典型差距：顺序访问带宽可达 40-100 GB/s，随机访问可能只有 1-5 GB/s。

易错点

❌ 误解 MESI 的 E 状态
// 常见误解：
// E（Exclusive）= 独占
// 以为读取操作都需要
// 经过总线通知

// 实际上 E 状态意味着：
// 1. 我是唯一持有者
// 2. 数据是干净的（与内存一致）
// 3. 可以静默转换为 M
//    不需要任何总线通信！

// E→M：直接写，无总线流量

误区：认为 E 状态写入也需要总线 Invalidate 通知。

// 正确理解 E 状态的价值
// E 是重要的性能优化：

// S→M（共享→修改）：
//   需要发送 Invalidate
//   等待所有核的 Ack
//   有总线流量开销

// E→M（独占→修改）：
//   直接修改，无总线通信
//   无需等待任何 Ack
//   这就是 E 状态的意义！

关键：E 状态允许无总线流量的静默 E→M 转换，是 MESI 相比 MSI 协议的核心优化。

❌ False Sharing 难以靠肉眼发现
// 看起来没问题的代码：
type Stats struct {
    Hits   int64  // offset 0
    Misses int64  // offset 8
}
// Thread 0 只写 Hits
// Thread 1 只写 Misses
// 逻辑上完全独立...

// 但 Hits 和 Misses 在
// 同一 64B cache line！
// 严重的 false sharing

陷阱：两个变量逻辑独立，但物理上共享同一 cache line。

// 修复：padding 隔离
const CacheLineSize = 64

type Stats struct {
    Hits   int64
    _      [56]byte // padding
    Misses int64
    _      [56]byte // padding
}
// 现在 Hits 和 Misses
// 各占独立 cache line

// 检测工具：
// perf c2c record ./app
// perf c2c report

修复：用 padding 使每个热点字段独占一个 cache line（Go sync.Mutex 内部也这样做）。
