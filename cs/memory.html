面试题

虚拟地址空间的大小和物理地址空间的大小有什么关系？▶
两者可以完全独立。x86-64 虚拟地址空间为 256TB（48位），而物理内存可能只有 16GB。虚拟地址空间可以远大于物理内存——这正是虚拟内存的价值所在：通过 swap/文件映射让程序"看到"比物理内存更大的地址空间。反过来物理内存也可大于单个进程的虚拟空间（多进程共享物理内存）。
TLB 为什么是全相联 Cache？通常有多少条目？▶
TLB 是全相联（fully-associative）结构，因为任意虚拟页号都可以映射到 TLB 中的任意条目，没有组索引限制，命中率最高。全相联的缺点是比较电路复杂，所以 TLB 容量很小。典型 L1 dTLB 有 64 条目（4KB页），L1 iTLB 有 128 条目，L2 TLB（STLB）有 1024~2048 条目。Intel Tiger Lake 的 L1 TLB 共 128 条目 + 2048 条目的 STLB。
多级页表 vs 倒排页表 vs Hugepage，各自的权衡？▶
多级页表（x86-64 四级）：只需为实际使用的虚拟地址分配页表内存，稀疏地址空间内存开销小，但遍历需要 4 次内存访问。
倒排页表：以物理帧为索引，整个系统共一张表，内存占用固定（正比于物理内存），但查找需哈希，TLB miss 代价高，x86 不用。
Hugepage（2MB/1GB）：一条 TLB 条目覆盖更大范围，TLB 压力小，适合 NUMA 大内存应用；缺点是内存碎片风险高，分配失败概率更大。
mmap 与 malloc 在缺页处理上有什么区别？▶
malloc 底层通过 brk/sbrk 或 mmap（大块）扩展堆，缺页时 OS 分配零页（anonymous mapping），写时才真正分配物理帧（demand paging）。mmap 文件映射的缺页需要从文件读取数据（file-backed），会触发磁盘 I/O，延迟高于匿名页；但 mmap 的好处是多进程可共享同一物理页（COW），且内核可以直接回收 clean page 而无需 swap。

易错点

⚠ TLB Shootdown：多核陷阱
// 进程 A 修改了页表（unmap/mprotect）
// 其他 CPU 的 TLB 仍缓存旧映射
// 必须通知所有 CPU 刷新 TLB

// Linux 内核：
// tlb_finish_mmu()
//   → send IPI to all CPUs
//   → each CPU: invlpg / CR3 reload
// 高核数时 IPI 广播是扩展瓶颈

TLB shootdown 是多核扩展的主要瓶颈之一，频繁 mmap/munmap 的程序在高核数机器上会有严重性能退化。

// 优化方案：
// 1. 延迟 TLB 刷新（batch）
// 2. 使用 PCID（Process Context ID）
//    让不同进程共用 TLB 而不需全刷
//    Linux 4.14+ 在 x86-64 开启 PCID
// 3. 减少 munmap 频率：
//    用内存池复用虚拟地址范围
//    避免频繁 malloc/free 大块内存

PCID 是 x86 的硬件特性，允许 TLB 条目携带进程标签，上下文切换无需全刷 TLB。

⚠ Hugepage 与 Go Runtime
// 2MB Hugepage 减少 TLB 条目数
// 64 条目 TLB × 2MB = 128MB 覆盖
// vs 64 条目 × 4KB = 只有 256KB

// 风险：内存碎片
// 系统无法组合出连续 2MB 物理页
// → hugepage 分配失败
// → 回退到 4KB 页，性能抖动

// Go runtime 的问题：
// GC 后大量小对象释放，
// 形成碎片化 hugepage，
// 导致 RSS 虚高（页未归还 OS）
// Go 1.16+ Linux 使用
// Transparent Hugepage (THP)
// MADV_HUGEPAGE hint

// 调优：
// echo madvise > /sys/kernel/mm/
//   transparent_hugepage/enabled

// Go 应用可通过 GOGC 和
// runtime/debug.FreeOSMemory()
// 主动归还内存页给 OS

// 对延迟敏感服务建议：
// GOGC=off + 手动触发 GC
// 或使用 arena 手动管理内存

Go 1.16+ 在 Linux 上对 heap arena 使用 MADV_HUGEPAGE，可提升大内存程序 TLB 命中率约 10-20%。
