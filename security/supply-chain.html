Security / Supply Chain / B 类型

供应链安全

现代软件 90% 的代码来自第三方依赖和开源组件。当攻击者无法直接入侵目标时，转而污染上游软件供应链——镜像、依赖包、构建环境。SBOM 是物料清单，Cosign 是防伪签名，go.sum 是校验和，每一层都是抵御供应链攻击的防线。

SBOMSPDXCycloneDXCosignSigstoresyftDependabotgo.sumKeyless
核心威胁模型：攻击者不攻击你的代码，而是攻击你信任的代码。供应链攻击的特点是从可信渠道投递恶意内容，传统安全扫描无法发现。
核心术语
SBOMSoftware Bill of Materials，软件物料清单，记录软件中所有组件的完整列表，包括版本、许可证、来源。
SigstoreLinux Foundation 项目，提供免费、透明的软件签名基础设施，包括 Cosign（签名工具）、Fulcio（CA）、Rekor（透明日志）。
Keyless 签名使用 OIDC 身份（如 GitHub Actions workflow）做临时密钥签名，无需管理长期密钥，签名可通过工作流身份验证。
SLSASupply chain Levels for Software Artifacts，Google 提出的供应链安全成熟度框架，L1-L4 逐级加固。
Provenance软件制品的出处证明，记录"谁"在"何时"用"什么"构建了这个版本，SLSA 的核心概念。

供应链攻击背景：真实案例

了解真实攻击才能理解防御的必要性：

SolarWinds Orion 后门 2020
攻击手法：攻击者（Cozy Bear/APT29）入侵了 SolarWinds 的构建服务器，在 Orion 软件的合法构建流程中植入后门 SUNBURST。恶意代码随官方软件更新推送给 18,000+ 客户（含美国政府、微软、FireEye）。

关键特征：代码经过正常签名，来自官方渠道，传统病毒扫描无法检测。后门在安装后休眠 14 天再激活，绕过沙箱检测。

防御启示：构建环境必须有独立安全保障；SBOM 可帮助快速定位受影响的组织；需要 Build Provenance（构建出处证明）验证构建过程的完整性。
xz-utils 后门 2024
攻击手法（社会工程学）：攻击者"Jia Tan"用 2 年时间通过持续贡献高质量 patch 建立信任，逐步获得 xz-utils 核心开发者权限。最终在 5.6.0/5.6.1 版本中植入后门，通过 liblzma 劫持 RSA_public_decrypt，为特定 SSH 密钥提供 RCE 通道。

关键特征：后门被混淆在测试文件（.m4 脚本）中，仅在 deb/rpm 打包流程中激活；正常 GitHub 源码编译不包含后门。Andres Freund 在注意到 SSH 延迟异常后靠人工审计发现。

防御启示：开源项目的代码审查和维护者身份验证需要更严格的机制；重要库的变更需要多人审核；SBOM 帮助快速排查哪些系统引入了受影响版本。
共同规律：两次攻击都通过合法渠道投递，且攻击者耐心准备时间以月/年计。防御方向：不仅要扫描代码，还要验证构建过程、签名和组件出处。

SBOM：软件物料清单

SBOM 是"你的软件里用了什么"的完整清单，类比食品的配料表。当新的 CVE 出现时，SBOM 可在分钟内定位受影响的服务：

  • SPDX：Linux Foundation 标准，ISO/IEC 5962:2021，JSON/YAML/RDF 格式，支持许可证合规分析
  • CycloneDX：OWASP 标准，JSON/XML，对安全分析更友好，被 Grype 原生支持
  • syft：Anchore 出品，可从镜像、目录、文件系统生成 SBOM，支持两种格式输出
  • grype：基于 SBOM 扫描 CVE，对接 NVD、GitHub Advisory、OSV 等多个漏洞数据库
# 1. 生成镜像的 SBOM
syft myapp:v1.2.3 -o cyclonedx-json > sbom.json
syft myapp:v1.2.3 -o spdx-json > sbom-spdx.json

# SBOM 内容示例（CycloneDX 片段）：
# {
#   "bomFormat": "CycloneDX",
#   "components": [
#     {
#       "name": "log4j-core",
#       "version": "2.14.0",
#       "purl": "pkg:maven/org.apache.logging.log4j/log4j-core@2.14.0",
#       "licenses": [{"license": {"id": "Apache-2.0"}}]
#     },
#     {
#       "name": "github.com/gin-gonic/gin",
#       "version": "v1.9.0",
#       "purl": "pkg:golang/github.com/gin-gonic/gin@v1.9.0"
#     }
#   ]
# }

# 2. 用 SBOM 扫描 CVE
grype sbom:./sbom.json --fail-on critical

# 输出示例：
# NAME          INSTALLED  FIXED-IN  TYPE  VULNERABILITY  SEVERITY
# log4j-core    2.14.0     2.17.0    java  CVE-2021-44228 Critical

# 3. 查询受 log4shell 影响的所有服务
# 对每个服务的 SBOM 执行：
grype sbom:sbom.json -q | grep "CVE-2021-44228"
# 分钟内完成全公司服务的影响排查

# 4. 将 SBOM 存储在镜像仓库（Cosign attach）
cosign attach sbom --sbom sbom.json myapp:v1.2.3
# SBOM 与镜像同仓库存储，易于审计
实战价值：log4shell（CVE-2021-44228）爆出时，有 SBOM 的公司 1 小时内完成影响范围排查；没有的公司花了数天甚至数周。SBOM 不仅是安全工具，也是合规和事件响应的基础设施。

镜像签名：Sigstore / Cosign

镜像 tag 是可变引用——同一个 :latest 可以指向完全不同的内容。镜像签名对不可变的 sha256 摘要签名，提供防篡改保证：

传统问题

镜像 tag 被覆盖（恶意推送）或 registry 被攻击，Pull 到的镜像内容与预期不一致，且无法察觉

Cosign 方案

对镜像摘要（sha256:...）签名，签名以 OCI 格式存储在同一 registry，验证时对比签名和摘要

Keyless 签名

GitHub Actions 通过 OIDC 获取临时证书（Fulcio CA），用临时密钥签名，私钥立即销毁，签名记录写入 Rekor 透明日志

K8s 准入控制

Admission Webhook（Sigstore Policy Controller / Kyverno）在 Pod 创建时强制验证镜像签名，未签名的镜像拒绝部署

# === 镜像签名（GitHub Actions 中使用 Keyless）===

# .github/workflows/build.yml
jobs:
  build:
    permissions:
      id-token: write       # 必须：允许 OIDC token 获取
      packages: write
    steps:
    - name: Build and push
      uses: docker/build-push-action@v5
      with:
        push: true
        tags: ghcr.io/myorg/myapp:v1.2.3

    - name: Sign image with Cosign (Keyless)
      uses: sigstore/cosign-installer@v3
    - run: |
        cosign sign --yes \
          ghcr.io/myorg/myapp@$(docker inspect \
            --format='{{index .RepoDigests 0}}' \
            ghcr.io/myorg/myapp:v1.2.3 | cut -d@ -f2)
        # 签名绑定到摘要（sha256），而非可变的 tag
        # 临时密钥用完即销毁，无密钥管理负担

# === 验证镜像签名 ===
cosign verify \
  --certificate-identity "https://github.com/myorg/myapp/.github/workflows/build.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  ghcr.io/myorg/myapp:v1.2.3

# 验证通过输出：
# Verification for ghcr.io/myorg/myapp:v1.2.3 --
# The following checks were performed on each of these signatures:
#   - The cosign claims were validated
#   - Existence of the claims in the transparency log was verified offline
#   - The code-signing certificate claims were validated

# === K8s Admission Webhook 强制验签 ===
# 使用 Sigstore Policy Controller
apiVersion: policy.sigstore.dev/v1alpha1
kind: ClusterImagePolicy
metadata:
  name: require-signed-images
spec:
  images:
  - glob: "ghcr.io/myorg/**"    # 匹配的镜像范围
  authorities:
  - keyless:
      url: https://fulcio.sigstore.dev
      identities:
      - issuer: https://token.actions.githubusercontent.com
        subject: "https://github.com/myorg/myapp/.github/workflows/build.yml@refs/heads/main"
  # 未通过验证的镜像 → AdmissionWebhook 拒绝部署

依赖安全

依赖包是供应链中最大的攻击面——你直接信任了成千上万行你从未读过的代码：

  • go.sum：Go Modules 的校验和文件，记录每个依赖的 sha256 摘要，go get 时自动校验，防止依赖被中间人篡改
  • npm audit / pip audit：扫描已知 CVE，与 npm Advisory、PyPA Advisory 数据库对比
  • Dependabot：GitHub 原生，自动检测依赖更新和安全漏洞，创建升级 PR
  • Renovate：更灵活的依赖更新工具，支持 monorepo、自定义规则、版本分组
  • 私有镜像仓库：使用内部代理缓存公共镜像，避免直接依赖 Docker Hub（被删除或污染风险）
# Go：go.sum 校验和保护
# 每个依赖的行格式：
# module@version h1:hash=
# github.com/gin-gonic/gin v1.9.0 h1:ZDYWmrnFbnIIEKZjPyfkRhjGA5e2GQKV8bHmGNT50DY=
# github.com/gin-gonic/gin v1.9.0/go.mod h1:W1Me9+hsUSyj3CePGrd1/QrKJMSJ1Tu/0hFEH89961k=

# GONOSUMCHECK：私有模块不走公共 sum 校验
export GONOSUMCHECK=github.com/mycompany/*
export GONOSUMDB=github.com/mycompany/*

# GOPROXY 使用内部代理（避免直接访问公网）
export GOPROXY=https://goproxy.mycompany.com,direct

# 扫描 Go 依赖 CVE
govulncheck ./...    # Google 官方工具，直接分析调用图
# 只报告实际调用到的漏洞函数（减少误报）

# npm：扫描和修复
npm audit                  # 列出已知漏洞
npm audit fix              # 自动修复（minor/patch 版本）
npm audit fix --force      # 包含 breaking change 的修复（需测试）

# 锁定依赖版本（防止浮动版本被替换）
npm ci                     # 严格按 package-lock.json 安装，不允许升级

# pip：依赖安全
pip-audit                              # 扫描 requirements.txt
pip-audit --requirement requirements.txt --fix   # 自动修复

# 固定版本（生产环境）
pip freeze > requirements-lock.txt    # 锁定所有依赖精确版本

# Dependabot 配置（.github/dependabot.yml）
version: 2
updates:
- package-ecosystem: "gomod"
  directory: "/"
  schedule:
    interval: "weekly"
  groups:
    go-dependencies:
      patterns: ["*"]        # 将所有 Go 依赖升级合并为一个 PR
  open-pull-requests-limit: 5

- package-ecosystem: "docker"

typosquatting 警告：npm/PyPI 中存在大量故意拼写相似的恶意包（如 lodahs 冒充 lodash）。安装前核对包名，使用内部代理仓库缓存白名单包，可避免此类攻击。

SLSA 框架：供应链安全成熟度

SLSA（Supply chain Levels for Software Artifacts）由 Google 提出，提供可量化的供应链安全等级：

等级要求防御的威胁
SLSA L1构建过程有脚本记录，可生成 Provenance（出处元数据）防止误操作覆盖构建产物
SLSA L2Provenance 由构建服务（如 GitHub Actions）自动生成和签名防止开发者本地构建替换 CI 产物
SLSA L3构建环境隔离，Provenance 不可伪造（硬件级信任根）防止 CI 系统本身被攻击
SLSA L4双人审核所有变更，可复现构建（hermetic build）防止内部人员作恶（如 xz-utils 场景）
 
# GitHub Actions SLSA Provenance 自动生成
jobs:
  build:
    uses: slsa-framework/slsa-github-generator/.github/workflows/builder_go_slsa3.yml@v1.9.0
    with:
      go-version: "1.22"
    # 自动生成 SLSA L3 级别 provenance
    # Provenance 记录：
    # - 构建触发的 workflow 和 commit sha
    # - 构建使用的镜像和工具版本
    # - 输出产物的 sha256 摘要
    # - OIDC 签名（可独立验证）

# 验证 SLSA Provenance
slsa-verifier verify-artifact myapp-binary \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/myorg/myapp \
  --source-tag v1.2.3
# 验证确认：这个二进制确实由指定 commit 的官方 CI 构建

面试问答

SBOM 和漏洞扫描有什么区别？为什么需要两者？▶
漏洞扫描（Trivy/Grype）是扫描 + 报告的一次性动作，每次扫描都需要重新分析软件成分。SBOM 是持久化的软件成分清单，一次生成后可重复使用。两者协作：1) 构建时生成 SBOM，存储在仓库；2) 每次有新 CVE 发布时，用新的漏洞数据库对比旧 SBOM，无需重新构建或拉取镜像。实际价值：log4shell 爆出时，有完整 SBOM 的组织只需 grype sbom:./service-sbom.json | grep CVE-2021-44228 就能立即定位受影响服务；没有 SBOM 的组织需要逐个部署去扫描，耗费数天。
Cosign Keyless 签名和传统 GPG 签名有什么优劣？▶
传统 GPG 问题：1) 私钥需要安全管理，泄露后历史签名全部失效；2) 公钥分发和信任建立复杂（Web of Trust）；3) CI 环境中需要存储长期私钥（Secret）。Cosign Keyless 优势：1) 无需管理长期私钥，每次签名用临时 OIDC 凭证；2) 签名身份绑定到工作流（"由 GitHub Actions 的某个 workflow 在某次 commit 构建"），更有语义；3) 所有签名记录在 Rekor 透明日志，不可否认，公开可审计。缺点：依赖 Sigstore 公共基础设施（Fulcio CA 和 Rekor），企业内网需自建实例（sigstore/scaffolding）。
如何防止像 xz-utils 这样的社会工程学攻击？▶
技术层面：1) 重要版本发布必须有 Build Provenance，验证构建来自指定 CI 流程；2) 包含构建脚本的测试文件变更需要多人 review（xz 后门藏在 .m4 测试脚本中）；3) SBOM + 依赖 pinning，精确锁定版本；4) 开启 Rekor 透明日志，可审计每次发布的签名历史。流程层面：1) 维护者角色变更需要现有维护者投票；2) 重大变更（发布脚本、构建配置）需要至少 2 名核心维护者 approve；3) 新维护者在获得发布权限前有审查期。现实上：大型开源项目资源有限，防止有耐心的国家级攻击者极为困难。SLSA L4 要求双人审核是最高防线，但也意味着更高维护成本。
构建环境（CI）的安全如何保障？▶
构建环境是供应链最关键的节点（SolarWinds 的教训）。关键措施：1) 最小权限 CI Token：能推送到 dev 的 token 不能推送到 prod；能推送镜像的 token 不能修改 registry 权限；2) Ephemeral Build Environment：每次构建使用全新的临时 runner（GitHub hosted runner 即是此模式），不复用环境，防止持久化后门；3) 依赖 pinning：Dockerfile 中的 base image 用 sha256 固定，GitHub Action 的 uses: 用 commit sha 而非 tag（uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683）；4) 构建日志不包含 secret：使用 masked secrets，日志中自动脱敏；5) 定期轮换所有 CI/CD 凭证（registry token、signing key）。

常见误区

⚠ 误区：只扫描自己写的代码，忽视依赖
# 典型错误：只扫描源码
trivy fs ./src --security-checks vuln
# 或只运行 SAST（静态应用安全测试）
# semgrep --config=auto ./src

# 问题：
# - ./src 只包含业务代码
# - 不扫描 node_modules（数千个包）
# - 不扫描 vendor/ 目录
# - 不扫描运行时依赖的系统包
# - 现代应用 ~90% 代码来自第三方

# 结果：log4shell 出来时
# 不知道自己的 Java 服务是否用了 log4j
# 花数天人工排查每个服务

问题：只扫描自研代码等于漏掉了 90% 的攻击面。大多数真实 CVE 都在依赖中。

# 正确：扫描镜像整体（含所有依赖）
trivy image myapp:v1.2.3
# 扫描范围：OS 包 + 语言依赖
# - alpine/debian 系统包
# - go.sum 中所有 Go 依赖
# - package-lock.json npm 依赖
# - requirements.txt pip 依赖
# - jar 包内的 Maven 依赖（嵌套扫描）

# 同时生成 SBOM 以备后续使用
syft myapp:v1.2.3 -o cyclonedx-json > sbom.json

# CI 门控：CRITICAL CVE 阻断
trivy image --exit-code 1 \
  --severity CRITICAL,HIGH \
  myapp:v1.2.3

# 持续监控：每天重扫已部署镜像
# （新 CVE 每天都在发布）

正确：扫描完整镜像，包含所有系统包和语言依赖，并在 CI 中设置阻断门槛。

⚠ 误区：信任 Docker Hub "官方镜像" = 完全安全
# 常见误解
FROM node:18-alpine
# "官方镜像，应该是安全的"
# 实际：
# - 官方镜像基于 alpine 3.18
# - alpine 3.18 有若干 CVE
# - node 18 本身可能有未修复 CVE
# - "官方" 只代表由 Docker 维护
#   不代表 0 漏洞

# 验证：
trivy image node:18-alpine
# 可能发现 5-20 个已知 CVE
# 其中部分可能是 HIGH/CRITICAL

# Docker Hub 本身的风险：
# - 2023年 Docker Hub 限速/删除
#   导致大量 CI 破坏
# - 公共仓库无法验证推送者身份
# - 镜像可随时被删除或覆盖

问题：官方镜像减少了维护负担，但不等于无漏洞。且对 Docker Hub 的直接依赖引入可用性风险。

# 正确：使用私有 registry 代理 + 定期扫描

# 1. 搭建私有 registry（Harbor/Nexus/ECR）
# 作为 Docker Hub 的缓存代理
# 即使 Docker Hub 不可用，CI 仍正常

# 2. 固定基础镜像到摘要
FROM node:18-alpine@sha256:3d4a5d...9f1c
# 确保每次构建拉取的是同一镜像
# 摘要变化说明镜像被修改（需调查）

# 3. 使用更小的基础镜像减少漏洞面
FROM gcr.io/distroless/nodejs18-debian12
# distroless 是 Google 维护的极简镜像
# 无 shell / apt / 大量系统工具
# CVE 数量远少于通用 ubuntu/debian 镜像

# 4. CI 中自动扫描基础镜像更新
# dependabot + docker ecosystem
# 基础镜像有安全更新时自动 PR

正确：使用私有 registry 代理，固定到 sha256 摘要，选择最小化基础镜像，并持续扫描更新。

⚠ 高危：CI/CD 令牌权限过大，成为攻击入口
# 危险：一个 token 统管所有环境
# .env or GitHub Secret:
# REGISTRY_TOKEN=超级管理员 token
# （可推送到 dev/staging/prod 所有仓库）

# GitHub Actions 权限未限制：
# permissions: write-all  # 高危！

# 问题：
# - 开发者 fork 的 PR 可触发 CI
#   并尝试读取 secrets
# - CI runner 被攻击后可推送
#   恶意镜像到 prod registry
# - token 不轮换，长期暴露
# - 单一 token 泄露 = 全线失守

问题：CI token 权限过大是最高风险的供应链节点，一旦 CI 环境被攻击，直接影响所有部署环境。

# 正确：最小权限 + 环境隔离 + OIDC

# GitHub Actions 最小权限声明
permissions:
  contents: read     # 默认给予最小
  packages: write    # 只给需要推送镜像的步骤

# 使用 OIDC 替代长期 token
# AWS OIDC（无需存储 AWS key）
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/ci-ecr-push
    aws-region: us-east-1
    # 临时 STS token，15分钟有效

# 环境隔离：prod 部署需要额外 approval
environment: production
# GitHub: 需要指定 reviewer 批准才能执行

# 定期轮换 secrets（自动化）
# Dependabot secrets rotate / Vault lease
# 建议每 90 天轮换一次

# fork PR 不可访问 org secrets（默认）
# 只在 trusted PR 中开放（review 后允许）

正确：使用 OIDC 替代长期 token，按环境隔离权限，生产环境部署需人工批准，定期轮换凭证。
