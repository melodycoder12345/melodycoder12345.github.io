HTTP/2

HTTP/2 引入二进制帧、多路复用和头部压缩，解决了 HTTP/1.1 的应用层队头阻塞问题，是理解 gRPC、Server Push 和 QUIC 的基础。

二进制帧多路复用HPACKServer Push
核心术语
  • StreamHTTP/2 流：一个双向字节流，携带一次完整的请求/响应交换，多个流复用同一 TCP 连接。
  • Frame二进制帧：HTTP/2 通信的最小单位，有 HEADERS/DATA/SETTINGS/PUSH_PROMISE 等类型。
  • HPACK头部压缩算法：维护静态表和动态表，只传输头部增量，消除重复头部开销。
核心机制详解

1HTTP/1.1 的问题

HTTP/1.1 是文本协议，每个请求都需要完整的头部，且同一连接上请求必须串行处理（队头阻塞）。浏览器为绕过限制会并发 6–8 个 TCP 连接，但每条连接的建立都有握手和慢启动开销。

  • 队头阻塞（HoL）：前一个请求未响应，后续请求在应用层被阻塞（即使网络空闲）。
  • 头部冗余：每次请求都重复发送相同的 Cookie、User-Agent、Accept 等头部字段。
  • 多 TCP 连接浪费：多连接占用端口和内存，慢启动让每条连接初始带宽极低。
  • Keep-Alive 局限：Connection: keep-alive 复用连接，但串行限制仍在，无法真正并发。

Pipelining（HTTP/1.1 管道化）理论上可并发，但响应必须按请求顺序返回，问题未根本解决，且代理兼容性差，默认被禁用。

2HTTP/2 核心机制：帧、流与多路复用

HTTP/2 把 HTTP 语义（方法、头部、主体）映射到二进制帧，多个请求的帧可以交错传输，在同一 TCP 连接上实现真正的并发。

帧格式（9 字节固定头）：

Length
3B
Type
1B
Flags
1B
Stream ID
4B
Payload
0–16383B

Stream ID 标识所属请求，客户端发起的流用奇数 ID（1, 3, 5...），服务端推送用偶数 ID。

// HTTP/2 帧类型
HEADERS   0x1  // 请求/响应头，可含 END_HEADERS/END_STREAM
DATA      0x0  // 请求/响应体
SETTINGS  0x4  // 连接配置（初始窗口大小等）
WINDOW_UPDATE 0x8 // 流量控制
PUSH_PROMISE  0x5 // 服务端推送预告
GOAWAY    0x7  // 优雅关闭连接
RST_STREAM 0x3 // 重置单个流

3HPACK 头部压缩

HPACK（RFC 7541）通过三种机制大幅减少头部体积，解决 HTTP/1.1 每次请求重复传输大量相同头部的问题。

  • 静态表（61 个预定义条目）：把常见头部（:method: GET、:status: 200、content-type 等）编码为 1–2 字节索引。
  • 动态表：连接期间添加的自定义头部（如 authorization），后续请求可用索引引用，只传变化的部分。
  • Huffman 编码：对字符串值使用 Huffman 压缩，比原始 ASCII 再压缩约 30%。
// 示意：第二次请求只传增量头部
// 首次请求：完整头部
HEADERS { ":method": "GET", ":path": "/api/users",
           "authorization": "Bearer eyJ..." }

// 第二次请求：复用动态表索引，只传变化的 path
HEADERS { idx(":method: GET"), ":path": "/api/orders",
           idx("authorization") }

HPACK 动态表让重复头部接近零开销，API 密集型应用（大量同域请求）效果最明显。

4Server Push 与 Stream 优先级

Server Push 允许服务端在客户端发出请求前主动推送资源（如页面引用的 CSS/JS），减少客户端额外请求的 RTT。

// 服务端响应 / 时，同时推送 /style.css
PUSH_PROMISE stream_id=2, ":path": "/style.css"
// 客户端可发 RST_STREAM 拒绝不需要的推送
RST_STREAM stream_id=2, error=CANCEL

Stream 优先级（Priority frame，HTTP/2）允许客户端声明流的权重和依赖关系，服务端可据此调度传输顺序，优先保证关键路径资源（如 HTML、首屏 CSS）先到达。

  • 权重范围 1–256，父子依赖关系形成优先级树。
  • HTTP/2 优先级在 HTTP/3（QUIC）中由 Extensible Priorities（RFC 9218）取代，更简洁。

6常见误区

HTTP/2 不能解决 TCP 层队头阻塞：多个流复用同一 TCP 连接，一旦 TCP 丢包，所有流都被阻塞，等待重传。弱网场景下 HTTP/2 可能比 HTTP/1.1 更慢（后者多 TCP 连接互不干扰）。HTTP/3 over QUIC 才真正解决这个问题。

Server Push 并不总是更快：浏览器可能已有缓存，重复推送浪费带宽；浏览器需要发 RST_STREAM 取消，增加 RTT。Chrome 已在 2022 年移除 HTTP/2 Server Push 支持。

HTTP/2 并不在所有场景都比 HTTP/1.1 快：少量请求（1–2 个）差异不大；对象数量极少时 HTTP/1.1 多 TCP 慢启动影响也小；在高丢包率网络（>1%）下 HTTP/2 可能反而更慢。

HTTP/2 的最大价值在于：大量并发小请求（API 微服务、SPA 应用）、头部重复率高（API Token）、服务器到客户端实时推送（SSE over HTTP/2）这三类场景。
