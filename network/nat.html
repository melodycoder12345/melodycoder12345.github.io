NAT

NAT（Network Address Translation，网络地址转换）是 IPv4 地址耗尽时代的产物——将私有 IP 映射到公有 IP，让数以亿计的内网设备共享少量公网地址。NAT 不只是地址替换，它还维护连接跟踪状态，成为有状态的防火墙。NAT 的副作用是破坏端对端透明性，导致 P2P 通信困难，WebRTC/STUN/TURN/ICE 协议栈就是为解决 NAT 穿透而生的。理解 NAT 是理解家庭网络、云网络（VPC）和容器网络（Kubernetes Service）的基础。

核心术语
  • SNAT替换源地址，内网出口场景，路由器/防火墙最常见用途。
  • DNAT替换目标地址，端口映射/负载均衡/K8s Service 实现方式。
  • NAT 穿透STUN 探测外部映射，ICE 协商直连或 TURN 中继。
  • Symmetric NAT每目标用不同映射端口，穿透最困难，必须 TURN 中继。

SNAT 工作原理

  • 场景：家庭局域网 192.168.1.0/24 共享一个公网 IP 203.0.113.1 出网
  • 连接跟踪表（conntrack）：五元组 (proto, src_ip, src_port, dst_ip, dst_port)，NAT 网关为每个出站连接记录原始私有地址和映射的公网端口
  • 出站转换：192.168.1.100:54321 → 203.0.113.1:1024（NAT 替换源 IP 和源 Port）
  • 入站反转：响应包目标是 203.0.113.1:1024 → NAT 查表 → 转发给 192.168.1.100:54321
  • 端口耗尽：单个公网 IP 最多 65535 个映射，高并发企业场景需要多个公网 IP 轮换
  • conntrack 老化：超时未使用的条目被删除（TCP FIN/RST 触发即时删除，UDP 超时 30-60s），需注意 TCP keepalive
# Linux iptables SNAT（指定出口 IP） iptables -t nat -A POSTROUTING \ -s 192.168.1.0/24 -o eth0 \ -j SNAT --to-source 203.0.113.1 # MASQUERADE（动态获取出口 IP，适合 DHCP 环境） iptables -t nat -A POSTROUTING \ -s 192.168.1.0/24 -o eth0 \ -j MASQUERADE

DNAT 与端口映射

  • 典型场景：内网 192.168.1.10 运行 Web 服务 80 端口，外网访问 203.0.113.1:8080 时转发进来
  • 处理时机：DNAT 发生在 iptables PREROUTING 链（路由决策之前），修改目标地址后内核路由到正确内网接口
  • Kubernetes Service：ClusterIP 是虚拟 IP，iptables kube-proxy 为每个 Service 生成 DNAT 规则链，将目标 ClusterIP:Port 随机选择一个 Pod Endpoint 替换
  • IPVS 模式：K8s 的高性能替代，用内核级 IPVS hash 表替代 iptables 链，10000+ Service 时性能差异显著（O(1) vs O(n)）
# DNAT 端口映射：外网 8080 → 内网 80 iptables -t nat -A PREROUTING \ -d 203.0.113.1 -p tcp --dport 8080 \ -j DNAT --to-destination 192.168.1.10:80 # 同时需要 SNAT（让回程包经过 NAT 设备） iptables -t nat -A POSTROUTING \ -d 192.168.1.10 -p tcp --dport 80 \ -j MASQUERADE
Kubernetes Service 的 ClusterIP 之所以能工作，本质是 kube-proxy 在每台 Node 上维护 DNAT iptables 规则，将目标 ClusterIP 替换为实际 Pod IP。

NAT 类型与穿透难度

NAT 类型映射规则入站过滤穿透难度
Full Cone固定映射端口无最容易
Restricted Cone固定映射端口按源 IP容易
Port Restricted Cone固定映射端口按源 IP:Port可打洞
Symmetric按目标不同端口按源 IP:Port必须中继
  • 如何判断 NAT 类型：用 STUN 协议向两个不同 IP:Port 的 STUN 服务器发包，比较两次获得的映射地址是否相同
  • 家用路由器现状：大部分是 Port Restricted Cone NAT，STUN 打洞成功率约 80%；运营商级 NAT（CGN）多为 Symmetric，成功率低

STUN / TURN / ICE 穿透协议

  • STUN（Session Traversal Utilities for NAT）：RFC 5389。内网主机向公网 STUN 服务器发包，服务器返回"你的外部 IP:Port 是 X.X.X.X:YYYY"，主机由此得知自己在 NAT 后的映射地址
  • 打洞（Hole Punching）：A 和 B 都通过信令服务器交换 STUN 地址，A 向 B 的外部地址发包（让 NAT 创建从 A 到 B 的映射），B 同时向 A 发包，两个 NAT 映射建立后互通
  • TURN（Traversal Using Relays around NAT）：RFC 5766。直连失败时退化为中继：双方都与 TURN 服务器建立连接，通过服务器中转流量，100% 成功但延迟高且带宽消耗在服务器
  • ICE（Interactive Connectivity Establishment）：RFC 8445。WebRTC 使用的完整框架，按优先级尝试候选地址：Host（直连）→ Server Reflexive（STUN 打洞）→ Relayed（TURN 中继），选第一个成功的
# WebRTC ICE 候选地址示例 # host：直接内网地址 candidate:1 1 UDP 2130706431 192.168.1.100 54321 typ host # srflx：STUN 服务器探测到的外部映射地址 candidate:2 1 UDP 1694498815 203.0.113.1 44444 typ srflx \ raddr 192.168.1.100 rport 54321 # relay：TURN 中继地址（最后手段） candidate:3 1 UDP 16777215 198.51.100.2 55555 typ relay \ raddr 203.0.113.1 rport 44444

NAT 在云和容器环境中
  • AWS VPC NAT Gateway：托管式 SNAT 服务，内网 EC2 通过 NAT Gateway 出公网。高可用、按使用量计费，替代旧的 NAT Instance 方案
  • 云 VPC 中的安全组：不同于 iptables，AWS/GCP 安全组是有状态的（stateful），允许入站时自动允许对应出站响应，本质是 conntrack 的抽象
  • 容器网络 CNI：flannel/calico 等 CNI 插件为 Pod 网络在节点上设置 SNAT 规则（Pod IP → Node IP），使 Pod 能出公网
  • NodePort Service：K8s 在每个 Node 的 30000-32767 端口上监听，访问 NodeIP:NodePort 时先 DNAT 到 ClusterIP，再 DNAT 到 Pod IP
  • LoadBalancer Service：云厂商创建外部负载均衡器，流量 → LB VIP → NodePort → DNAT 到 Pod，多层 NAT 叠加

NAT 的问题与 IPv6 的未来

  • 破坏端对端原则：互联网最初设计中每台设备有唯一 IP，NAT 使外部无法主动发起连接，P2P 需要额外协议处理
  • 协议兼容性问题：FTP 主动模式、SIP 语音等协议在 payload 中内嵌 IP 地址，普通 NAT 不理解 payload 导致连接失败，需要 ALG（Application Level Gateway）特殊处理
  • NAT 状态持久性：NAT 设备重启导致所有 conntrack 状态丢失，存量 TCP 连接全部中断；高可用方案需要 conntrack 状态同步
  • CGN（运营商级 NAT）：ISP 在骨干网层面再做一层 NAT，用户处于双重 NAT 后，STUN 打洞几乎失败，只能 TURN 中继
  • IPv6 的目标：128 位地址空间消除地址短缺，理论上每台设备都有唯一公网 IPv6 地址，不再需要 SNAT；但 IPv6 过渡期 NAT64/NAT66 仍然存在
IPv6 在全球的渗透率已超过 40%，但 IPv4 NAT 仍将存在很长时间。理解 NAT 的工作原理和局限，是理解现代网络架构为什么如此复杂的基础。
