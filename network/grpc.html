gRPC / Protobuf

gRPC 用 HTTP/2 做传输、Protobuf 做序列化，支持四种流模式。理解服务定义、序列化机制和四种 RPC 类型，是构建高性能微服务间通信的基础。

核心术语
  • ProtobufProtocol Buffers：IDL 定义接口，字段有编号，序列化为紧凑二进制，向前向后兼容，比 JSON 小 3–5x。
  • Streaming流式 RPC：服务端流、客户端流、双向流三种模式，底层复用 HTTP/2 stream，适合大数据/实时场景。
  • Interceptor拦截器：类似 HTTP middleware，用于认证/监控/重试/限流等横切逻辑，可组成拦截器链。

背景与机制

HTTP/1.1 + JSON 存在队头阻塞、文本解析开销大和接口无 schema 等问题。gRPC 选择 HTTP/2 解决多路复用和头部压缩，选择 Protobuf 解决序列化效率和接口契约。Protobuf 使用字段编号（field number）而非字段名，字段删除只需标记 reserved，不影响已有编码，实现向前向后兼容。

常见误区

  • Protobuf 不能替代 JSON 的可读性——调试时需要 protoc 或 grpc_cli 解码，日志和 API 网关需要 JSON 转码层。
  • gRPC 的 HTTP/2 多路复用不能完全消除队头阻塞——TCP 层丢包仍会阻塞整个连接，HTTP/3 over QUIC 才真正解决。
  • 截止时间（Deadline）要在 context 里传播，忘记设置会导致无限等待和资源泄漏。

工程场景

  • 微服务内部通信：etcd、TiKV、Kubernetes 的组件间通信都使用 gRPC。
  • 流式场景：日志流、进度推送、大文件分片上传，使用 Server/Client/Bidirectional Streaming。
  • API 网关 gRPC-Gateway：自动生成 REST ↔ gRPC 转码，让前端也能用 HTTP/JSON 访问 gRPC 服务。
  • 拦截器链：认证（JWT/mTLS）→ 限流 → 追踪（OpenTelemetry）→ 重试，全部通过 interceptor 组合。

边界与恢复
