TLS 1.3

TLS 1.3 把握手从 2-RTT 缩短到 1-RTT，并用 ECDHE 保证前向安全。理解握手流程、证书链验证和 0-RTT 的重放风险，是排查 HTTPS 延迟和证书问题的基础。

核心术语
  • HandshakeTLS握手：客户端和服务端协商加密套件、交换密钥、验证身份的过程，TLS 1.3 只需 1-RTT。
  • Forward Secrecy前向安全：即使长期密钥泄漏，历史会话也无法被解密——依赖 ECDHE 每次生成临时密钥对。
  • Session Ticket会话复用：客户端携带上次握手缓存的 ticket，服务端验证后可跳过完整握手，实现 0-RTT。

背景与机制

TLS 1.2 需要 2 次往返（TCP 握手 + TLS 握手）才能发送第一个字节。TLS 1.3 移除了 RSA 密钥交换和弱算法（RC4、DES、3DES、MD5、SHA-1），强制使用 ECDHE 保证前向安全，把握手压缩到 1-RTT（首次）或 0-RTT（会话恢复）。密钥派生使用 HKDF，握手全程加密，握手消息不暴露给网络中间设备。

常见误区

  • 把 HTTPS 等同于"安全"——TLS 只保护传输中的数据，服务端漏洞和 DNS 劫持需额外防护。
  • 0-RTT 有重放风险：攻击者可截获并重播 0-RTT 数据，只适合幂等请求（GET），不可用于写操作。
  • 握手变快不等于整体更快——证书链过长或缺少 OCSP Stapling 仍会造成明显延迟。

工程场景

  • CDN 终止 TLS 后的证书生命周期管理，Let's Encrypt ACME 协议自动续期。
  • 双向 TLS（mTLS）：客户端也提供证书，用于微服务互信（Istio、Envoy sidecar）。
  • gRPC 和 QUIC 都依赖 TLS 1.3；排查握手延迟可用 openssl s_client -connect host:443 -tls1_3。
  • 证书固定（Certificate Pinning）防中间人，但更新证书时需同步更新 Pin，否则服务中断。

边界与恢复

动画覆盖三类场景：正常 1-RTT 握手到应用数据传输；证书验证失败（过期 / 域名不匹配 / CA 不受信任）导致握手中止并触发 alert；0-RTT 快速重连利用 session ticket 跳过握手直接发送数据。线上可用 curl -v --tlsv1.3 https://example.com 观察握手细节和证书链。
