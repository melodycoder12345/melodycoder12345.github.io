WebSocket

WebSocket 通过 HTTP Upgrade 握手建立全双工连接，之后数据以帧格式双向传输。理解握手升级、帧格式和心跳机制，是构建实时应用（聊天、协同编辑、游戏）的基础。

HTTP Upgrade全双工Frame心跳
核心术语
  • Upgrade协议升级：HTTP 101 Switching Protocols，连接从 HTTP 变为 WebSocket 持久全双工连接。
  • Frame帧格式：数据以帧传输，有 text/binary/ping/pong/close 类型，FIN 位标识消息是否完整，支持分片。
  • Heartbeat心跳：通过 Ping/Pong 帧检测连接存活，避免代理或 NAT 因超时自动断开连接。

背景与机制

HTTP 长轮询（Long Polling）和 SSE 是单向推送，每次请求都有 HTTP header 开销。WebSocket 在初始 HTTP 升级后变为原始的二进制帧协议，消除了 HTTP 头部开销，支持双向低延迟通信。WebSocket 帧头最小 2 字节，客户端发送的帧必须用 4 字节 masking key 进行 XOR 掩码，防止缓存污染。

常见误区

  • WebSocket 不等于"无限制双工"——代理和 CDN 可能不支持或有连接时间限制（通常 30–300s）。
  • 心跳间隔太长会导致 NAT/代理静默断开，太短会增加服务端压力；建议 30–45s Ping。
  • 断线重连必须有指数退避和最大重试次数，否则大规模重连风暴会压垮服务端。

工程场景

  • 聊天应用：服务端主动推送消息，客户端发送消息，双向低延迟。
  • 实时协同编辑（如 Figma、飞书文档）：操作变换（OT）或 CRDT 通过 WS 同步。
  • 在线游戏：帧同步或状态同步，要求 RTT 低且稳定，WebSocket over QUIC 是趋势。
  • 监控 Dashboard：服务端每秒推送指标，无需前端轮询，节省带宽和服务器资源。

边界与恢复

动画覆盖三类场景：正常的 HTTP Upgrade → 全双工通信 → 心跳 → 关闭；心跳超时导致连接异常断开（服务端或客户端未在规定时间内收到 Pong）；以及正常 Close Handshake（发送 close frame，等待对端回复 close frame，然后关闭 TCP）。线上排查可用 wscat -c wss://example.com/ws 测试连通性。
