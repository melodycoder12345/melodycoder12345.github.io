MVCC 多版本并发控制

通过为每行数据维护多个版本（版本链），配合 ReadView 实现快照隔离，让读操作无需加锁即可获取一致性视图，读写互不阻塞。

版本链ReadViewUndo Log快照读隔离级别
核心术语
  • 版本链每行数据的多个历史版本通过 roll_pointer 串联，形成单向链表。
  • ReadView快照读时生成的可见性快照，决定哪些版本对当前事务可见。
  • trx_id事务唯一标识，版本节点记录创建者的 trx_id 用于可见性比较。
  • roll_pointer指向 undo log 中前一个版本的指针，构成版本链。

背景与机制

传统锁机制下读写互斥导致高并发性能瓶颈。MVCC 通过保留数据的历史版本，让读操作访问快照而非当前值，从而实现读写并发。InnoDB 使用 undo log 存储旧版本，通过 roll_pointer 将同一行的所有版本串成链表。每次快照读根据 ReadView 从链表头部开始遍历，找到第一个对当前事务可见的版本。

常见误区

  • MVCC 并非完全消除锁：当前读（SELECT FOR UPDATE、UPDATE、DELETE）仍需加行锁。
  • RR 级别下 MVCC 可防止不可重复读，但幻读需要间隙锁（Gap Lock）配合解决。
  • 长事务持有旧 ReadView 会导致 undo log 无法被 purge，引发 undo 表空间膨胀。

工程场景

  • 监控 trx_id 推进速度：information_schema.innodb_trx 可查看活跃事务列表及持续时间。
  • undo 表空间配置：innodb_undo_tablespaces、innodb_max_undo_log_size 控制 undo 文件数量和大小。
  • innodb_purge_threads 控制 purge 线程数，高并发写入场景可适当增加。
  • pseudocode 逻辑：读取时从 head 沿 roll_pointer 遍历，对每个版本判断 trx_id 与 ReadView 的关系。

边界与恢复

  • Purge 延迟：当存在长事务时，purge 无法推进，undo 日志持续增长，需设置事务超时机制。
  • 大事务风险：单事务修改大量行会产生大量 undo 版本，回滚代价极高。
  • RC vs RR：RC 每次读都重新生成 ReadView 看到最新已提交数据；RR 复用首次读的 ReadView 保证可重复读。
  • 动画覆盖：初始状态 → 事务开始 → 版本创建 → 可见性判断 → 提交 → 隔离级别差异 → 锁冲突 → purge 回收。
