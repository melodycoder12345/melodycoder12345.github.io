数据库连接池

连接池复用数据库连接，避免每次查询建立新连接的开销。理解池大小设置、超时参数和连接泄漏检测，是防止数据库成为性能瓶颈的关键。

连接复用池大小超时泄漏检测
核心概念
  • 连接建立成本TCP 三次握手 + TLS 握手 + MySQL 认证握手，合计 1-10ms，高并发下完全不可接受
  • 连接泄漏程序忘记归还连接到池，导致池耗尽，新请求无限等待或立即失败
  • 池大小权衡不是越大越好：DB 端每个连接消耗内存（~1MB），过多连接导致 DB 内存压力和上下文切换

1为什么需要连接池？

建立一个数据库连接的实际开销：

阶段耗时
TCP 三次握手0.5-2ms（局域网）
TLS 握手（若开启 SSL）2-5ms
MySQL 认证握手0.5-3ms
合计1-10ms（每次请求）

假设 QPS=10000，平均查询耗时 5ms：

  • 无连接池：建连耗时 > 查询耗时，数据库吞吐腰斩
  • 连接池 100 连接：100 × (1/5ms) = 20000 QPS 上限，绰绰有余

连接池本质是一个 对象池：预先建立连接，查询时借出，完成后归还，下次直接复用。

2连接池核心参数

以 Go database/sql 为例（标准库内置连接池）：

db, _ := sql.Open("mysql", dsn)

// 最大连接数（活跃+空闲）
db.SetMaxOpenConns(100)

// 最大空闲连接数（保持热连接）
db.SetMaxIdleConns(10)

// 连接最大生命周期（防止 MySQL gone away）
db.SetConnMaxLifetime(time.Hour)

// 空闲连接最大闲置时间
db.SetConnMaxIdleTime(10 * time.Minute)

3池大小如何设置？

理论公式（Littel's Law）：

最优连接数 ≈ 并发请求数 × 平均 DB 查询时间（秒）

// 示例：100 并发，每次查询 10ms
// 最优连接数 = 100 × 0.01 = 1 个？？
// 实际：留 2-3× 余量处理峰值
// 推荐：5-20 个连接 for 大多数 OLTP 场景

// HikariCP 推荐公式（Java 生态）：
// pool_size = (core_count × 2) + effective_spindle_count
// 8核 SSD: (8×2) + 1 = 17 个连接
  • 不是越大越好：DB 端每连接约消耗 1MB 内存；超过 200-500 连接上下文切换剧增
  • MaxIdleConns 设太小：频繁销毁重建空闲连接；设太大：闲置连接浪费 DB 资源
  • 读写分离场景：读库和写库各自维护独立连接池
  • 连接池满时新请求会等待（有超时），不应直接失败

4连接泄漏

泄漏是最常见的连接池故障，症状：连接数缓慢爬升，最终池耗尽，服务超时。

典型 Go 泄漏模式：
// ❌ 忘记关闭 rows
rows, err := db.Query("SELECT ...")
// if err != nil { return } ← 此处 rows 为 nil，不会泄漏
// 但如果 rows != nil 且忘记 rows.Close()：
for rows.Next() { ... }
// ← 缺少 defer rows.Close()！连接不归还！

// ❌ 事务忘记回滚
tx, _ := db.Begin()
if err != nil {
    return err // ← 缺少 tx.Rollback()！
}

// ✅ 正确写法：
rows, err := db.Query(...)
if err != nil { return err }
defer rows.Close()

tx, _ := db.Begin()
defer tx.Rollback() // commit 后 rollback 是 no-op
检测方法：监控 db.Stats().InUse（活跃连接数）。InUse 持续增长不回落 → 有泄漏。

5超时配置

参数位置作用
connect_timeoutDSN建立 TCP 连接超时（驱动参数）
readTimeoutDSN读取响应超时，防止慢查询挂死
writeTimeoutDSN发送请求超时
wait_timeoutMySQL Server空闲连接超时断开（默认 8h）
ConnMaxLifetimeGo SDK连接最大存活时间，应 < wait_timeout
 
// Go DSN 超时配置示例：
dsn := "user:pass@tcp(host:3306)/db" +
    "?timeout=3s" +        // 建连超时
    "&readTimeout=30s" +   // 读超时
    "&writeTimeout=5s" +   // 写超时
    "&parseTime=true"
常见陷阱：MySQL wait_timeout 默认 8h，若 ConnMaxLifetime 不设置或设置过长，空闲连接被 MySQL 主动断开后，应用发请求会报 invalid connection。将 ConnMaxLifetime 设为 < wait_timeout（如 1h）可避免此问题。

6HikariCP / pgxpool 最佳实践

HikariCP（Java / Spring Boot 默认连接池）：

// Spring Boot application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20      # MaxOpenConns
      minimum-idle: 5            # MinIdleConns
      connection-timeout: 3000   # ms，获取连接等待超时
      idle-timeout: 600000       # 10min 空闲超时
      max-lifetime: 1800000      # 30min，< wait_timeout
      keepalive-time: 60000      # 心跳保活

pgxpool（Go + PostgreSQL）：

pool, _ := pgxpool.New(ctx, connStr)
pool.Config().MaxConns = 20
pool.Config().MinConns = 2
pool.Config().MaxConnLifetime = time.Hour
pool.Config().HealthCheckPeriod = 30 * time.Second

监控指标（必须告警）：

  • WaitCount：等待获取连接的请求累计数，增长说明池容量不够
  • WaitDuration：平均等待时间，>10ms 需扩池或优化查询
  • InUse：活跃连接数，持续 = MaxOpenConns 说明满负荷
  • Idle：空闲连接数，长期为 0 说明 MaxIdleConns 设置不够
