MySQL 主从复制

MySQL 主从复制通过 Binlog 将主库的写操作异步或半同步地传播到从库，实现读写分离和高可用。理解 GTID、复制延迟和半同步模式，是排查主从延迟和实现 CDC 的基础。

BinlogGTID半同步复制延迟
核心术语
  • Binlog（二进制日志）记录所有修改数据的 SQL 或行变更，格式有 STATEMENT/ROW/MIXED，是主从复制的核心传输载体
  • GTID（全局事务 ID）每个事务有全局唯一 ID，从库通过 GTID 集合知道自己的执行进度，方便主从切换
  • 复制延迟（Replication Lag）从库处理 Binlog 速度跟不上主库写入速度，导致从库数据落后，影响读一致性

ROW vs STATEMENT 格式

  • STATEMENT：记录原始 SQL，体积小，但 NOW()/RAND() 等非确定函数在从库重放会不一致
  • ROW：记录每行变更的前后镜像，精确可重放，但 UPDATE 全表时体积暴增
  • MIXED：默认用 STATEMENT，检测到非确定函数时自动切换 ROW
  • MySQL 8.0 默认 ROW，推荐生产使用 ROW + binlog_row_image=MINIMAL 节省空间

并行复制（多线程 SQL Thread）

MySQL 5.7+ 的 MTS（Multi-Threaded Slave）：从库 SQL Thread 拆分为 coordinator + worker pool，并行执行不同事务。

  • slave_parallel_type=LOGICAL_CLOCK：同一 binlog 提交组（group commit）内的事务并行执行
  • MySQL 8.0 WRITESET：不冲突的事务（写入不同行）可跨 group 并行，大幅降低复制延迟
  • 并行度由并行 worker 参数控制；MySQL 8.0.26 起推荐使用 replica_parallel_workers 命名，取值应按事务冲突率、CPU 与复制延迟压测

Binlog 做 CDC（变更数据捕获）

  • Canal（阿里）：伪装成从库连接主库，消费 Binlog 事件，推送到 MQ
  • Debezium：开源，支持 MySQL/PostgreSQL/MongoDB，输出 Kafka 消息
  • ROW 格式必须开启，binlog_row_image=FULL 才能获取完整前后镜像
  • CDC 延迟取决于事务大小、网络、连接器与下游处理能力，应以端到端延迟指标和积压量监控，而非假定固定小于 100ms

GTID 主从切换

传统文件位置复制需要管理 binlog 文件与 position；GTID 自动定位可按已执行 GTID 集合请求缺失事务，简化重新挂载。MySQL 8.0.23 起推荐使用 CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION=1；提升新主、数据补齐和脑裂防护仍需由高可用编排系统负责。
