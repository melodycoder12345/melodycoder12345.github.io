事务与死锁检测

两阶段锁（2PL）协议保证事务的可串行化隔离，但多个事务交叉加锁可能产生循环等待。数据库通过构建 Wait-for Graph 并运行 DFS 检测有向环来发现死锁，选择代价最小的事务回滚以恢复系统活性。

2PL死锁Wait-for Graph行锁Gap Lock
核心术语
  • 两阶段锁Growing 阶段只加锁不释放，Shrinking 阶段只释放不加锁，保证可串行化。
  • 等待图有向图中节点为事务，边 T1→T2 表示 T1 等待 T2 释放锁。环即死锁。
  • Victim 选择回滚代价最小的事务（undo 日志量、持有锁数、已执行时间等综合考虑）。
  • 间隙锁锁定索引记录间的间隙，防止幻读，InnoDB 在 RR 隔离级别默认启用。

Background

事务并发控制的核心矛盾：隔离性要求事务互不干扰，但完全串行执行吞吐量极低。两阶段锁通过允许并发加锁、但严格按阶段释放来平衡正确性与性能。

  • 写-写冲突必须用排他锁（X-lock）互斥
  • 读-写冲突可用共享锁（S-lock）或 MVCC 解决
  • 2PL 保证冲突可串行化，但可能产生死锁
  • 死锁是正确协议的副产品，不是 bug

Misconceptions

  • 死锁 = 代码 bug？ 错误。死锁是并发调度的正常现象，数据库有自动检测和恢复机制。
  • Gap Lock 只锁「间隙」？ 实际上 Next-Key Lock = Record Lock + Gap Lock，锁定的是左开右闭区间。
  • innodb_lock_wait_timeout = 死锁检测？ 不是。超时是被动放弃等待，死锁检测（innodb_deadlock_detect）是主动发现环路。
  • 加大超时就能避免死锁？ 只会让等待更久，真正的死锁永远不会自行解开。

Engineering

  • SHOW ENGINE INNODB STATUS 查看最近死锁信息（LATEST DETECTED DEADLOCK 段）
  • 一致的加锁顺序（如按主键升序）可从根本上避免循环等待
  • 应用层重试模式：捕获 Deadlock Error（MySQL 1213），随机退避后重试事务
  • DFS 检测算法：对 Wait-for Graph 做深度优先搜索，维护 recStack 标记当前路径，若访问到 recStack 中的节点则发现环
  • 时间复杂度 O(V+E)，V = 活跃事务数，E = 等待边数，通常很小
  • 减小事务粒度、缩短事务持锁时间是降低死锁概率的最佳实践

Boundaries

  • 检测开销：每次加锁失败触发检测，高并发时 O(n^2) 开销可观；MySQL 8.0.18 引入后台线程批量检测
  • 锁升级：行锁过多时 InnoDB 不会自动升级为表锁（与 SQL Server 不同），但会消耗大量内存
  • 分布式死锁：跨节点的等待图需要全局协调，XA 事务只能依赖超时
  • Phantom 与 Gap Lock：RR 级别下 Gap Lock 有效防止幻读，但可能锁住比预期更大的范围，导致意外阻塞
