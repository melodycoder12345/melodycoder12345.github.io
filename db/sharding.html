分库分表

分库分表将数据按 shard key 哈希后路由到不同的分片（Shard）。动画展示：数据行按 user_id 哈希落入不同分片，柱状图显示各分片数据量；带 shard key 的查询直接命中单分片（快），不带 shard key 的查询 scatter-gather 扇出到所有分片（慢）；新增分片时一致性哈希只迁移部分数据块，双写保证迁移期间一致性。

Shard Key哈希分片Scatter-Gather一致性哈希再平衡
核心术语
  • Shard Key决定数据路由的字段，通常是 user_id 或 tenant_id。
  • Scatter-Gather不带 shard key 的查询扇出到所有分片再汇总。
  • 一致性哈希增加节点只迁移 1/N 数据，比取模哈希迁移成本低得多。
  • 跨分片事务避免，用 Saga 或应用层补偿替代，代价极高。

分片键选择原则

  • 高基数：区分度高，避免某个值占大多数（如 status 字段不适合）
  • 均匀分布：哈希后各分片数据量相近，避免热点分片
  • 业务关联：同一用户的数据在同一分片，避免跨分片 JOIN
  • 稳定性：分片键的值不能更改，否则需要跨分片迁移数据
  • 反例：按时间分片（range sharding）容易造成写入热点，最新时间段一直是热分片

分库 vs 分表

  • 分表（单库）：将一张大表拆分为多张小表（orders_0, orders_1），解决单表行数过多的问题，索引效率提升
  • 分库：将表分到不同的数据库实例，解决单机连接数/写入 TPS 上限
  • 分库分表结合：N 个库 × M 个表，总分片数 = N×M，通常 N 和 M 都是 2 的幂
  • 工具：ShardingSphere、Vitess（MySQL 分片代理）、MyCAT

全局 ID 方案

  • 分片后不能用 AUTO_INCREMENT（每个分片独立自增，会重复）
  • Snowflake：时间戳 41bit + 机器 ID 10bit + 序列号 12bit，64bit 全局唯一
  • UUID v4：随机 128bit，全局唯一但写入 B-tree 索引会随机 IO（页分裂）
  • UUID v7：时间戳前缀，有序写入，兼顾唯一性和 B-tree 性能
  • 数据库号段：批量申请 ID 段（如每次取 1000 个），减少 DB 请求

分片后的工程挑战

  • 跨分片分页：LIMIT 10 OFFSET 100 需要各分片都返回 110 条再截取，性能差
  • 全局排序：在 coordinator 做内存排序，数据量大时耗时
  • 二级索引：按 user_id 分片，按 order_time 查询需要 scatter-gather，可维护一张单独的索引表
  • 运维复杂度：DDL 变更需要在所有分片执行，schema 迁移工具（gh-ost、pt-osc）必须支持分片
  • 评估先于分片：单表可承载的数据量没有通用行数阈值，取决于行宽、索引、访问模式、SLA 与硬件；应先用容量和性能指标评估索引、归档、冷热分离或读扩展
