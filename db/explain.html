DB / MySQL 优化

EXPLAIN 执行计划

EXPLAIN 是 MySQL 查询优化的主要入口，通过分析执行计划可以发现全表扫描、低效索引和不必要的 filesort。理解每个字段的含义是优化 SQL 性能的基本技能。

typekeyrowsExtra
关键字段
  • type（访问类型）重要的访问路径提示；ALL 表示全表扫描，但小表、低选择性查询或分析型扫描中可能是合理选择
  • key（实际索引）优化器实际选择的索引。NULL 表示未使用任何索引
  • rows × filtered估算返回行数 = rows × filtered/100，影响 JOIN 顺序决策

1EXPLAIN 基础用法

三种调用形式，复杂度递增：

-- 基础：显示执行计划各列
EXPLAIN SELECT * FROM orders WHERE user_id = 100;

-- JSON 格式：显示成本数据（cost）
EXPLAIN FORMAT=JSON
SELECT * FROM orders WHERE user_id = 100;

-- ANALYZE（MySQL 8.0.18+）：实际执行并显示
-- 真实 rows、loops、actual time
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 100;

EXPLAIN ANALYZE 会真正执行查询，不适合线上大表。FORMAT=JSON 的 cost_info 是优化器的实际评估成本，比较不同方案时最有价值。

2type 列（访问类型，最重要）

从最优到最差，必须记住这个顺序：

system只有一行（系统表），理论最优
const主键/唯一索引等值查询，最多一行
eq_refJOIN 时被驱动表主键等值，每行最多一匹配
ref非唯一索引等值，可能多行
range索引范围扫描（BETWEEN/>/</IN）
index全索引扫描（无需回表，但扫全索引）
ALL全表扫描；需结合表大小、过滤比例和实际耗时判断是否优化
-- const：主键等值
EXPLAIN SELECT * FROM users WHERE id = 1;

-- ref：非唯一索引等值
EXPLAIN SELECT * FROM orders WHERE user_id = 100;

-- range：索引范围
EXPLAIN SELECT * FROM orders
WHERE created_at > '2024-01-01';

-- ALL：全表扫描，需要优化！
EXPLAIN SELECT * FROM users
WHERE email LIKE '%test%';

3key 和 key_len

key：优化器实际选择的索引名。NULL 表示没使用索引，possible_keys 显示备选索引。

key_len：索引使用的字节数，揭示联合索引用了几个列：

  • INT：4 bytes；BIGINT：8 bytes；允许 NULL 多 1 byte
  • VARCHAR(n) UTF8MB4：n×4 + 2 bytes（长度前缀）
  • 联合索引 (a, b, c)，key_len 只覆盖 a+b → 说明 c 没用上
-- 联合索引 idx(user_id, status, created_at)
-- key_len=8 → 只用了 user_id(BIGINT 8B)
-- key_len=12 → 用了 user_id + status(INT 4B)
EXPLAIN SELECT * FROM orders
WHERE user_id = 100 AND status = 1;

key_len 分析是判断联合索引命中情况的最直接方法，配合 possible_keys 可以发现优化器选错索引的场景。

4rows 和 filtered

rows：优化器估算需要检查的行数（基于统计信息，不精确）。大表 ANALYZE TABLE 可更新统计。

filtered：WHERE 条件过滤后的比例（%）。实际预期行数 = rows × filtered / 100。

rowsfiltered预期返回行含义
1000100%1000索引条件等于 WHERE 条件，无额外过滤
100010%100还有索引外的 WHERE 条件在做过滤
1000000.1%100索引选择性很差，考虑换索引

JOIN 时优化器用 rows×filtered 估算驱动表大小，选择 rows×filtered 最小的表作为外层（driving table）。

5Extra 列关键值

Extra 值含义是否需要优化
Using index覆盖索引：查询所需字段全在索引中，无需回表（最优情况）好，保持
Using index conditionICP（Index Condition Pushdown）：部分 WHERE 条件在存储引擎层过滤，减少回表次数好
Using whereWHERE 条件有部分在 Server 层过滤（索引无法完全覆盖），会产生额外判断开销可接受，考虑优化
Using filesort无法直接利用索引顺序，需要额外排序；名称并不表示一定落盘结合实际行数判断
Using temporary执行中需要内部临时表；是否落盘及代价取决于数据类型、大小和服务器配置结合实际耗时判断
Using join bufferJOIN 时被驱动表无有效索引，使用 Block Nested Loop 算法，大量内存/IO 消耗需加索引

6典型优化案例与高级工具

联合索引最左匹配失效案例：

-- 联合索引 idx(a, b, c)
-- ✅ 命中：a=1                      → type=ref, key_len=a
-- ✅ 命中：a=1 AND b=2              → type=ref, key_len=a+b
-- ✅ 命中：a=1 AND b>2              → type=range, key_len=a+b
-- ❌ 失效：b=2（跳过 a）             → type=ALL
-- ❌ 失效：a LIKE '%prefix'          → 前缀通配符
-- ❌ 失效：WHERE YEAR(created_at)=2024 → 函数包裹索引列

-- 覆盖索引：SELECT 只取索引覆盖的列
CREATE INDEX idx_user_status
  ON orders(user_id, status, id);
EXPLAIN SELECT id FROM orders
WHERE user_id=100 AND status=1;
-- Extra: Using index（无回表，最优）

强制索引与 Optimizer Trace：

-- 强制指定索引（优化器选错时使用）
SELECT * FROM orders FORCE INDEX(idx_user_id)
WHERE user_id = 100;

-- Optimizer Trace：查看优化器完整决策过程
SET optimizer_trace = 'enabled=on';
SELECT * FROM orders WHERE user_id = 100;
SELECT * FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace = 'enabled=off';
