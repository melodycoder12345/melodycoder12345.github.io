LSM Tree

LSM Tree 把随机写转成顺序追加写，再通过后台合并维持查询效率。

WALMemTableCompaction
LSM 是现代写密集型存储引擎的基础，RocksDB / LevelDB / TiKV / Cassandra 均基于此结构。
核心术语
MemTable内存中的有序表（通常 Skip List），接收最新写入。
SSTableSorted String Table，磁盘上的不可变有序文件，按 key 排列。
Compaction把多个 SSTable 合并、去重、下推到更低层，减少读放大。

背景

B-tree 每次写入可能触发多次随机磁盘 IO（更新叶节点 + 可能的页分裂 + WAL），在写密集场景下成为瓶颈。

LSM Tree（Log-Structured Merge Tree）的核心设计哲学：牺牲读性能换写性能，通过后台 compaction 渐进恢复读效率。

  • 将随机写转化为内存有序写 + 顺序磁盘追加，利用磁盘/SSD 顺序写带宽
  • 代价：读取需要查多层文件（读放大），后台合并消耗额外 IO（写放大），旧版本数据占用空间（空间放大）
  • 三大放大因子的权衡是 LSM 调优的核心：write amplification、read amplification、space amplification
  • 适合 write-heavy workload：日志、时序数据、消息队列底层存储
  • RocksDB 在 LSM 基础上增加了 Column Family、前缀 Bloom、Rate Limiter、Compaction Filter 等工程优化

运行机制

  • Write Path：写入 → 追加 WAL（顺序写，保证 crash recovery）→ 插入 MemTable（通常 Skip List）
  • Flush：MemTable 达到阈值 → 变为 Immutable MemTable → 后台线程 flush 成 L0 SSTable（有序、不可变）
  • Compaction (Size-Tiered / STCS)：同层 SSTable 数量超阈值后合并为更大文件；写放大低（~O(层数)）但空间放大高（最坏 2x）
  • Compaction (Leveled / LCS)：每层容量固定倍数关系（如 10x），L(n) 满后选取 SSTable 与 L(n+1) 重叠部分合并；空间放大低（~10%）但写放大高
  • Read Path：MemTable → Immutable → L0（可能多个重叠文件全查）→ L1（二分查找确定唯一文件）→ ... → Ln
  • Bloom Filter：每个 SSTable 附带布隆过滤器，点查时先检查 key 是否可能存在，跳过无关文件（假阳性率 ~1%，10 bits/key）
  • Tombstone 删除：写入墓碑标记，compaction 时与旧版本合并后回收空间
  • Block Cache：缓存热 SSTable 的 data block 和 index block，减少磁盘随机读
  • WAL 回收：MemTable 成功 flush 后对应 WAL 文件可删除，避免磁盘空间持续增长

代码示例

Go 伪代码：LSM 写入路径 + 读取路径 + Compaction 触发：

type LSM struct {
    wal     *os.File
    mem     *SkipList        // active MemTable
    imm     *SkipList        // immutable, waiting flush
    levels  [][]*SSTable     // L0, L1, ..., Ln
    mu      sync.Mutex
}

func (l *LSM) Put(key, val []byte) error {
    // 1. 先写 WAL（顺序追加，crash 后重放恢复 MemTable）
    if err := l.wal.Append(encodeKV(key, val)); err != nil {
        return err
    }
    // 2. 写入 MemTable（内存有序结构）
    l.mu.Lock()
    l.mem.Insert(key, val)
    if l.mem.Size() >= MemTableThreshold { // 默认 64MB
        l.imm = l.mem
        l.mem = NewSkipList()
        go l.flushImmutable()
    }
    l.mu.Unlock()
    return nil
}

func (l *LSM) Get(key []byte) ([]byte, bool) {
    // 查找顺序：越新的数据源越优先
    if v, ok := l.mem.Get(key); ok {
        return v, true
    }
    if l.imm != nil {
        if v, ok := l.imm.Get(key); ok {
            return v, true
        }
    }
    for _, level := range l.levels {
        for i := len(level) - 1; i >= 0; i-- {
            if level[i].BloomMayContain(key) {
                if v, ok := level[i].Get(key); ok {
                    return v, true
                }
            }
        }
    }
    return nil, false
}

func (l *LSM) flushImmutable() {
    sst := BuildSSTable(l.imm.Iterator())
    l.levels[0] = append(l.levels[0], sst)
    l.imm = nil
    if len(l.levels[0]) >= L0CompactThreshold { // 默认 4
        go l.compact(0)
    }
}

面试问答

写放大是什么？LSM 如何缓解？▶
写放大 = 实际写入磁盘的数据量 / 用户写入的数据量。Leveled compaction 下，一条数据从 L0 到 Ln 每层都可能被重写一次，写放大约为 O(层数 * 扇出比)，典型值 10-30x。缓解方法：1) 调大每层容量比（如 RocksDB 默认 10）减少层数；2) 使用 Size-Tiered 策略牺牲空间换写放大；3) 动态调整 compaction 优先级（Universal Compaction）；4) 采用 FIFO compaction 只保留最新数据（TTL 场景）。
Bloom Filter 在 LSM 中的作用和局限？▶
Bloom Filter 为每个 SSTable 维护一个位图，查询时先检查 key 是否可能存在于该文件。若返回 false 则 100% 不存在，跳过该文件的磁盘 IO。局限：1) 只能判断点查（Get），无法加速范围查询（Scan）；2) 假阳性率与内存占用成正比（通常 10 bits/key 得到 1% 假阳性）；3) L0 层文件 key range 重叠，需要检查所有 L0 文件的 Bloom；4) 前缀 Bloom 可加速前缀扫描但设计更复杂。
Size-Tiered vs Leveled Compaction 如何选择？▶
Size-Tiered：同大小文件合并为更大文件，写放大低（约 O(层数)），但空间放大高（最坏 2x），读放大也高（同层文件 key range 重叠需全查）。适合写多读少场景如日志存储。Leveled：严格分层且层内 key 无重叠，空间放大低（~10%），读放大低（每层最多查一个文件），但写放大高（10-30x）。适合读写均衡的在线存储。RocksDB 的 Universal Compaction 尝试在两者之间动态切换。
Compaction 会阻塞前台写入吗？▶
直接阻塞不会，但间接影响严重：1) Compaction 占满磁盘带宽时 flush 变慢，MemTable 堆积导致 write stall；2) L0 文件过多触发 slowdown/stop（RocksDB level0_slowdown_writes_trigger=20, level0_stop_writes_trigger=36）；3) RocksDB 通过 Rate Limiter 限制 compaction IO 带宽，优先保证前台写入。监控指标：stall 时间百分比、pending compaction bytes、L0 文件数。实际上 write stall 是 LSM 系统线上最常见的性能问题。

常见陷阱

误解：LSM 写入就是顺序写所以一定比 B-tree 快
// 只看前台写入路径
// WAL 顺序写 + MemTable 内存写
// 结论：写性能碾压 B-tree

// 忽略了 compaction 的隐性成本：
// - 实际写放大 10-30x (leveled)
// - 磁盘带宽被后台 compaction 抢占
// - Write stall 导致 P99 剧增
// - SSD 寿命被写放大消耗

// B-tree (如 InnoDB) 随机写场景：
// 写放大约 2-3x（仅 WAL + 数据页）
// 但需要更多 IOPS

问题：前台写快不代表总写入开销低，compaction 是 LSM 的隐性"信用卡账单"。

// 完整评估 LSM vs B-tree
//
// LSM 优势场景：
// - 写入远多于读取（write 90%+）
// - 顺序键写入（时序、日志）
// - SSD 有充足写入预算
//
// B-tree 优势场景：
// - 读写均衡或读多写少
// - 需要稳定的 P99 延迟
// - 频繁范围查询
//
// 监控指标：
// - write_amplification_factor
// - compaction_pending_bytes
// - stall_micros / interval_stall_percent

正确：评估 LSM 要看写放大总量、尾延迟和 write stall，而非仅看前台写入吞吐。

误解：删除数据后磁盘空间立即释放
// 执行大量删除
for key := range expiredKeys {
    db.Delete(key)
}
// 期望：磁盘使用量立即下降
// 实际：
// - 每次 Delete 写入一条 tombstone
// - 旧数据仍在 SSTable 中
// - 磁盘占用反而增加
// - 等 compaction 合并到最底层时才回收

问题：大量删除后空间不降反升，tombstone 本身也占空间，可能等数小时才被 compaction 清理。

// 正确认知和应对
// 1. Delete = Put(key, tombstone marker)
// 2. 空间回收依赖 compaction 到达底层
// 3. 手动触发范围 compaction：
db.CompactRange(startKey, endKey)

// 4. 设计层面优化：
// - 按时间分区（TTL compaction filter）
//   过期 SSTable 直接删除文件
// - FIFO compaction：最老文件直接丢弃
// - 监控 estimate-num-keys vs
//   estimate-live-data-size 差异

// 5. tombstone 过多还会拖慢范围查询
//    需要监控 tombstone 比例

正确：LSM 的删除是逻辑删除，物理回收取决于 compaction 进度；大量删除场景要主动触发或设计按时间分区。
