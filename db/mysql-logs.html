MySQL 日志体系

Redo Log、Undo Log、Binlog 三日志协同工作，通过 WAL 原则和两阶段提交机制，确保事务的崩溃安全性(crash safety)与主从复制一致性。

背景与机制

  • Redo Log 保证持久性（crash-safe）：物理日志，记录页级变更，循环覆盖写。
  • Undo Log 保证原子性和隔离性：记录旧值，支持回滚和 MVCC 快照读。
  • Binlog 保证复制一致性：逻辑日志，追加写，永久保留，用于主从复制和 PITR。
  • WAL 原则：先写日志再写数据页，顺序 IO 替代随机 IO，是性能与安全的基石。

常见误区

  • Redo Log 不等于 Binlog：前者是 InnoDB 层物理日志（循环写），后者是 Server 层逻辑日志（追加写）。
  • "Double Write" 不是写两份日志，而是 InnoDB 防止 partial page write 的机制。
  • fsync 完成不等于事务提交：两阶段提交中，redo COMMIT 标记写入才是最终提交点。
  • Group Commit 并非总是更快：低并发下分组效果有限，反而可能增加延迟。

工程场景

  • innodb_flush_log_at_trx_commit：=1 每次提交写并刷盘；=2 每次提交写入 OS 缓冲、通常每秒刷盘；=0 通常每秒写并刷盘，实际丢失窗口受调度与系统影响。
  • sync_binlog：=1 每次提交同步 binlog（配合 flush=1 常称“双 1”配置）；=0 由操作系统决定同步时机。
  • 监控 redo log 利用率：当 write_pos 快追上 checkpoint 时可能触发更激进的刷脏并造成抖动。
  • Redo 容量没有通用“buffer pool 倍数”：应依据峰值 redo 生成速率、可接受 checkpoint 压力与恢复时间做压测和监控后确定。

边界与恢复

  • Redo Log 太小会增加 checkpoint 压力，过大可能增加恢复扫描工作。MySQL 8.0.30+ 使用 innodb_redo_log_capacity 管理容量，并在数据目录的 #innodb_redo 下维护一组 redo 文件；旧版常见的固定 ib_logfile0/1 描述不再适用。
  • Binlog 格式选择：ROW 精确但日志量大，STATEMENT 紧凑但有函数不一致风险，MIXED 折中。
  • 崩溃恢复流程：扫描 redo log 中 PREPARE 状态记录，比对 binlog 中是否存在对应 XID，有则提交无则回滚。
  • 恢复时间受未 checkpoint 的 redo 量、页状态和 I/O 能力等共同影响，大事务也可能延长恢复。
