DB / NoSQL

NoSQL 数据库分类

NoSQL 不是单一数据库，而是一个家族：文档型（MongoDB）存灵活的 JSON 文档，宽列型（Cassandra/HBase）做海量时序写入，键值型（Redis/DynamoDB）提供 O(1) 极速访问，图型（Neo4j）高效遍历多跳关系。选择哪类 NoSQL，取决于你的数据模型、查询模式和 CAP 取舍——理解这四种数据模型的根本差异，才能做出正确选型而不是被流行趋势左右。

核心术语
  • BASE 与 ACID它们描述不同维度，不能用来把 NoSQL 与关系型数据库简单二分；不少 NoSQL 产品也提供强一致读或多记录事务。
  • 宽列存储（Wide-column）行键+列族稀疏矩阵，每行列数可不同，适合海量时序/日志场景。
  • 图数据库节点和边为一等公民，多跳关系遍历效率远超关系型 DB 的 JOIN 操作。

为什么需要 NoSQL？

  • 关系型 DB 的扩展瓶颈：垂直扩展（更大机器）成本指数级增长；水平分片（Sharding）破坏跨分片事务；JOIN 操作在分布式环境代价极高
  • Schema 僵化：ALTER TABLE 在 TB 级数据表上可能锁表数小时；敏捷开发需要频繁变更数据结构
  • 特殊数据模型需求：关系型 DB 表达图结构、时序数据、文档嵌套需要多表 JOIN，性能差且模型不自然

CAP 定理三角：分布式系统在网络分区（P）时必须在一致性（C）和可用性（A）之间二选一。

NoSQL 的出发点不是"不要 SQL"，而是"在特定场景放弃关系型约束，换取更好的水平扩展、更灵活的 Schema 或更适合的数据模型"。

文档型数据库（MongoDB）

Document DB
  • 数据模型：以 JSON/BSON 文档为基本单元，文档可包含嵌套子文档和数组，同一集合（Collection）内文档结构可以不同（Schema-free）
  • 嵌套结构优势：将关联数据嵌入同一文档（如订单内嵌商品列表），读取一次即可获得完整数据，避免 JOIN
  • 聚合管道：类似 SQL GROUP BY + JOIN 的链式操作，支持 $match、$group、$lookup、$project 等阶段，适合复杂统计
  • 索引支持：支持单字段、复合、地理空间、全文索引；TTL 索引自动过期文档，适合缓存场景
  • 适合场景：用户画像（属性频繁变化）、内容管理系统、电商商品目录（属性各异）、实时分析仪表板
MongoDB 查询示例 vs SQL：见代码区对比
-- SQL 查询
SELECT u.name, COUNT(o.id) orders
FROM users u JOIN orders o ON u.id = o.user_id
WHERE u.city = 'Beijing'
GROUP BY u.id;

// MongoDB 聚合管道等价查询
db.orders.aggregate([
  { $lookup: { from: "users", localField: "userId",
               foreignField: "_id", as: "user" }},
  { $match: { "user.city": "Beijing" }},
  { $group: { _id: "$userId", orders: { $sum: 1 }}}
]);

宽列型数据库（Cassandra / HBase）

Wide-Column
  • 数据模型：行键（Partition Key）决定数据分布到哪个节点；列族（Column Family）是列的分组，每行在同一列族内可以有不同的列，稀疏存储
  • 时序数据天然适合：以设备ID+时间戳作为行键前缀，时间范围扫描极其高效，无需全表扫描
  • Cassandra vs HBase：Cassandra AP（可用性优先，最终一致，无单点），HBase CP（强一致，依赖 HDFS + ZooKeeper）
  • 写多读少优化：LSM-Tree 存储引擎，顺序追加写入极快（~1ms），读取需合并多个 SSTable；不适合频繁更新和复杂查询
  • Cassandra 一致性级别：QUORUM（多数节点确认）、ONE（任意一个节点确认）、ALL（全部节点确认），可按读/写单独配置
数据建模原则：Cassandra 要"先想查询再设计表"——必须按查询模式建表，不支持临时 ad-hoc 查询，允许数据冗余（查询驱动设计）。

键值型数据库（Redis / DynamoDB）

Key-Value
  • 极简数据模型：Key → Value，通过 Key 精确查找，O(1) 读写，是最简单也是吞吐量最高的 NoSQL 模型
  • Redis 丰富数据结构：String（缓存）、Hash（用户会话）、List（消息队列）、Set（去重集合）、ZSet（排行榜）、Stream（消息流）、HyperLogLog（基数估计）、Bitmap（签到）
  • Redis 使用场景：缓存热数据（Cache-Aside 模式）、分布式锁（SET NX + 过期时间）、限流（INCR + TTL）、实时排行榜（ZSet sorted by score）
  • DynamoDB：AWS 全托管，按 Partition Key + Sort Key 组织数据，自动分片、按需扩展，支持全局表（跨区域多主复制）；一致性模型可选最终一致或强一致读
  • 局限：只能按 Key 点查，不支持范围扫描或复杂过滤（DynamoDB 有 GSI 辅助索引可部分弥补）

图数据库（Neo4j / TigerGraph）

Graph DB
  • 属性图模型：节点（Node）有标签（Label）和属性（Properties），边（Relationship）有类型和属性，节点和边都是一等公民存储在索引数据结构中
  • 多跳查询性能：关系型 DB 查询"6 度人脉"需要 6 次 JOIN，图 DB 通过指针遍历（Index-Free Adjacency），每一跳都是 O(1)，性能差距随跳数指数级扩大
  • Cypher 查询语言：声明式，用 ASCII Art 表达图模式，直观易读
  • 适合场景：社交网络（关注关系、共同好友）、知识图谱（实体关系推理）、欺诈检测（异常交易关系链）、推荐系统（协同过滤）、血缘分析（数据 lineage）
  • TigerGraph：支持并行图计算（GSQL），亿级节点规模下多跳查询毫秒级响应
// Cypher: 查询 Alice 2 跳内的朋友
MATCH (alice:Person {name: "Alice"})
      -[:FRIENDS_WITH*1..2]-
      (friend:Person)
WHERE friend <> alice
RETURN DISTINCT friend.name, friend.age
ORDER BY friend.name;

// 创建节点和关系
CREATE (alice:Person {name: "Alice", age: 30})
       -[:KNOWS {since: 2020}]->
       (bob:Person {name: "Bob", age: 28});

工程误区

  • NoSQL 不是万能替代：关系型 DB 在多表复杂查询、强一致事务、数据完整性约束（外键）场景仍是最佳选择；OLTP + OLAP 的核心业务 DB 不要随便替换
  • "MongoDB 万能"陷阱：文档 DB 不适合需要跨文档事务的场景（虽然 MongoDB 4.x+ 支持多文档事务，但性能开销大），强关联的关系型数据强行用 MongoDB 会带来大量 $lookup
  • Cassandra 的高写放大：LSM-Tree 的 Compaction 会消耗大量 I/O；UPDATE 实际上是插入新版本，频繁更新同一行会导致读时需合并大量版本
  • Redis 内存成本：Redis 的活动数据集通常驻留内存，容量受内存与淘汰策略约束；可通过分片扩展。它能否作为主存储取决于持久化、复制、故障恢复和业务耐久性要求，不能一概而论
  • 图 DB 的冷启动：图数据库需要将图结构加载到内存才能高速遍历，冷启动时间较长；不适合超大单节点（数百亿边）场景，需要分布式图计算框架
  • 混合使用策略：生产系统常见组合——PostgreSQL（主业务 OLTP）+ Redis（热缓存）+ Elasticsearch（全文搜索）+ ClickHouse（OLAP 分析）+ Neo4j（关系推理），各司其职
最常见错误：以"NoSQL 更快"为由盲目替换关系型 DB，而不分析实际查询模式。正确做法是先确认"数据模型"和"查询模式"，再选择对应的数据库类型。
